GPU.js: this.thread vs Texture Memory Lookups

In GPU.js, performance often hinges on how data is accessed inside a kernel. Reading values from this.thread provides virtually instantaneous access to thread-index registers generated directly by the GPU's hardware scheduler. In contrast, retrieving values from input textures or arrays requires memory transactions against the GPU's video memory (VRAM) via the texture cache. Understanding the architectural differences between register-based thread coordinates and texture memory lookups helps developers optimize kernel execution times and minimize memory bottlenecks.

Architectural Difference: Registers vs. Texture Memory

this.thread.x, this.thread.y, and this.thread.z represent the current execution coordinates assigned to an individual invocation of the kernel. These values do not reside in memory; instead, the GPU assigns them directly into thread registers upon dispatch. Because registers represent the fastest storage tier on a GPU, accessing this.thread incurs zero memory latency and zero bandwidth consumption.

Texture lookups occur whenever you read from an input array, matrix, or previously generated GPU.js texture (e.g., myArray[this.thread.y][this.thread.x]). Under the hood, GPU.js converts standard JavaScript arrays into WebGL textures. Reading from these inputs requires the GPU to:

  1. Translate array coordinates into normalized UV texture coordinates.
  2. Query the on-chip texture cache (L1/L2).
  3. Fall back to VRAM to fetch the data if a cache miss occurs.

Latency and Memory Bandwidth

  • Latency: Register operations, such as reading this.thread, take 1 to 2 clock cycles. A texture lookup can take anywhere from a few cycles (if the data is already in the L1/L2 texture cache) to several hundred clock cycles if the memory request has to travel all the way to global VRAM.
  • Bandwidth Consumption: Accessing this.thread consumes no memory bus bandwidth. Reading textures actively consumes GPU memory bandwidth. If multiple threads simultaneously request data scattered across different memory addresses, memory stalls occur, degrading performance.

Spatial Locality and Caching

GPUs process threads in groups called warps (Nvidia) or wavefronts (AMD). When neighboring threads in a warp access neighboring coordinates in a texture—such as thread \((x, y)\) reading texture coordinate \((x, y)\)—the hardware can fetch the required data in a single coalesced memory transaction. In this optimal scenario, the texture cache absorbs much of the latency.

However, non-linear access patterns (such as reading rotated, transposed, or randomized texture indices) cause cache misses. In these cases, texture lookups become significantly slower than operations purely derived from this.thread.

When to Use Each Approach

  • Rely on this.thread for Procedural Workloads: If your kernel generates values through mathematical formulas, noise functions, coordinate mapping, or procedural geometry, calculate results entirely using this.thread. Generating values computationally is often orders of magnitude faster than storing and retrieving them from texture memory.
  • Use Texture Lookups for Data-Driven Workloads: Texture memory is mandatory when your algorithm requires preexisting data sets, such as image processing, neural network inference, or matrix multiplication.

Optimization Takeaway

When designing GPU.js kernels, minimize texture lookups whenever data can be mathematically derived from this.thread. When texture reads are unavoidable, structure your indexing so that adjacent threads access adjacent elements in the input arrays to maximize cache hits and maintain high memory throughput.
