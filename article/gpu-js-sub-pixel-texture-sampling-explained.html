GPU.js Sub-Pixel Texture Sampling Explained

This article explores how gpu.js handles sub-pixel texture sampling under the hood when executing parallel computations on the GPU. In gpu.js, data arrays and matrices are frequently passed to kernels as WebGL textures. Understanding how the library translates discrete thread coordinates into continuous texture coordinates, the role of half-pixel offsets, and the enforcement of nearest-neighbor filtering is essential for avoiding boundary inaccuracies and data corruption during high-performance compute tasks.

Texture Representation in gpu.js

Under the hood, gpu.js compiles JavaScript functions into GLSL shaders executed via WebGL. Because GPUs process graphics primitives natively, input arrays, matrices, and kernel outputs are encoded into WebGL 2D textures.

In standard graphics rendering, colors are sampled across continuous surfaces using normalized texture coordinates \((u, v)\) that range from 0.0 to 1.0. However, general-purpose GPU (GPGPU) computations require exact array indexing rather than smooth graphical transitions. Every thread index (such as this.thread.x or this.thread.y) must map deterministically to a specific memory cell (texel) within the underlying texture.

The Half-Texel Offset

When mapping integer thread indices to normalized texture coordinates, sampling directly on texel boundaries creates ambiguity due to floating-point rounding errors. For example, sampling a texture of width \(W\) at integer position \(x\) using \(u = \frac{x}{W}\) targets the exact left boundary of a texel. Microscopic floating-point precision variances can cause the GPU to sample the preceding texel (\(x - 1\)) rather than the intended target (\(x\)).

To prevent boundary ambiguity, gpu.js applies a half-texel offset during texture coordinate calculation:

\[u = \frac{x + 0.5}{W}\] \[v = \frac{y + 0.5}{H}\]

By adding 0.5, sampling occurs directly at the geometric center of the target texel. This ensures that even with slight floating-point imprecision across different hardware architectures, the lookup remains safely within the bounds of the intended element.

Default Filtering: Nearest Neighbor

In graphical rendering, sub-pixel sampling often invokes bilinear filtering (gl.LINEAR) to smooth transitions between pixels. For numerical compute kernels, this interpolation would corrupt data by blending neighboring array values.

To ensure computational integrity, gpu.js configures its WebGL textures with gl.NEAREST filtering for both TEXTURE_MIN_FILTER and TEXTURE_MAG_FILTER:

  • No Interpolation: If an intermediate coordinate falls between two texels, the GPU does not blend adjacent values.
  • Deterministic Snapping: The texture unit snaps any sub-pixel coordinate to the single nearest texel center.
  • Preserved Types: Raw float or integer values stored in memory channels remain unchanged during read operations.

Data Packing and Dimensionality

When multi-dimensional arrays or large 1D vectors exceed the maximum texture size supported by the hardware (MAX_TEXTURE_SIZE), gpu.js packs data into 2D textures using specific memory layouts (such as distributing elements across red, green, blue, and alpha channels, or encoding 3D arrays into 2D sheets).

Sub-pixel coordinate calculation becomes critical during this unpacking phase in the generated GLSL fragment shader:

  1. Index Decoding: The shader performs integer division and modulo operations to determine the logical 1D, 2D, or 3D index.
  2. Coordinate Normalization: The target coordinates are calculated using the texture's actual physical dimensions with the half-pixel shift included.
  3. Precision Qualifiers: Shaders use highp float precision qualifiers to prevent rounding errors that could cause sub-pixel offsets to drift out of the target texel bounds during coordinate arithmetic.

Summary of Behavior

When indexing textures in gpu.js:

  • Sub-pixel sampling snaps strictly to the nearest texel due to gl.NEAREST filtering.
  • Coordinates are internally shifted by +0.5 texels to ensure lookups land in the center of data points.
  • Bilinear blending does not occur, ensuring mathematical data remains exact and isolated across thread boundaries.
