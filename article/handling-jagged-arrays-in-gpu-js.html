Handling Jagged Arrays in GPU.js

This article explains how GPU.js processes multidimensional array inputs with non-uniform or jagged row lengths. Because WebGL and GPU architectures require strict, uniform memory structures, GPU.js does not natively support ragged or jagged arrays. Below, you will discover why this limitation exists, what happens when non-uniform data is supplied to a kernel, and the standard engineering workarounds—specifically array padding and 1D flattening with offset tracking—used to process such data efficiently.

Native Incompatibility with Jagged Arrays

GPU.js compiles JavaScript functions into WebGL shader language (GLSL) code. WebGL maps multidimensional arrays into fixed-dimension textures (typically 2D or 3D grids) where every row shares the exact same width and every column shares the exact same height.

Because memory addressing in GPU hardware relies on uniform strides to calculate memory offsets rapidly, GPU.js requires regular, rectangular multidimensional arrays. It cannot inherently allocate variable-length memory rows within a single multidimensional input structure.

What Happens When Jagged Arrays Are Passed

If you pass a jagged array directly into a GPU.js kernel (for example, [[1, 2], [3, 4, 5, 6]]), the library determines the texture dimensions using the length of the top-level array and the length of the first inner array:

  1. Shorter Subsequent Rows: If a subsequent row is shorter than the first row, reading beyond its length results in undefined values being coerced into 0, NaN, or garbage memory data depending on the platform's WebGL implementation.
  2. Longer Subsequent Rows: If a subsequent row is longer than the first row, any elements extending past the initial row's width are silently truncated and ignored because the allocated texture width is too small.
  3. Compilation/Runtime Errors: In certain versions or modes (such as CPU fallback mode), passing irregular arrays may throw explicit type errors or length mismatch exceptions during the input texture preparation phase.

Workaround 1: Array Padding (Rectangularization)

The simplest method to handle non-uniform rows is to pad shorter rows with a sentinel value (such as 0, -1, or NaN) so that all rows match the length of the longest row.

function padJaggedArray(arr, fillValue = 0) {
  const maxLength = Math.max(...arr.map(row => row.length));
  return arr.map(row => {
    const padded = new Array(maxLength).fill(fillValue);
    for (let i = 0; i < row.length; i++) {
      padded[i] = row[i];
    }
    return padded;
  });
}

Within the GPU.js kernel, you can check for the fill value to ignore padding elements during calculations. While this approach introduces unused memory overhead, it keeps array indexing straightforward.

Workaround 2: 1D Flattening with an Offset Array

For highly irregular or sparse datasets where padding consumes excessive memory, the optimal pattern is to flatten the jagged array into a single continuous 1D array and supply a secondary 1D array containing row offsets or lengths. This technique mirrors the standard Compressed Sparse Row (CSR) storage format.

function flattenJaggedArray(arr) {
  const flatData = [];
  const rowOffsets = [0];

  for (let i = 0; i < arr.length; i++) {
    for (let j = 0; j < arr[i].length; j++) {
      flatData.push(arr[i][j]);
    }
    rowOffsets.push(flatData.length);
  }

  return { flatData, rowOffsets };
}

In your GPU.js kernel, configure the output dimension to match the number of rows. Each thread uses the rowOffsets array to determine the start index and end index for its assigned row within the flatData array, iterating only through the actual data elements present.
