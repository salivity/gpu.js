GPU.js Lexical Scoping for Let and Const

This article explores how GPU.js resolves JavaScript block scoping when converting kernel functions into WebGL-compatible GLSL (OpenGL Shading Language). GPU.js achieves this by parsing the JavaScript code into an Abstract Syntax Tree (AST), tracking scopes across nested blocks, resolving variable shadowing through name mangling, and inferring static types for GLSL output.

AST Parsing and Scope Tracking

GPU.js does not execute kernel functions directly in the CPU's JavaScript runtime; instead, it transpiles the function source code into GLSL shaders. This process begins by parsing the JavaScript function using an AST parser (such as Acorn).

When the parser encounters a BlockStatement containing let or const declarations (represented as VariableDeclaration nodes with a let or const kind), GPU.js creates a distinct scope context. Unlike var, which hoists to the function body, let and const bindings are bound to their immediate enclosing block. GPU.js maintains a scope chain—a stack of symbol tables—that tracks active identifiers, their types, and their current nesting depth as it traverses into and out of blocks such as if statements, for loops, and standalone {} blocks.

Variable Shadowing and Name Mangling

GLSL supports basic compound statement scoping inside curly braces { ... }, but implementations across graphics drivers and WebGL backends are notoriously strict and inconsistent regarding variable shadowing. In standard JavaScript, an inner block can declare a let variable with the same name as an outer variable without conflict:

let x = 1.0;
if (condition) {
    let x = 2.0;
}

To prevent shader compilation errors and undefined behavior across diverse GPU drivers, GPU.js inspects the scope chain during code generation. If an identifier declared via let or const inside a nested block conflicts with an existing identifier in an outer scope, the compiler renames (mangles) the inner variable. By appending a unique suffix or scope-based index to the identifier in the generated GLSL, GPU.js eliminates collision risks while preserving lexical integrity.

Type Inference and Static Declaration

JavaScript variables declared with let and const are dynamically typed, whereas GLSL requires explicit, static types (e.g., float, int, vec4). When compiling a let or const declaration inside a nested block:

  1. Initial Value Evaluation: GPU.js analyzes the right-hand expression assigned to the variable.
  2. Type Inference: The compiler determines the primitive type resulting from the expression (such as identifying that let i = 0; produces an integer or let val = 1.5; produces a float).
  3. GLSL Emission: The variable declaration is emitted directly inside the corresponding GLSL block with its inferred type prepended.

Because const declarations cannot be reassigned, GPU.js can often optimize them by substituting their literal values directly into expressions (constant folding) or declaring them with the GLSL const qualifier.

Retention of Compound Blocks

Once identifiers are disambiguated and types are assigned, GPU.js translates JavaScript control flow blocks directly into corresponding GLSL compound statements. The compiler outputs the mangled let and const variables within matching curly braces {} in the shader text. This ensures that the GPU's native shader compiler deallocates registers and limits variable lifetimes identically to JavaScript's lexical scoping rules.
