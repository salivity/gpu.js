Does GPU.js Support 64-Bit Double Precision?

This article examines whether GPU.js natively supports 64-bit double-precision floating-point arithmetic (FP64). It details the architectural reasons behind GPU.js's precision capabilities, the constraints imposed by WebGL, the practical impacts on high-precision numerical computing, and the available workarounds for developers who require FP64 accuracy.

Native FP64 Support in GPU.js

GPU.js does not natively support 64-bit double-precision floating-point arithmetic. All floating-point operations executed on the GPU via GPU.js default to 32-bit single-precision floats (highp float).

If you pass 64-bit floats from standard JavaScript—which uses IEEE 754 double precision by default for numbers—GPU.js automatically downcasts them to 32-bit single precision when compiling and executing kernels on the GPU.

Why GPU.js Lacks Native 64-Bit Support

The absence of native double-precision support is due to the underlying graphics APIs used by GPU.js:

  • WebGL Limitations: GPU.js compiles JavaScript functions into GLSL (OpenGL Shading Language) and executes them using WebGL 1 or WebGL 2 contexts. WebGL is based on OpenGL ES, which was designed for mobile devices and real-time graphics where 32-bit single precision is standard.
  • No double Type in WebGL: WebGL 2 supports integer types and 32-bit floating-point textures, but it lacks the core GLSL double data type found in desktop OpenGL. Because browsers do not expose 64-bit float extensions to WebGL, GPU.js cannot access hardware FP64 units even if the underlying physical GPU supports them.

Practical Implications for Developers

Because calculations occur in 32-bit precision, developers must account for specific limitations:

  • Precision Loss: 32-bit floats provide roughly 7 decimal digits of precision, whereas 64-bit floats provide roughly 15 to 17 digits.
  • Accumulated Roundoff Errors: Iterative scientific simulations, large-scale matrix multiplications, and financial computations run the risk of catastrophic cancellation and drift over time.
  • Dynamic Range Constraints: Single-precision values have an exponent range of roughly \(10^{-38}\) to \(10^{38}\), which may cause underflow or overflow in computations requiring the broader range of FP64 (\(10^{-308}\) to \(10^{308}\)).

Alternatives and Workarounds

Developers requiring double-precision accuracy have several alternatives:

  1. Software-Emulated Double Precision: You can emulate 64-bit precision within 32-bit WebGL shaders using "double-single" arithmetic. This method represents a double as a pair of two 32-bit floats (a high part and a low part). While it increases accuracy, it requires custom shader algorithms and carries a significant performance penalty.
  2. CPU Fallback via WebAssembly: For workloads where precision is paramount, running compiled C++, Rust, or Fortran via WebAssembly on the CPU guarantees native IEEE 754 FP64 arithmetic, though it forfeits GPU parallelism.
  3. WebGPU: As WebGPU adoption grows, future browser-based compute platforms may introduce broader FP64 capabilities, although current WebGPU standards also focus primarily on 32-bit float (f32) and 16-bit float (f16) operations.
