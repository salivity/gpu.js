Dynamic Force-Directed Graphs with GPU.js

This article explains how to implement high-performance, dynamic force-directed network graph layouts using GPU.js. By offloading computationally intensive n-body calculations to the GPU via WebGL shaders, you can simulate thousands of interacting nodes in real time. Below, you will find the theoretical foundation of force-directed physics, the data structure adaptations required for GPU processing, and a practical implementation using GPU.js kernels to compute repulsive and attractive forces dynamically.

Understanding the Force-Directed Bottleneck

A classic force-directed graph layout applies physical simulations to position nodes aesthetically:

  1. Repulsive Forces (Coulomb's Law): Every node repels every other node, preventing overlap. This operation scales at \(\mathcal{O}(N^2)\) complexity.
  2. Attractive Forces (Hooke's Law): Connected nodes (edges) attract each other like springs, pulling related clusters together. This scales at \(\mathcal{O}(E)\) complexity, where \(E\) is the number of edges.

When the node count exceeds a few hundred, CPU-based JavaScript engines face frame-rate drops due to the \(\mathcal{O}(N^2)\) repulsion calculations. GPU.js compiles JavaScript functions into WebGL fragment shaders, executing thousands of coordinate evaluations in parallel.

Prerequisites and Data Representation

GPU kernels do not accept standard JavaScript object graphs (such as arrays of node objects with nested pointers). Instead, graph data must be flattened into typed arrays or continuous buffers:

  • Positions: A 2D array or flat array of coordinates [x, y].
  • Velocities: A 2D array representing velocity vectors [vx, vy].
  • Adjacency Matrix: A flattened binary matrix representing connections, where matrix[i * N + j] === 1 denotes an edge between node \(i\) and node \(j\).

Step 1: Initialize GPU.js and Define Simulation Constants

Set up the GPU instance and declare the simulation constants, such as repulsion strength, spring stiffness, damping, and time step delta.

const gpu = new GPU();

const NODE_COUNT = 1000;
const K_REPULSE = 5000.0;
const K_ATTRACT = 0.05;
const DAMPING = 0.85;
const DELTA_TIME = 0.016;

Step 2: Create the Repulsion Kernel

The repulsion kernel runs for each node \(i\) and loops over all nodes \(j\) to compute the net repulsive displacement.

const computeRepulsion = gpu.createKernel(function(positions, count, kRepulse) {
    const i = this.thread.x;
    let fx = 0.0;
    let fy = 0.0;
    const px = positions[i][0];
    const py = positions[i][1];

    for (let j = 0; j < count; j++) {
        if (i !== j) {
            const dx = px - positions[j][0];
            const dy = py - positions[j][1];
            const distSq = dx * dx + dy * dy + 0.1; // Epsilon prevents division by zero
            const dist = Math.sqrt(distSq);
            const force = kRepulse / distSq;

            fx += (dx / dist) * force;
            fy += (dy / dist) * force;
        }
    }

    return [fx, fy];
})
.setOutput([NODE_COUNT])
.setDynamicOutput(true);

Step 3: Create the Attraction Kernel

The attraction kernel iterates through the adjacency matrix to compute spring tension between connected nodes.

const computeAttraction = gpu.createKernel(function(positions, adjacency, count, kAttract) {
    const i = this.thread.x;
    let fx = 0.0;
    let fy = 0.0;
    const px = positions[i][0];
    const py = positions[i][1];

    for (let j = 0; j < count; j++) {
        if (adjacency[i * count + j] === 1) {
            const dx = positions[j][0] - px;
            const dy = positions[j][1] - py;
            
            fx += dx * kAttract;
            fy += dy * kAttract;
        }
    }

    return [fx, fy];
})
.setOutput([NODE_COUNT])
.setDynamicOutput(true);

Step 4: Integrate Positions and Velocities

A final integration kernel combines the forces, updates velocities with damping, and shifts the node positions.

const updatePositions = gpu.createKernel(function(positions, velocities, repForces, attForces, damping, dt) {
    const i = this.thread.x;

    const totalFx = repForces[i][0] + attForces[i][0];
    const totalFy = repForces[i][1] + attForces[i][1];

    // Verlet/Euler integration step
    const vx = (velocities[i][0] + totalFx * dt) * damping;
    const vy = (velocities[i][1] + totalFy * dt) * damping;

    const px = positions[i][0] + vx * dt;
    const py = positions[i][1] + vy * dt;

    return [px, py, vx, vy];
})
.setOutput([NODE_COUNT])
.setPipeline(true); // Keeps data on GPU memory between loops

Step 5: The Simulation Loop

Coordinate the kernels in a dynamic render loop using requestAnimationFrame. When pipeline mode is enabled, data stays inside texture memory, minimizing CPU-GPU bus transfer latency.

let positions = initializeRandomPositions(NODE_COUNT);
let velocities = new Array(NODE_COUNT).fill(0).map(() => [0, 0]);
const adjacency = generateAdjacencyMatrix(NODE_COUNT);

function tick() {
    const repForces = computeRepulsion(positions, NODE_COUNT, K_REPULSE);
    const attForces = computeAttraction(positions, adjacency, NODE_COUNT, K_ATTRACT);
    
    // Compute integrated positions and velocities
    const state = updatePositions(
        positions, 
        velocities, 
        repForces, 
        attForces, 
        DAMPING, 
        DELTA_TIME
    );

    // Read values back only when rendering to Canvas/WebGL
    const result = state.toArray();
    for (let i = 0; i < NODE_COUNT; i++) {
        positions[i][0] = result[i][0];
        positions[i][1] = result[i][1];
        velocities[i][0] = result[i][2];
        velocities[i][1] = result[i][3];
    }

    renderGraph(positions, adjacency);
    requestAnimationFrame(tick);
}

requestAnimationFrame(tick);

Performance Optimization Strategies

  • Keep Data on the Texture Buffer: Avoid .toArray() whenever possible. If rendering with WebGL or Pixi.js, bind the GPU.js output texture directly to the rendering context to completely avoid moving array data across the CPU bus.
  • Tiling for Large Datasets: For graphs with over \(10,000\) nodes, implement a Barnes-Hut quadtree on the CPU, or break the \(N \times N\) loop in the GPU fragment shader into fixed-size computational tiles to avoid GPU watchdog timer crashes (TDR limits).
