How to Verify GPU.js Execution Mode

GPU.js accelerates JavaScript calculations by compiling code into WebGL shaders to execute on the graphics card, automatically falling back to JavaScript on the CPU when hardware acceleration is unavailable. This article details the primary diagnostic properties and methods available in GPU.js to verify whether a kernel is actively running on the GPU or executing in CPU fallback mode.

Inspecting the Kernel SubClass

The most direct and reliable way to determine the active execution engine of a compiled kernel is through its underlying kernel runner class. When GPU.js compiles a kernel, it instantiates an internal runner tailored to the environment.

You can inspect the subClass property of a created kernel instance:

const gpu = new GPU();
const myKernel = gpu.createKernel(function() {
  return this.thread.x;
}).setOutput([10]);

// Execute or inspect the kernel runner
console.log(myKernel.subClass.name);

Depending on your platform and available hardware, myKernel.subClass.name will output one of the following concrete class names:

  • WebGL2Kernel: Executing on the GPU using WebGL 2.0.
  • WebGLKernel: Executing on the GPU using WebGL 1.0.
  • HeadlessGLKernel: Executing on the GPU in a Node.js environment via headless-gl.
  • CPUKernel: Executing on the CPU as standard JavaScript loops due to lack of WebGL support or manual configuration.

Checking Mode Enforcement at Initialization

By default, GPU.js operates with automatic fallback. If WebGL context creation fails, it quietly downgrades execution to the CPU. You can detect hardware availability diagnostically by enforcing the mode during GPU instantiation:

// Force GPU execution without silent CPU fallback
try {
  const gpu = new GPU({ mode: 'gpu' });
  const kernel = gpu.createKernel(function() {
    return this.thread.x;
  }).setOutput([10]);
  
  kernel();
  console.log("GPU execution confirmed.");
} catch (error) {
  console.error("GPU acceleration is not supported in this environment:", error);
}

If the environment does not support WebGL or HeadlessGL, passing { mode: 'gpu' } will throw an error immediately rather than defaulting to CPU emulation, providing an explicit diagnostic signal.

Automated Diagnostic Helper

To programmatically determine the active execution mode at runtime across multiple kernels or environments, you can implement a lightweight diagnostic check:

function getExecutionMode(kernel) {
  if (!kernel || !kernel.subClass) {
    return 'unknown';
  }

  const runnerName = kernel.subClass.name;

  if (runnerName === 'CPUKernel') {
    return 'CPU';
  } else if (runnerName === 'WebGL2Kernel' || runnerName === 'WebGLKernel' || runnerName === 'HeadlessGLKernel') {
    return `GPU (${runnerName})`;
  }

  return runnerName;
}

const gpu = new GPU();
const compute = gpu.createKernel(function(a, b) {
  return a[this.thread.x] + b[this.thread.x];
}).setOutput([5]);

console.log(`Active Mode: ${getExecutionMode(compute)}`);

Monitoring Console Warnings

When running in standard environments with default settings, GPU.js logs warning messages to the browser or terminal console if a WebGL context cannot be created. Observing the developer console during the initialization of the GPU instance or during the first kernel invocation serves as a passive diagnostic indicator for identifying why a fallback to CPUKernel occurred.
