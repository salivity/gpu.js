Bridge Three.js WebGLRenderer and gpu.js State

Bridging state between a Three.js WebGLRenderer and a standalone gpu.js instance allows you to perform high-performance general-purpose GPU (GPGPU) computations while rendering complex 3D scenes on the same canvas. Achieving this requires sharing a single underlying WebGLRenderingContext, managing WebGL state cache invalidation, and passing data between pipelines using raw WebGL textures to avoid CPU readback bottlenecks.

1. Share the WebGL Context

To avoid memory duplication and context thrashing, initialize gpu.js using the existing WebGL context managed by Three.js. Extract the context directly from the initialized WebGLRenderer.

import * as THREE from 'three';
import { GPU } from 'gpu.js';

const renderer = new THREE.WebGLRenderer({ antialias: true });
renderer.setSize(window.innerWidth, window.innerHeight);
document.body.appendChild(renderer.domElement);

const gl = renderer.getContext();
const gpu = new GPU({
  context: gl,
  canvas: renderer.domElement
});

Passing the existing context ensures both libraries manipulate the same hardware state machine and share the resource namespace (textures, buffers, and framebuffers).

2. Manage WebGL State Invalidation

Three.js aggressively caches WebGL state—including active program bindings, bound framebuffers, vertex array objects (VAOs), blending modes, and texture units—to minimize driver overhead. Because gpu.js operates independently, it alters this state without notifying Three.js.

To prevent visual glitches or shader errors, you must reset the Three.js state cache immediately after running any gpu.js kernel:

renderer.resetState();

Calling resetState() forces Three.js to rebind its programs, re-enable its required blend states, and reset vertex attributes during the next renderer.render() call.

3. Pass Data Using Textures (Zero-Copy)

Transferring data between Three.js and gpu.js via the CPU (using readPixels or array serializations) eliminates the performance benefits of GPU execution. Instead, keep the data in VRAM by operating directly on WebGL textures.

Outputting from gpu.js to Three.js

Configure the gpu.js kernel to output a texture using the pipeline mode or texture output mode:

const computeKernel = gpu.createKernel(function() {
  // GPGPU compute logic
  return this.thread.x / 512;
})
.setOutput([512, 512])
.setPipeline(true);

const resultTexture = computeKernel();

Wrap the native WebGL texture produced by gpu.js inside a Three.js ExternalTexture or WebGLTexture wrapper:

const threeTexture = new THREE.Texture();
const textureProperties = renderer.properties.get(threeTexture);

// Assign the raw WebGLTexture produced by gpu.js
textureProperties.__webglTexture = resultTexture.texture;
threeTexture.needsUpdate = false; // Prevent Three.js from uploading null data

Inputting Three.js Render Targets into gpu.js

When processing a Three.js scene inside gpu.js, render the scene into a THREE.WebGLRenderTarget, retrieve the internal WebGL texture reference, and pass it as an argument:

renderer.setRenderTarget(renderTarget);
renderer.render(scene, camera);
renderer.setRenderTarget(null);

const rawTexture = renderer.properties.get(renderTarget.texture).__webglTexture;
// Pass the native texture reference to your custom gpu.js wrapper or kernel

4. The Unified Execution Loop

Coordinate execution order strictly within the requestAnimationFrame loop to ensure synchronization:

function animate() {
  requestAnimationFrame(animate);

  // 1. Run gpu.js compute passes
  computeKernel();

  // 2. Invalidate Three.js state cache
  renderer.resetState();

  // 3. Render Three.js scene
  renderer.render(scene, camera);
}

animate();

By keeping textures resident on the GPU and resetting the internal WebGL state between compute and render passes, you maintain optimal throughput and prevent driver conflicts between both engines.
