Calculating Screen-Space Reflections in GPU.js

Screen-space reflections (SSR) across planar surfaces can theoretically be calculated using gpu.js, but the approach involves significant architectural trade-offs. This article examines the feasibility of using gpu.js for screen-space ray marching, how planar reflection math maps to general-purpose GPU computing, and why native WebGL or WebGPU pipelines remain the preferred choice for real-time graphics.

Understanding Planar Screen-Space Reflections

Planar screen-space reflections work by tracing rays across the visible scene using data already rendered to the screen. For a planar surface—such as a flat mirror, polished floor, or still body of water—the algorithm performs the following steps:

  1. Identifies the surface normal and orientation of the planar reflector.
  2. Calculates a reflected view vector for each pixel belonging to the plane.
  3. Marches along the reflected vector in screen space using the camera's depth buffer.
  4. Detects intersections where the ray's depth matches or exceeds the scene geometry depth.
  5. Samples the color buffer at the intersection coordinates to generate the reflected color.

Because the surface is planar, the initial reflection vectors are uniform and predictable, making ray setup mathematically simpler than reflections over arbitrary, rough surfaces.

Implementing Planar SSR in gpu.js

gpu.js is a library that compiles JavaScript functions into WebGL fragment shaders to run general-purpose computations on the GPU. Calculating planar SSR with gpu.js requires treating the reflection pass as a general-purpose computation (GPGPU) problem.

To achieve this in gpu.js:

  • Input Data: You must pass the rendered scene color buffer, the linear depth buffer, the camera projection matrices, and the plane equation into a gpu.js kernel as textures or 2D arrays.
  • The Kernel Function: The kernel function executes once per pixel of the output buffer. Inside the kernel, you implement a ray-marching loop that steps through the 2D coordinate space, sampling depth values from the input depth texture to check for ray-surface intersections.
  • Output: The kernel outputs an array or a WebGL texture containing the reflected color values or screen coordinates for a subsequent compositing pass.

gpu.js supports graphical output modes (graphical: true), allowing the kernel to draw directly to an HTML5 canvas or output a WebGL texture, which is required to prevent costly memory transfers between GPU and CPU memory.

Limitations and Practical Bottlenecks

While mathematically feasible, using gpu.js for planar screen-space reflections introduces several practical bottlenecks:

  • Pipeline Fragmentation: Real-time SSR depends heavily on the existing graphics pipeline. Passing framebuffers, depth textures, and normal maps from a rendering engine (like Three.js or Babylon.js) into gpu.js and back incurs synchronization overhead.
  • Lack of Advanced Shader Features: gpu.js abstracts away many low-level WebGL controls, such as manual mipmap sampling (useful for simulating glossy planar reflections), custom blending states, and hardware-accelerated texture interpolation.
  • Control Flow Constraints: Screen-space ray marching relies on early exits (break) to stop marching once an intersection occurs. While gpu.js supports basic loops, complex branching in translated shaders can lead to performance degradation depending on how the loop unrolls on different graphics drivers.

Verdict

Planar screen-space reflections can be calculated with gpu.js because the library provides the necessary parallel execution model, texture inputs, and math operations needed for screen-space ray marching. However, it is an inefficient choice for production 3D engines. For real-time graphics, implementing the SSR pass directly in a custom WebGL or WebGPU post-processing shader is substantially faster and integrates cleanly with the existing render pipeline.
