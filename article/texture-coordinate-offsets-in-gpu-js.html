Texture Coordinate Offsets in gpu.js

This article explains how the gpu.js library manages texture coordinate offsets and avoids sampling artifacts when reading data at non-integer boundaries in WebGL. Because gpu.js translates JavaScript array operations into GPU fragment shaders, it must map array indices directly to floating-point texture coordinates. To guarantee data precision and prevent interpolation errors, gpu.js utilizes half-texel offsets, strict nearest-neighbor texture filtering, and automated coordinate conversion in its generated GLSL code.

The Half-Texel Problem in WebGL

In WebGL and OpenGL, texture coordinates (\(U, V\)) are normalized between 0.0 and 1.0. A texel is not an infinitesimal point; it is an area. The integer coordinates of a discrete texel represent its outer boundary, while the true center of the texel lies at an offset of half a unit:

\[\text{Texel Center} = x + 0.5\]

If a shader samples a texture directly at a texel edge (an exact integer boundary in pixel space), floating-point rounding errors can cause the GPU to sample either the intended texel or its adjacent neighbor. For graphics, this creates minor visual blur; for general-purpose GPU (GPGPU) compute tasks where texels hold numerical data, it corrupts calculations.

Automated Half-Texel Offsetting

To prevent boundary ambiguity, the gpu.js shader compiler automatically adds a 0.5 offset to coordinate calculations during index-to-UV translation. When an internal kernel reads from an input array mapped as a texture, the generated GLSL does not query index \(x\) directly. Instead, it computes the normalized coordinate using:

vec2 uv = (vec2(x, y) + vec2(0.5, 0.5)) / textureDimensions;

By explicitly targeting the center of the texel, the sample point sits as far away from the texel's bounding borders as possible. This margin accommodates IEEE 754 floating-point inaccuracies inherent in GPU arithmetic, ensuring that small precision drifts do not push the sample into an adjacent memory cell.

Nearest-Neighbor Filtering Enforcement

Texture samplers in standard rendering pipelines often rely on bilinear filtering (gl.LINEAR), which blends adjacent texels when queried at non-integer coordinates. This behavior is catastrophic for scientific computing and matrix operations.

gpu.js configures its WebGL texture parameters to use nearest-neighbor sampling:

  • gl.TEXTURE_MIN_FILTER = gl.NEAREST
  • gl.TEXTURE_MAG_FILTER = gl.NEAREST
  • gl.TEXTURE_WRAP_S = gl.CLAMP_TO_EDGE
  • gl.TEXTURE_WRAP_T = gl.CLAMP_TO_EDGE

With gl.NEAREST, the GPU evaluates any non-integer texture coordinate by snapping it to the nearest texel center. Combined with gl.CLAMP_TO_EDGE, samples that fall slightly outside the range [0.0, 1.0] due to non-integer bounds or edge arithmetic do not wrap around to the other side of the array; instead, they clamp safely to the border texel.

Handling Non-Integer Lookups in Shaders

When user-written kernel code generates non-integer indices dynamically, gpu.js handles coordinate resolution via internal GLSL mathematical utilities.

If fractional indices are passed into built-in lookup functions, the compiler generates instructions to truncate or floor the incoming value before applying the half-texel offset. This ensures that:

  1. The fractional index is explicitly converted to an integer index.
  2. The + 0.5 bias is added to the resolved integer.
  3. The result is divided by the texture dimension to normalize the coordinate.

Through this sequence—clamping the texture edges, applying a half-texel shift, enforcing nearest-neighbor selection, and normalizing coordinates against texture dimensions—gpu.js ensures that memory reads at or near texel boundaries reliably retrieve exact, uncorrupted numerical values.
