What Happens to GPU.js Textures in Background Tabs

When a browser tab running gpu.js is moved to the background, allocated textures remain stored in GPU memory by default, but their lifecycle becomes precarious due to browser optimization strategies. While the data persists initially, background execution is heavily throttled, and the underlying WebGL context is placed at high risk of being purged by the browser's memory management engine, leading to potential data loss or execution errors.

Immediate State: Memory Retention and Throttling

Moving a tab to the background does not instantly destroy allocated textures. Because gpu.js relies on WebGL to perform calculations, textures reside in video RAM (VRAM) as standard WebGL texture objects. These allocations remain intact as long as the tab's WebGL context is preserved.

However, the browser immediately changes how that tab executes:

  • Execution Pauses or Throttles: Browsers heavily throttle JavaScript execution timers (setTimeout, setInterval) and completely pause requestAnimationFrame callbacks for background tabs. Any continuous computational loop processing or writing to textures will stall or run at an extremely low frequency (often once per second or less).
  • VRAM Allocation Unchanged: Existing textures consume the same amount of GPU memory as they did when the tab was active.

The Threat of WebGL Context Loss

The primary risk to textures in a backgrounded gpu.js application is WebGL context loss. Modern browsers prioritize foreground tasks, such as active rendering, video playback, and active tabs. When the operating system or browser encounters memory pressure, background tabs are the first candidates to have their GPU resources reclaimed.

If the browser decides to reclaim resources:

  1. Context Loss Trigger: The browser fires the webglcontextlost event on the canvas used by gpu.js.
  2. Immediate Deallocation: All hardware-accelerated resources associated with that context—including framebuffers, shaders, and allocated textures—are wiped from VRAM.
  3. Stale References: The JavaScript wrapper objects in gpu.js lose their link to the underlying hardware buffers. Any subsequent attempt to read from or write to these textures without re-initializing will fail or return null values.

Tab Freezing and Tab Discarding

Beyond context loss, modern browser features like Chrome’s "Memory Saver" or Firefox's tab unloading can impact textures:

  • Tab Freezing: The browser suspends JavaScript execution entirely. Textures remain in VRAM, but no pipeline operations can occur until the tab is focused again.
  • Tab Discarding (Unloading): If system memory remains low, the browser may completely unload the background tab from RAM and VRAM while keeping the tab visible in the tab bar. When the user clicks the tab again, the entire page reloads from scratch, destroying all existing gpu.js instances and texture data.

Preventing and Handling Texture Loss

To maintain application stability when users switch tabs, applications relying on gpu.js should implement defensive state management:

  • Listen for Context Events: Attach event listeners for webglcontextlost and webglcontextrestored on the canvas context underlying the GPU instance. Prevent the default event behavior on webglcontextlost to allow eventual restoration.
  • Re-upload Critical Data: Treat GPU textures as transient. Retain a fallback copy of critical input data in standard JavaScript typed arrays (CPU memory) so textures can be regenerated if the context is restored.
  • Read Out Textures Before Inactivity: If predictable idle periods occur, download computed texture results back to CPU memory using kernel.setOutputOrder('read') or equivalent output-reading methods before the tab loses focus.
