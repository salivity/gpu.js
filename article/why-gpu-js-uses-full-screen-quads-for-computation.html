Why GPU.js Uses Full-Screen Quads for Computation

GPU.js accelerates JavaScript code by translating it into WebGL shaders that execute on the graphics processing unit. Because traditional WebGL lacks native compute shaders, the library repurposes the standard graphics rendering pipeline for general-purpose computing (GPGPU). To execute parallel computations across an entire dataset, GPU.js renders a full-screen quad—a rectangle made of two triangles covering the entire viewport—which forces the GPU rasterizer to invoke the fragment shader for every single output data element.

The WebGL Rendering Constraint

Standard WebGL 1.0 and 2.0 were designed primarily for rasterization-based rendering rather than arbitrary compute tasks. Unlike modern graphics APIs such as WebGPU, Direct3D 11, or Vulkan, WebGL does not feature dedicated "compute shaders" designed to process flat memory buffers directly. Instead, processing must occur within the constraints of the classic graphics pipeline: geometry inputs are processed by vertex shaders, assembled into primitive shapes, rasterized into pixels (fragments), and shaded by fragment shaders before writing to a framebuffer.

Mapping Data to Textures and Fragments

To bypass this limitation, GPU.js treats mathematical data as visual textures:

  • Input arrays and matrices are encoded into floating-point or standard textures.
  • The output calculation space is treated as a rendering target (a framebuffer backed by a texture) of dimensions \(W \times H\), representing the dimensions of the result array.
  • The JavaScript function provided by the developer is compiled into GLSL code that resides inside a fragment shader.

In this architecture, every pixel in the output texture represents a single compute thread or item in the output array.

How the Full-Screen Quad Triggers Processing

A fragment shader cannot execute on its own; it requires primitives to be rasterized into the viewport. If no geometry is submitted to the GPU, no fragments are generated, and the fragment shader never runs.

GPU.js addresses this by submitting two triangles forming a flat, screen-aligned quad with vertices covering normalized device coordinates from \((-1, -1)\) to \((1, 1)\).

  1. Complete Viewport Coverage: Because the quad covers the exact boundaries of the output surface, the GPU's fixed-function rasterizer produces a fragment for every single pixel in the target framebuffer without any gaps or overlaps.
  2. Deterministic Parallel Invocation: As the rasterizer creates fragments across the entire grid, the GPU schedules the fragment shader to run simultaneously on thousands of execution cores.
  3. Implicit Indexing: The fragment shader uses built-in coordinates (such as gl_FragCoord) to determine the exact row and column of the pixel being calculated. This spatial coordinate maps directly back to the index of the output array.

Execution Flow Summary

When a GPU.js kernel executes, it binds the input textures, attaches an output texture to a framebuffer, binds the full-screen quad vertex buffer, and issues a standard draw call (such as gl.drawArrays). The quad acts purely as a mechanical trigger: its geometry is trivial, but its rasterization causes the GPU to execute the computation across all target output elements in massive parallel batches.
