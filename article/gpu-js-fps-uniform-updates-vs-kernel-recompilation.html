GPU.js FPS: Uniform Updates vs Kernel Recompilation

In GPU.js, managing dynamic data through uniform updates rather than constant kernel recompilation is the single most critical factor in sustaining real-time frame rates. Recompiling a kernel forces the browser to regenerate and link WebGL shaders on every cycle, destroying animation smoothness and causing severe frame drops. Conversely, using dynamic uniforms allows the pre-compiled GPU program to execute continuously, keeping processing overhead minimal and maintaining stable 60+ frames per second (FPS) performance.

The Cost of Kernel Recompilation

When a GPU.js kernel is created or altered in a way that requires recompilation, several synchronous and resource-intensive steps occur:

  1. JavaScript-to-GLSL Transpilation: The JavaScript function string must be parsed, validated, and converted into GLSL (OpenGL Shading Language).
  2. Shader Compilation: The browser sends the GLSL source code to the graphics driver to compile both vertex and fragment shaders.
  3. Program Linking: The compiled shaders are linked into a WebGLProgram object, allocating GPU memory and setting up execution pipelines.

These steps are heavily CPU-bound and block the main JavaScript thread. Because shader compilation in WebGL is typically synchronous, forcing this process on every frame creates micro-stutters and drastically reduces throughput. In typical workloads, recompiling a kernel every frame causes frame rates to collapse from 60 FPS down to 1–5 FPS.

The Efficiency of Uniform Updates

Uniforms are read-only variables available to all parallel threads in a GPU shader that remain constant throughout a single draw call, but can change between calls.

When you define a kernel once and pass changing values (such as delta time, mouse coordinates, or interactive parameters) as arguments:

  • The kernel compiles exactly once during initialization.
  • Each execution merely updates WebGL uniform values (gl.uniform* calls under the hood).
  • Uniform state transfers take mere microseconds and occur without interrupting the GPU pipeline.

By bypassing code generation and shader recompilation, the CPU workload per frame is reduced to almost zero, leaving the GPU free to process matrix calculations or pixel data at native hardware speeds.

Frame Rate Comparison

  • Continuous Recompilation: Each frame incurs tens to hundreds of milliseconds of overhead depending on shader complexity and device drivers. The resulting frame times easily exceed the 16.6ms threshold required for 60 FPS, resulting in severe lag and unresponsiveness.
  • Uniform Updates: The execution cost per frame is bounded almost entirely by the actual computation time on the GPU. Frame times typically stay well within 1–5ms for moderate workloads, enabling consistent 60 FPS to 144 FPS rendering loops.

Implementation Best Practice

To preserve frame rates in animations or interactive simulations, construct the kernel function outside your execution loop and pass all variable values directly into the resulting function:

// Compile ONCE outside the loop
const renderKernel = gpu.createKernel(function(multiplier, time) {
  return this.thread.x * multiplier + Math.sin(time);
}).setOutput([512, 512]);

function animate(time) {
  // Pass dynamic values as uniforms inside the loop
  const result = renderKernel(2.5, time * 0.001);
  
  requestAnimationFrame(animate);
}

requestAnimationFrame(animate);

Treating kernels as immutable compiled pipelines and using arguments as dynamic uniforms ensures GPU.js runs at peak performance without introducing pipeline stalls.
