GPU.js Integer Overflow Handling Explained

This article explores how the GPU.js library handles integer overflow when variables exceed 32-bit signed boundaries. Because GPU.js transpiles JavaScript functions into WebGL shader code, its numerical limits and overflow characteristics are determined by the underlying Graphics Library Shading Language (GLSL) rather than standard JavaScript runtime behavior. Readers will learn about two's complement wrap-around in WebGL 2, the effects of float fallback in WebGL 1, and the discrepancies between CPU and GPU numerical precision.

The Transpilation Layer: JavaScript to GLSL

GPU.js works by parsing standard JavaScript functions and transpiling them into GLSL shaders executed directly on the GPU. In native JavaScript, numbers are 64-bit double-precision floating-point values (IEEE 754), capable of representing integers safely up to \(2^{53} - 1\).

When code is offloaded to the GPU via GPU.js, variables typed as integers are mapped to GLSL 32-bit signed integers (int). Consequently, standard JavaScript numerical safety limits no longer apply within kernel execution.

WebGL 2: Hardware Two's Complement Wrap-Around

When GPU.js runs in a WebGL 2 context, it utilizes native 32-bit signed integer types (int). The boundary limits for these values are:

  • Minimum: \(-2,147,483,648\) (\(-2^{31}\))
  • Maximum: \(2,147,483,647\) (\(2^{31} - 1\))

If an operation exceeds \(2,147,483,647\), the GPU does not throw an exception, clamp the value, or raise a warning. Modern graphics hardware evaluates integer arithmetic using two's complement binary representation. When an integer exceeds the maximum limit, the sign bit flips, causing the value to wrap around to the negative boundary:

\[2,147,483,647 + 1 = -2,147,483,648\]

Similarly, underflowing below \(-2,147,483,648\) wraps around back to the maximum positive integer:

\[-2,147,483,648 - 1 = 2,147,483,647\]

While the GLSL specification defines integer overflow as undefined behavior, contemporary GPU architectures consistently execute wrap-around arithmetic at the register level.

WebGL 1 Fallback: Single-Precision Float Emulation

In environments where WebGL 2 is unavailable, GPU.js falls back to WebGL 1. WebGL 1 shaders lack native support for integer arithmetic in many implementations and instead emulate numbers using 32-bit single-precision floating-point values (highp float).

In this scenario, numbers do not exhibit traditional two's complement wrap-around:

  • A 32-bit float provides 24 bits of mantissa precision.
  • Integers are accurately represented only up to \(2^{24}\) (\(16,777,216\)).
  • Calculations exceeding \(16,777,216\) suffer from precision degradation rather than sudden sign inversion. Increments of 1 will round to the nearest representable float, leading to silent inaccuracies instead of wrapping to negative values.

Discrepancies Between Kernel Code and JavaScript

The primary hazard when using GPU.js is the behavioral divergence between the CPU and the GPU:

  1. CPU Execution: If a kernel falls back to CPU execution (e.g., via mode: 'cpu'), operations proceed using standard JavaScript 64-bit floats. A value exceeding \(2,147,483,647\) continues incrementing normally up to \(9,007,199,254,740,991\).
  2. GPU Execution: The exact same code executed on the GPU via WebGL 2 wraps around to negative numbers as soon as it passes \(2,147,483,647\).

Preventing Integer Overflow in GPU.js

To avoid unexpected wrap-around or precision errors during kernel execution:

  • Enforce Manual Modulo Operations: If maintaining cyclic counter states, explicitly restrict boundaries using the modulo operator before reaching the 32-bit limit.
  • Utilize Floating-Point Math: Declare variables intended for large computations as floats rather than integers to leverage a broader numerical range, accounting for standard floating-point precision constraints.
  • Normalize Inputs: Scale large integer data down on the CPU before passing input arrays or textures into the GPU kernel.
