What Happens to GPU.js Textures on Page Refresh

When a browser window navigates away or refreshes, all GPU textures allocated by gpu.js are automatically reclaimed and destroyed alongside the underlying WebGL context. Because the browser terminates the execution context and tears down the associated canvas element, the graphics driver releases the allocated Video RAM (VRAM). As a result, you do not face persistent VRAM leaks across page reloads, even if you fail to explicitly dispose of your textures in JavaScript.

The Underlying WebGL Context Lifecycle

gpu.js operates by compiling JavaScript functions into GLSL shaders and running them via WebGL. When you configure kernels to output textures—often using the pipeline mode via kernel.setOutputToTexture(true)—gpu.js stores the resulting computational data directly inside native WebGL texture objects (WebGLTexture) on the GPU.

These textures belong strictly to the WebGLRenderingContext or WebGL2RenderingContext created by gpu.js. WebGL contexts are bound directly to the Document Object Model (DOM) and the lifetime of the document. When a navigation or refresh event occurs:

  1. The browser initiates an unload sequence (beforeunload and pagehide).
  2. The document and its associated DOM nodes, including any off-screen or rendered canvas elements created by gpu.js, are destroyed.
  3. The browser sends a signal to the GPU process to dispose of the WebGL context.
  4. The graphics driver deallocates all associated GPU resources, including vertex buffers, framebuffers, compiled shader programs, and allocated textures.

Automatic VRAM Reclamation vs. Manual Cleanup

In long-running Single Page Applications (SPAs) where navigation occurs without a full browser refresh, manual cleanup is critical. In those scenarios, failing to call texture.delete() or gpu.destroy() causes textures to accumulate in VRAM, eventually triggering an Out of Memory (OOM) error or context loss.

However, during a hard refresh (F5 / Ctrl+R) or navigation to a new URL, manual cleanup inside an unload or beforeunload event listener is unnecessary:

  • Synchronous Termination: Browsers prioritize fast teardown during page transitions. Relying on JavaScript unload hooks to call .delete() on individual textures often fails because modern browsers limit or outright ignore complex synchronous execution during page dismissal.
  • Process-Level Isolation: Modern browsers (such as Chrome, Firefox, and Edge) isolate WebGL instances within a sandboxed GPU process. When the renderer process terminates, the GPU process handles the deallocation of texture handles at the operating system and driver level.

Driver Edge Cases and Context Loss

While the browser guarantees that references are dropped, actual physical VRAM reclamation depends on the operating system and graphics hardware driver:

  • Delayed Garbage Collection: Some GPU drivers do not immediately zero out or return memory blocks to the OS pool upon context loss; instead, they mark the blocks as free and defer compaction until another process requests VRAM. This can make it appear as though memory is still reserved immediately after a refresh.
  • Context Loss Events: If a user repeatedly refreshes a page running heavy gpu.js allocations, the rapid cycling of texture creation and teardown can overwhelm the GPU driver's command buffer. This may trigger a webglcontextlost event, causing the browser to temporarily disable WebGL acceleration until the GPU resets.
