How GPU.js Handles Canvas Renderbuffer Allocation

When using GPU.js in graphical mode to render directly to an HTML5 canvas, the framework's internal memory management diverges significantly from its standard general-purpose computing (GPGPU) pipeline. This article breaks down how GPU.js handles renderbuffer allocation during direct canvas rendering, explaining the shift from explicit offscreen framebuffers to the WebGL default drawing buffer, the lifecycle management dictated by the canvas dimensions, and the performance optimizations achieved by eliminating redundant memory copies.

The Shift from GPGPU Textures to the Default Framebuffer

In standard compute mode, GPU.js treats the GPU as a data processor. To retrieve data arrays from kernels, it allocates custom WebGL Framebuffer Objects (FBOs) and binds 2D textures as color attachments. The fragment shader writes mathematical calculations to these textures, which GPU.js either keeps on the GPU for chained calculations or extracts to JavaScript memory via gl.readPixels().

When a kernel is initialized with { graphical: true }, GPU.js bypasses these custom offscreen framebuffers. Instead of allocating internal WebGL renderbuffers or color textures via gl.createRenderbuffer() and gl.renderbufferStorage(), GPU.js sets the active framebuffer target to null:

gl.bindFramebuffer(gl.FRAMEBUFFER, null);

Binding null targets the WebGL context's default drawing buffer. This default buffer is intrinsically tied to the canvas element itself, offloading the physical allocation of color, depth, and stencil renderbuffers directly to the browser's graphics subsystem and the underlying GPU driver.

Browser-Managed Drawing Buffer Allocation

Because GPU.js targets the default framebuffer in graphical mode, it does not explicitly manage byte-level renderbuffer sizing through WebGL API allocation commands. Instead, renderbuffer sizing is handled reactively:

  1. Dimension Synchronization: GPU.js matches the WebGL viewport to the kernel output dimensions using gl.viewport(0, 0, width, height).
  2. Backing Store Allocation: The browser automatically allocates the color renderbuffer (the canvas drawing buffer) based on the canvas DOM element's width and height properties, rather than its CSS display size.
  3. Double Buffering: The WebGL runtime creates and manages double-buffered color storage (a front buffer and a back buffer) to prevent screen tearing during draw calls.

If the canvas resolution changes, the browser deallocates the existing backing store and reallocates a new color buffer to accommodate the new dimensions, completely abstracting manual renderbuffer destruction and reallocation away from GPU.js.

Shader Pipeline and Direct Output

In graphical mode, GPU.js generates a fragment shader configured specifically for visual output rather than numeric encoding. A standard full-screen quad (two triangles covering normalized device coordinates from [-1, -1] to [1, 1]) is rasterized over the viewport.

Within the kernel code, the developer calls this.color(r, g, b, a). GPU.js translates this internal API call directly into writes to the native fragment shader output:

  • In WebGL 1, it compiles to assignments targeting gl_FragColor.
  • In WebGL 2, it binds to an out vec4 output variable targeted at index 0.

Because the active render target is the canvas back buffer, each fragment's color is written directly to the swap chain memory.

Context Options and Memory Overhead

When GPU.js instantiates or adopts a canvas context for graphical rendering, the underlying renderbuffer footprint is constrained by the WebGL context attributes. By default, GPU.js attempts to configure contexts efficiently:

  • Depth and Stencil Buffers: Unless explicitly required, depth and stencil renderbuffers are omitted, saving significant VRAM since graphical kernels operate strictly as 2D screen-space pixel shaders.
  • Preserve Drawing Buffer: By leaving WebGL's preserveDrawingBuffer set to false, GPU.js allows the browser to clear or swap the canvas renderbuffer immediately after the compositor presents the frame to the display, reducing GPU memory pressure and enabling zero-copy hardware presentation.
