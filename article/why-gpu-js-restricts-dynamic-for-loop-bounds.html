Why gpu.js Restricts Dynamic For-Loop Bounds

Dynamic for-loop bounds with non-constant limits are restricted in certain gpu.js configurations because the library transpiles JavaScript into WebGL shader language (GLSL), which is subject to strict graphics hardware and shader compilation constraints. In older target environments such as WebGL 1.0, the underlying GLSL specification explicitly prohibits non-constant loop bounds to guarantee loop termination and enable static optimization. Understanding why this restriction exists requires looking at shader compilation standards, GPU hardware architecture, and compiler loop unrolling.

WebGL 1.0 Specification and GLSL ES 1.00 Limitations

When gpu.js compiles a kernel function, it parses the JavaScript code and converts it into GLSL code. By default or in backward-compatible fallbacks, gpu.js targets WebGL 1.0, which is built upon the GLSL ES 1.00 specification.

Appendix A of the GLSL ES 1.00 specification enforces strict syntactic limitations on loop structures. Specifically, it mandates that:

  • The loop condition must compare the loop index against an integer or floating-point constant expression.
  • The loop increment must be a constant expression.

Because non-constant variables—such as dynamic parameters, varying values, or dependent calculations—do not resolve to compile-time constants, the underlying WebGL shader compiler will reject the shader and fail to compile the pipeline.

Loop Unrolling and Static Analysis

GPU drivers rely heavily on loop unrolling to maximize execution speed. During compilation, the shader compiler replaces a loop with repeated sequences of the loop body. This removes the branch instructions, minimizes pipeline stalls, and allows instruction-level parallelism.

For the compiler to unroll a loop or determine exact register allocation, the iteration count must be known before execution begins. When a loop limit is dynamic and varies per thread or per draw call, the compiler cannot calculate the static unroll factor or optimize register pressure, leading to unpredictable shader execution times and driver compilation failures.

SIMD Architecture and Branch Divergence

GPUs process data using Single Instruction, Multiple Threads (SIMT). Threads are grouped into fixed-size units, such as warps on NVIDIA hardware or wavefronts on AMD hardware, which execute the exact same instruction at any given clock cycle.

If a for-loop utilizes a non-constant bound that differs across individual threads (for example, depending on thread position or input array values), it causes branch divergence:

  • Threads requiring fewer iterations must idle while threads with larger limits continue processing.
  • The execution time of the entire warp becomes equivalent to the thread with the highest iteration count.

To mitigate this massive performance penalty, older graphics APIs strictly disallowed non-uniform loop conditions.

Overcoming the Restriction

Developers encountering dynamic loop bound errors in gpu.js can resolve them using a few specific techniques:

  1. Target WebGL 2: Modern implementations based on WebGL 2.0 (GLSL ES 3.00) lift many of the strict constant-bound restrictions found in WebGL 1.0, permitting dynamic evaluation of loop conditions.
  2. Fixed Upper Bounds with Early Exits: Use a static, constant maximum limit for the loop, and terminate execution early using a dynamic condition inside the loop body: 
    for (let i = 0; i < MAX_LIMIT; i++) {
    if (i >= dynamicLimit) break;
    // Kernel computation
}
  3. Use Uniform Constants: If the bound is constant across all execution threads for a specific run, pass it as a uniform variable into a WebGL 2-backed kernel rather than calculating it per-pixel or per-thread.
