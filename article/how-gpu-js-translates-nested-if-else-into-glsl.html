How gpu.js Translates Nested If-Else into GLSL

This article explores the transpilation pipeline used by gpu.js to convert complex, nested JavaScript if-else structures into valid OpenGL Shading Language (GLSL) code. It covers Abstract Syntax Tree (AST) generation, recursive traversal of conditional nodes, type inference synchronization, and how the resulting GLSL code is structured to accommodate the execution model of modern graphics hardware.

Abstract Syntax Tree (AST) Extraction

gpu.js begins transpilation by taking the raw JavaScript kernel function and passing it through a JavaScript parser (such as Acorn). The parser produces an Abstract Syntax Tree (AST) adhering to the ESTree specification.

In an AST, an if-else ladder is represented hierarchically. A single IfStatement node consists of three primary properties:

  • test: The condition to evaluate (an expression).
  • consequent: The block of code executed if the test evaluates to true.
  • alternate: The code executed if the test evaluates to false.

When an else if ladder is formed in JavaScript, the parser nests a secondary IfStatement node directly inside the alternate property of the primary IfStatement. Deeply nested ladders simply extend this tree structure downward.

Recursive AST Traversal and Code Generation

During the translation phase, gpu.js walks the AST using an internal visitor pattern. When the transpiler encounters an IfStatement node, it executes a recursive translation routine:

  1. Condition Translation (test): The expression inside the test node is translated into a GLSL-compliant boolean expression. This includes converting JavaScript operators (such as strict equality ===) into their GLSL equivalents (==) and casting variables to boolean types if needed.
  2. Consequent Processing: The transpiler generates an opening GLSL block (if (...) {) and processes all child statements within the consequent body.
  3. Alternate Processing: If the alternate property exists:
    • If the alternate node is itself an IfStatement, the transpiler outputs else if (...) and recursively calls the conditional generation method.
    • If the alternate node is a standard BlockStatement, the generator emits a trailing else { ... } block.

Because GLSL natively supports if, else if, and else constructs matching C syntax, the mechanical mapping from nested AST nodes to GLSL syntax is direct and preserves the original lexical nesting depth.

Type Tracking and Variable Hoisting

A major difference between JavaScript and GLSL is that GLSL is statically typed. In JavaScript, a variable can be declared and assigned different types inside separate branches of an if-else ladder.

To manage this, gpu.js analyzes variable declarations across all branches before emitting the GLSL conditional block:

  • Type Inference: gpu.js determines the expected type (e.g., float, int, vec4) by inspecting the values assigned within the branch blocks.
  • Hoisting Declarations: If a variable is declared inside an if block but referenced outside of it, gpu.js hoists the variable declaration above the entire conditional structure in the emitted GLSL, assigning it a default initial value.
  • Assignment Mutation: Inside the generated GLSL if and else branches, statements that originally combined declaration and assignment (such as let x = 5.0;) are rewritten strictly as assignments (x = 5.0;) to avoid scope-shadowing and syntax errors.

Hardware Execution Implications

While gpu.js generates human-readable nested if-else GLSL code, the final execution is handled by the GPU driver's shader compiler.

On parallel GPU architectures, threads within the same warp or wavefront execute instructions in lockstep:

  • Uniform Conditions: If every thread evaluates the ladder identically, execution takes a single path without performance degradation.
  • Divergent Conditions: If different threads take different branches in a nested ladder, the GPU must execute all active branches sequentially, disabling threads that do not belong to the current branch via predication.

gpu.js outputs clean, standard GLSL syntax, leaving it to the underlying GPU compiler to optimize these conditional branches into predicated instructions or jump targets based on the specific graphics hardware target.
