How GPU.js Compiles Switch Cases with Fallthrough

This article examines how the gpu.js compiler translates JavaScript switch-case statements that use fallthrough behavior into GPU-compatible shader code. Because target shading languages like GLSL either lack native switch support or strictly disallow fallthrough between non-empty cases, gpu.js employs an AST-level desugaring strategy. It transforms switch statements into sequential conditional blocks regulated by synthetic state-tracking flags, ensuring that JavaScript's dynamic fallthrough semantics execute predictably on parallel GPU hardware.

The Target Language Constraint

To understand the compilation strategy of gpu.js, one must first understand the limitations of its compilation target: OpenGL Shading Language (GLSL) for WebGL.

In WebGL 1.0 (GLSL ES 1.00), the switch statement does not exist at all. In WebGL 2.0 (GLSL ES 3.00), switch statements exist, but the specification explicitly forbids fallthrough from one non-empty case block to another. If a case contains statements, it must end in an explicit jump like break or return. As a result, direct, one-to-one mapping from JavaScript's flexible switch fallthrough into native GLSL switch constructs is syntactically invalid across WebGL runtimes.

AST Desugaring and State Flag Emulation

gpu.js resolves this discrepancy during its Abstract Syntax Tree (AST) parsing phase. Rather than emitting a hardware-native switch, the compiler desugars the JavaScript SwitchStatement into a flattened series of conditional statements governed by a boolean state variable.

When the compiler encounters a switch block, it performs the following steps:

  1. Discriminant Caching: The switch expression (the discriminant) is evaluated once and assigned to an internal, temporary variable to prevent repeated evaluation side effects.
  2. Flag Declaration: The compiler declares an internal boolean state flag (effectively a matchFound or fallthrough tracker) initialized to false.
  3. Conditional Cascades: Each SwitchCase node is converted into an independent if block. Instead of relying solely on equality checks against the discriminant, the conditional check tests whether the fallthrough flag is already true OR if the discriminant equals the current case expression.
  4. Flag Latching: Inside the case body, the flag is latched to true. This ensures that if this case executed, any subsequent case bodies will automatically evaluate as true, replicating JavaScript's fallthrough behavior.

Handling the break Statement

In native JavaScript, fallthrough continues sequentially until a break or return statement is encountered. In the transpiled GLSL output, standard break keywords cannot simply be retained if they are no longer inside an actual loop or native switch block.

To handle break semantics within the desugared cascade, gpu.js applies one of two patterns depending on the backend pipeline:

  • Flag Resetting: The transpiler treats a break statement as an instruction to clear the fallthrough state or bypass the remaining case checks, often by wrapping the switch logic in a single-iteration execution block or tracking an active execution state.
  • Control-Flow Wrapping: The desugared sequence is enclosed within a single-iteration do-while(false) loop or labeled block. Inside this container, a break statement becomes syntactically valid in GLSL and immediately jumps to the end of the entire switch structure, terminating any active fallthrough instantly.

Default Case Positioning and Execution

The default clause introduces an additional layer of complexity when fallthrough is present, especially if placed before standard case labels. gpu.js handles this by tracking whether any prior case matched before entering the default block, while still maintaining the fallthrough flag to allow execution to spill downward into lower cases if the default clause does not end in a break.

Performance Implications on the GPU

While this emulation strategy guarantees functional parity with the ECMAScript specification, it introduces control flow divergence at the hardware level. On SIMD/SIMT architectures, GPUs process threads in lockstep warps or wavefronts. Converting fallthrough switch structures into sequential conditional checks with boolean state dependencies can lead to branch divergence, where threads in the same warp must execute both sides of disabled branches, increasing execution latency compared to flat mathematical mapping or pure if-else trees.
