CPU Mode in GPU.js: Loops, Recursion, and APIs

GPU.js accelerates JavaScript calculations by compiling code into GLSL to run on the GPU, but it also includes a CPU fallback mode when WebGL is unavailable or manually toggled. This article explains how CPU mode functions internally, specifically focusing on how it bypasses shader compilation constraints to execute loops, recursive functions, and standard JavaScript APIs directly on the host machine.

The Mechanism Behind CPU Mode

When running in GPU mode, GPU.js parses the kernel function’s Abstract Syntax Tree (AST) and transpiles it into GLSL shaders, which are executed across GPU threads. When configured to run in CPU mode (mode: 'cpu'), GPU.js circumvents GLSL code generation entirely. Instead, it generates a standard JavaScript loop structure matching the defined output dimensions.

Within these nested loops, the kernel function is executed for each coordinate, injecting the thread coordinates via this.thread.x, this.thread.y, and this.thread.z. Because the kernel runs natively within the host JavaScript engine (such as V8 in Node.js or modern browsers), the strict hardware and language restrictions of GLSL no longer apply.

Handling Loops

In GPU/WebGL mode, loops must comply with GLSL specifications. This often requires loop bounds to be constant expressions or strictly deterministic so the shader compiler can unroll or analyze them properly. Highly dynamic conditional terminates can lead to compilation errors or massive performance degradation on the GPU.

In CPU mode, loops behave as standard ECMAScript loops:

  • Dynamic Bounds: Loops can iterate over variables that change at runtime without pre-declarations or constant size limits.
  • Loop Types: Full support is available for standard for, while, and do...while loops.
  • Control Flow: Statements like break and continue function identically to standard JavaScript, stopping or skipping iterations without compiler intervention.

Handling Recursion

GLSL ES 1.0 and 2.0 (the foundation of WebGL 1 and 2) explicitly forbid recursion because GPUs historically rely on flat call stacks and statically allocated memory to achieve massive parallelism. Attempting to run a recursive function inside a GPU-targeted kernel will throw a compilation error.

In CPU mode, recursion is fully supported:

  • Call Stack: The kernel function utilizes the JavaScript engine's native call stack.
  • Execution Limits: Self-referential and mutually recursive functions work as long as they do not exceed the JavaScript engine's maximum call stack size (RangeError: Maximum call stack size exceeded).
  • Use Cases: Algorithms that require divide-and-conquer structures, tree traversal, or nested evaluations can be tested and debugged in CPU mode, although they will fail if switched back to GPU mode.

Handling Standard JavaScript APIs

When targeting the GPU, functions are limited to a specialized subset of operations that map directly to GLSL equivalents (such as Math.sin, Math.cos, and basic arithmetic operations). Complex objects, string manipulations, arrays of variable lengths, and standard browser/Node.js APIs are stripped or cause compilation failures.

In CPU mode, the restriction boundary is removed:

  • Debugging Tools: Developers can use console.log() inside kernels to inspect thread coordinates, intermediate calculations, and memory state at runtime.
  • Native Objects and Methods: JavaScript objects, closures, Date.now(), Array.prototype methods, and external helper functions run normally.
  • Type Coercion: Standard JavaScript dynamic typing and automatic type coercion apply, whereas GPU mode demands strict scalar and vector typing.

While CPU mode allows loops, recursion, and full API access, writing kernels that rely on these features sacrifices portability. Code that utilizes native JavaScript features unavailable in GLSL will throw errors if execution is switched back to WebGL or WebGPU pipelines.
