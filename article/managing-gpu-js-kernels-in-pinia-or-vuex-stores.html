Managing GPU.js Kernels in Pinia or Vuex Stores

Using GPU.js kernels inside Pinia or Vuex stores for global state computations is possible, but storing raw kernel instances directly in reactive state introduces significant stability and performance risks. Because Vue’s reactivity system wraps state objects in proxies, internal WebGL references within GPU.js can break or trigger massive reactivity overhead. However, you can safely manage GPU.js kernels within state management architectures by decoupling the non-reactive WebGL instances from reactive application state, leveraging utility functions like markRaw, or treating the GPU runner as an isolated service layer invoked exclusively by store actions.

The Reactivity Conflict

GPU.js works by compiling JavaScript functions into WebGL shader code, binding data to GPU textures, and managing an underlying HTML5 canvas or headless WebGL context. These kernel instances contain complex, deeply nested objects and private methods tied directly to browser hardware APIs.

When you assign a GPU.js kernel to a standard Pinia or Vuex state property, Vue attempts to recursively track every property using reactive proxies. This causes two major issues:

  1. Broken Internal References: Proxied WebGL contexts and typed arrays often throw native TypeError exceptions when invoked because internal methods expect direct access to the underlying hardware context rather than a proxy target.
  2. Performance Degradation: Vue attempts to observe deeply nested WebGL metadata and texture buffers, causing excessive CPU-bound dependency tracking that nullifies the performance benefits of offloading computations to the GPU.

How to Safely Store Kernels in Pinia

To safely use GPU.js in Pinia, you must prevent Vue from making the kernel instance reactive. You can achieve this using markRaw or shallowRef.

import { defineStore } from 'pinia';
import { GPU } from 'gpu.js';
import { markRaw } from 'vue';

export const useComputationStore = defineStore('computation', {
  state: () => ({
    gpuInstance: null,
    matrixKernel: null,
    result: [],
    isComputing: false,
  }),
  actions: {
    initializeGpu() {
      if (this.matrixKernel) return;

      const gpu = new GPU();
      const kernel = gpu.createKernel(function (a, b) {
        let sum = 0;
        for (let i = 0; i < 512; i++) {
          sum += a[this.thread.y][i] * b[i][this.thread.x];
        }
        return sum;
      }).setOutput([512, 512]);

      // markRaw prevents Pinia from wrapping the kernel in a reactive Proxy
      this.gpuInstance = markRaw(gpu);
      this.matrixKernel = markRaw(kernel);
    },

    computeMultiplication(matrixA, matrixB) {
      if (!this.matrixKernel) this.initializeGpu();

      this.isComputing = true;
      try {
        // Output from GPU.js is returned as a nested typed array or raw texture
        const rawOutput = this.matrixKernel(matrixA, matrixB);
        
        // Store only the final, serializable data in reactive state
        this.result = Array.isArray(rawOutput) ? rawOutput : rawOutput.toArray();
      } finally {
        this.isComputing = false;
      }
    },

    disposeGpu() {
      if (this.matrixKernel) {
        this.matrixKernel.destroy();
        this.matrixKernel = null;
      }
      if (this.gpuInstance) {
        this.gpuInstance.destroy();
        this.gpuInstance = null;
      }
    }
  }
});

The Service Pattern: A Cleaner Alternative

Rather than keeping the GPU.js kernel inside the store's state tree, the recommended architectural approach is the singleton service pattern. Keep the GPU instance and its compiled kernels in a separate, plain JavaScript module, and use Pinia or Vuex purely as the bridge to pass input arrays and store computed results.

// services/gpuService.js
import { GPU } from 'gpu.js';

const gpu = new GPU();

export const vectorAddKernel = gpu.createKernel(function (a, b) {
  return a[this.thread.x] + b[this.thread.x];
}).setOutput([1000000]);

export function cleanUpGpu() {
  gpu.destroy();
}
// stores/useVectorStore.js
import { defineStore } from 'pinia';
import { vectorAddKernel } from '@/services/gpuService';

export const useVectorStore = defineStore('vector', {
  state: () => ({
    vectorData: [],
  }),
  actions: {
    runAddition(vecA, vecB) {
      // Direct execution without any reactivity risks
      this.vectorData = vectorAddKernel(vecA, vecB);
    }
  }
});

Resource Management and WebGL Lifecycle

When integrating GPU.js with client-side state managers, lifecycle considerations are essential:

  • WebGL Context Limits: Browsers enforce a maximum limit on concurrent WebGL contexts (often between 8 and 16). Creating new GPU.js instances on every store action will crash existing contexts. Instantiate kernels once and reuse them.
  • Context Loss: WebGL contexts can be dropped by the operating system under high graphics load. You should listen for the webglcontextlost event on the GPU canvas if your application performs long-running calculations.
  • Memory Deallocation: Pinia and Vuex stores often live for the entire duration of a single-page application. When a store unmounts or resets, always call kernel.destroy(true) to release GPU VRAM buffers and prevent hardware memory leaks.
