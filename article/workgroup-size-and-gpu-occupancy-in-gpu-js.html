Workgroup Size and GPU Occupancy in gpu.js

This article examines how configuring workgroup and thread grid sizes impacts GPU occupancy and execution efficiency in gpu.js. It details the relationship between hardware compute units and kernel dimensions, outlines the trade-offs between undersubscribing and oversubscribing hardware resources, and explains how to balance these parameters to maximize throughput in browser-based GPU computing.

Understanding Thread Grids and Workgroups in gpu.js

In gpu.js, the total problem space is defined using the .setOutput([x, y, z]) method. This configuration forms the overall thread grid, specifying the total number of parallel kernel invocations across one, two, or three dimensions. Under the hood, gpu.js executes these threads via WebGL fragment shaders or WebGPU compute passes, depending on the operational mode and hardware support.

In compute-oriented architectures like WebGPU, this large grid is divided into smaller, discrete clusters known as workgroups (or thread blocks). Each workgroup is dispatched to an individual Streaming Multiprocessor (SM) or Compute Unit (CU) on the GPU, where threads execute synchronously in smaller hardware batches, typically called warps (NVIDIA, 32 threads) or wavefronts (AMD, 32 or 64 threads).

What Is GPU Occupancy?

GPU occupancy refers to the ratio of active warps or wavefronts on a compute unit relative to the maximum theoretical number of warps that the hardware can support simultaneously. High occupancy allows the GPU's hardware scheduler to hide memory latency: when one group of threads stalls waiting for data from VRAM, the processor instantly switches execution to another active group, maintaining continuous arithmetic throughput.

The Impact of Workgroup Size on Occupancy

The local workgroup size directly dictates how efficiently an SM's resources are allocated:

  • Workgroups That Are Too Small: If a workgroup contains fewer threads than the native warp or wavefront size (for example, setting a workgroup size of 8 or 16 on a GPU with 32-thread warps), the hardware scheduler cannot fully populate execution lanes. This leads to underutilization, wasted clock cycles, and poor occupancy.
  • Workgroups That Are Too Large: Each workgroup consumes a finite pool of hardware resources, primarily registers and shared local memory. When a workgroup requests too many resources, fewer workgroups can reside concurrently on a single compute unit. This creates a bottleneck that limits the total number of active in-flight threads.
  • Non-Multiple Alignments: Choosing dimensions that are not clean multiples of 32 or 64 causes edge-case padding, where partial warps run with deactivated threads. This lowers the effective computational density.

The Impact of the Global Grid Size (setOutput)

While workgroup size governs local execution efficiency, the global output dimensions determine whether the GPU can achieve full saturation:

  • Grid Undersubscription: If the output array specified in setOutput() is small (e.g., a few hundred elements), the total number of generated workgroups will be insufficient to occupy all physical compute units on modern GPUs. Many SMs remain completely idle, resulting in low global occupancy.
  • Grid Saturation: A sufficiently large grid ensures that every compute unit has a full queue of workgroups waiting to be processed. Once an active workgroup finishes, the scheduler immediately assigns a new one without idle time.

WebGL Fallback vs. WebGPU Compute Modes

The degree of control over occupancy in gpu.js depends heavily on the underlying backend:

  1. WebGL Mode (Default): gpu.js emulates general-purpose computation by rendering textured quads across a 2D viewport. The browser and the underlying graphics driver implicitly manage thread scheduling, rasterization, and block allocation. In this mode, developers influence occupancy primarily through output dimension shape and texture coordinate alignment rather than explicit workgroup control.
  2. WebGPU Mode: When compute pipelines are active, workgroup dimensions are defined more explicitly. Developers must align the local sizes with the target device's hardware limits (maxComputeWorkgroupSizeX/Y/Z and maxComputeInvocationsPerWorkgroup) to maintain high occupancy.

Optimization Guidelines

To maintain high GPU occupancy when developing kernels in gpu.js:

  • Target Multiples of 32 or 64: Ensure that both the local execution dimensions and the total output dimensions align with common warp/wavefront boundaries to prevent partial-execution penalties.
  • Keep Kernel Register Pressure Low: Minimize complex local variable declarations within kernel functions. Lower register usage per thread allows the GPU to fit more concurrent workgroups onto each compute unit.
  • Benchmark Problem Sizes: For small workloads where the overhead of dispatching workgroups outweighs execution time, consider batching inputs into larger combined grids to keep the compute units fully occupied.
