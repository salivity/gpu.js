How GPU.js Handles Break and Continue in Nested Loops

This article examines how the gpu.js compiler translates JavaScript break and continue statements within nested loop architectures into OpenGL Shading Language (GLSL). It explains the underlying abstract syntax tree (AST) transpilation, scoping rules, the absence of labeled statement support, and the performance implications of hardware branch divergence in WebGL environments.

AST Translation to GLSL

gpu.js operates by parsing JavaScript kernel functions into an Abstract Syntax Tree (AST) and transpiling those nodes into GLSL shader code. When encountering loop architectures, the transpiler processes ForStatement or WhileStatement nodes and recursively translates their bodies.

When break (BreakStatement) or continue (ContinueStatement) appear within a loop body, gpu.js maps them directly to native GLSL equivalents:

// JavaScript input inside a loop
if (condition) break;
if (otherCondition) continue;

// Resulting GLSL output
if (condition) {
    break;
}
if (otherCondition) {
    continue;
}

Because modern WebGL2 contexts (and WebGL1 with standard loop extensions) support dynamic loop control, GLSL natively recognizes break and continue keywords with syntax and behavior analogous to C and JavaScript.

Scoping and Nesting Semantics

In nested loop structures, gpu.js preserves standard JavaScript scoping semantics:

  • break: Immediately exits the innermost enclosing loop context. Execution resumes at the statement immediately following that specific inner loop. The outer loop continues its remaining iterations unaffected.
  • continue: Skips the remaining instructions in the body of the innermost enclosing loop and jumps directly to that inner loop’s increment/update expression and condition check.

Because GLSL handles inner-loop control natively, the generated code maintains strictly local scoping:

// GPU.js Kernel
for (let i = 0; i < 10; i++) {
    for (let j = 0; j < 10; j++) {
        if (j > 5) break; // Exits only the 'j' loop
        if (j % 2 === 0) continue; // Skips only the current 'j' iteration
    }
    // Execution continues here for each iteration of 'i'
}

The Limitation on Labeled Statements

JavaScript supports labeled loops, allowing a program to break out of an outer loop from within an inner loop using a statement like break outerLoop;.

GLSL does not support goto statements or labeled breaks. Consequently, gpu.js cannot transpile labeled break or continue statements across nested hierarchies. If a kernel attempts to break out of multiple loop depths using labels, gpu.js will fail during the transpilation phase or generate invalid shader code. Developers must emulate multi-level exits using state flags evaluated within each respective loop level.

Hardware Execution and Warp Divergence

While gpu.js correctly transpiles the logic into GLSL, the physical GPU architecture executes loops differently than a CPU. GPUs process threads concurrently in lockstep groups (known as warps or wavefronts) using Single Instruction, Multiple Threads (SIMT).

When threads within the same warp execute a nested loop containing conditional break or continue statements:

  1. Thread Masking: If Thread A hits a break in the inner loop at iteration 2, but Thread B within the same warp continues until iteration 8, the hardware masks Thread A off. Thread A remains idle while Thread B finishes.
  2. Performance Cost: The warp as a whole must execute every iteration required by the slowest thread. A nested loop does not yield performance gains from early termination unless all threads in the active warp encounter the exit condition simultaneously.

gpu.js strictly maps inner loop control statements to native shader instructions, ensuring correct program logic at the software level while relying on GPU hardware masking to resolve divergent execution paths across nested levels.
