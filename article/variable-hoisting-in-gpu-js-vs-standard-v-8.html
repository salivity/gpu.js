Variable Hoisting in gpu.js vs Standard V8

Variable hoisting does not behave identically in a gpu.js kernel compared to standard V8 execution. While the V8 engine strictly adheres to the ECMAScript specification by hoisting variable declarations to the top of their functional or block scopes, gpu.js parses a restricted subset of JavaScript into an Abstract Syntax Tree (AST) to transpile it into WebGL GLSL (OpenGL Shading Language). Because GLSL requires all identifiers to be declared and typed before they are referenced, attempting to rely on JavaScript-style variable hoisting inside a gpu.js kernel leads to transpilation errors or shader compilation failures rather than standard V8 runtime behavior.

How V8 Handles Variable Hoisting

In standard V8 execution, JavaScript engines separate variable declaration from initialization during the compilation phase:

  • var Declarations: V8 hoists the declaration to the top of the enclosing function scope and initializes it to undefined. Accessing a var variable before its lexical declaration produces undefined rather than an error.
  • let and const Declarations: V8 hoists these declarations to the top of their block scope but does not initialize them. Accessing them before their lexical declaration triggers a ReferenceError due to the Temporal Dead Zone (TDZ).
  • Function Declarations: Entire function bodies are hoisted to the top of the scope, allowing them to be called before they are declared in the source code.

How gpu.js Transpiles Kernel Functions

A gpu.js kernel is not executed directly by V8 at runtime. Instead, gpu.js reads the function string, parses it using an internal AST parser, and translates the JavaScript syntax into static C-style shader code (GLSL).

GLSL does not support runtime hoisting, dynamic type resolution, or undefined initial states. In GLSL, every variable must have an explicit type and must be declared in the source flow before any statement attempts to read or write to it.

The Differences in Behavior

The differences between V8 and gpu.js execution environments manifest in several distinct ways:

  1. Premature Access of var: In V8, reading a var before its assignment returns undefined. In gpu.js, the AST-to-GLSL transpiler walks the syntax tree sequentially. If it encounters a variable read before its declaration statement, it cannot infer the type or find a corresponding GLSL symbol, causing the kernel compilation to fail immediately.
  2. Temporal Dead Zone (TDZ): V8 handles TDZ violations at runtime by throwing a ReferenceError. In gpu.js, code that would trigger a TDZ fails at transpile time during kernel initialization, preventing the GPU program from ever building.
  3. Scope Flattening: In GLSL output, nested scopes and closures do not map directly to JavaScript lexical environments. gpu.js flattens many operations, making lexical hoisting logic entirely unsupported across scope blocks.

Best Practices for gpu.js Kernel Variables

To ensure predictable compilation and avoid transpilation errors when writing gpu.js kernels:

  • Declare Before Use: Always declare and initialize variables at the top of the kernel function or directly at the start of the block where they are needed.
  • Avoid undefined Logic: Never rely on a variable evaluating to undefined before assignment, as GPU hardware operates exclusively on concrete numerical types (e.g., float, int, vectors).
  • Use Clean Variable Scoping: Keep declarations strictly local to the expressions they serve to ensure the AST compiler can accurately deduce types and generate valid shader declarations.
