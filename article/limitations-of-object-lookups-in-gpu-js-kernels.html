Limitations of Object Lookups in GPU.js Kernels

GPU.js allows developers to write accelerated parallel programs using JavaScript syntax by transpiling functions into WebGL shaders or WebGPU compute pipelines. However, running JavaScript on a graphics processor introduces severe constraints regarding how data can be structured and accessed. Because GPU shading languages like GLSL are statically typed and lack the JavaScript runtime environment, object property lookups inside GPU.js kernels face strict structural, dynamic, and memory-related limitations.

Absence of Dynamic Property Access

In standard JavaScript, properties can be accessed dynamically at runtime using bracket notation with variables (e.g., data[key]). In GPU.js kernels, dynamic property lookup is entirely unsupported. The transpiler cannot resolve dynamic keys because GLSL does not possess a hash table or dictionary mechanism. Property lookups must be statically analyzable at compile time using standard dot notation or constant literal keys.

Incompatibility with JavaScript Prototypes and Methods

GPU.js kernels operate on raw numerical data structures and do not instantiate standard JavaScript execution contexts. As a result:

  • Prototype chains are inaccessible; inherited properties cannot be read.
  • Standard methods such as Object.keys(), Object.values(), or hasOwnProperty() cannot be compiled into shader instructions.
  • Custom methods defined on objects will cause kernel compilation errors if invoked inside the kernel body.

Strict Structural and Type Uniformity

GPU architectures rely on uniform, predictable memory layouts. When objects are passed into a kernel as constants or uniforms:

  • Fixed Schemas: Objects must map directly to equivalent GLSL struct definitions. Every instance of an object must strictly adhere to the exact same schema.
  • Primitive Types Only: Properties can only hold primitive numbers (integers or floats) or fixed-size vectors. Objects cannot store strings, nested heterogeneous structures, or dynamic arrays.
  • No References: Objects are evaluated by value rather than by reference. Pointer-chasing, circular references, and dynamic references across objects are impossible inside shader execution units.

Nesting and Complexity Constraints

While shallow objects representing simple coordinates or configuration settings can be compiled into GLSL structs, deep nesting creates significant transpilation overhead and often leads to compilation failure. GLSL requires all struct definitions to be fully resolved and bounded. Deeply nested hierarchies inflate register usage, reduce thread occupancy on the GPU, and may exceed hardware uniform buffer limits.

Recommended Alternatives

To achieve optimal execution and avoid lookup errors inside GPU.js kernels, avoid using objects to store runtime data:

  • Flatten Data into Arrays: Convert collections of objects into flattened 1D, 2D, or 3D numeric arrays.
  • Use Parallel Typed Arrays: Instead of an array of objects ([{x, y}, {x, y}]), use structure-of-arrays formatting with separate typed arrays (Float32Array for x values, another for y values).
  • Texture Memory: Pass large datasets as input textures or matrices, which align natively with GPU memory hardware and support fast indexing via numeric thread coordinates (this.thread.x, this.thread.y).
