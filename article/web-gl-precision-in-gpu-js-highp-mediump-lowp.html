WebGL Precision in GPU.js: Highp, Mediump, Lowp

When running accelerated JavaScript using GPU.js, code is transpiled into WebGL Shading Language (GLSL) to execute directly on the graphics card. Inside these generated shaders, floating-point and integer values must be qualified with highp, mediump, or lowp to define their bit-depth and numerical range. This article explains why WebGL enforces these precision qualifiers, how they balance computational accuracy against hardware performance, and what role they play in GPU.js kernel execution.

The Origin: OpenGL ES and WebGL Architecture

WebGL is based on OpenGL ES (Embedded Systems), a graphics specification originally tailored for mobile devices and embedded hardware with strictly limited memory and processing power. Unlike standard desktop OpenGL, where 32-bit floating-point math is universally standard, OpenGL ES required developers to explicitly declare the required arithmetic precision to conserve power, memory bandwidth, and register allocation.

Because GPU.js translates JavaScript functions into GLSL shaders under the hood, it directly inherits these WebGL constraints. Without precision qualifiers, WebGL fragment shaders fail to compile.

Definition of Precision Qualifiers

GLSL defines three distinct precision levels for floating-point and integer types:

  • highp (High Precision): Uses a minimum of 32-bit floating-point representation (comparable to standard IEEE 754 single-precision floats). It provides a 24-bit mantissa with an exponent range from -62 to 62. This format avoids truncation and rounding errors during iterative arithmetic and coordinate calculations.
  • mediump (Medium Precision): Uses a minimum of 16-bit floating-point representation (half precision). It provides a 10-bit mantissa with an exponent range from -14 to 14. It is significantly faster on mobile GPUs but can introduce noticeable rounding artifacts in complex numerical routines.
  • lowp (Low Precision): Uses an 8-bit to 10-bit representation, typically mapped to fixed-point ranges such as -2.0 to 2.0. It is suitable primarily for simple color components and normalized values.

Why GPU.js Defaults to highp

JavaScript natively uses double-precision (64-bit) floating-point numbers for all numeric calculations. When a developer writes mathematical algorithms in GPU.js, they typically expect numerical stability close to standard JavaScript behavior.

Because of this expectation, GPU.js generates shaders that declare precision highp float; at the top of the generated code. Using highp ensures:

  1. Numerical Stability: Matrix multiplication, neural network training, and scientific simulations require sufficient bit-depth to prevent values from collapsing into zero or overflowing to infinity.
  2. Parity with CPU Fallbacks: GPU.js provides fallback execution on the CPU when WebGL is unavailable. highp minimizes numerical drift between GPU output and CPU output.

Hardware Impact and Performance Trade-Offs

While modern desktop GPUs almost always run arithmetic at full 32-bit precision regardless of qualifiers, mobile and integrated GPUs physically alter their hardware paths based on the precision specified:

  • Register Allocation: Lower precision (mediump or lowp) allows the GPU's execution units to pack multiple values into a single register, enabling greater thread concurrency and throughput.
  • Memory Bandwidth: Storing textures and buffers at lower precision reduces the memory footprint and the bandwidth required to stream data to and from the GPU cores.
  • Power Consumption: On mobile chipsets, 16-bit floating-point ALUs consume substantially less power and generate less heat than 32-bit ALUs.

Precision qualifies as highp, mediump, or lowp in GPU.js because WebGL must instruct the GPU compiler how to allocate hardware registers and arithmetic pipelines across diverse computing environments.
