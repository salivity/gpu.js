Using Pinned Memory and SharedArrayBuffer in gpu.js

This article examines whether low-level memory optimizations—specifically pinned host memory and SharedArrayBuffer—can be integrated into data transfers using gpu.js. Because gpu.js relies on WebGL abstractions to execute general-purpose compute kernels, native hardware concepts like page-locked host memory cannot be directly controlled. While SharedArrayBuffer can assist with multi-threaded CPU-side preparation, neither technology enables true zero-copy, direct memory access (DMA) transfers to the GPU within the library.

Understanding the Abstraction Layer of gpu.js

gpu.js accelerates JavaScript calculations by compiling specialized functions into GLSL shaders and executing them on the graphics hardware via WebGL. Because WebGL is a sandboxed, browser-level graphics API, it intentionally abstracts away direct physical memory addresses, hardware-specific DMA engines, and kernel-level memory management. All data transfers to the GPU are handled through standard WebGL texture allocation and buffer binding mechanisms.

Pinned Host Memory: Not Supported

In native compute frameworks like CUDA or OpenCL, pinned (page-locked) host memory prevents the operating system from paging memory out to disk. This allows the GPU’s DMA controller to read host memory directly without CPU intervention, significantly speeding up host-to-device transfers.

In gpu.js, pinned host memory is impossible to implement because:

  1. JavaScript Memory Management: The JavaScript engine (V8, SpiderMonkey, etc.) manages heap allocations automatically via garbage collection, abstracting away low-level virtual memory mapping.
  2. WebGL Limitations: WebGL provides no API endpoints for page-locking memory. Host-to-device transfers occur when data is uploaded to textures via calls like texImage2D or texSubImage2D, which copy memory through driver-managed staging buffers.

Consequently, native-style pinned memory transfers cannot be integrated into gpu.js pipelines.

SharedArrayBuffer Integration and Limitations

SharedArrayBuffer allows multiple web workers to read and write to the same shared memory space concurrently. While this is a powerful feature for CPU-side parallelism, its integration with data transfers in gpu.js faces strict constraints.

Zero-Copy Transfers Are Unavailable

Even when a TypedArray is backed by a SharedArrayBuffer, passing that data to gpu.js does not grant the GPU direct access to that shared memory. gpu.js must still serialize or upload the array into WebGL texture memory. The transfer remains a synchronous or asynchronous copy operation, not a zero-copy mapping.

WebGL Specification Restrictions

Browsers enforce strict security policies regarding SharedArrayBuffer due to side-channel attacks like Spectre. WebGL specifications generally mandate that data passed to texture upload functions must be backed by an unshared ArrayBufferView. Passing a TypedArray backed by a SharedArrayBuffer directly into texture upload functions can throw a TypeError in many browser implementations unless the data is first cloned into a standard, non-shared ArrayBuffer.

Practical Alternatives for Optimizing gpu.js Transfers

Since pinned memory and zero-copy shared buffers cannot bypass the WebGL upload bottleneck, maximizing transfer performance in gpu.js relies on optimizing how data enters and stays within the GPU context:

  • Use TypedArrays Directly: Pass contiguous Float32Array or Int32Array instances rather than standard nested JavaScript arrays. This eliminates the CPU overhead of flattening nested arrays before upload.
  • Pipeline Mode (Keep Data on the Device): The most effective way to avoid transfer latency is to prevent data from returning to the CPU. Set pipeline: true on your gpu.js kernels to output results directly as textures, which can be fed immediately into subsequent kernels without round-trip host transfers.
  • Worker-Based Preprocessing: You can use SharedArrayBuffer across a pool of Web Workers to handle heavy CPU preprocessing. Once processing is complete, copy the required slice into a standard TypedArray to dispatch it to gpu.js.
