Can Additive Synthesizers Run in GPU.js?

Additive synthesis with thousands of dynamic partials requires massive parallel floating-point computation, making GPU acceleration an appealing solution. While the library gpu.js allows developers to execute parallel calculations in the browser through WebGL shaders, implementing a real-time sound engine this way faces severe architectural challenges. This article examines the computational feasibility, structural bottlenecks, and practical limitations of running dense additive synthesis in gpu.js.

The Computational Alignment

Additive synthesis generates complex timbres by summing hundreds or thousands of individual sine waves, each with independent frequency, amplitude, and phase trajectories. Calculating millions of sample points per second creates heavy CPU load on traditional architectures.

Because each partial operates largely independently of the others during a single audio frame, the workload is embarrassingly parallel. In terms of raw processing power, gpu.js excels at this model. By compiling JavaScript into GLSL shaders, gpu.js can evaluate trigonometric functions and sum partial amplitudes across massive matrices significantly faster than pure JavaScript running on a single CPU thread.

The Real-Time Audio Bottleneck

Despite superior calculation throughput, running a real-time audio engine via gpu.js encounters severe data-transfer bottlenecks. Real-time digital audio operates under strict latency constraints, typically requiring buffers of 128 to 512 samples delivered every 2.9 to 11.6 milliseconds at standard sample rates (44.1 kHz or 48 kHz).

  1. Memory Transfer Overhead: Dynamic additive synthesis requires sending updated parameters—such as pitch envelopes and amplitude changes—from the CPU to the GPU every frame. The overhead of packing and uploading dynamic partial data to WebGL textures diminishes the computational gains.
  2. Buffer Readback Latency: To output sound, the computed audio samples must travel back from the GPU to the CPU audio stack. WebGL traditionally relies on methods like readPixels to retrieve data, which either stalls the main JavaScript thread synchronously or incurs multi-frame latency asynchronously. This delay inevitably causes audio dropouts, clicks, or noticeable input lag.

AudioWorklet and Threading Isolation

Modern Web Audio architectures rely on the AudioWorkletNode, which runs inside a dedicated, high-priority audio rendering thread to prevent interface lag from interrupting sound processing.

gpu.js runs on WebGL, which is tied to the main thread or requires an OffscreenCanvas inside a dedicated Web Worker. Because WebGL contexts cannot run natively inside an AudioWorklet thread, audio data generated by gpu.js must be passed across thread boundaries using messaging channels. The serialization, deserialization, and thread synchronization steps introduce variable jitter that breaks real-time guarantees.

Practical Verdict

An additive synthesizer sound engine with thousands of dynamic partials can mathematically run in gpu.js, but it cannot reliably function as a low-latency, real-time instrument.

gpu.js is well-suited for non-real-time audio tasks, such as offline rendering, pre-baking complex wavetables, or scientific audio analysis. For interactive, real-time performance with thousands of dynamic partials, developers must bypass WebGL-based wrappers like gpu.js in favor of native AudioWorklets optimized with WebAssembly (Wasm) and SIMD, or explore modern WebGPU compute pipelines that support shared memory and asynchronous buffer mapping.
