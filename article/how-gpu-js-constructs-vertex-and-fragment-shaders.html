How GPU.js Constructs Vertex and Fragment Shaders

GPU.js enables general-purpose computing on the GPU (GPGPU) inside web environments by translating standard JavaScript functions into WebGL-compatible GLSL shaders. Because standard WebGL lacks dedicated compute shaders in older versions, GPU.js repurposes the graphical rendering pipeline to perform mathematical calculations. Behind the scenes, it manages this by pairing a lightweight, largely static vertex shader with a dynamically transpiled, complex fragment shader that executes the actual algorithm across thousands of parallel threads.

The Vertex Shader: Setting Up the Computation Plane

In traditional graphics pipelines, vertex shaders process 3D vertex data to project 3D models onto a 2D screen. In GPU.js, calculations do not require real geometry; they require an execution grid where each output element behaves like a pixel.

To achieve this, GPU.js constructs a minimal, standardized vertex shader behind the scenes:

  1. Rendering a Full-Screen Quad: GPU.js establishes a static geometry composed of two triangles forming a rectangle (a full-screen quad) spanning normalized device coordinates from [-1, -1] to [1, 1].
  2. Passing Texture Coordinates: The vertex shader simply receives these positions as attributes and sets gl_Position. It passes interpolated UV texture coordinates directly down to the rasterizer via a varying variable (typically named vTexCoord).
  3. Static Generation: Because the geometry never changes regardless of the calculation, this vertex shader is generated from a fixed internal template. Its sole objective is to instruct the GPU's rasterizer to spawn a fragment (pixel) for every cell within the declared output dimensions.

The Fragment Shader: Compiling the Kernel Logic

The fragment shader is where GPU.js performs almost all of its heavy lifting. It executes once per pixel (or "thread") covered by the full-screen quad. The fragment shader is dynamically built using a multi-step Abstract Syntax Tree (AST) compilation process:

  1. AST Parsing and Translation: When a kernel is compiled, GPU.js parses the provided JavaScript function into an AST. It walks this syntax tree and converts JavaScript syntax, variable declarations, math operations, and control structures (like for loops and if statements) into equivalent GLSL data types and functions.
  2. Thread Coordinate Mapping: To emulate parallel computing models (like CUDA or OpenCL), the fragment shader injects logic to determine its thread position. By reading gl_FragCoord.xy (the pixel coordinates), the generated GLSL derives values for this.thread.x, this.thread.y, and this.thread.z. GPU.js injects mathematical transformations directly into the fragment shader header to map 2D fragment coordinates into 1D, 2D, or 3D kernel space.
  3. Data Ingestion via Textures: JavaScript arrays and numerical inputs cannot be passed directly into GLSL as typical arrays due to size constraints. GPU.js uploads input data to the GPU as textures (sampler2D). The fragment shader is constructed with specialized texture-lookup functions (texelFetch or custom floating-point decoding routines) to read input values based on memory indices.
  4. Encoding Outputs: WebGL fragment shaders natively output color vectors (gl_FragColor or vec4). The compiled fragment shader wraps the return value of your JavaScript function in packing routines. If the platform lacks float-texture support, GPU.js inserts bit-shifting algorithms that pack floating-point computational results across the 8-bit red, green, blue, and alpha channels of the output fragment.

By delegating geometric orchestration to a uniform vertex shader and converting user algorithms into pixel-level operations inside the fragment shader, GPU.js turns the standard rendering pipeline into a high-performance compute engine.
