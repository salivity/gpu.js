GPU.js Mini-Batch Parallelization in Neural Networks

This article explores how gpu.js accelerates neural network training by parallelizing mini-batch operations on graphics hardware. It examines how JavaScript functions compile into WebGL fragment shaders, how multidimensional mini-batch tensors map across GPU execution threads, and how the forward and backward propagation passes execute concurrently to maximize computational throughput.

Shader Compilation and Thread Dispatch

gpu.js achieves hardware acceleration by transpiling specialized JavaScript functions into WebGL GLSL (OpenGL Shading Language) shaders. During neural network training, standard JavaScript loops are converted into parallel execution kernels. Instead of processing input samples sequentially on the CPU, gpu.js utilizes the GPU’s massively parallel architecture to dispatch thousands of lightweight threads simultaneously, treating each thread as a single compute unit within a graphical context.

Multi-Dimensional Kernel Mapping for Batches

Mini-batch parallelization relies on multidimensional kernel output configurations. When training with a mini-batch of size \(N\) and a layer output size of \(M\), gpu.js sets the kernel output dimensions to [M, N].

Inside the kernel execution:

  • The first dimension corresponds to the neurons in the current layer.
  • The second dimension indexes the distinct training examples within the active mini-batch.

Each individual thread running on the GPU uses built-in thread coordinates (this.thread.x, this.thread.y) to determine its exact computational assignment. Thread \((x, y)\) evaluates the activation for neuron \(x\) belonging exclusively to sample \(y\) in the batch. This spatial division allows the entire mini-batch to execute in a single GPU pass without branching overhead.

Concurrent Forward Propagation

During the forward pass, layer activations are calculated using matrix multiplication between the weight matrices and the input mini-batch tensor. Data is passed into GPU memory encoded as 2D or 3D floating-point textures.

Because the mini-batch dimension is mapped directly across the GPU thread grid, all samples within the batch undergo linear transformations (\(Z = W \cdot X + B\)) and nonlinear activation functions (such as ReLU or Sigmoid) concurrently. Because reads from texture memory are cached and executed across wide vector pipelines, arithmetic intensity remains high, eliminating the performance penalties associated with single-sample updates.

Gradient Calculation and Parallel Reduction

Backpropagation within a mini-batch requires two distinct phases: computing error gradients per sample and aggregating those gradients to update network parameters.

  1. Per-Sample Gradient Computation: Similar to the forward pass, error deltas for each neuron are calculated in parallel across all samples in the mini-batch. Threads read the saved activation textures and layer weights to compute local gradients concurrently.
  2. Batch Aggregation via Reduction Kernels: Weight updates require the sum or mean of gradients across the entire mini-batch. Because standard WebGL fragment shaders cannot write to arbitrary memory locations (preventing atomic addition across threads), gpu.js utilizes reduction kernels. These kernels iteratively sum gradients along the mini-batch dimension through multi-pass rendering (ping-pong technique) until a single aggregated gradient matrix remains.

Memory Pipeline and WebGL Textures

To maintain high throughput during mini-batch operations, gpu.js avoids continuous memory transfer over the CPU-GPU bus (PCIe). Input batches, weight matrices, intermediate activations, and error gradients remain in GPU memory as textures throughout training epochs. The outputs of the forward pass kernels feed directly into the backward pass kernels as texture inputs using the pipeline: true mode. This architectural design ensures that mini-batch parallelization overhead is limited almost entirely to shader execution time rather than data serialization.
