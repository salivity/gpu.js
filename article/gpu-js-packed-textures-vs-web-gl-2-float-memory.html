GPU.js Packed Textures vs WebGL 2 Float Memory

This article examines the memory footprint differences in gpu.js between packed texture layouts and native WebGL 2 floating-point textures. In gpu.js, managing memory consumption depends on how floating-point numbers are mapped into texture elements (texels). While native WebGL 2 implementations leverage single-channel 32-bit float textures to achieve a 1:1 memory footprint, packed textures in gpu.js multiplex multiple data points into multi-channel formats to bypass WebGL 1 limitations or optimize vector hardware, resulting in distinct trade-offs in VRAM consumption, memory alignment, and cache behavior.

Texture Formats and Byte-Level Allocation

To evaluate the footprint difference, it is necessary to examine how both approaches store numbers in GPU video memory (VRAM):

  • Native WebGL 2 Floating-Point Textures (R32F): WebGL 2 natively supports single-channel, 32-bit floating-point textures (gl.R32F). Each scalar value in an array maps directly to one texel containing a single 32-bit (4-byte) IEEE-754 float. A 1,000,000-element array of 32-bit floats takes: \[\text{1,000,000} \times 4\text{ bytes} \approx 4\text{ MB of VRAM}\]
  • Packed Textures in gpu.js (RGBA32F or RGBA8): In gpu.js, "packing" generally refers to grouping four adjacent scalar values into the four components (\(R, G, B, A\)) of a single texel.
    • Packed RGBA32F (Float Mode): Four 32-bit float values are grouped into a single 16-byte texel. The theoretical memory usage remains identical to R32F: \[\frac{\text{1,000,000}}{4}\text{ texels} \times 16\text{ bytes} \approx 4\text{ MB of VRAM}\]
    • Unpacked WebGL 1 Fallback (RGBA32F): When packing is disabled in environments lacking single-channel support, gpu.js allocates an entire 4-channel RGBA32F texel per scalar, leaving the \(G, B,\) and \(A\) channels unused. This expands memory consumption by 400%: \[\text{1,000,000} \times 16\text{ bytes} \approx 16\text{ MB of VRAM}\]
    • Byte-Packed WebGL 1 Fallback (RGBA8): In environments without floating-point texture support, gpu.js encodes a single 32-bit float across four 8-bit unsigned integer channels (\(R, G, B, A\)). This consumes 4 bytes per float (4 MB total), equivalent in raw byte size to native R32F, but incurs severe computational decoding overhead in the fragment shader.

Texture Dimensionality and Alignment Overhead

A primary source of memory footprint divergence between packed textures and native WebGL 2 float textures is dimension padding. GPUs require texture dimensions (width and height) to adhere to hardware-level stride and power-of-two or sub-allocation boundaries:

  1. Grid Compression: Packed mode reduces the total number of texels by a factor of 4. For instance, a 1D array of length \(N\) is converted into an internal 2D texture with one-fourth the number of texels. If \(N\) is not cleanly divisible by 4, gpu.js must pad the texture with empty components to align the texels, causing fractional VRAM bloat on smaller arrays.
  2. Row Alignment (Striding): WebGL implementations often align rows of texture memory to multiples of 4 or 8 bytes. Because packed textures store 16 bytes per texel (RGBA32F), every texel automatically satisfies row byte alignments. Conversely, native R32F textures use 4 bytes per texel, which can introduce padding bytes at the end of odd-numbered row dimensions unless the texture width is explicitly aligned.

Bandwidth and Cache Footprint

Memory footprint is not solely static storage; it directly affects memory bus occupancy during kernel execution:

  • Native WebGL 2 (R32F): Native float textures maximize L1/L2 texture cache utility when memory access patterns are sequential. When a kernel reads a scalar float, the GPU cache line fills exclusively with contiguous floats, eliminating unused channel data from the cache.
  • Packed Textures: Reading one component from a packed texel pulls all four components (\(R, G, B, A\)) into the cache line simultaneously. If the kernel algorithm performs non-contiguous or strided reads, 75% of the fetched data in that 16-byte texel is discarded, effectively reducing available texture cache capacity and wasting memory bandwidth.

Native WebGL 2 floating-point textures provide the most deterministic 4-byte-per-element footprint with zero packing math and optimal cache utilization for scalar data. Packed textures in gpu.js match this 4-byte density under ideal conditions, but they risk stride overhead, tail padding on non-multiple array lengths, and cache thrashing during non-vectorized memory access patterns.
