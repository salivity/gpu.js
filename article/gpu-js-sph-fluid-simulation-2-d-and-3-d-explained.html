GPU.js SPH Fluid Simulation: 2D and 3D Explained

This article examines whether gpu.js can simulate 2D and 3D Smoothed-Particle Hydrodynamics (SPH) for fluid motion. It explores the technical feasibility of executing particle-based fluid dynamics through gpu.js, compares implementation challenges between 2D and 3D domains, highlights performance bottlenecks inherent to browser-based GPU acceleration, and evaluates whether modern alternatives like WebGPU are better suited for large-scale fluid simulations.

Understanding SPH and GPU.js Capabilities

Smoothed-Particle Hydrodynamics (SPH) is a computational method used for simulating fluid flows by discretizing a continuum fluid into pseudo-particles. Each particle carries properties such as mass, momentum, and density. SPH relies heavily on evaluating interactions between neighboring particles through smoothing kernels to resolve the Navier-Stokes equations.

GPU.js is an open-source JavaScript library that transpiles a subset of JavaScript into WebGL shaders (fragment shaders), allowing parallel execution on the GPU without writing raw GLSL. Because particle operations in SPH are inherently parallel, gpu.js can execute these calculations substantially faster than CPU-bound JavaScript.

Simulating 2D SPH in GPU.js

Simulating 2D SPH in gpu.js is entirely feasible and relatively straightforward to implement for moderate particle counts (typically between 1,000 and 20,000 particles).

In a 2D environment, the computational pipeline consists of three core steps:

  1. Density and Pressure Evaluation: Calculating the local density for each particle based on its distance to neighboring particles.
  2. Force Computation: Computing pressure-gradient forces and viscosity forces exerted by adjacent particles.
  3. Integration: Updating velocities and positions over discrete time steps using algorithms like Euler or Verlet integration.

For smaller particle counts, a brute-force approach (\(O(N^2)\) complexity) can be written directly in gpu.js by passing particle arrays into a kernel where each thread loops over every other particle. For larger particle counts, an \(O(N)\) or \(O(N \log N)\) approach is required. This involves spatial partitioning (such as a uniform grid or spatial hashing), which can be represented in gpu.js using structured textures to index neighboring cells.

Simulating 3D SPH in GPU.js

Simulating 3D SPH in gpu.js is technically possible, but it introduces significant architectural and performance hurdles:

  • Data Representation: WebGL fragment shaders output data to 2D textures. Representing a 3D coordinate space and performing neighbor searches requires flattening 3D spatial grids into 2D memory layouts, which increases kernel complexity and memory overhead.
  • Neighbor Search Overhead: In 3D space, each particle must check up to 27 neighboring cells (the host cell plus 26 adjacent cells) instead of the 9 cells required in 2D. Without native compute capabilities, managing these lookups in a fragment shader creates high memory bandwidth pressure.
  • Particle Count Constraints: Visually convincing 3D fluid simulations generally require hundreds of thousands to millions of particles. The abstraction layer of gpu.js introduces overhead that typically bottlenecks performance before reaching production-grade particle volumes in 3D.

Technical Limitations of GPU.js for SPH

While gpu.js handles the mathematical parallelization of SPH kernels, it suffers from several underlying constraints:

  1. Lack of Atomic Operations and Shared Memory: SPH spatial partitioning algorithms often rely on atomic operations to bin particles into grid cells. Because gpu.js relies on WebGL fragment shaders rather than dedicated compute shaders, it lacks native atomics and fast shared local memory.
  2. Ping-Pong Buffering Overhead: Since fragment shaders cannot read from and write to the same texture simultaneously, multi-pass simulations require ping-pong framebuffers, increasing driver overhead between pipeline steps.
  3. CPU-GPU Transfer Costs: Reading particle data back to the CPU (e.g., via kernel()) causes pipeline stalls. To maintain high frame rates, rendering must occur entirely within the WebGL context without reading the simulation state back to JavaScript.

Conclusion

GPU.js can successfully simulate 2D SPH fluid dynamics for real-time interactive demos, educational visualizations, and smaller datasets. While it is theoretically capable of simulating 3D SPH, the architectural limitations of fragment-shader-based compute and memory indexing make it inefficient for complex 3D fluids. For robust 3D fluid simulations in the browser, modern WebGPU implementations provide compute shaders, storage buffers, and atomic operations that are substantially better equipped for the task.
