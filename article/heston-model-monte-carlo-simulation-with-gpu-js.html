Heston Model Monte Carlo Simulation with GPU.js

This article evaluates the feasibility and implementation of running Monte Carlo simulations for the Heston stochastic volatility model using gpu.js. It covers how the mathematical framework of the Heston model maps onto parallel graphics hardware, explores the technical challenges of pseudo-random number generation and floating-point precision within WebGL shaders, and explains how to structure kernels to price financial derivatives efficiently in a JavaScript environment.

Feasibility of the Heston Model in GPU.js

The Heston stochastic volatility model can be evaluated using Monte Carlo simulations in gpu.js. Monte Carlo methods are inherently embarrassingly parallel: each sample path representing the underlying asset price and its variance evolves independently over discrete time intervals. GPU.js compiles a subset of JavaScript into WebGL compute shaders, enabling browsers and Node.js runtimes to execute thousands of concurrent simulation paths on the GPU instead of sequentially on the CPU.

Mathematical Dynamics and Discretization

The Heston model assumes the asset price \(S_t\) and its variance \(v_t\) follow coupled stochastic differential equations:

\[dS_t = \mu S_t dt + \sqrt{v_t} S_t dW_t^S\] \[dv_t = \kappa (\theta - v_t) dt + \xi \sqrt{v_t} dW_t^v\]

where \(dW_t^S\) and \(dW_t^v\) are Brownian motions with correlation \(\rho\), \(\kappa\) is the rate of mean reversion, \(\theta\) is the long-term variance, and \(\xi\) is the volatility of volatility.

To implement this on a GPU via Euler-Maruyama discretization, each path advances across \(N\) discrete time steps \(\Delta t\):

  1. Generate two independent standard normal variables, \(Z_1\) and \(Z_2\).
  2. Compute correlated random variables: \(Z_v = Z_1\) and \(Z_S = \rho Z_1 + \sqrt{1 - \rho^2} Z_2\).
  3. Update variance: \(v_{t+\Delta t} = v_t + \kappa(\theta - v_t)\Delta t + \xi \sqrt{\max(v_t, 0)}\sqrt{\Delta t} Z_v\). A full-truncation scheme (\(\max(v_t, 0)\)) prevents negative values under the square root.
  4. Update asset price: \(S_{t+\Delta t} = S_t \exp\left( (\mu - 0.5 v_t)\Delta t + \sqrt{\max(v_t, 0)}\sqrt{\Delta t} Z_S \right)\).

Implementing the Simulation with GPU.js

Because GPU.js restricts kernels to a subset of JavaScript and compiles code to GLSL, simulation logic must adhere to specific architectural constraints:

1. On-Chip Pseudo-Random Number Generation (PRNG)

GPU.js kernels cannot access Math.random(). Instead, a deterministic hash-based PRNG—such as a linear congruential generator (LCG) or a PCG algorithm—must be implemented inside the kernel function. Standard uniform values are converted to Gaussian variates using the Box-Muller transform:

function boxMuller(u1, u2) {
  const r = Math.sqrt(-2.0 * Math.log(u1));
  const theta = 2.0 * 3.141592653589793 * u2;
  return [r * Math.cos(theta), r * Math.sin(theta)];
}

Seeds should incorporate the unique GPU thread index (this.thread.x) and the simulation time step to guarantee statistical independence across paths.

2. Kernel Design and Output Aggregation

Transferring millions of simulated paths from GPU memory back to JavaScript memory creates a severe bandwidth bottleneck. To optimize performance, the kernel should compute the terminal option payoff directly on the GPU rather than returning the entire path history.

const gpu = new GPU();

const hestonKernel = gpu.createKernel(function(S0, v0, K, r, kappa, theta, xi, rho, T, steps, seed) {
  const dt = T / steps;
  let S = S0;
  let v = v0;
  let currentSeed = seed + this.thread.x * 1000.0;

  for (let i = 0; i < steps; i++) {
    // 1. Generate pseudo-random variables using custom uniform RNG
    // 2. Map via Box-Muller to correlated normals
    // 3. Update v and S using discretized Heston dynamics
  }

  // Calculate terminal European call payoff
  const payoff = Math.max(S - K, 0);
  return payoff;
}).setOutput([100000]); // 100,000 independent paths

After the kernel runs, the CPU averages the array of terminal payoffs and discounts them by \(\exp(-rT)\) to produce the option price.

Performance Considerations and Limitations

  • Precision: WebGL operates primarily in 32-bit single-precision floating-point arithmetic (float). While sufficient for rough pricing and risk calculations, single precision can lead to drift or numerical instability in long-dated paths compared to traditional 64-bit (double) quantitative finance engines.
  • Watchdog Timers: When running in browser environments, kernels with excessive step counts can trigger the browser's WebGL watchdog timer, resulting in context loss. Breaking simulations into chunked kernel dispatches prevents interface freezing.
  • Feller Condition: When \(2\kappa\theta < \xi^2\), the variance process can reach zero frequently. Simple Euler-Maruyama discretization may cause excessive truncation at zero; using an adapted scheme, such as the Quadratic-Exponential (QE) discretization, offers higher fidelity, though it requires more complex branching within the GLSL kernel.
