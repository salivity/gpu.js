How gpu.js Represents Numbers Internally

This article explores how gpu.js handles numerical data under the hood when executing computational kernels on the graphics card. Because JavaScript runs in a CPU environment with 64-bit floats while WebGL operates in a specialized GPU shading pipeline, gpu.js must translate, downcast, and encode numerical data into graphics memory formats. Readers will learn about the shift from double precision to single precision, the role of GLSL precision qualifiers, and the texture-packing techniques used to store and read values via GPU framebuffers.

Transition from Float64 to Float32

Standard JavaScript treats all numbers as IEEE 754 double-precision 64-bit floating-point values (float64). However, consumer GPU pipelines and the underlying WebGL standard are primarily optimized for single-precision 32-bit floating-point arithmetic (float32).

When passing numerical arrays into a gpu.js kernel, the library casts these 64-bit values down to 32-bit floats. Inside the generated GLSL (OpenGL Shading Language) fragment shader, values are processed as native float types. Because of this conversion, calculations requiring double-precision accuracy will encounter precision degradation when handled by the GPU.

Precision Qualifiers in GLSL

To maintain consistency and avoid artifacts across diverse mobile and desktop hardware, gpu.js configures the WebGL context with the highest supported precision qualifiers in its generated shaders:

precision highp float;
precision highp int;

The highp qualifier ensures that the GPU allocates the maximum allowable precision for floating-point calculations—typically adhering to standard 32-bit IEEE 754 single-precision (with 1 sign bit, 8 exponent bits, and 23 mantissa bits). On low-power hardware where highp is unavailable, WebGL falls back to mediump (often 16-bit half-precision), which further reduces the numerical range and accuracy of values.

Texture-Based Memory Storage and Packing

GPUs process data through rendering pipelines where outputs are written to framebuffers backed by textures rather than standard memory addresses. How gpu.js represents numbers in these textures depends on the WebGL version and hardware extensions available:

  1. Native Floating-Point Textures (WebGL 2 / Extensions):
    In modern environments supporting WebGL 2 or the OES_texture_float and EXT_color_buffer_float extensions, numbers are stored directly in 32-bit floating-point textures (such as R32F or RGBA32F). The GPU writes float values directly to color channels without modification.

  2. RGBA Byte-Packing (WebGL 1 Fallback):
    In baseline WebGL 1 contexts where rendering directly to floating-point textures is unsupported, textures only accept 8-bit unsigned integers per channel (RGBA8). To store a 32-bit float without loss of resolution, gpu.js utilizes bitwise arithmetic and mathematical encoding within the fragment shader to split the 32-bit float across the four 8-bit color channels (Red, Green, Blue, and Alpha).

    During this encoding process:

    • The sign, exponent, and mantissa of the 32-bit float are separated and scaled into four separate bytes (\(4 \times 8 = 32\text{ bits}\)).
    • The resulting vector is output as vec4(r, g, b, a).
    • When transferring data back to the CPU via gl.readPixels, gpu.js reconstructs the 32-bit float values from the byte array using JavaScript ArrayBuffer and DataView structures.

Non-Floating-Point Types

While native GLSL supports integers and booleans, gpu.js kernels prioritize floating-point arithmetic for universal compatibility. Booleans are internally mapped to standard float equivalents (1.0 for true, 0.0 for false). When integer outputs are requested, values are typically calculated as floats within the kernel and either truncated via GLSL floor functions or cast back to integers upon CPU retrieval.
