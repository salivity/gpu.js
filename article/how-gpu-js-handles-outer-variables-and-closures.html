How GPU.js Handles Outer Variables and Closures

This article explains how GPU.js manages JavaScript closures and outer lexical scope when compiling kernel functions to GPU shaders. Because GPU.js transpiles a subset of JavaScript directly into WebGL or WebGPU shader code (such as GLSL), it cannot use standard JavaScript runtime closures. Instead, attempting to directly reference outer variables produces compilation errors unless those variables are explicitly passed as kernel arguments or bound using GPU.js constants.

The Transpilation Barrier

In standard JavaScript, functions maintain access to variables in their surrounding lexical environment via closures. When a function executes on the CPU, the JavaScript engine resolves variable references by traversing the scope chain in system memory.

GPU.js operates differently. Instead of executing JavaScript code on the CPU, it takes the kernel function’s source code, parses its Abstract Syntax Tree (AST), and transpiles that AST into a shader language (such as GLSL) to execute across thousands of GPU cores. The GPU execution environment is entirely isolated from the JavaScript runtime heap. Consequently, the GPU has no direct memory access to the host engine's scope chain, making standard lexical closures technically impossible to resolve at runtime.

What Happens When a Closure Is Attempted

If you write a GPU.js kernel that attempts to capture an outer variable directly:

const multiplier = 2.5;

const kernel = gpu.createKernel(function(data) {
  return data[this.thread.x] * multiplier;
}).setOutput([100]);

GPU.js will parse the AST and encounter the identifier multiplier. Because it is neither declared inside the kernel nor defined as a parameter, the transpiler cannot deduce its type or locate its value in GPU memory. As a result, GPU.js will fail during kernel compilation, throwing an error indicating that the variable is an undeclared symbol or unsupported identifier.

Supported Methods for Passing Outer State

To work around the absence of traditional lexical closures, GPU.js provides two deterministic mechanisms to bridge outer data into the kernel.

1. Kernel Arguments

The most dynamic way to supply external values to a kernel is through function parameters. When arguments are supplied to the kernel call, GPU.js translates them into GLSL uniforms or texture bindings:

const kernel = gpu.createKernel(function(data, multiplier) {
  return data[this.thread.x] * multiplier;
}).setOutput([100]);

kernel(myArray, 2.5);

Passing values as parameters allows variables to change between invocations without forcing the shader to recompile.

2. The constants Configuration Object

When outer lexical values do not change frequently and represent static configuration, GPU.js allows you to inject them via the constants property in the kernel settings:

const multiplier = 2.5;

const kernel = gpu.createKernel(function(data) {
  return data[this.thread.x] * this.constants.multiplier;
}, {
  constants: { multiplier: multiplier },
  output: [100]
});

kernel(myArray);

When using constants, GPU.js evaluates the values at the time of kernel creation and inlines them directly into the generated shader code as static definitions or uniform constants. This replaces the need for lexical capture while retaining the performance benefits of native shader constants.

3. Handling Outer Helper Functions

Just as primitive variables cannot be closed over, external JavaScript functions cannot be called from within a kernel via standard lexical scoping. To call an external helper function inside a kernel, you must register it ahead of time using gpu.addFunction():

function square(x) {
  return x * x;
}

gpu.addFunction(square);

const kernel = gpu.createKernel(function(data) {
  return square(data[this.thread.x]);
}).setOutput([100]);

Registering the function enables GPU.js to translate the helper into a native shader function before compiling the main kernel.
