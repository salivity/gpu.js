How GPU.js Maps 1D Arrays to Multi-Dimensions

This article explains how GPU.js translates flat 1D TypedArrays into multi-dimensional data structures during GPU-accelerated computing. By leveraging WebGL textures, row-major index mapping, and automated shader transpilation, GPU.js allows developers to interact with multi-dimensional matrices in JavaScript while preserving the contiguous 1D memory buffers required for high-performance graphics hardware execution.

The Memory Discrepancy Between CPU and GPU

In JavaScript, high-performance numeric computations typically rely on TypedArray views (such as Float32Array or Int32Array). These arrays are strictly linear, contiguous blocks of binary data allocated in system memory.

Web browsers expose GPU compute capabilities primarily via WebGL (and increasingly WebGPU). WebGL operates using shaders that process 2D textures composed of pixels (RGBA channels) rather than native n-dimensional arrays. Consequently, GPU.js must bridge two fundamental gaps: converting multi-dimensional logical array indices into 1D memory offsets, and packing that 1D memory into 2D WebGL textures.

Row-Major Index Transformation

When a user defines an output dimension or passes a multidimensional structure into a GPU.js kernel, the library employs a standard mathematical layout called row-major order to map high-dimensional coordinates to a 1D offset.

In a multi-dimensional context defined by width (\(W\)), height (\(H\)), and depth (\(D\)), the coordinates \((x, y, z)\) map to a single index (\(i\)) using the following formulas:

  • 2D Mapping: \[\text{Index} = y \times W + x\]

  • 3D Mapping: \[\text{Index} = z \times (W \times H) + y \times W + x\]

This calculation guarantees that adjacent elements across the \(X\)-axis reside next to each other in memory, maximizing spatial locality and memory throughput.

Texture Packing and Memory Encoding

WebGL cannot directly consume arbitrary CPU-side pointers. GPU.js transfers 1D TypedArrays to the GPU by re-encoding them as 2D textures:

  1. Dimension Balancing: A large 1D TypedArray of length \(N\) is shaped into a 2D texture grid of size \(P \times Q\) such that \(P \times Q \ge N\).
  2. Channel Encoding: Depending on the kernel configuration and floating-point precision support (precision: 'single' or 'unsigned'), values are written into the Red (R) channel or split across the Red, Green, Blue, and Alpha (RGBA) channels using bit-shift arithmetic to preserve 32-bit floating-point precision on devices lacking floating-point texture support.
  3. Texture Upload: The packed array is passed to the graphics card via gl.texImage2D().

Runtime Decoding via this.thread Coordinates

Inside a GPU.js kernel function, developers access coordinates through the this.thread object (this.thread.x, this.thread.y, this.thread.z). GPU.js handles multi-dimensional access by translating these thread variables into native WebGL shader code (GLSL).

When a kernel references an input array with coordinates—such as matrix[y][x]—the GPU.js transpiler converts this JavaScript syntax into a customized GLSL lookup function:

  1. It evaluates the linear index: int index = thread.y * width + thread.x;
  2. It converts the linear index into 2D texture coordinates \((u, v)\) normalized between 0.0 and 1.0.
  3. It queries the texture using texture2D(uSampler, vec2(u, v)).
  4. It decodes the RGBA color vector back into the original scalar numeric value.

Output Reconstruction

Once the GPU finishes rendering the output frame, the process occurs in reverse. The fragment shader writes the computed values to an off-screen framebuffer. GPU.js reads this data back into CPU memory using gl.readPixels().

The returned data is initially a 1D TypedArray. If the kernel's declared output dimensions are multi-dimensional (for example, output: [width, height]), GPU.js reconstructs nested JavaScript arrays wrapping the underlying 1D data buffer, or returns the raw 1D TypedArray directly if configured for maximum performance.
