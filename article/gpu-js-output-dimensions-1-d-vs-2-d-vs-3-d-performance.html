GPU.js Output Dimensions: 1D vs 2D vs 3D Performance

In gpu.js, the choice of output dimensions—1D, 2D, or 3D—directly influences execution speed, memory layout, and GPU instruction overhead. Because WebGL natively uses two-dimensional textures to execute computation, multidimensional outputs require hardware-level mathematical translation. Choosing the right output dimensionality ensures efficient cache utilization and avoids redundant fragment shader operations, making the difference between high-throughput parallel execution and severe performance bottlenecks.

The Underlying Architecture: 2D WebGL Textures

To understand why dimensions matter in gpu.js, you must understand how gpu.js runs on a GPU. WebGL does not natively support true 1D or 3D compute buffers; it relies on fragment shaders writing to 2D textures.

When you define kernel output using setOutput([x]), setOutput([x, y]), or setOutput([x, y, z]), gpu.js maps those dimensions onto a physical 2D texture. The GPU computes each element by executing a fragment shader for each "pixel" of this texture. The variables this.thread.x, this.thread.y, and this.thread.z are calculated inside the shader from the raw 2D pixel coordinates.

1D Output: Linear Data and Texture Clamping

A 1D kernel (setOutput([n])) is intuitive for flat vectors, financial series, or linear arrays. However, it exhibits distinct performance characteristics:

  • Coordinate Simplicity: The shader only calculates this.thread.x. There is no multi-axis index calculation for small arrays.
  • Texture Wrapping Overhead: GPUs enforce a maximum texture dimension (typically 4,096 to 16,384 pixels). If your 1D array length exceeds this limit, gpu.js automatically packs the linear array into a 2D grid. The generated shader must then inject division and modulo operations to recalculate the 1D index, introducing mathematical overhead.
  • Memory Read Patterns: If input data is structured linearly, 1D outputs provide optimal coalesced reads, reducing cache misses.

2D Output: The Native Sweet Spot

A 2D kernel (setOutput([width, height])) aligns directly with WebGL’s native architecture and is generally the most performant shape:

  • Zero Coordinate Translation: Because WebGL targets a 2D framebuffer directly, this.thread.x and this.thread.y map cleanly to the horizontal and vertical coordinates of the rendering pipeline. Minimal coordinate decoding is required in the fragment shader.
  • Optimal Spatial Locality: Modern GPU texture caches are optimized for 2D spatial locality. Threads processing neighboring pixels in a 2D block can share data loaded into texture caches, which is ideal for matrix math, image filters, and grid simulations.
  • Large Capacity Without Folding: You can process large datasets (e.g., \(4096 \times 4096 = 16,777,216\) elements) while staying well within standard texture dimension limits on almost any GPU hardware.

3D Output: Increased Mathematical Overhead

A 3D kernel (setOutput([x, y, z])) is useful for volumetric rendering, physics simulations, or 3D tensor computations, but it comes with performance costs:

  • Instruction Overhead: To derive this.thread.z, the fragment shader must perform integer divisions, modulos, and floor operations on every single invocation across the entire dataset. This consumes GPU register space and adds instruction cycles to every thread.
  • Cache Thrashing: Neighboring threads along the Z-axis may map to distant points on the underlying 2D texture memory layout. This can lead to cache misses if threads concurrently access memory non-sequentially across slices.
  • Precision Bottlenecks: On systems relying on standard floating-point precision, heavy index math for extremely large 3D dimensions can occasionally introduce precision truncation issues if values exceed safe integers.

Summary of Performance Trade-offs

Shape Hardware Alignment Coordinate Calculation Overhead Optimal Use Case
1D High for \(N < \text{Max Texture Size}\); Moderate when folded Very Low (flat) to Moderate (folded) Vector math, reduction passes, simple 1D signals
2D Native / Optimal Minimal Matrix multiplication, image processing, cellular automata
3D Emulated via 2D tiling High (requires modulo/division math) Volumetric simulations, 3D grids, tensor operations

Best Practices

  1. Prefer 2D for Large Flat Datasets: If you have millions of elements, reshaping a large 1D problem into a balanced 2D array avoids the edge-case math of linear folding while remaining within GPU texture bounds.
  2. Match Output Shape to Logic: Do not artificially force 3D problems into 1D if it forces manual coordinate reconstruction in your own JavaScript-to-GLSL code; gpu.js optimizes built-in dimensions better than manual arithmetic.
  3. Keep Thread Blocks Square in 2D: Textures with balanced aspect ratios (e.g., \(1024 \times 1024\)) leverage GPU hardware schedulers and caches more evenly than long, narrow strips (e.g., \(1,048,576 \times 1\)).
