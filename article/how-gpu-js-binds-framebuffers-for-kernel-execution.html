How GPU.js Binds Framebuffers for Kernel Execution

GPU.js accelerates JavaScript operations by transpiling functions into WebGL fragment shaders, utilizing off-screen framebuffers to capture computational results directly into WebGL textures. Before executing a kernel, GPU.js configures the WebGL state by generating or selecting an existing framebuffer object, allocating a target texture configured to receive output data, attaching this texture as a color attachment, and adjusting the viewport to align with the kernel's output dimensions.

The Render-to-Texture Architecture

Because WebGL is fundamentally a rasterization pipeline rather than a general-purpose compute API (like WebGPU compute shaders), GPU.js achieves general-purpose computing by rendering a simple geometry—typically a full-screen quad composed of two triangles—across an off-screen render target. The computation itself occurs per-pixel inside the fragment shader. Instead of rendering to the default screen canvas, GPU.js uses WebGL Framebuffer Objects (FBOs) to redirect fragment output to memory textures.

Texture Allocation for Kernel Output

Before binding, GPU.js determines the required memory dimensions based on the kernel's specified output dimensions (1D, 2D, or 3D arrays). It creates a WebGL texture using gl.createTexture() and configures it via gl.texImage2D:

  • Precision and Type: Depending on WebGL support and required precision, GPU.js sets the texture format to floating-point (e.g., via extensions like OES_texture_float in WebGL 1 or native float textures in WebGL 2) or packed integer/RGBA formats.
  • Filtering and Wrapping: Minification and magnification filters are set to gl.NEAREST, and wrap modes are set to gl.CLAMP_TO_EDGE to prevent interpolation artifacts when sampling intermediate calculations.

Framebuffer Binding and Attachment

Once the texture memory is allocated, GPU.js attaches it to the framebuffer through the following sequence:

  1. Binding the Target Framebuffer:
    GPU.js binds the framebuffer using gl.bindFramebuffer(gl.FRAMEBUFFER, framebuffer). This directs all subsequent drawing commands away from the canvas and into the specified FBO.
  2. Attaching the Texture:
    The target texture is connected to the framebuffer’s color attachment slot via: 
    gl.framebufferTexture2D(
  gl.FRAMEBUFFER,
  gl.COLOR_ATTACHMENT0,
  gl.TEXTURE_2D,
  outputTexture,
  0
);
    In kernels configured for multiple render targets (MRT) under WebGL 2, GPU.js attaches multiple textures across sequential attachment points (gl.COLOR_ATTACHMENT0, gl.COLOR_ATTACHMENT1, etc.) and activates them via gl.drawBuffers().
  3. Completeness Verification:
    GPU.js verifies the framebuffer status using gl.checkFramebufferStatus(gl.FRAMEBUFFER). If the status returns gl.FRAMEBUFFER_COMPLETE, the pipeline is validated for drawing.

Viewport Configuration and Pipeline Execution

Immediately following attachment, GPU.js sets the rendering boundaries:

  • Viewport Adjustment: gl.viewport(0, 0, width, height) is invoked, explicitly matching the width and height of the bound texture attachment. This ensures that the fragment shader renders a 1:1 mapping between pixels and kernel array indices.
  • Execution: Input arguments and textures are bound to uniform locations and texture units, vertex buffers representing the full-screen quad are bound to attribute locations, and gl.drawArrays() is invoked to run the computation.

Pipelined Kernels and Ping-Pong Binding

When multiple kernels run sequentially or when recursive computations take place, GPU.js avoids expensive texture allocation cycles. It maintains a dual-buffer system ("ping-ponging"), where one texture is bound to the framebuffer as gl.COLOR_ATTACHMENT0 for writing, while the preceding kernel's output texture is bound to an active texture unit (gl.TEXTURE0, gl.TEXTURE1, etc.) as a readable uniform sampler. Once execution finishes, their roles swap for the next pass.
