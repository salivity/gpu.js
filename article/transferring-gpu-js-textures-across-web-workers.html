Transferring GPU.js Textures Across Web Workers

Directly transferring gpu.js textures between Web Workers without memory duplication is fundamentally impossible using current web APIs. Because gpu.js relies on WebGL contexts bound to specific execution threads, texture objects cannot be detached and shared across workers as zero-copy primitives. This article details why WebGL architecture restricts texture sharing, the mechanisms that cause memory duplication, and the best architectural patterns to bypass these limitations.

The Technical Limitation of WebGL Textures

Under the hood, gpu.js utilizes WebGL to execute computations on the GPU. When a kernel outputs a texture (using pipeline: true), gpu.js manages a native WebGLTexture reference within that specific WebGL rendering context.

In the browser's threading model, WebGL contexts are bound to the thread in which they are initialized. A WebGLTexture is an opaque handle managed by a specific context and is not a transferable object. The Web Workers specification restricts zero-copy operations (transferList in postMessage) strictly to designated types such as:

  • ArrayBuffer
  • MessagePort
  • ImageBitmap
  • OffscreenCanvas
  • ReadableStream / WritableStream

Because WebGLTexture and gpu.js Texture wrapper instances are omitted from this list, they cannot be transferred natively without extracting and copying the underlying data.

Why Memory Duplication Occurs

Attempting to move data produced by a gpu.js texture to another worker requires converting the data into a transportable format. This process inevitably duplicates memory in one of two ways:

  1. GPU-to-CPU Readback (toArray()): Converting a texture back into an array requires the browser to read pixels from VRAM into host RAM (gl.readPixels). This not only creates an allocation in system memory alongside the texture in VRAM, but it also causes a pipeline stall on the GPU.
  2. Buffer Serialization: If the converted array is passed to another worker without transferring its underlying ArrayBuffer via postMessage(data, [data.buffer]), the browser performs a structured clone, allocating a second copy of the data in the receiving worker's memory heap.

Workarounds and Alternative Architectural Patterns

While true zero-copy texture sharing across workers cannot be achieved, application architectures can be adjusted to minimize memory overhead.

1. Dedicate a Single Worker for all GPU.js Computations

The most effective pattern is to isolate all gpu.js pipelines inside a single dedicated Web Worker. Instead of moving textures between workers, chain multiple gpu.js kernels sequentially inside the same worker thread. This allows intermediate outputs to remain in VRAM as native textures without any CPU readbacks, cross-thread transfers, or memory cloning.

2. OffscreenCanvas Context Handoff

If texture rendering must move from the main thread to a worker, initialize the WebGL context using an OffscreenCanvas. The entire canvas ownership can be transferred to a worker once without duplication:

const offscreen = htmlCanvasElement.transferControlToOffscreen();
worker.postMessage({ canvas: offscreen }, [offscreen]);

Once transferred, the worker initializes gpu.js using that canvas. Note that this moves the entire execution context, not individual textures between running contexts.

3. Zero-Copy Host Memory Transfers via ArrayBuffers

If data must be distributed to secondary workers, minimize the duplication footprint by reading the texture into a typed array and transferring its buffer directly:

// Inside the primary worker executing gpu.js
const result = kernel(); // outputs a typed array or read-back texture
const buffer = result.buffer;

// Transfer ownership with zero-copy across the thread boundary
secondaryWorker.postMessage({ data: result }, [buffer]);

While this method still requires the initial VRAM-to-RAM copy, it prevents the CPU-to-CPU memory duplication typically introduced by standard worker messaging.
