GPU.js Multi-Operator FM Synthesis at 48kHz

GPU.js can successfully synthesize multi-operator frequency modulation (FM) audio signals at 48kHz by utilizing WebGL shaders to compute audio sample buffers in parallel. While the GPU provides vastly more mathematical throughput than necessary to calculate multi-operator phase modulation at 48,000 samples per second, the real-world performance depends heavily on handling the input-output overhead between the GPU and the browser's Web Audio API.

Mathematical Viability and Parallelism

At 48kHz, an audio engine must compute 48,000 discrete 32-bit floating-point samples per second for a single channel. Multi-operator FM synthesis—such as the classic 6-operator architecture found in Yamaha DX-series synthesizers—relies on cascading sine wave functions, where the output of one oscillator modulates the phase input of another.

Modern GPUs excel at trigonometric calculations. A single shader invocation can evaluate the phase, envelope, and frequency calculations for 6 to 8 operators simultaneously for a single sample index. Because feed-forward FM algorithms rely entirely on time-dependent mathematical functions rather than recursive states, each audio sample is embarrassingly parallel:

\[\text{Sample}(t) = \sin(\omega_c t + I \cdot \sin(\omega_m t))\]

In GPU.js, each execution thread can map directly to a sample index within a time window, allowing blocks of thousands of samples to be calculated in sub-millisecond timeframes.

Managing Feed-Forward vs. Feedback Operators

Feed-forward configurations—where operators modulate downstream targets without cycles—are straightforward to implement in a GPU.js kernel. You pass global parameters (pitch, carrier/modulator ratios, modulation indices, and ADSR envelope positions) as uniform values, and calculate the sample value based on the absolute time index this.thread.x.

Feedback loops, where an operator modulates its own phase based on previous outputs, introduce sequential dependencies. Because standard parallel execution threads do not share state with adjacent sample threads, true single-sample feedback cannot be calculated across parallel GPU cores. To resolve this in GPU.js:

  • Internal Loop Iteration: Assign each thread a larger segment of consecutive samples to compute sequentially in a local loop.
  • Approximations: Use self-modulating mathematical approximations that mimic feedback behavior without referencing preceding sample outputs.

The Real-Time Bottleneck: WebGL Readback

While GPU.js easily computes the raw math, integrating the output into a real-time 48kHz audio stream introduces data transfer bottlenecks. Web Audio API runs on the CPU, typically within an AudioWorkletNode executing at block sizes of 128 samples (every 2.67 milliseconds at 48kHz).

Transferring data from WebGL back to the CPU via gl.readPixels() (the underlying operation in GPU.js) is synchronous and creates pipeline stalls. If you attempt to compute audio in standard 128-sample real-time blocks, the transfer latency will cause audio dropouts and buffer underruns.

Optimal Implementation Strategy

To reliably use GPU.js for 48kHz FM synthesis, apply the following strategies:

  1. Batch Synthesis: Do not generate audio in small 128-sample frames. Instead, generate large buffers (e.g., 2048 to 48,000 samples at once) to amortize the CPU-GPU transfer overhead.
  2. Double Buffering: Implement a ring buffer on the CPU. While the Web Audio API plays the current audio buffer, GPU.js asynchronously renders the next buffer block.
  3. Offline Rendering: GPU.js is ideal for non-real-time audio rendering, asset pre-generation, or wavetable generation, where the overhead of readPixels() does not compromise immediate playback stability.

GPU.js has more than enough processing power to synthesize complex multi-operator FM signals at 48kHz, provided audio generation is handled in batched blocks rather than low-latency, per-block synchronous audio callbacks.
