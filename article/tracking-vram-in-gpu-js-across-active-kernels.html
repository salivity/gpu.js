Tracking VRAM in GPU.js Across Active Kernels

GPU.js accelerates JavaScript operations by compiling code into shaders that run on the GPU via WebGL, but managing Video RAM (VRAM) across multiple active kernel instances requires understanding both browser security boundaries and texture lifecycles. Because WebGL does not expose direct hardware-level memory queries to JavaScript, GPU.js does not maintain a real-time global hardware VRAM counter. Instead, tracking and managing VRAM usage across active kernels relies on internal texture dimension calculations, manual lifecycle disposal, and pipeline configuration.

The WebGL Abstraction and Hardware Limits

GPU.js relies on WebGL (or HeadlessGL in Node.js) to interface with the graphics processor. WebGL APIs intentionally omit direct hardware monitoring features—such as querying total used or free physical VRAM—to mitigate security vulnerabilities and prevent hardware fingerprinting.

As a result, GPU.js cannot natively query the GPU driver to report that a specific number of megabytes remain available. When multiple kernels run simultaneously, VRAM consumption is bounded strictly by the browser’s internal allocations and OS-level limits, which trigger a webglcontextlost event if exceeded.

Internal Memory Tracking via Texture Footprints

While GPU.js cannot query physical hardware registers, it allocates memory deterministically. Data passed into and returned from kernels are stored as WebGL textures. You can calculate the approximate VRAM footprint of an active kernel instance based on its input arrays and output dimensions:

  1. Texture Dimensions: Every input array and output matrix is packed into a 2D texture (width \(\times\) height).
  2. Precision and Channels: GPU.js typically uses 32-bit floating-point textures (gl.FLOAT) using four channels (RGBA) per pixel for operations.
  3. Byte Calculation: A single output texture consumes roughly: \[\text{Memory (bytes)} = \text{Width} \times \text{Height} \times 4 \text{ channels} \times 4 \text{ bytes per float}\]

Across multiple active kernels, the cumulative VRAM footprint is the aggregate size of all bound input textures, intermediate framebuffers, and output textures that have not yet been garbage-collected or explicitly destroyed.

Managing Multiple Kernel Lifecycles

When multiple kernels are initialized under a single new GPU() instance, they share the underlying WebGL context. Memory management across these instances is handled through specific lifecycle methods:

  • Explicit Deallocation: Calling kernel.destroy() deletes the compiled WebGL program and its associated framebuffers. To release output data, calling texture.delete() frees the underlying WebGL texture from memory immediately, bypassing JavaScript garbage collection delays.
  • Pipeline Mode: When chaining multiple kernels, setting { pipeline: true } instructs GPU.js to leave the output data on the GPU as a texture instead of serializing it back to a CPU-side JavaScript array. While this improves performance, leaving intermediate textures open across multiple active kernels increases concurrent VRAM usage.
  • Context Sharing vs. Isolation: If kernels are instantiated under separate new GPU() objects, each creates its own WebGL context. Browsers enforce a strict limit on simultaneous active WebGL contexts (often between 8 and 16). Exceeding this limit causes older contexts—and all their allocated VRAM—to be forcefully evicted by the browser.

Preventing VRAM Exhaustion

To prevent active kernel instances from consuming excessive VRAM, reuse existing kernel instances with new arguments rather than instantiating new kernels inside loops. When textures are no longer needed as inputs for subsequent calculations, call .delete() on the texture object to ensure immediate release within the shared WebGL context.
