How GPU.js Resolves Function Hoisting in Kernels

GPU.js allows developers to write complex parallel computations in JavaScript and run them on the GPU using WebGL or WebGPU. Because the library transpiles JavaScript into WebGL Shading Language (GLSL), it must bridge the gap between JavaScript's native function hoisting and GLSL's strict requirement that functions be declared before they are called. GPU.js resolves this difference by parsing code into an Abstract Syntax Tree (AST), analyzing function dependencies, and rearranging the transpiled code so that all helper functions precede the generated main() entry point.

The Architectural Conflict: JavaScript vs. GLSL

In standard JavaScript, function declarations are hoisted to the top of their enclosing scope during compilation. This behavior allows developers to invoke a function before its lexical definition appears in the source code.

// Native JavaScript permits this:
function kernel() {
  return calculateValue(5);
}

function calculateValue(x) {
  return x * 2;
}

GLSL, the C-based language targeted by GPU.js, does not support automatic hoisting. In GLSL, an identifier or function must either have its complete definition or a forward declaration prototype physically present higher in the source file than the site where it is called. Direct transpilation of hoisted JavaScript without structural adjustment would result in shader compilation errors.

Step 1: AST Parsing via Acorn

When a kernel is initialized with gpu.createKernel(function() { ... }) or when helper functions are provided via gpu.addFunction(), GPU.js does not execute the function natively. Instead, it extracts the function's string representation using .toString() and parses it into an Abstract Syntax Tree (AST) using Acorn.

This AST representation turns the function's lexical structure into an object-based tree containing nodes for FunctionDeclaration, CallExpression, Identifier, and other syntax components.

Step 2: Dependency Analysis and Collection

During the compilation step, the GPU.js kernel runner traverses the AST to identify all calls made within the kernel body.

  1. Sub-function Discovery: GPU.js maintains an internal registry of available helper functions. When the AST traversal encounters a CallExpression, it checks whether the identifier maps to a registered sub-function.
  2. Dependency Resolution: If helper functions call additional nested helper functions, GPU.js traces these references recursively, generating an ordered dependency graph.

Step 3: Transpilation to GLSL

Once all dependencies are identified, the GPU.js transpiler converts each JavaScript AST branch into valid GLSL code:

  1. Type Inference: Argument and return types are inferred or validated against user-defined signatures.
  2. Signature Formatting: JavaScript parameters are converted to typed GLSL parameters (e.g., float, vec2, int).
  3. Body Conversion: JavaScript mathematical operations and control flow are rewritten into equivalent GLSL constructs.

Step 4: Code Reordering and Shader Assembly

The final shader program is assembled as a single formatted GLSL string. Regardless of the order in which functions were written in JavaScript, GPU.js builds the string sequentially:

  1. Precision Declarations & Headers: GLSL version tags, precision qualifiers (e.g., precision highp float;), and built-in constants.
  2. Helper Function Implementations: Transpiled versions of all registered helper functions, arranged so that every function is defined before it is referenced by another function.
  3. The Kernel (void main()): The transpiled body of the main kernel function.

By synthesizing the GLSL source code through this structured pipeline, GPU.js eliminates hoisting errors entirely, ensuring that helper functions defined below call sites in JavaScript are properly positioned above their execution contexts in the GPU pipeline.
