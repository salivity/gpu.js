GPU.js vs CPU: Dataset Size Performance Threshold

While GPU.js brings the massive parallel computing power of WebGL to JavaScript environments, it is not always faster than a standard CPU execution loop. This article breaks down the data size crossover point where GPU acceleration justifies its architectural overhead, exploring how memory transfer costs, kernel compilation, and arithmetic intensity establish an ideal threshold—typically starting between 65,000 and 1,000,000 data points—for GPU.js to decisively beat the CPU.

The Memory Transfer Overhead

The primary reason GPU.js struggles with small datasets is the transfer latency between system RAM and GPU VRAM. Before the graphics hardware can execute a GPU.js kernel, the input arrays must be converted into textures, uploaded across the PCI Express bus (or shared memory bus on integrated chips) to the GPU, processed, and then read back to the CPU via gl.readPixels or similar WebGL operations.

For small computations, this round-trip transfer takes significantly longer than the actual computation. The CPU, utilizing optimized V8 execution pipelines, branch prediction, and L1/L2 caches, will execute thousands of iterations before the GPU even finishes initializing its shader pipelines.

The Crossover Threshold

The exact threshold where GPU.js outperforms the CPU depends heavily on the computational complexity (arithmetic intensity) per element.

  • High Arithmetic Intensity (e.g., Matrix Multiplication, Image Processing, Ray Marching):
    The threshold is lower, typically around \(256 \times 256\) elements (approximately 65,500 operations) up to \(512 \times 512\) elements (approximately 262,000 operations). Because each data point requires multiple mathematical operations (such as dot products in matrix multiplication), the compute time quickly eclipses the memory transfer overhead, allowing GPU.js to pull ahead at moderate matrix sizes.

  • Low Arithmetic Intensity (e.g., Array Mapping, Basic Addition, Element-wise Scaling):
    The threshold increases substantially, requiring at least \(1,000,000\) to \(2,000,000\) elements to outperform native JavaScript loops. In operations where each element is accessed only once to perform a single arithmetic step, memory bandwidth bottlenecks dominate, often making CPU single-thread performance or Web Workers more efficient until datasets reach multi-million element scales.

Key Factors Altering the Threshold

  1. Integrated vs. Dedicated GPUs:
    Systems with integrated graphics (such as Intel Iris or Apple Silicon) share unified memory between the CPU and GPU, which lowers transfer latency and decreases the performance threshold. Dedicated GPUs (NVIDIA, AMD) incur higher bus transfer penalties, pushing the crossover threshold higher, though they achieve drastically higher peak throughput once that threshold is crossed.

  2. Pipeline Chaining:
    If multiple GPU.js kernels run sequentially without transferring intermediate data back to the CPU (using { output: 'texture' }), the memory transfer penalty is paid only at the very beginning and end of the pipeline. In chained workflows, the dataset size threshold drops significantly, often making GPU.js faster on datasets as small as 10,000 to 50,000 elements.

  3. Precision and Compilation:
    The initial run of a GPU.js kernel incurs a shader compilation cost. Benchmark comparisons must always measure execution after the first run ("warmup"), as the compilation phase alone will artificially skew results against the GPU for initial iterations.

Practical Recommendation

As a rule of thumb, do not introduce GPU.js for arrays smaller than 100,000 elements unless chaining multiple texture-based operations. For \(O(n^3)\) operations like matrix math, transition to GPU.js once matrices reach \(512 \times 512\), where GPU.js typically yields 5x to 20x performance gains over native CPU execution.
