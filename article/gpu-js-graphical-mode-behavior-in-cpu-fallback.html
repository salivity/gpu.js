GPU.js Graphical Mode Behavior in CPU Fallback

When gpu.js is forced to run in CPU fallback mode with graphical mode enabled, it shifts from hardware-accelerated WebGL fragment rendering to a software-based pixel rendering emulation. The library maintains API compatibility by outputting visual data directly to an HTML canvas element, but it substitutes GPU parallel processing with standard JavaScript loops and pixel buffer manipulation. While visual parity is largely preserved, the execution shifts entirely to the main CPU thread, resulting in severe performance drops.

Canvas Management and Context Adaptation

Under standard operation, setting .setGraphical(true) configures gpu.js to output directly to a canvas using a WebGL or WebGL2 context. When forced into CPU mode (mode: 'cpu'), WebGL is bypassed entirely.

Instead, gpu.js utilizes a standard HTML5 2D canvas context (CanvasRenderingContext2D) in browser environments, or a simulated pixel buffer in headless environments. The internal kernel creates an ImageData object to match the specified kernel output dimensions.

Color Mapping and Pixel Buffer Emulation

In graphical mode, kernels use the this.color(r, g, b, a) method to assign pixel colors, accepting normalized floating-point values between 0 and 1.

In CPU fallback mode:

  • The kernel function executes sequentially for every coordinate (x, y) in the defined output dimensions.
  • When this.color(r, g, b, a) is invoked, the CPU runtime intercepts the values, multiplies each channel by 255, clamps them to the [0, 255] range, and writes the 8-bit unsigned integers directly into the ImageData.data Uint8ClampedArray.
  • Once all iterations finish, the array is pushed to the canvas via ctx.putImageData().

Performance and Execution Impact

The most noticeable consequence of CPU fallback in graphical mode is execution latency:

  • Single-Threaded Bottleneck: Unlike the GPU, which shades thousands of pixels simultaneously, the CPU evaluates pixels one by one across nested JavaScript loops.
  • UI Freezing: Because software rendering runs synchronously on the browser's main execution thread, large resolutions (e.g., 1080p) will block the event loop, causing user interface stutter or temporary browser lockups.
  • Frame Rate Degradation: Dynamic, real-time graphical outputs that easily achieve 60 FPS via WebGL often drop to low single-digit frame rates on the CPU.

Visual Fidelity and Precision Differences

For most rendering tasks, the visual output remains identical between GPU and CPU modes. However, minor discrepancies can appear:

  • Float Precision: WebGL shaders adhere to specific hardware-based 16-bit or 32-bit floating-point standards, whereas the CPU executes standard 64-bit JavaScript floats. Complex math can lead to subtle anti-aliasing or gradient variations.
  • Color Clamping: Built-in safeguards in the CPU fallback actively prevent out-of-bounds array operations, handling NaN or undefined values differently than a GPU shader pipeline would.
