Memory Locality and Cache Usage in GPU.js

Designing high-performance algorithms for gpu.js requires a fundamental shift from traditional CPU memory management to the hardware realities of graphics processors operating under the WebGL pipeline. While CPU programming heavily leverages deep, hierarchical hardware caches to minimize latency for sequential instructions, gpu.js compiles JavaScript logic into fragment shaders where memory is represented as textures. This article explores how memory access patterns, spatial and temporal cache architectures, and WebGL abstraction boundaries dictate how you must structure data and algorithmic loops when writing GPU-accelerated code in JavaScript.

The Architectural Shift: Latency Optimization vs. Throughput Caching

CPUs rely on large L1, L2, and L3 caches coupled with speculative execution and hardware prefetchers. When designing a CPU algorithm, sequential array iterations exploit these large cache lines, giving high performance via temporal and spatial locality.

GPUs invert this model. They utilize thousands of smaller cores designed for raw throughput rather than single-thread latency. Instead of relying on massive caches to speed up stalled memory requests, GPUs use massive multithreading to switch between workgroups (warps or wavefronts) when one group is waiting on data from global video memory (VRAM). As a result, per-thread cache is miniscule compared to a CPU, meaning traditional assumptions about variable reuse inside a single execution thread do not yield the same performance benefits.

The Texture Memory Abstraction in GPU.js

Because gpu.js runs on top of WebGL, it stores input arrays and matrices as 2D floating-point or RGBA textures in VRAM. This abstraction alters how spatial locality works:

  1. 2D Spatial Locality over 1D Contiguity: Traditional caches fetch contiguous 1D blocks of linear memory. GPUs feature dedicated texture sampling hardware optimized for 2D spatial locality. When a thread samples a texture coordinate, neighboring texels along both the X and Y axes are pulled into the texture cache simultaneously. Algorithms that process matrices or images benefit more from accessing 2D localized patches than long, horizontal 1D strides.
  2. Read-Only Restrictions: In WebGL, a texture cannot be read from and written to within the same pipeline pass. Unlike CPU code where an algorithm can update an array in place (taking advantage of hot data in L1/L2 cache), gpu.js requires creating an entirely new output buffer. Algorithms must be designed as pure functions without in-place mutations.

Coalesced Access vs. Thread-Level Locality

In CPU programming, spatial locality means that Thread A accesses array[i] and then immediately accesses array[i + 1].

In gpu.js, optimal memory access is dictated by coalesced reads across parallel threads executing in lockstep:

  • Coalesced Reads: If thread index this.thread.x reads from data[this.thread.y][this.thread.x], adjacent threads in the execution block read adjacent columns in memory. The GPU's memory controller bundles these simultaneous requests into a single memory transaction.
  • Strided/Divergent Reads: If threads index memory along the Y-axis (e.g., data[this.thread.x][this.thread.y]), adjacent threads request disparate rows that sit far apart in the underlying texture buffer. This forces the memory controller to execute multiple serialized memory transactions, degrading throughput and thrashing the small GPU texture cache.

Temporal Locality and Recomputation

Temporal locality relies on reusing recently fetched data before it is evicted from the cache. In gpu.js, temporal locality is frequently weaker than on the CPU because the high volume of parallel threads rapidly evicts data from the relatively small GPU caches.

When designing algorithms for gpu.js:

  • Avoid Repeated Global Lookups: Repeatedly reading the same texture coordinates inside nested loops across multiple threads can cause severe cache thrashing.
  • Math vs. Memory: Fetching data from VRAM is often significantly more expensive than performing arithmetic. In many cases, recalculating a value mathematically inside the kernel is faster than reading a precomputed lookup table stored in an array.

Multi-Pass Kernels and Pipeline Latency

Complex algorithms (such as iterative solvers or Fast Fourier Transforms) must be broken into multiple passes using kernel.combineKernels() or chained kernel runs.

Each pass incurs an operational boundary:

  • Intermediate results are flushed to a WebGL framebuffer (a texture in VRAM).
  • The subsequent pass must reload that texture into the texture cache.
  • This eliminates inter-pass temporal caching.

To maximize efficiency, consolidate as many operations into a single kernel as possible to keep intermediate values stored directly inside GPU registers rather than writing out to textures.
