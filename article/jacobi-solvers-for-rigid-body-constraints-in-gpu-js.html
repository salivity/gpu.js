Jacobi Solvers for Rigid Body Constraints in GPU.js

Iterative constraint resolution for rigid body physics can be successfully implemented in gpu.js using a Jacobi solver, but it requires specific architectural trade-offs compared to traditional CPU methods. While standard physics engines rely on the sequential Projected Gauss-Seidel (PGS) algorithm, the Jacobi method calculates constraint impulses simultaneously, making it inherently parallel and compatible with GPU architectures. This article explores how to implement iterative Jacobi constraint solving in gpu.js, its mathematical formulation, and the practical challenges associated with WebGL-based compute.

Why Jacobi Solvers Fit the GPU

In rigid body dynamics, constraints (such as joints, contacts, and limits) are typically modeled as a system of linear equations or a Linear Complementarity Problem (LCP):

\[J M^{-1} J^T \lambda = b\]

Where:

  • \(J\) is the constraint Jacobian.
  • \(M^{-1}\) is the inverse mass and inertia matrix.
  • \(\lambda\) represents the constraint impulses (Lagrange multipliers).
  • \(b\) is the constraint error vector.

Projected Gauss-Seidel (PGS) updates \(\lambda\) sequentially: calculating constraint \(i\) immediately updates the velocities used to calculate constraint \(i+1\). This feedback loop prevents race conditions on a CPU, but it cannot be directly parallelized across thousands of GPU threads.

A Jacobi solver, by contrast, decouples these dependencies. Every constraint is evaluated simultaneously using velocities and positions strictly from the previous iteration. Because the output of one thread does not immediately affect another in the same pass, the algorithm avoids write conflicts and matches the SIMD (Single Instruction, Multiple Data) paradigm of graphics processors.

Implementing the Jacobi Approach in gpu.js

Because gpu.js compiles JavaScript functions into WebGL fragment shaders, it does not support arbitrary read/write memory within a single execution pass. To solve constraints iteratively, you must implement a "ping-pong" buffering architecture:

  1. Data Representation: Store physical states—positions, orientations (quaternions), linear velocities, angular velocities, and constraint definitions—in 2D or 1D float arrays. In gpu.js, these are passed as textures to the kernels.
  2. The Solving Kernel: Write a gpu.js kernel that maps one thread per constraint (or one thread per rigid body). Each thread reads the shared velocities, computes the delta impulse needed to correct its assigned constraint, and outputs the calculated delta.
  3. Velocity Update Kernel: A secondary kernel aggregates the constraint impulses applied to each body, updates the velocities, and writes them to an alternate output texture.
  4. Iteration Loop: Run the solving and update kernels sequentially across multiple iterations (typically 10 to 30 times per physics step) by swapping the input and output textures on the CPU side without reading data back to the JavaScript main thread.

Convergence Issues and Under-Relaxation

The primary drawback of the standard Jacobi solver is stability. While Gauss-Seidel converges reliably for stiff systems, a pure Jacobi solver often overshoots, leading to high-frequency oscillations or explosive instability, especially in long constraint chains (like ropes or articulated ragdolls).

To stabilize a Jacobi solver in gpu.js, you must apply under-relaxation (often related to the Jacobi-SOR method):

\[\lambda^{(k+1)} = \lambda^{(k)} + \omega \Delta \lambda\]

Where \(\omega\) is a relaxation parameter typically chosen in the range of \(0.1 \le \omega \le 0.6\). This scales down the immediate correction of each constraint to account for the simultaneous corrections being applied by neighboring constraints. While under-relaxation prevents system explosion, it introduces a "spongy" or elastic appearance, requiring more iterations to achieve rigid behavior.

Limitations of gpu.js for Constraint Solving

While technically feasible, solving rigid body constraints with Jacobi solvers inside gpu.js presents several practical bottlenecks:

  • Kernel Invocation Overhead: Iterative solvers require dozens of iterations per frame. Calling gpu.js kernels inside nested JavaScript loops creates significant WebGL draw call and state-change overhead.
  • Scattering vs. Gathering: A constraint produces impulses for two distinct bodies (scattering), but WebGL fragment shaders can only write to the coordinate of the target pixel (gathering). Structuring data so that bodies aggregate forces from connected constraints requires complex indexing structures that degrade shader performance.
  • Memory Readback Costs: Transferring the final simulation state from the GPU back to the CPU via readPixels (which gpu.js uses under the hood) is synchronous and can cause pipeline stalls.

Conclusion

Rigid body constraints can be solved iteratively using Jacobi solvers in gpu.js. The decoupled nature of the Jacobi algorithm allows parallel execution within the constraints of WebGL fragment shaders. However, due to the need for under-relaxation to maintain stability and the inherent overhead of managing iterative draw calls in WebGL, this approach is best suited for large volumes of simple constraints (such as mass-spring networks or non-interlocking particle collisions) rather than complex, highly rigid articulated mechanisms.
