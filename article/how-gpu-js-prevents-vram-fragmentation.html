How GPU.js Prevents VRAM Fragmentation

This article explores how the GPU.js library manages intermediate memory buffers to prevent Video RAM (VRAM) fragmentation during high-throughput computing. By abstracting WebGL compute passes, GPU.js avoids native memory degradation through texture recycling pools, execution pipelining, and static resource allocation strategies that circumvent frequent driver-level memory allocations and deallocations.

The Problem of VRAM Fragmentation in WebGL

GPU.js compiles JavaScript functions into GLSL shader code executed via WebGL contexts. In WebGL, compute operations rely on 2D textures as intermediate storage buffers instead of direct compute buffers like those found in WebGPU, Vulkan, or CUDA.

When an application performs rapid computation with changing or chained data sets, repeatedly invoking gl.createTexture() and gl.deleteTexture() introduces severe performance bottlenecks:

  • Driver-Level Fragmentation: Continuous allocation and deallocation of varied texture sizes leaves gaps in native GPU memory spaces, preventing contiguous allocation for subsequent tasks.
  • CPU-GPU Synchronization Pauses: Deletion requests in WebGL are non-blocking, but garbage collection sweeps or memory shortages force synchronous driver syncs, stalling execution.
  • JavaScript Engine Pressure: Rapid object generation creates overhead for the V8 (or browser-equivalent) garbage collector.

To maintain high throughput, GPU.js mitigates these issues by maintaining tight control over texture lifecycles.

Texture Pooling and Recycling

Rather than allowing intermediate textures to be destroyed and collected by the browser’s garbage collector, GPU.js implements texture pooling.

When an intermediate buffer finishes its role as the output target of a render pass or as the input to a subsequent kernel:

  1. Retention Over Deletion: The underlying WebGL texture object (WebGLTexture) is not deleted using gl.deleteTexture().
  2. Dimension Matching: GPU.js caches textures based on their width, height, and format (e.g., UNSIGNED_BYTE, FLOAT, or half-float formats enabled via WebGL extensions like OES_texture_float).
  3. Re-assignment: When a subsequent operation requires an intermediate render buffer of identical dimensions, GPU.js retrieves the unused texture from the pool rather than issuing new allocation instructions to the GPU driver.

By reusing existing buffers, the total number of physical allocations is bounded to the peak simultaneous memory footprint of the program, completely halting continuous fragmentation.

Kernel Pipelining (pipeline: true)

A key design feature in GPU.js for intermediate buffer management is the pipelining mode. When configured with { pipeline: true }, kernel functions return a Texture object instead of reading pixels back to the CPU via gl.readPixels().

const kernel = gpu.createKernel(function(data) {
  return data[this.thread.x] * 2;
}, {
  output: [1024],
  pipeline: true
});

Pipelining combats fragmentation in two specific ways:

  • FrameBuffer Swapping (Ping-Pong Buffering): For iterative algorithms (such as simulations or neural network layers), GPU.js reuses two static textures in a ping-pong pattern. Texture A acts as the input and Texture B acts as the render target; on the next iteration, their roles swap. This enables indefinite iterations with zero dynamic allocations.
  • Decoupling Allocation from Loop Cycles: By passing WebGL textures directly between kernels, the pipeline avoids dynamic intermediate reformatting, keeping memory addresses stable across compute cycles.

Static Allocation via Kernel Instances

GPU.js kernels are pre-compiled and bound to explicit output topologies. When a kernel instance is created via gpu.createKernel(), its execution context and required Framebuffer Object (FBO) targets are determined ahead of time.

Because output boundaries are defined statically:

  • Intermediate textures are bound to pre-allocated FBO attachments.
  • Data updates are pushed to textures using gl.texSubImage2D() rather than re-allocating with gl.texImage2D(), modifying the existing VRAM region in-place without altering its allocated footprint.

Cleanup and Disposal

When memory must genuinely be reclaimed, GPU.js provides explicit disposal APIs rather than relying on automatic garbage collection. Calling .destroy() on a kernel or texture manually releases the associated FBOs, renderbuffers, and pooled textures cleanly through the WebGL context:

kernel.destroy();
texture.delete();

This explicit release ensures that the WebGL driver can deallocate the entire contiguous block of resources at once, preventing isolated dead allocations from trapping usable VRAM.
