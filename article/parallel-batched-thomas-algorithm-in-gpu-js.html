Parallel Batched Thomas Algorithm in gpu.js

The Thomas algorithm—a specialized form of Gaussian elimination for tridiagonal systems—is fundamentally serial along a single matrix, making individual solves difficult to accelerate on a GPU. However, when applied across large batches of independent tridiagonal systems, the algorithm can be parallelized with high efficiency using gpu.js. By dedicating one GPU thread per matrix system, developers can bypass inter-thread communication and synchronization bottlenecks, achieving substantial throughput gains compared to CPU execution, provided the matrix dimension fits within the architectural constraints of WebGL kernels.

The Inherent Bottleneck of a Single System

The standard Thomas algorithm solves a tridiagonal system \(Ax = d\) in two main stages: a forward elimination sweep to eliminate the lower subdiagonal, followed by a back-substitution sweep to compute the solution vector. Both stages rely on strictly recursive recurrence relations:

  • Forward sweep: \(c'_i = \frac{c_i}{b_i - a_i c'_{i-1}}\) and \(d'_i = \frac{d_i - a_i d'_{i-1}}{b_i - a_i c'_{i-1}}\)
  • Back substitution: \(x_i = d'_i - c'_i x_{i+1}\)

Because each step depends directly on the output of the preceding step, parallelizing a single tridiagonal solve requires complex alternatives like Parallel Cyclic Reduction (PCR) or recursive doubling. These algorithms introduce significant thread communication, branching, and memory overhead, which are challenging to implement efficiently within the WebGL-based pipeline of gpu.js.

Why Batch Parallelization Succeeds

While solving a single tridiagonal matrix on the GPU yields poor efficiency, numerical simulations—such as 2D/3D Alternating Direction Implicit (ADI) methods, multi-asset financial models, or batched spline interpolations—often require solving thousands of independent tridiagonal systems simultaneously.

In this scenario, the batch dimension becomes embarrassingly parallel:

  1. One Thread per System: A gpu.js kernel can be defined over a 1D or 2D output grid where each thread identifier (this.thread.x) maps directly to an independent tridiagonal system in the batch.
  2. Serial Execution per Thread: Inside the kernel, each thread executes the standard, unmodified \(O(N)\) sequential Thomas algorithm on its assigned matrix.
  3. Zero Inter-Thread Communication: Because each tridiagonal system is completely disjoint from the others, GPU threads require no synchronization barriers or shared memory exchanges.

Technical Limitations in gpu.js

While the algorithmic approach is sound, several practical constraints of gpu.js must be considered:

  • Local Memory Allocation: gpu.js compiles JavaScript kernels into WebGL GLSL fragment shaders. GLSL does not support dynamic memory allocation. The system dimension \(N\) must typically be a compile-time constant or sufficiently small so that intermediate arrays can be allocated without exhausting GPU register space.
  • Register Pressure: Allocating intermediate storage inside each thread consumes shader registers. If the matrix size \(N\) is too large (e.g., \(N > 256\)), register spilling or compilation failures occur, diminishing occupancy and performance.
  • Data Transfer Bottlenecks: Transferring large input matrices and retrieving output buffers across the WebGL boundary can easily dominate execution time. High throughput is only realized when data remains on the GPU across multiple successive operations (such as time-stepping loops).

Conclusion

The Thomas algorithm can be parallelized effectively across batches in gpu.js. Assigning one independent tridiagonal system per thread eliminates communication overhead and fully utilizes the GPU's massively parallel architecture. For systems where the batch size is large (thousands of systems) and the matrix dimension \(N\) is small to moderate (under a few hundred rows), batched execution delivers superior performance compared to multi-threaded CPU equivalents.
