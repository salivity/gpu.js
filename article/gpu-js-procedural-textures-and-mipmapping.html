GPU.js Procedural Textures and Mipmapping

Generating procedural textures using gpu.js leverages the GPU's parallel processing capabilities through WebGL, but utilizing these textures with mipmapping introduces specific architectural and performance considerations. This article examines how the underlying WebGL context handles textures produced by gpu.js kernels, the mechanisms required to generate and update mipmaps for dynamic content, hardware constraints regarding texture dimensions and formats, and alternative strategies for managing level-of-detail and aliasing.

The Underlying WebGL Context and Texture Output

gpu.js compiles high-level JavaScript functions into GLSL shaders, executing them across GPU threads and outputting results either to typed arrays or directly to a WebGL texture via the pipeline: true or graphical: true execution modes.

When configured to output to a texture, gpu.js writes the procedurally calculated values to an offscreen WebGL framebuffer attached to a standard WebGLTexture. By default, gpu.js configures these textures for linear or nearest-neighbor filtering at a single base resolution (level 0). Because gpu.js functions as a general-purpose compute tool rather than a full graphics engine, it does not automatically build mipmap chains for its outputs.

Triggering Mipmap Generation

To use standard hardware mipmapping with a texture generated by gpu.js, the developer must explicitly invoke the WebGL API on the underlying texture handle.

  1. Accessing the Texture Handle: Extract the raw WebGLTexture reference from the gpu.js kernel output or its internal context.
  2. Binding the Texture: Bind the texture to gl.TEXTURE_2D using the native WebGL context managed by gpu.js or a shared context.
  3. Generating Levels: Call gl.generateMipmap(gl.TEXTURE_2D). This commands the GPU to automatically downsample the base procedural image into progressively smaller resolutions (halving dimensions down to 1x1).
  4. Setting Texture Parameters: Configure sampling modes such as gl.TEXTURE_MIN_FILTER to gl.LINEAR_MIPMAP_LINEAR (trilinear filtering) or gl.LINEAR_MIPMAP_NEAREST to allow the rendering pipeline to sample from the generated levels.

Format and Dimension Constraints

When generating mipmaps from gpu.js outputs, two primary technical limitations apply:

  • Dimensions (Power of Two): In WebGL 1.0 environments, gl.generateMipmap strictly requires the texture width and height to be powers of two (e.g., 256x256, 512x512). If the gpu.js output dimensions are non-power-of-two (NPOT), mipmap generation will fail, and texture wrapping modes are constrained. WebGL 2.0 removes this restriction for basic formats, but powers of two remain optimal for performance.
  • Pixel Formats: gpu.js often operates using floating-point buffers (FLOAT or HALF_FLOAT) to preserve numerical precision during compute passes. In WebGL, generating mipmaps on floating-point textures is not universally supported and frequently requires specific extensions (such as OES_texture_float_linear or WebGL 2 color buffer float extensions). If the output is a 32-bit floating-point texture, downsampling hardware may fail to compute mip levels, requiring the data to be rendered to an 8-bit unsigned byte (gl.RGBA) format instead.

Dynamic Generation vs. Performance Overhead

Procedural textures generated via gpu.js can be static (generated once at load time) or dynamic (regenerated every frame based on time, physics, or user interaction).

  • Static Textures: If a texture is calculated once, running gl.generateMipmap immediately after execution is efficient. The one-time computational cost of generating the mipmap pyramid is amortized across all subsequent rendering frames, providing effective antialiasing and cache-friendly texture lookups.
  • Dynamic Textures: If the procedural kernel runs every frame to update an animated pattern, regenerating mipmaps on every frame introduces significant overhead. The downsampling passes require GPU bandwidth and synchronization, which can offset the performance gains of running the procedural logic on the GPU.

Alternative Approaches: Analytic Antialiasing

For animated or constantly changing procedural surfaces, relying on hardware mipmaps generated by gl.generateMipmap can become a bottleneck. An alternative approach is handling antialiasing directly inside the procedural generation kernel:

  • Screen-Space Derivatives: Rather than post-generating mipmaps, evaluate procedural formulas (such as Perlin noise or checkerboard patterns) using frequency clamping.
  • Direct Multi-Scale Generation: Design the gpu.js kernel to write pre-filtered or downscaled versions into specific render targets or an atlas, bypassing the native mipmap generator and maintaining precision within floating-point buffers.
