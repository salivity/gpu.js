How GPU.js Eliminates Texture Swizzling Penalties

This article examines how the gpu.js library mitigates performance degradation caused by texture swizzling during frequent readback operations from the GPU to the CPU. It outlines the architectural mismatch between non-linear GPU memory patterns and linear CPU memory layouts, and details the specific mechanisms—such as texture chaining, flat array packing, and optimized framebuffer configurations—that gpu.js uses to preserve high-throughput computation.

The Texture Swizzling Bottleneck

Modern GPUs do not store textures in linear, row-major order. Instead, they organize texture memory using non-linear space-filling curves, such as Morton order (Z-order) or tiled memory blocks, a process known as texture swizzling. Swizzling maximizes 2D spatial locality in GPU cache lines, significantly improving rendering and texture sampling speeds.

However, the CPU expects data in standard linear contiguous arrays (such as JavaScript Float32Array). During a readback operation using WebGL commands like gl.readPixels(), the GPU must deswizzle the tiled data back into a linear layout before transferring it across the PCIe bus. In pipelines requiring frequent readbacks, this continuous hardware unswizzling and pixel unpacking introduces severe memory latency and pipeline stalls.

Pipeline Retention via Texture Outputs

The primary way gpu.js prevents swizzling penalties during multi-stage processing is by avoiding the readback entirely through texture pipelining.

By default, when a kernel execution finishes, developers can configure the kernel to return a texture reference directly:

kernel.setOutputOrder('closest');
kernel.setPipeline(true);

When pipelining is enabled, the output stays on the GPU as a native WebGLTexture encapsulated in a Texture object. Subsequent kernels accept this texture directly as an input parameter. Because the data remains in native GPU texture space, the GPU does not invoke deswizzling logic between operational steps. The memory layout stays optimized for the hardware texture units until an absolute CPU readback is necessary.

1D-to-2D Linear Output Mapping

When an application finally requires data transfer back to the CPU, gpu.js utilizes specialized internal shaders to map 1D or n-dimensional data into 2D texture coordinates in a linear-friendly fashion.

WebGL 1 and 2 impose limitations on maximum texture sizes, forcing 1D computational arrays to be sliced across 2D surfaces. The gpu.js compiler injects indexing math directly into the kernel's fragment shader that calculates row and column access using linear indices. Because the pixel coordinates map systematically to standard row-major blocks, the subsequent readback operates on textures formatted to match CPU memory expectations as closely as the underlying driver allows, reducing complex indexing penalties during conversion.

Channel Packing and Direct Buffer Allocation

When working in environments that lack full support for 32-bit floating-point textures (OES_texture_float or EXT_color_buffer_float), gpu.js packs a single 32-bit float across four 8-bit RGBA channels.

During readbacks, gpu.js streams the data directly into a pre-allocated typed array (Uint8Array or Float32Array). By matching the internal packing format to the data structure passed to gl.readPixels(), gpu.js eliminates secondary format conversion overhead on the CPU side. When float textures are supported, it binds linear floating-point targets that transfer directly into Float32Array buffers, avoiding both driver-side format conversions and unnecessary byte manipulation.
