Why Math.random Cannot Run Inside GPU.js

GPU.js accelerates web applications by compiling standard JavaScript functions into WebGL shader code (GLSL) to execute parallel operations directly on the graphics card. However, dynamic and non-deterministic JavaScript functions like Math.random() cannot function unpredictably inside a GPU kernel because the GPU lacks the JavaScript runtime environment, relies on a massively parallel execution model that forbids centralized mutable states, and statically evaluates CPU functions prior to execution.

JavaScript Transpilation to GLSL

GPU.js does not run a JavaScript engine like V8 or SpiderMonkey on the graphics card. Instead, it parses your JavaScript function’s Abstract Syntax Tree (AST) and converts the logic into GLSL (OpenGL Shading Language).

Because GLSL is a strictly typed, C-like language running directly on the hardware rasterizer or compute pipeline, it has no native access to the JavaScript standard library, the DOM, or the host CPU's memory. Any native JavaScript methods called inside the kernel must either have a predefined GLSL equivalent mapped by GPU.js or be evaluated ahead of time on the CPU.

Constant Folding and the Compilation Phase

When an unsupported or native dynamic function such as Math.random() is encountered during the creation of a kernel, it cannot be dynamically called per thread on the GPU. Instead, one of two things happens:

  1. Pre-computation (Constant Folding): The JavaScript runtime evaluates Math.random() once during the kernel compilation step on the CPU. The resulting single float value is hardcoded directly into the compiled shader source code. As a result, every single parallel GPU thread reads the exact same pre-calculated number, entirely eliminating unpredictability.
  2. Compilation Failure: If used dynamically in a way that the AST parser cannot pre-calculate or translate to native GLSL, the compilation will fail outright.

The Problem of State in Massively Parallel Architectures

Traditional CPU-based pseudo-random number generators (PRNGs), like the implementation behind Math.random(), maintain an internal mutable state. Every time Math.random() is called, the algorithm reads the current state, mutates it via a mathematical formula, and updates the seed for the next call.

GPUs operate on thousands of concurrent hardware threads simultaneously. If thousands of threads attempt to read and write to a single mutable seed at the exact same clock cycle, it creates massive memory race conditions and bottlenecks. Graphics pipelines are designed for isolated, independent mathematical calculations where each thread calculates its output without needing to communicate with or modify the state of neighboring threads.

Achieving Unpredictable Numbers in GPU.js

To generate varying values across threads in GPU.js, you must use deterministic, coordinate-based pseudo-random algorithms. Instead of relying on a sequential mutable state, shaders generate pseudo-randomness by feeding unique, immutable per-thread data—such as this.thread.x and this.thread.y—into a specialized mathematical hash function. To make the output change unpredictably over time, an external seed (such as a CPU-generated Math.random() value or timestamp) must be passed into the kernel as a uniform argument on each execution frame.
