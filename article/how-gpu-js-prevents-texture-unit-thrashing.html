How GPU.js Prevents Texture Unit Thrashing

Passing dozens of input arrays into a single GPU.js kernel can quickly overwhelm the graphics hardware's physical texture limits, causing severe performance degradation known as texture unit thrashing. GPU.js avoids this bottleneck by leveraging texture packing, internal texture caching, uniform sampler re-mapping, and intelligent multi-pass kernel synthesis. This article explains the underlying WebGL constraints and the specific mechanisms GPU.js employs to safely process large numbers of inputs without triggering continuous texture swapping.

The Problem: WebGL Texture Unit Limits

In WebGL, shaders access external data primarily via textures bound to specific texture image units. Browsers and graphics drivers impose a strict hardware ceiling on simultaneous texture bindings, defined by gl.MAX_TEXTURE_IMAGE_UNITS (typically 8, 16, or 32 units).

When a shader requires more active textures than the hardware supports, the application must repeatedly unbind existing textures and bind new ones during execution. This frequent rebinding introduces pipeline stalls, invalidates driver-level GPU caches, and degrades throughput.

1. RGBA Channel Packing and Vectorization

Rather than creating a distinct texture for each scalar input or small array, GPU.js packs data into the red, green, blue, and alpha (RGBA) channels of a single 32-bit floating-point or unsigned byte texture.

  • 4:1 Data Consolidation: A dataset that would otherwise occupy four distinct single-channel textures is combined into a single 4-element vector per pixel.
  • Dimensional Encoding: For multi-dimensional matrices, GPU.js converts 2D and 3D array inputs into flattened 2D memory layouts that conform to standard GPU power-of-two or rectangular texture boundaries, reducing the total count of required sampler instances.

2. Texture Pooling and Persistent Binding Cache

GPU.js maintains an internal texture manager that tracks which textures are currently assigned to WebGL texture units:

  • State Tracking: The engine maintains an internal map of active texture units. If an input texture was bound to TEXTURE0 in a previous tick and remains unchanged, GPU.js skips the costly gl.activeTexture() and gl.bindTexture() invocations entirely.
  • Uniform Sampler Mapping: Instead of binding new textures to the same unit inside a single draw cycle, GPU.js statically assigns samplers to reserved slots during the kernel compilation step, ensuring the WebGL pipeline never swaps texture targets midway through a fragment shader pass.

3. Texture Atlasing for Sub-Kernel Inputs

When multiple static arrays are passed to a kernel, GPU.js can combine them into a single larger composite texture (an atlas).

The generated GLSL code automatically computes coordinate offsets based on the target array's position within the composite texture. This allows dozens of logically distinct inputs to be queried using only one physical sampler uniform, completely bypassing the MAX_TEXTURE_IMAGE_UNITS restriction.

4. Pipeline Decomposition and Multi-Pass Fallbacks

If the number of unique dynamic inputs fundamentally exceeds the hardware sampler capacity and cannot be merged into an atlas, GPU.js prompts multi-pass kernel design:

  • Kernel Chaining: Complex kernels requiring excessive inputs can be broken down using kernel.setOutput(true) to output directly to framebuffers.
  • Intermediate Textures: Intermediate calculation results are written directly to offscreen WebGL framebuffers (render targets) and piped into subsequent kernel passes, maintaining GPU residency without overloading any single execution stage with too many simultaneous read textures.
