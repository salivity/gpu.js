Using Math.atan2 in Multi-Threaded gpu.js Kernels

When invoked inside a multi-threaded gpu.js kernel, Math.atan2 is transpiled from JavaScript into native WebGL shading language (GLSL), allowing it to execute simultaneously across thousands of GPU cores. Rather than executing sequentially with standard JavaScript 64-bit double-precision floats, it runs in a massively parallel Single Instruction, Multiple Threads (SIMT) architecture using 32-bit single-precision floating-point arithmetic. This article explains how Math.atan2 is mapped to hardware, its execution flow across parallel threads, precision considerations, and edge-case behaviors.

Transpilation to GLSL

gpu.js operates by parsing JavaScript Abstract Syntax Trees (AST) and translating supported mathematical functions into equivalent GLSL expressions.

In standard JavaScript, the signature is:

Math.atan2(y, x)

During kernel compilation, gpu.js maps this call directly to the overloaded GLSL function:

atan(float y, float x)

Because both JavaScript's Math.atan2 and GLSL's two-argument atan accept y as the first argument and x as the second argument, the parameter order remains identical. The GPU compiler generates machine code targeting the hardware’s native Special Function Units (SFUs), which calculate trigonometric and transcendental values directly in silicon.

Parallel Thread Execution

In gpu.js, "multi-threading" corresponds to GPU thread invocation over a defined output grid (output: [width, height, depth]).

When a thread runs:

  1. Each thread evaluates this.thread.x, this.thread.y, or this.thread.z.
  2. Threads pass thread-specific inputs into Math.atan2(y, x).
  3. The GPU cores process these operations in lockstep via warps (Nvidia) or wavefronts (AMD).
  4. Since Math.atan2 is a pure function that does not read or write shared memory, there are no race conditions, memory barriers, or thread synchronization overheads. Every compute unit computes the angle \((-\pi \text{ to } \pi)\) independently.

Precision and Performance Differences

While the programmatic syntax mirrors JavaScript, execution on the GPU introduces behavioral variations:

  • 32-bit vs. 64-bit Precision: Standard V8/browser JavaScript computes Math.atan2 using IEEE 754 double precision (64-bit). GPUs typically run WebGL shaders using single precision (highp float, 32-bit). As a result, outputs on the GPU may exhibit subtle truncation differences in the least significant digits compared to CPU execution.
  • Hardware Approximation: Most GPUs calculate trigonometric values using polynomial approximations or the CORDIC algorithm inside hardware SFUs. While significantly faster, slight variations in precision can occur between different GPU vendors (e.g., Nvidia vs. AMD vs. Intel integrated graphics).

Boundary Conditions and Edge Cases

The behavior of edge cases generally aligns with standard IEEE 754 rules, but hardware implementations can produce slight deviations:

  • Zero Division / Origin (0, 0): In JavaScript, Math.atan2(0, 0) returns 0. In GLSL, atan(0.0, 0.0) is defined to return 0.0 in most modern drivers, though older GLSL specifications marked this condition as technically undefined.
  • Signs of Zero: IEEE 754 recognizes signed zeroes (+0 and -0). Math.atan2 uses these signs to determine the quadrant. Most modern mobile and desktop GPUs preserve signed zeroes properly, matching standard JavaScript quadrant behavior.
  • Infinities and NaNs: If inputs contain Infinity or NaN, the GPU handles these according to hardware floating-point capabilities. Some low-power mobile GPUs clamp values rather than propagating NaN, which can produce divergent values from CPU-based JavaScript runs.

CPU Fallback Mode

If gpu.js fails to initialize hardware acceleration (such as when WebGL is unsupported or disabled), the kernel falls back to CPU execution. In this fallback state, gpu.js runs standard JavaScript loops using multi-core CPU workers or a single thread. When this happens, Math.atan2 runs using the host machine’s standard 64-bit IEEE 754 implementation, restoring full JavaScript precision at the cost of parallel throughput.
