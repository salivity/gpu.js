Why gpu.js Lacks Cross-Thread Synchronization

During a single execution pass in gpu.js, individual execution threads cannot communicate, share state, or synchronize with one another. This article explores the architectural and software constraints that prevent cross-thread communication, focusing on the underlying WebGL pipeline, hardware execution models, memory access limits, and how multi-pass pipelines serve as the standard workaround.

The WebGL Abstraction Model

gpu.js operates by transpiling JavaScript functions into GLSL (OpenGL Shading Language) and executing them on the GPU, typically via the WebGL API. Under the WebGL model, compute operations are mapped onto fragment shaders running across a generated mesh. Each thread corresponds to a specific pixel or data element in an output texture.

WebGL treats every fragment invocation as a fully isolated, stateless operation. The graphics pipeline is intentionally architected this way so the GPU driver can dispatch, execute, and discard fragment operations without tracking interdependencies. Because the runtime environment abstracts the GPU as a graphics rasterizer rather than a generalized compute platform, native communication primitives do not exist within the execution context of a single pass.

Unpredictable Scheduling and Deadlock Risks

GPUs achieve high throughput by running thousands of threads concurrently across multiple Compute Units or Streaming Multiprocessors. However, the hardware provides no guarantee regarding the order in which these threads execute.

If thread \(A\) attempts to read data produced by thread \(B\) within the same pass, there is no guarantee that thread \(B\) has executed yet, is currently executing, or has finished writing to memory. Introducing synchronization barriers across arbitrary threads in this graphics-based architecture would lead to hardware deadlocks. If a thread stalls waiting for a signal from another thread that has not yet been scheduled on an execution warp or wavefront, execution halts permanently.

Memory Isolation and Pipeline Hazards

In a standard gpu.js kernel, memory access is strictly segregated:

  • Input data (passed as arrays, textures, or matrices) is read-only.
  • Output data (the returned value for this.thread.x, this.thread.y, etc.) is write-only for that specific thread's coordinate.

Web APIs forbid simultaneous reading and writing to the same texture bound to an active framebuffer to prevent pipeline hazards and undefined behavior. Because a thread cannot read from the active write buffer, it cannot inspect values written by adjacent threads during that same execution cycle.

Lack of Shared Memory Primitives

Low-level compute APIs such as CUDA, OpenCL, and raw WebGPU support thread grouping (workgroups) equipped with fast on-chip shared memory and barrier instructions (such as workgroupBarrier()). These primitives allow tightly bound threads within a single block to exchange data safely.

gpu.js abstracts away this low-level hardware configuration to provide a simple, cross-platform JavaScript interface. It does not expose workgroup topology or shared local memory structures. Without shared memory registers and hardware-level barrier primitives, threads are physically unable to stage intermediate data for neighboring threads to read.

Overcoming the Limitation with Multi-Pass Computation

Because cross-thread communication within a single pass is fundamentally impossible under this design, algorithms requiring inter-thread dependency—such as reductions, cellular automata, or blur filters—must rely on multi-pass architectures:

  1. Pass 1: Threads compute intermediate values independently and write them to an output texture.
  2. State Transition: The execution pass completes, establishing an implicit global barrier across the entire GPU. The written output texture is rebound as a read-only input.
  3. Pass 2: A new kernel launches, where threads safely read the stabilized results produced by any thread from the preceding pass.

By chaining multiple execution passes (often implemented via ping-pong framebuffers), developers achieve cross-thread data propagation deterministically without violating GPU memory models.
