32-Bit Float Precision Limitations in GPU.js

GPU.js enables parallel computing in web browsers and Node.js by compiling JavaScript functions into WebGL shader language (GLSL). Because WebGL natively relies on 32-bit single-precision floating-point numbers (IEEE 754 standard), developers working with GPU.js inevitably encounter accuracy constraints that do not exist in standard 64-bit JavaScript. Understanding these precision boundaries—including significand limits, accumulation drift, catastrophic cancellation, and hardware inconsistencies—is essential for writing accurate computational kernels.

The IEEE 754 Single-Precision Format

Standard JavaScript uses 64-bit double-precision floats (Float64), offering 53 bits of mantissa (approximately 15 to 17 significant decimal digits). In contrast, GPU.js executes kernels using 32-bit single-precision floats (Float32), which structure bits as follows:

  • 1 bit for the sign
  • 8 bits for the exponent
  • 23 bits for the mantissa (significand)

This 23-bit mantissa allows for only 24 bits of precision (accounting for the implicit leading 1), which yields roughly 6 to 7 decimal digits of precision. Any continuous calculation requiring accuracy beyond the seventh significant digit will experience truncation or rounding artifacts.

Key Precision Limitations in GPU.js

1. Machine Epsilon and Inability to Represent Close Values

The machine epsilon for standard single-precision floats is approximately \(1.19 \times 10^{-7}\). If an algorithm adds a very small number to a relatively large number—where the ratio exceeds \(2^{24}\) (approx. \(16,777,216\))—the smaller number is effectively rounded down to zero. In iterative tasks such as gradient descent, particle simulations, or continuous integration, these small updates can be dropped completely.

2. Accumulation Error in Reductions

Parallel reductions, matrix multiplications, and large-array summations often accumulate hundreds of thousands of terms. Because single-precision rounding errors compound with every operation, summing large arrays in GPU.js can produce results that diverge substantially from equivalent 64-bit CPU implementations.

3. Catastrophic Cancellation

When subtracting two numbers that are nearly identical, the most significant digits cancel each other out, leaving only the least significant digits. Because 32-bit floats possess only 7 decimal digits of information, catastrophic cancellation strips away valid data rapidly, often leaving results dominated purely by rounding noise.

4. WebGL Precision Qualifiers (highp, mediump, lowp)

GPU.js relies on WebGL's highp precision qualifier to achieve 32-bit float accuracy. However, standard compliance varies across hardware:

  • Desktop GPUs: WebGL implementations almost uniformly grant full 32-bit IEEE 754 compliance for highp.
  • Mobile GPUs: Some mobile chipsets implement highp with as few as 16 bits of precision (the minimum allowed by the original WebGL specification) or omit strict IEEE 754 edge-case handling (such as subnormal numbers and exact NaN/Infinity behaviors).

5. Lack of Native 64-Bit Float (Double) Support

WebGL 1.0 and 2.0 do not natively support 64-bit integers or 64-bit floating-point numbers. Passing a Float64Array into a GPU.js kernel will automatically downcast values to 32-bit floats during texture encoding, causing an irreversible loss of precision before computation even begins.

Strategies for Mitigating Limitations

  • Data Normalization: Rescale data inputs so values remain close to a common order of magnitude, avoiding operations that combine extremely large and extremely small values.
  • Compensated Algorithms: Implement algorithms designed to reduce float drift, such as Kahan summation, directly inside GPU.js kernels.
  • Double-Float Emulation: For algorithms requiring 64-bit accuracy, emulate double precision using pairs of 32-bit floats (often referred to as float-float arithmetic) inside the kernel logic at the cost of execution speed.
