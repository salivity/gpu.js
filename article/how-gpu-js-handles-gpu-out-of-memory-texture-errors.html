How GPU.js Handles GPU Out-of-Memory Texture Errors

This article explores how the GPU.js library behaves when allocating computational textures that exceed hardware VRAM limits or maximum dimension boundaries. It breaks down the interaction between GPU.js and the underlying WebGL context, covers how errors like gl.OUT_OF_MEMORY and WebGL context loss are triggered, clarifies the limits of automatic CPU fallback during runtime memory exhaustion, and outlines necessary architectural strategies to prevent and handle memory failures.

WebGL Texture Allocation in GPU.js

GPU.js accelerates JavaScript calculations by compiling custom functions into GLSL shaders and executing them using WebGL (or WebGL2). Because GPUs process data through graphics pipelines, GPU.js encodes input arrays, matrices, and output targets as WebGL textures.

When a kernel is invoked, GPU.js queries the GPU to allocate framebuffers and textures matched to the dimensions of the input and expected output. This operation relies on the native graphics driver and the browser's WebGL implementation. Consequently, GPU.js does not manage raw VRAM directly; it delegates allocation requests down to the WebGL API.

Dimension Boundaries vs. Physical VRAM Limits

Memory failures during texture allocation in GPU.js stem from two distinct constraints:

  1. Hardware Dimension Caps (MAX_TEXTURE_SIZE): WebGL enforces a strict upper limit on the width and height of any individual texture, typically 4096, 8192, or 16384 pixels depending on the GPU. If an array's computed texture layout exceeds gl.getParameter(gl.MAX_TEXTURE_SIZE), allocation fails immediately at the WebGL state validation layer.
  2. Physical VRAM Depletion: Even if dimensions fall within legal hardware limits, the total volume of simultaneous allocations can exceed the available video memory. This occurs when large matrices, multiple intermediate pipeline textures, or concurrent browser processes consume all available VRAM.

How GPU.js Reacts to Out-of-Memory Conditions

GPU.js does not provide an internal virtual memory manager or paging system. When allocating an oversized texture fails due to memory exhaustion, the failure cascades through distinct stages:

WebGL Allocation Failure (gl.OUT_OF_MEMORY)

When an allocation exceeds capacity, the native driver rejects the call (such as gl.texImage2D or gl.renderbufferStorage). The graphics pipeline sets an internal error flag to gl.OUT_OF_MEMORY. WebGL operations following this call fail silently or return null references to textures and framebuffers.

WebGL Context Loss

In most modern browsers, failing to allocate essential graphics memory or causing a severe driver-level stall triggers a WebGL context loss (webglcontextlost). The browser forcibly terminates the WebGL context to prevent system-wide instability or GPU hangs. GPU.js loses its handle to the GPU pipeline, invalidating all currently compiled kernels and loaded textures.

JavaScript Exceptions

Because GPU.js expects valid texture bindings to execute its draw calls, the failure of an allocation or a lost context results in runtime exceptions. Typical symptoms include:

  • Uncaught errors during framebuffer binding.
  • Failures within internal compilation routines (e.g., Error: Error compiling shader).
  • Generic WebGL execution errors thrown when invoking the kernel runner.

GPU.js does not catch these runtime OOM exceptions automatically to re-slice or page the textures across multiple passes.

The Limitations of CPU Fallback During Runtime OOM

GPU.js includes a CPU fallback mode that executes computational kernels using pure JavaScript when WebGL is unsupported. However, this fallback mechanism is primarily evaluated during initialization or kernel compilation.

If a kernel is initialized in GPU mode and subsequently crashes mid-run due to an oversized texture allocation or VRAM exhaustion, GPU.js does not automatically catch the error, re-route the input data, and re-execute the job on the CPU. The developer must explicitly design fault tolerance to catch the runtime failure and instantiate an alternate CPU kernel.

Mitigating Out-of-Memory Errors in GPU.js

To avoid texture allocation failures when working with large datasets, implementations must incorporate explicit memory safety patterns:

  • Chunking and Tiling: Split massive datasets into smaller sub-matrices or batches. Execute individual kernel passes on smaller slices that comfortably fit within VRAM, then assemble the results.
  • Inspect Hardware Limits: Query gpu.internalKernels or inspect the WebGL context directly via gl.getParameter(gl.MAX_TEXTURE_SIZE) before defining texture layouts to verify dimension boundaries.
  • Pipeline Cleanup: Call .destroy() on kernels, inputs, and textures that are no longer needed. Holding references to textures produced by previous kernel runs prevents the garbage collector and WebGL from releasing backing VRAM.
  • Wrap Kernel Runs with Try/Catch: Wrap memory-intensive kernel executions in standard error handling blocks to catch WebGL context losses and invoke a CPU-based instance (new GPU({ mode: 'cpu' })) as a safety net.
