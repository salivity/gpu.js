Why Array Methods Like Map Do Not Work in GPU.js

GPU.js allows developers to accelerate computational tasks by translating JavaScript functions into WebGL shader code to run massively parallel operations on the GPU. However, standard JavaScript methods like Array.prototype.map, filter, and reduce throw errors when called inside a GPU.js kernel. This limitation occurs because the GPU execution environment is not a JavaScript engine; instead, GPU.js transpiles a strictly limited subset of JavaScript into native shading languages like GLSL (OpenGL Shading Language), where dynamic prototypes and higher-order functions do not exist.

Compilation Replaces JavaScript Execution

When you define a kernel in GPU.js, the library does not pass your function to a JavaScript runtime like Google V8 or SpiderMonkey. Instead, it reads the JavaScript function's Abstract Syntax Tree (AST) and parses the syntax directly into GLSL source code.

Because the code ultimately executes on the graphics card hardware via WebGL, there is no underlying JavaScript Virtual Machine, dynamic runtime, or prototype chain present during execution. Built-in prototypes, including Array.prototype, belong to the ECMAScript host environment and simply do not exist within compiled GPU shaders.

Shaders Require Static Types and Fixed Memory

Standard array prototype methods rely heavily on dynamic behaviors native to JavaScript:

  • Dynamic Memory Allocation: Methods like .map() dynamically allocate memory for a new array on the heap and adjust size as items are returned. GPUs, by contrast, require predetermined memory buffers. They cannot dynamically allocate arbitrary memory addresses during shader execution.
  • Garbage Collection: JavaScript relies on automatic memory management and garbage collection. GPU hardware does not support runtime garbage collection.
  • Higher-Order Functions: Methods like .map() accept callback functions. GLSL does not support function pointers, closures, or passing functions as arguments.

The SIMD/SIMT Architecture Mismatch

The functional design of Array.prototype.map() conflicts directly with how GPU hardware processes data. Standard JavaScript maps iterate through array elements sequentially on a single thread (or iteratively via background threads).

GPUs operate under a Single Instruction, Multiple Threads (SIMT) architecture. Instead of taking an existing array and iterating over it to produce a new structure, a GPU.js kernel executes thousands of instances of your function concurrently. Each concurrent thread calculates the output for a single cell based on its coordinates, accessible via this.thread.x, this.thread.y, and this.thread.z.

The Alternative Approach in GPU.js

To perform transformations that would typically use Array.prototype.map, developers must rely on the thread-based indexing model native to GPU programming:

  • Output Dimensions: Define the kernel's output shape using the .setOutput([width, height]) configuration.
  • Index Mapping: Read directly from input buffers using array indexing based on thread position (e.g., inputArray[this.thread.x]).
  • Deterministic Control Flow: Use standard, fixed-bound for loops and basic arithmetic supported by the GPU.js syntax subset rather than declarative functional iterations.
