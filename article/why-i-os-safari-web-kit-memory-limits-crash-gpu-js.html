Why iOS Safari WebKit Memory Limits Crash gpu.js

Running high-performance computations on iOS Safari using gpu.js frequently leads to abrupt tab crashes where the browser displays the message, "A problem repeatedly occurred with this webpage." These crashes are not standard JavaScript runtime errors, but are forced process terminations executed by iOS's WebKit memory management system. This article examines how WebKit’s strict per-process memory limits, WebGL texture buffer overhead, and deferred garbage collection combine to trigger these sudden crashes, along with practical methods to prevent them.

WebKit's Jetsam Memory Enforcement

iOS manages system resources through Jetsam, an aggressive low-memory killer. Unlike desktop operating systems that rely heavily on swap space, iOS keeps all active tasks in physical RAM. To prevent an individual web page from exhausting device resources and crashing the operating system, WebKit assigns a strict memory footprint ceiling to each individual WebContent process.

Depending on the device hardware, a single Safari tab is often restricted to between 1 GB and 1.5 GB of RAM, with older or budget devices (such as base iPads or older iPhones) restricted to significantly less. If a tab exceeds this threshold for even a few milliseconds, the operating system kernel kills the WebContent process immediately. Because this termination happens at the OS level, JavaScript cannot catch it with a try...catch block.

How gpu.js Multiplies Memory Footprints

gpu.js compiles high-level JavaScript functions into GLSL shaders, running parallel calculations on the mobile GPU via WebGL. While this yields significant performance gains, it inherently inflates the tab's memory footprint through several interconnected mechanisms:

  1. Floating-Point Texture Overhead: WebGL pipelines in gpu.js transfer and store numerical arrays using textures. To maintain mathematical precision, gpu.js utilizes 32-bit floating-point textures (OES_texture_float). These textures require substantially more memory than typical image-based WebGL textures. Large matrices or repeated calculations quickly produce hundreds of megabytes of raw uncompressed buffer data.
  2. Duplicated Memory Buffers: When passing data into a gpu.js kernel and retrieving the result, data often exists simultaneously in three places: standard JavaScript heap memory (typed arrays), browser-managed WebGL staging memory, and dedicated GPU VRAM. In unified memory architectures like Apple Silicon, all these allocations draw from the same physical RAM pool, accelerating the trajectory toward the WebKit memory ceiling.
  3. Decoupled Garbage Collection: JavaScript's garbage collector operates independently of native WebGL resource management. When a gpu.js kernel or texture reference is dropped in JavaScript, the underlying WebGL textures and framebuffer objects in the native WebKit layer may remain allocated until a major garbage collection cycle occurs. During intensive iterative loops, allocations outpace garbage collection, causing a momentary spike that breaches the memory threshold.

Preventing Spontaneous WebKit Crashes

To run gpu.js reliably on iOS devices without triggering WebKit terminations, developers must actively manage the lifecycle of WebGL resources rather than relying on automatic cleanup:

  • Explicitly Destroy Resources: Do not let textures go out of scope naturally. Manually call the .destroy() method on kernels, textures, and contexts when they are no longer required to immediately release native allocations.
  • Reuse Kernel Instances: Avoid instantiating gpu.js kernels inside application loops or render loops. Create kernels once globally and update their uniform values and input arrays dynamically.
  • Pipeline Mode Management: When chaining computations using gpu.js pipeline mode ({ pipeline: true }), ensure intermediate textures are consumed and released promptly. Pipelining keeps textures in GPU memory, which improves execution speed but compounds the total memory footprint if chains are long.
  • Tuning Matrix Dimensions: Scale computation batches based on client hardware. Detecting mobile Safari user agents and reducing output dimensions prevents oversized allocations that immediately trigger memory thresholds.
