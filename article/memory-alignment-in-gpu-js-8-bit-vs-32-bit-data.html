Memory Alignment in GPU.js: 8-Bit vs 32-Bit Data

This article explores how gpu.js handles memory alignment and texture packing when processing 8-bit and 32-bit data through WebGL shaders. Because GPUs rely on strictly aligned memory strides to maximize throughput, data types of varying byte widths cannot be treated identically. The following sections explain the underlying WebGL memory rules, the structural packing strategies used for 8-bit versus 32-bit payloads, and how gpu.js ensures data integrity across diverse hardware architectures.

The WebGL Alignment Model

Under the hood, gpu.js compiles JavaScript functions into WebGL fragment shaders and passes data to the GPU in the form of 2D textures. WebGL enforces strict pixel store parameters, most notably gl.UNPACK_ALIGNMENT, which defaults to 4 bytes. This default alignment requires that the start of every row of pixel data in host memory aligns with a multiple of 4 bytes.

When mapping CPU-allocated typed arrays to GPU textures, mismatched alignments between array element sizes and row widths can lead to corrupt uploads or runtime crashes if not managed explicitly.

Managing 32-Bit Data

Standard calculations in gpu.js default to 32-bit IEEE 754 floating-point numbers. Handling 32-bit data aligns naturally with modern GPU memory architectures, but implementation details vary based on WebGL capabilities:

  • WebGL 2 and Float Extensions: When native floating-point textures are supported (e.g., gl.RGBA32F or gl.R32F), 32-bit floats are written directly to texture memory. Because a single 32-bit float is 4 bytes, row boundaries naturally align with the default 4-byte stride requirement without requiring software-level byte shifting.
  • WebGL 1 Fallback (Byte Encoding): On platforms lacking native float texture rendering support, gpu.js encodes each 32-bit float across the four 8-bit channels (Red, Green, Blue, Alpha) of a standard gl.RGBA texture. This mathematical packing splits the 32-bit mantissa and exponent across four 1-byte components, producing a single 4-byte pixel that automatically satisfies the 4-byte alignment rule.

Managing 8-Bit Data

Handling 8-bit data (such as Uint8Array or standard image pixel data) presents different alignment challenges:

  • Four-Channel Aggregation: When 8-bit data is supplied as RGBA values, four contiguous 8-bit integers combine into a 32-bit (4-byte) structure. In this layout, each pixel matches the 4-byte boundary naturally, preventing misaligned stride offsets between texture rows.
  • Single-Channel and Flat Byte Arrays: When single-channel 8-bit arrays are uploaded, arbitrary row widths can easily violate the 4-byte boundary. To prevent reading out-of-bounds or shifted bytes, gpu.js alters the unpack state (using gl.pixelStorei(gl.UNPACK_ALIGNMENT, 1)) or reshapes the underlying 1D array into padded 2D textures where each row length is a multiple of 4.

Texture Reshaping and Memory Padding

GPUs cannot efficiently address arbitrary 1D arrays of dynamic sizes. gpu.js maps 1D and irregularly sized input arrays into rectangular 2D textures.

When the total count of elements does not evenly form a rectangular texture aligned to GPU hardware constraints, gpu.js pads the internal texture dimensions. The generated GLSL shader code includes boundary checks that ignore these padded, unaligned memory addresses, ensuring that memory reads and writes map exclusively to valid input indices while preserving cache-friendly memory strides.
