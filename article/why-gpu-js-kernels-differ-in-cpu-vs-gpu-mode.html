Why GPU.js Kernels Differ in CPU vs GPU Mode

GPU.js allows developers to write complex parallel computations in JavaScript that compile to WebGL shaders on the GPU, while providing a pure JavaScript fallback for CPU execution. While the library strives for parity between these two runtime environments, identical kernel code can yield divergent results or unexpected behaviors when switching between modes. These discrepancies primarily stem from differences in floating-point precision, static versus dynamic typing, array boundary handling, and underlying hardware implementations of mathematical functions.

Floating-Point Precision

The most frequent cause of calculation divergence is precision. JavaScript running on the CPU natively uses IEEE 754 double-precision 64-bit floating-point numbers. Conversely, GPU mode transpiles your code into WebGL/GLSL shaders, which typically execute using single-precision 32-bit (or even 16-bit medium-precision) floats depending on device capabilities and WebGL settings. Cumulative operations, such as deep iterative loops, trigonometric reductions, or matrix multiplications, can rapidly accumulate rounding errors that cause GPU output to drift significantly from CPU output.

Type Coercion and Strictness

JavaScript is weakly and dynamically typed, allowing operations like adding an integer to a float or implicit boolean-to-number casting without warnings. GLSL (OpenGL Shading Language), the target language for GPU mode, is strictly and statically typed. While the GPU.js compiler attempts to infer and coerce types automatically, ambiguous syntax can behave differently. For instance, an expression like 1 / 2 evaluates to 0.5 in JavaScript on the CPU, but if parsed as integer division in GLSL, it evaluates to 0.

Array Bounds and Out-of-Range Access

When indexing an array beyond its declared boundaries in CPU mode, JavaScript safely returns undefined (which evaluates to NaN in arithmetic expressions). In GPU mode, arrays are mapped directly to WebGL textures. Reading outside the boundary of a texture does not yield undefined; instead, depending on the texture wrapping mode configured in the GPU pipeline, it may return clamped edge values, wrapped-around values from the other side, or raw memory artifacts, completely altering the calculation's state.

Hardware-Level Math Implementations

Functions provided by JavaScript's standard Math library (such as Math.sin(), Math.pow(), and Math.sqrt()) map directly to native GLSL functions on the GPU. Modern GPU architectures prioritize speed over extreme accuracy for trigonometric and transcendental functions, often relying on hardware lookup tables and specialized approximations. As a result, the low-level bit representation of a math operation on the CPU will rarely match the GPU's hardware-accelerated equivalent precisely.

Branching and Loop Constraints

CPUs excel at complex branching and non-deterministic loops, executing conditional paths with low latency. GPUs, however, execute threads in parallel lockstep (warps or wavefronts). In GPU mode, loops with dynamic, runtime-determined termination conditions may fail to compile or may execute every branch of a conditional statement internally, masking off unselected results. If a kernel contains complex control flow or early returns that the transpiler cannot map cleanly to GLSL, CPU mode may execute the logic as intended while GPU mode produces execution stalls, unexpected branch evaluations, or silent failures.
