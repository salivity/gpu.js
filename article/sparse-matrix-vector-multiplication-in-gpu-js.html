Sparse Matrix-Vector Multiplication in GPU.js

Sparse matrix-vector multiplication (SpMV) is a foundational computational kernel in scientific computing, machine learning, and graph analytics, where matrices contain predominantly zero values. In gpu.js, a JavaScript library that compiles JavaScript functions into WebGL shaders, implementing SpMV requires mapping compressed matrix formats into GPU-friendly textures or flat arrays to avoid the memory overhead and wasted operations of dense computation. This article examines how SpMV is implemented in gpu.js using Compressed Sparse Row (CSR) formatting, how the kernel manages row-parallel execution, and the primary optimization techniques applied to minimize memory latency and thread divergence.

Representing Sparse Matrices for GPU Kernels

Dense matrix representations allocate memory for every element, which leads to substantial GPU memory waste and inefficient memory bandwidth usage. To perform SpMV efficiently in gpu.js, the matrix must be converted into a sparse representation on the CPU before transfer. The standard format for this operation is Compressed Sparse Row (CSR), defined by three 1D arrays:

  1. Values (val): A contiguous array containing all non-zero floating-point numbers.
  2. Column Indices (col): An array matching val in length, indicating the column index of each non-zero value.
  3. Row Pointers (ptr): An array of length N + 1 (where N is the number of rows), indicating the index in val where each row begins and ends.

Because gpu.js runs computations via WebGL shaders, passing these three 1D arrays alongside the dense vector enables the GPU to iterate exclusively through non-zero entries.

Kernel Implementation

In gpu.js, an SpMV kernel is structured so that each GPU thread corresponds to one row of the resulting vector. The kernel outputs an array with an execution dimension equal to the total number of rows.

const spmvKernel = gpu.createKernel(function(values, colIndices, rowPointers, vector) {
    let row = this.thread.x;
    let start = rowPointers[row];
    let end = rowPointers[row + 1];
    let sum = 0;

    for (let i = start; i < end; i++) {
        sum += values[i] * vector[colIndices[i]];
    }

    return sum;
}).setOutput([rowCount]);

Each thread evaluates this.thread.x to determine its target row, reads the start and end boundary indices from the rowPointers array, and executes a loop that multiplies each non-zero element by the corresponding component of the input vector.

Optimization Strategies

While the basic CSR implementation significantly reduces compute cycles relative to dense multiplication, executing it on WebGL hardware introduces specific performance bottlenecks. Optimizing SpMV in gpu.js requires resolving hardware-level constraints:

1. Managing Thread Divergence

The primary drawback of standard CSR on GPUs is load imbalance. GPU threads run in lockstep groups (warps or wavefronts). If adjacent rows have vastly different numbers of non-zero entries, threads with fewer non-zeros idle while waiting for the longest row in the warp to finish.

  • ELLPACK / Hybrid Formats: To mitigate divergence, matrices can be transformed into the ELLPACK format, which pads rows with zeros to an identical length, or a hybrid (HYB) format that handles the dense portion via ELLPACK and long outliers via CSR. This homogenizes loop bounds and eliminates branch divergence across adjacent shader invocations.
  • Row Sorting: Rows can be permuted on the CPU by non-zero count prior to executing the kernel. Grouping rows of similar lengths together ensures threads within the same execution block complete roughly at the same time.

2. Vector Caching and Coalesced Reads

In the inner loop, accessing vector[colIndices[i]] generates indirect, non-contiguous memory access patterns that can lead to cache misses.

  • Pre-arranging column indices through bandwidth-reduction algorithms (such as Reverse Cuthill-McKee) keeps non-zero entries close to the diagonal, localizing reads to the dense vector.
  • Where supported, structuring the dense vector data as a 2D texture instead of a 1D linear array in WebGL allows hardware texture caches to exploit spatial locality during lookups.

3. Data Transfer Overhead

Data marshaling between the CPU (JavaScript engine) and the GPU (WebGL context) often outweighs computation time for single-run SpMV operations. To maximize throughput, inputs should be initialized as typed arrays (e.g., Float32Array, Int32Array) and marked as immutable or reused across multiple iterations (such as in iterative solvers like Conjugate Gradient), avoiding redundant CPU-to-GPU data transfers.
