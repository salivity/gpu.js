Computing Fluid Forces with Neighbor Loops in GPU.js

Calculating viscosity and surface tension forces in particle-based fluid simulations using neighbor loops in gpu.js is entirely possible. In Smoothed Particle Hydrodynamics (SPH), both forces depend on the relative positions and velocities of surrounding particles within a defined smoothing radius. While gpu.js translates JavaScript functions into WebGL shaders, achieving these calculations requires a gather-based architecture that navigates WebGL loop constraints, texture-based memory layouts, and spatial partitioning strategies.

The Physics of Viscosity and Surface Tension

Particle-based fluid dynamics simulate fluids as discrete interpolation points. Interaction forces are computed based on neighboring particles within a support radius \(h\):

  1. Viscosity Force: Viscosity acts as a diffusion of momentum that resists relative motion between adjacent fluid layers. It is calculated by taking the Laplacian of the velocity field. In an SPH framework, this is typically approximated by summing the velocity differences between a target particle \(i\) and its neighbor \(j\), scaled by fluid mass, density, and the second derivative of a smoothing kernel (such as the SPH viscosity kernel).
  2. Surface Tension: Surface tension minimizes the surface area of the fluid. It is commonly implemented using the Color Field method, where each particle has a color value of 1. The gradient of this field yields the surface normal vector, and the Laplacian of the field yields the surface curvature. Particles at the free surface experience an inward-pointing restorative force proportional to this curvature.

Implementing Neighbor Loops in gpu.js

Because gpu.js runs on top of WebGL compute abstractions, memory writing is restricted: a kernel cannot write to arbitrary memory locations ("scatter"). Instead, it must use a "gather" approach, where each thread computes the forces acting on a single particle by querying its neighbors.

1. The All-Pairs Approach (\(O(N^2)\))

For small simulations (typically under 2,000 to 4,000 particles), an exhaustive loop is the most straightforward solution. The kernel iterates through all particles in the system:

const calculateForces = gpu.createKernel(function(positions, velocities, densities, numParticles, h, viscosityCoeff) {
    const i = this.thread.x;
    let forceX = 0;
    let forceY = 0;

    const px = positions[i][0];
    const py = positions[i][1];
    const vx = velocities[i][0];
    const vy = velocities[i][1];

    for (let j = 0; j < 2048; j++) {
        if (j < numParticles && i !== j) {
            const dx = px - positions[j][0];
            const dy = py - positions[j][1];
            const dist = Math.sqrt(dx * dx + dy * dy);

            if (dist < h && dist > 0.0001) {
                // Viscosity computation using a standard SPH Laplacian kernel
                const q = dist / h;
                const kernelLaplacian = (45 / (Math.PI * Math.pow(h, 6))) * (h - dist);
                const viscFactor = viscosityCoeff * (1 / densities[j]) * kernelLaplacian;

                forceX += (velocities[j][0] - vx) * viscFactor;
                forceY += (velocities[j][1] - vy) * viscFactor;
            }
        }
    }

    return [forceX, forceY];
}).setOutput([numParticles]);

2. Spatial Grid Partitioning (\(O(N)\))

For larger simulations, exhaustive loops become a performance bottleneck. To optimize, particles must be sorted into uniform spatial grid cells:

  • The simulation space is divided into a grid where each cell has a side length equal to the smoothing radius \(h\).
  • Particles are mapped to cell coordinates \((cx, cy) = (\lfloor x/h \rfloor, \lfloor y/h \rfloor)\).
  • Instead of iterating through all particles, the gpu.js kernel iterates through the 9 neighboring cells (or 27 in 3D).
  • Because gpu.js lacks dynamic arrays, neighbor grids must be stored in static-width textures (e.g., fixed maximum particles per cell) or managed through a sorted index lookup buffer generated via GPU radix sort.

Constraints and Technical Challenges in gpu.js

When implementing fluid neighbor loops in gpu.js, several platform-specific constraints must be managed:

  • Static Loop Bounds: WebGL shaders often require loop bounds to be constant integers at compile time to allow unrolling. Variable-length loops can cause compilation failures or extreme driver overhead. When writing loops in gpu.js, define the loop limit using a fixed constant that matches the maximum supported particle capacity, then use an internal if check against the dynamic particle count.
  • Multi-Pass Dependencies for Surface Tension: Surface tension cannot be solved accurately in a single neighbor loop. Calculating the normal requires a first neighbor pass (gradient of the color field). Calculating curvature requires a second neighbor pass (divergence of the normals). In gpu.js, this necessitates splitting the physics update into chained kernels where the output texture of the normal calculation is fed as an input texture into the surface tension force kernel.
  • Floating-Point Precision: SPH calculations are sensitive to precision limits. Force equations often divide by small distances or densities. In gpu.js, ensure float textures are enabled and add a small epsilon value (\(\epsilon \approx 10^{-5}\)) to distance denominators to prevent NaN artifacts from propagating across frames.
