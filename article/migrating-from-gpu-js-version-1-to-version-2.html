Migrating from GPU.js Version 1 to Version 2

This guide outlines the critical steps required to migrate an existing codebase from GPU.js version 1 to version 2. Upgrading to version 2 introduces significant performance optimizations, a modernized module structure, stricter dimension management, and refined APIs for kernels, custom functions, and pipeline modes. By systematically updating your imports, dimension definitions, kernel configurations, and graphical outputs, you can smoothly transition your project to the updated architecture.

Step 1: Update the Dependency and Import Syntax

Version 2 modernizes its module export structure. In version 1, the library was often imported as a default export. In version 2, you must destructure the GPU class from the package.

Version 1:

const GPU = require('gpu.js');
const gpu = new GPU();

Version 2:

const { GPU } = require('gpu.js');
const gpu = new GPU();

For browser environments using ES modules:

import { GPU } from 'gpu.js';
const gpu = new GPU();

Step 2: Standardize Kernel Dimension Ordering

In GPU.js v1, multi-dimensional array mapping sometimes caused ambiguity regarding row-major and column-major order. Version 2 strictly standardizes output dimensions to follow [x, y, z] coordinate mapping, where:

  • x maps to width (this.thread.x)
  • y maps to height (this.thread.y)
  • z maps to depth (this.thread.z)

Ensure your setOutput calls align with this convention:

// Creates a 2D grid: 512 width (x) by 256 height (y)
const kernel = gpu.createKernel(function() {
    return this.thread.x + this.thread.y;
}).setOutput([512, 256]);

If your v1 implementation inverted array indexes when iterating over nested outputs, invert the output arguments back to [width, height] to match standard Cartesian coordinates.

Step 3: Modernize Custom Function Declarations

Version 1 required using gpu.addFunction() directly on the GPU instance before compiling a kernel. Version 2 allows you to pass functions directly via kernel settings or through strongly typed declarations.

Version 1:

gpu.addFunction(function customAdd(a, b) {
    return a + b;
});

Version 2: You can still register global functions via gpu.addFunction(), but you can also scope them directly to specific kernels using the functions property:

function customAdd(a, b) {
    return a + b;
}

const kernel = gpu.createKernel(function(x, y) {
    return customAdd(x[this.thread.x], y[this.thread.x]);
}, {
    functions: [customAdd]
}).setOutput([100]);

If your function returns or accepts specific argument types that the compiler struggles to infer, declare the signature explicitly:

gpu.addFunction(customAdd, {
    argumentTypes: { a: 'Float', b: 'Float' },
    returnType: 'Float'
});

Step 4: Refactor Graphical Kernels and Canvas Integration

In version 1, rendering to a canvas often relied on implicit canvas binding or varying methods depending on the browser context. Version 2 unifies canvas handling under explicit kernel settings.

Replace deprecated graphical settings with the following pattern:

const kernel = gpu.createKernel(function() {
    this.color(1, 0, 0, 1);
}, {
    graphical: true,
    output: [512, 512]
});

kernel();

// Access the compiled canvas directly from the kernel
document.body.appendChild(kernel.canvas);

Step 5: Update Pipeline Mode and Texture Handling

Version 2 overhauls the pipeline API to make multi-pass algorithms faster by keeping data on the GPU as textures.

To pass textures directly from one kernel to another without reading data back to the CPU:

const firstKernel = gpu.createKernel(function(data) {
    return data[this.thread.x] * 2;
})
.setOutput([100])
.setPipeline(true);

const secondKernel = gpu.createKernel(function(texture) {
    return texture[this.thread.x] + 1;
})
.setOutput([100]);

const textureResult = firstKernel(inputData);
const finalResult = secondKernel(textureResult);

If you need to extract the raw JavaScript array from a pipeline result texture, use toArray():

const rawArray = textureResult.toArray();

Step 6: Verify Headless Node.js Environments

If running GPU.js server-side, version 2 requires explicit management of the underlying WebGL context. Ensure you have installed the appropriate headless bindings:

npm install gl

When initializing GPU.js in Node.js, version 2 will automatically detect and bind gl. If you encounter context errors, explicitly specify the fallback mode:

const gpu = new GPU({ mode: 'gpu' }); // Will throw if WebGL is unavailable instead of silently falling back to CPU

Run your test suite across both GPU and CPU modes (mode: 'cpu') to verify that calculations remain numerically consistent between backends.
