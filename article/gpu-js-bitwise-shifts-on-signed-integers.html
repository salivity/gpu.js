GPU.js Bitwise Shifts on Signed Integers

This article explores how GPU.js handles bitwise shift-left (<<) and shift-right (>>) operators on signed integers when transpiling JavaScript code into GPU-accelerated shaders. It details how the library maps JavaScript AST operations to GLSL, the role of WebGL 2's native integer support, how sign extension and bit overflow behave, and key differences to watch out for between CPU and GPU execution.

AST Parsing and Transpilation to GLSL

GPU.js processes JavaScript kernel functions by parsing them into an Abstract Syntax Tree (AST) using Acorn. When the parser encounters binary expressions using the shift-left (<<) or shift-right (>>) operators, it translates these expressions into corresponding OpenGL Shading Language (GLSL) code.

JavaScript inherently treats operands of bitwise operations as 32-bit signed integers. To replicate this behavior accurately on the GPU, GPU.js targets WebGL 2 (GLSL ES 3.00), which introduced native support for 32-bit signed integers (int) and bitwise operators. In legacy WebGL 1 environments, where integers are emulated via floating-point numbers, bitwise shifts are unsupported or require cumbersome mathematical emulation via multiplication and division by powers of two. Consequently, native bitwise shifts in GPU.js require a WebGL 2 context.

Handling Shift-Left (<<)

For signed integers, the shift-left operator behaves identically in GLSL ES 3.00 as it does in standard JavaScript:

  • Bit Shift: The bits of the 32-bit signed integer are shifted to the left by the specified number of positions.
  • Zero Padding: The vacant bits on the right (least significant bits) are filled with zeros.
  • Overflow: Bits shifted beyond the 32nd position are discarded. If a bit shifts into the 31st position (the sign bit), the sign of the integer changes accordingly, matching two's complement signed integer behavior.

In generated WebGL 2 shaders, a << b directly becomes a << b where both operands are typed as signed int.

Handling Shift-Right (>>)

JavaScript differentiates between the arithmetic shift-right (>>) and the logical (zero-fill) shift-right (>>>). For signed integers, GPU.js maps the >> operator directly to GLSL's signed shift-right:

  • Sign Propagation (Arithmetic Shift): Because the operand is defined as a signed 32-bit int, the hardware executes an arithmetic right shift. The most significant bit (the sign bit) is copied into the vacant positions on the left.
  • Negative Numbers: If the integer is negative (sign bit is 1), shifting right fills the left-hand bits with ones, preserving the negative sign. This matches the behavior of JavaScript's >>.
  • Positive Numbers: If the integer is positive (sign bit is 0), the vacated bits are filled with zeros.

Discrepancies Between JavaScript and GLSL

While GPU.js provides a direct translation for these operators, differences between JavaScript's specification and GLSL hardware execution introduce subtle edge cases:

  1. Shift Distance Masking: In JavaScript, the shift count is masked to five bits (count & 0x1F), meaning shifting by 32 is equivalent to shifting by 0, and shifting by 33 is equivalent to shifting by 1. In GLSL ES 3.00, shifting by an amount less than zero or greater than or equal to the bit-width (32) results in undefined behavior depending on the underlying GPU architecture.
  2. Type Casting: GPU.js enforces strict typing in GLSL. If non-integer variables (such as floats) are shifted, GPU.js must explicitly cast them using int() before the operation can execute, truncating any fractional components.
