Parallel Gabor Filter Banks Using gpu.js

Gabor filter banks are widely used in computer vision for texture feature extraction by capturing localized frequency and orientation data across an image. This article explores whether and how multiple Gabor filters across varying angles can be parallelized using gpu.js, a JavaScript library that compiles code into WebGL shaders. By exploiting GPU architecture, developers can compute spatial convolutions across multiple orientations simultaneously, transforming computationally heavy texture extraction pipelines into high-performance, real-time web applications.

The Suitability of Gabor Filtering for GPU Parallelization

Gabor filtering is inherently parallel. A standard 2D Gabor filter operates as a linear filter that modulates a sinusoidal plane wave with a Gaussian envelope. When applied across multiple orientations (\(\theta\)) and frequencies (\(\lambda\)), the filtering process involves convolving the input image with several discrete kernels.

Each pixel’s response to a specific filter depends solely on the local neighborhood surrounding that pixel and is entirely independent of other pixels. Furthermore, each filter orientation is independent of the others. This satisfies the definition of an embarrassingly parallel workload:

  • Spatial Independence: Every output pixel \((x, y)\) can be evaluated independently.
  • Filter Independence: Every angle \(\theta\) can be evaluated without relying on the results of other orientations.

Because gpu.js maps computational threads directly to GPU execution units via WebGL fragment shaders, it is exceptionally well-suited for this two-level parallelism.

Structuring the Parallel Pipeline in gpu.js

In traditional CPU implementations, filtering across multiple angles typically requires a nested loop: an outer loop iterating through each orientation and inner loops traversing the image rows and columns. In gpu.js, these loops can be collapsed into a single 3D compute kernel.

1. Dimension Mapping

By defining the output dimensions of the gpu.js kernel as a 3D array [imageWidth, imageHeight, numberOfAngles], gpu.js maps the computation across a 3D thread space:

  • this.thread.x corresponds to the pixel's \(x\)-coordinate.
  • this.thread.y corresponds to the pixel's \(y\)-coordinate.
  • this.thread.z corresponds to the angle/filter index.

2. Kernel Generation vs. Dynamic Mathematical Evaluation

There are two approaches to computing the filter responses inside gpu.js:

  • Precomputed Kernel Textures: Generate the 2D Gabor masks on the CPU, upload them to the GPU as arrays or textures, and perform a straightforward convolution using this.thread.z to sample from the corresponding kernel. This approach is optimal when using large filter sizes, as it minimizes mathematical evaluations per thread.
  • On-the-Fly Calculation: Directly calculate the Gabor equation within the shader function for each neighbor in the convolution window. Because modern GPUs excel at floating-point arithmetic (trigonometric functions like sin and cos), calculating the kernel mathematically on the fly avoids texture lookups, potentially reducing memory bandwidth bottlenecks.

Implementation Architecture

A basic multi-angle Gabor extractor in gpu.js follows this design:

const { GPU } = require('gpu.js');
const gpu = new GPU();

const kernelRadius = 4; // 9x9 kernel
const kernelSize = kernelRadius * 2 + 1;
const orientations = [0, Math.PI / 4, Math.PI / 2, (3 * Math.PI) / 4];
const lambda = 4.0; // Wavelength
const sigma = 2.0;  // Gaussian envelope spread
const gamma = 0.5;  // Spatial aspect ratio

const gaborFilterBank = gpu.createKernel(function(image, angles, lambda, sigma, gamma, radius) {
    const x = this.thread.x;
    const y = this.thread.y;
    const angleIndex = this.thread.z;
    const theta = angles[angleIndex];

    let sum = 0.0;

    for (let ky = -radius; ky <= radius; ky++) {
        for (let kx = -radius; kx <= radius; kx++) {
            // Coordinate rotation relative to orientation
            const xPrime = kx * Math.cos(theta) + ky * Math.sin(theta);
            const yPrime = -kx * Math.sin(theta) + ky * Math.cos(theta);

            // Gabor equation
            const gaussian = Math.exp(-(xPrime * xPrime + gamma * gamma * yPrime * yPrime) / (2.0 * sigma * sigma));
            const sinusoid = Math.cos((2.0 * Math.PI * xPrime) / lambda);
            const weight = gaussian * sinusoid;

            // Sample image with boundary clamping
            const pixel = image[y + ky][x + kx];
            sum += pixel * weight;
        }
    }

    return sum;
})
.setOutput([imageWidth, imageHeight, orientations.length]);

Performance Considerations

While gpu.js provides significant acceleration, optimal throughput requires addressing key architectural constraints:

  • Memory Transfer Overhead: Moving high-resolution images between the CPU (RAM) and GPU (VRAM) introduces latency. To maximize efficiency, keep the input data on the GPU by chaining operations if further texture analysis or classification is required.
  • Kernel Size Limits: Convolution in the spatial domain scales quadratically (\(O(K^2)\)) with the kernel dimension. For large Gabor kernels (e.g., sizes exceeding \(31 \times 31\)), the spatial loop becomes costly. In such cases, frequency-domain multiplication via a GPU-accelerated Fast Fourier Transform (FFT) is preferred over direct spatial convolution.
  • Texture Format and Precision: By default, gpu.js utilizes 32-bit floating-point textures when supported by WebGL. Ensure that hardware precision extensions are available in the target environment to maintain numerical stability during feature extraction.
