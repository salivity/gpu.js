WebGL Out of Memory Errors in gpu.js Explained

WebGL out of memory (OOM) errors during large batch execution in gpu.js occur when computation demands exceed the physical or browser-allocated GPU memory. Because gpu.js maps high-dimensional JavaScript arrays into 2D WebGL textures for parallel processing, processing massive datasets pushes the limits of GPU texture dimensions, VRAM capacity, and the browser’s automatic garbage collection. Understanding the mechanics of texture allocation, kernel lifecycle management, and browser resource quotas reveals why these failures happen and how to prevent them.

1. Inefficient Garbage Collection and Texture Leaking

JavaScript uses an automated garbage collector that monitors system RAM, but it lacks direct visibility into GPU VRAM. When a gpu.js kernel runs in a loop, it generates underlying WebGL textures to hold inputs and intermediate outputs. If your code does not explicitly dispose of these textures, they remain in VRAM until the browser triggers a garbage collection cycle. During fast, iterative batch processing, the rate of GPU memory allocation outpaces the JavaScript engine's garbage collection routine, exhausting available VRAM and triggering a WebGL context loss or OOM error.

2. Pipelined Mode Accumulation

The pipeline: true option in gpu.js keeps calculation results stored directly on the GPU as textures, avoiding the costly performance penalty of transferring data back to the CPU via toArray(). However, if successive iterations in a batch create new pipelined textures without destroying previous references using texture.delete(), VRAM usage grows linearly with each batch. Once the driver’s allocation threshold is reached, WebGL throws an allocation error.

3. Maximum Texture Dimension Exceeded

WebGL relies on 2D textures to store array buffers. GPUs enforce a strict hardware limit on texture dimensions, accessible via the MAX_TEXTURE_SIZE parameter (typically 4096, 8192, or 16384 pixels). When a batch contains more elements than can fit within a supported 2D texture layout, gpu.js cannot allocate the required dimensions. While this is technically an allocation parameter failure rather than general memory exhaustion, WebGL frequently reports it as an out-of-memory or frame-buffer failure.

4. Browser and Operating System VRAM Quotas

Browsers implement strict security and stability sandboxes. Even if a host system has 16 GB of dedicated VRAM, web browsers like Chrome or Firefox restrict the maximum memory allocated to an individual WebGL context or tab (often capped around 1 GB to 2 GB). When a batch spikes memory usage beyond this safety limit, the browser forcibly terminates the WebGL context with a CONTEXT_LOST_WEBGL error to protect the operating system's display server from freezing.

5. Preventing WebGL Memory Exhaustion

To resolve and avoid these errors during intensive computing runs:

  • Explicitly Delete Textures: Call resultTexture.delete() on any pipelined textures once they are consumed by the next iteration.
  • Chunk Large Batches: Divide massive computational jobs into smaller micro-batches that fit comfortably within the hardware’s texture limits.
  • Destroy Unused Kernels: If dynamic kernels are instantiated inside loops, call kernel.destroy() to free shader programs and associated framebuffers.
  • Reuse Output Textures: Structure your pipeline using a ping-pong buffer technique, alternating between two pre-allocated textures rather than instantiating new textures on each step.
