How GPU.js Handles Denormalized Floating-Point Numbers

This article examines how the gpu.js library handles denormalized (subnormal) floating-point values when executing computations across diverse graphics hardware. Because gpu.js compiles JavaScript operations into WebGL and GLSL shaders rather than native machine code, it does not manage floating-point representations directly. Instead, the handling of subnormal numbers is dictated entirely by the underlying GPU hardware architecture, the graphics driver, and the WebGL specification's floating-point rules.

The WebGL Abstraction Barrier

gpu.js accelerates JavaScript by transpiling standard functions into GLSL (OpenGL Shading Language) fragments that run on the client’s GPU via WebGL. Unlike low-level compute APIs such as CUDA, OpenCL, or Vulkan—which provide flags to configure floating-point modes—WebGL abstracts low-level hardware registers.

Because of this abstraction, gpu.js cannot toggle CPU-style control words (such as MXCSR on x86) or GPU-level control flags (such as ftz in CUDA). If an operation produces an exponent below the minimum normalized threshold (\(2^{-126}\) for IEEE 754 single-precision float), gpu.js delegates the numeric resolution completely to the host platform's shader compiler and the physical execution unit.

Architecture-Specific Behavior

The IEEE 754 standard defines gradual underflow to preserve precision near zero using denormalized numbers. However, graphics hardware has historically prioritized throughput over strict IEEE 754 compliance. Consequently, behavior varies significantly across different classes of hardware:

Modern Desktop GPUs (NVIDIA and AMD)

Modern discrete architectures (such as NVIDIA Turing, Ampere, Ada Lovelace, and AMD RDNA) feature dedicated hardware pipelines capable of handling 32-bit single-precision (highp) denormals without severe throughput penalties. However, when executing via WebGL:

  • OpenGL and WebGL drivers often enforce Flush-to-Zero (FTZ) and Denormals-Are-Zero (DAZ) by default to maximize fragment processing speeds.
  • Even if the underlying hardware supports gradual underflow natively, the driver’s GLSL optimizer may truncate subnormal intermediate states to zero during shader compilation.

Mobile and Embedded GPUs (ARM Mali, Qualcomm Adreno, Apple Silicon)

Mobile system-on-chips (SoCs) prioritize energy efficiency and silicon surface area:

  • Mobile architectures almost universally rely on hardware-level FTZ. When a calculation in gpu.js yields a value between \(-1.17549435 \times 10^{-38}\) and \(+1.17549435 \times 10^{-38}\), mobile hardware abruptly clamps the value to 0.0.
  • Additionally, WebGL implementations on mobile devices may map highp precision to 16-bit half-precision (fp16) if full single-precision is unsupported by the target context, dramatically raising the underflow threshold to \(2^{-14}\) (\(6.10 \times 10^{-5}\)).

Intel Integrated Graphics

Intel integrated GPUs handle subnormals depending on the generation and OS driver stack:

  • Older generations (Gen9 and earlier) incur heavy clock cycle penalties if forced into subnormal arithmetic, leading drivers to flush denormals aggressively in GLSL contexts.
  • Modern Intel Iris Xe and Arc architectures include better hardware support, but WebGL pipelines frequently maintain FTZ to match typical browser rendering behaviors.

Practical Implications for gpu.js Pipelines

Because gpu.js lacks a mechanism to force standard IEEE 754 compliance across platforms, developers must design algorithms around the assumption that denormals will be flushed to zero.

  1. Division by Zero Hazards: Algorithms that assume non-zero values will decrease gradually near the lower precision bound can unexpectedly encounter division-by-zero errors if a subnormal intermediate value is flushed to 0.0.
  2. Platform Inconsistency: Running the identical gpu.js kernel on a high-end desktop workstation versus a smartphone may yield divergent numerical results if the algorithm relies on the edges of floating-point dynamic range.
  3. Manual Scaling Solutions: When extreme dynamic ranges are required, computations in gpu.js should apply manual range scaling (such as processing values in logarithmic space or pre-scaling data arrays by fixed exponents) before submitting workloads to the GPU context.
