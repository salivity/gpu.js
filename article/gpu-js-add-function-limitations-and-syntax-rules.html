GPU.js addFunction Limitations and Syntax Rules

When writing high-performance WebGL kernels using GPU.js, developers can modularize their code by registering external functions via gpu.addFunction. However, because GPU.js transpiles JavaScript directly into shader code (GLSL) to execute on the GPU, these functions are subject to severe syntax, type, and runtime constraints compared to standard JavaScript. This article outlines the key limitations and syntax restrictions you must adhere to when registering functions with gpu.addFunction.

Strict Type Signatures and Primitive Data Types

Unlike standard JavaScript, which is dynamically typed, the underlying GPU architecture requires strict static typing. Functions registered via gpu.addFunction must operate on primitive types supported by GLSL:

  • Allowed Types: Float, Integer, Boolean, and fixed-length vector arrays (e.g., Array(2), Array(3), Array(4)).
  • Unsupported Types: Complex JavaScript objects, classes, strings, dynamic arrays, and symbols cannot be parsed or used as arguments or return values.
  • Typing Definitions: If GPU.js cannot automatically infer the types of the function’s arguments and return value, you must explicitly declare them in the function configuration using argumentTypes and returnType. A mismatch between specified types and actual inputs causes compilation errors.

Complete Lack of Closures and Scope Access

Functions registered with gpu.addFunction must be pure and self-contained:

  • No Outer Scope Access: The function cannot read from or write to outer closures, global variables (window, globalThis), or module-level constants.
  • Data Flow: All input data must strictly be passed into the function as arguments.
  • No this Context: The this keyword is undefined and cannot be referenced within the registered function.

Prohibition of Recursion

GPU hardware and shader languages like GLSL do not utilize a traditional call stack in the way CPUs do. Consequently, GPU.js does not allow recursion. A registered function cannot call itself, nor can it be part of a mutual recursion loop. Any recursive syntax will cause the kernel compilation step to fail.

Exclusion of Standard JavaScript APIs

You cannot use the majority of standard JavaScript runtime functions or ES6+ array methods inside an added function:

  • No Native JS Built-ins: Objects like JSON, Date, RegExp, and Promise do not exist in the GPU pipeline.
  • No Array Methods: Methods such as .push(), .pop(), .map(), .filter(), and .slice() are entirely unavailable.
  • No Debugging Utilities: Functions such as console.log() cannot execute inside a shader.
  • Restricted Math Object: Only basic mathematical functions with direct GLSL equivalents (such as Math.sin, Math.cos, Math.floor, Math.sqrt, Math.min, and Math.max) are supported. Arbitrary standard library operations will produce transpilation errors.

Control Flow and Loop Restrictions

While basic if/else statements and standard for loops are permitted, control flow must remain predictable:

  • Loops should generally have fixed or determinable bounds. Dynamic loop conditions that cannot be evaluated at shader execution time may cause compilation failures or performance penalties.
  • Infinite loops or constructs like while(true) are prohibited, as they trigger GPU driver timeouts and browser context loss.
