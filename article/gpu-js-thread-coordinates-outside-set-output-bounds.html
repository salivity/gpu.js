GPU.js Thread Coordinates Outside setOutput Bounds

In GPU.js, the execution dimensions of a kernel are strictly bound by the setOutput configuration, meaning threads outside these dimensions are never spawned by the GPU pipeline. However, when an executing thread attempts to calculate and read data from coordinates exceeding these bounds—such as accessing an input array or texture beyond its defined limits—the result depends on the execution mode, generally yielding clamped values, zeroes, or undefined rather than triggering a fatal runtime crash.

Thread Allocation and the setOutput Limit

The setOutput method defines the dimensions of the output grid, which directly sets the WebGL viewport and determines how many parallel instances (threads) the GPU will execute. Because the GPU runtime generates threads strictly within the range of 0 to dimension - 1 for each axis:

  • A kernel will never execute with a this.thread.x, this.thread.y, or this.thread.z value natively outside the bounds defined by setOutput.
  • Threads beyond the defined grid simply do not exist, and no operations are dispatched for them.

Reading Out-of-Bounds Memory from an Active Thread

When an active thread inside the valid setOutput boundaries attempts to read an input collection at an index or coordinate that lies outside the input's actual dimensions (for instance, reading matrix[this.thread.y + offset][this.thread.x + offset]), GPU.js handles the operation differently depending on the active pipeline:

1. WebGL (GPU Mode)

In WebGL mode, input arrays are encoded into textures, and lookups are performed as texture samplers via generated GLSL shaders. When sampling a texture outside its defined coordinate space:

  • WebGL texture clamping or wrapping behaviors take over.
  • By default, texture samplers typically clamp to the edge pixels or return an empty vector (0.0, 0.0, 0.0, 0.0).
  • In mathematical kernels, this translates to returning 0 or repeating the boundary value, preventing the shader program from crashing the GPU context.

2. CPU Fallback Mode

If WebGL is unavailable and GPU.js falls back to JavaScript CPU execution:

  • Array reads outside valid indices follow standard JavaScript behavior and return undefined.
  • When mathematical operations attempt to process undefined, the result degrades to NaN, which is then committed to the output array for that specific thread.

Kernel logic relying on neighbor lookups (such as image convolutions or cellular automata) must manually implement boundary checks using conditionals like if (x >= width || x < 0) to guarantee consistent results across both GPU and CPU execution modes.
