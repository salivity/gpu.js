Name Scoping for Shared Functions in GPU.js

Sharing functions across multiple kernels in GPU.js requires understanding how JavaScript functions are translated into GPU-compatible shaders. When you share a helper function among kernels, GPU.js transpiles the JavaScript code into a low-level shading language (typically WebGL GLSL). Consequently, traditional JavaScript lexical scoping and closures do not apply; instead, names are resolved within a strictly isolated, flat namespace where only explicit parameters, kernel constants, and local variables exist.

Defining and Sharing Functions

Functions are typically shared across kernels in two ways: globally via gpu.addFunction() or locally per kernel via the functions configuration option.

When using gpu.addFunction(myHelper), the function becomes registered to the parent GPU instance and is made available to any kernel created by that instance. Alternatively, passing an array of functions to the kernel options (gpu.createKernel(..., { functions: [myHelper] })) scopes that function solely to that individual kernel execution context.

The Flat GLSL Scope

Because GPU.js compiles JavaScript into WebGL shader code, shared functions operate under GLSL scoping rules rather than JavaScript runtime rules:

  1. No Closures: Shared functions cannot capture or access variables from the outer JavaScript scope. Any variable defined outside the function body in your standard JavaScript code will be undefined or trigger a compilation error inside the GPU kernel.
  2. Top-Level Function Scope: All shared functions are injected as independent top-level subroutines in the compiled shader. They share the same global execution space as the primary kernel function.
  3. Explicit Parameters: All external data required by a shared function must be explicitly passed in through its arguments or accessed via declared kernel constants.

Name Collisions and Shadowing

Because the generated shader uses a flat global scope for functions:

  • Unique Identifiers: Every shared function must have a unique identifier. Registering two different functions with the same name will cause one to overwrite the other or produce a shader compilation error.
  • Variable Shadowing: Defining a local variable inside a shared function with the same name as a parameter or another function will follow standard C-like shadowing rules: the local variable takes precedence within its immediate block scope.
  • Built-in Shadowing: You cannot use function names that match GLSL built-in functions (such as sin, cos, dot, or length) or GPU.js internal reserved identifiers (like thread, constants, or dimensions), as this causes syntax conflicts during the transpilation stage.

Accessing Kernel Constants

While shared functions cannot access JavaScript lexical scope, they can access values injected via the kernel's constants object if the function is compiled within that kernel’s context. However, to keep shared functions modular, reusable, and predictable across varying kernels, the best practice is to design them as pure functions that rely strictly on their input arguments and local variables.
