How gpu.js Handles Texture Interpolation

This article explores how gpu.js handles texture coordinate interpolation when sampling non-integer coordinates during GPGPU operations. Because gpu.js compiles JavaScript into WebGL shaders, it converts array data into GPU textures and maps array indices to normalized texture coordinates. Understanding this process requires examining how WebGL texture filtering is configured, how texel centers are addressed, and what happens mathematically when kernels access fractional or off-grid coordinates.

WebGL Textures as Data Arrays

In gpu.js, numerical arrays passed into a kernel are converted into 2D WebGL textures. Each element in an array corresponds to a single pixel or "texel" in the texture. Because shaders access textures using normalized coordinates ranging from 0.0 to 1.0, gpu.js automatically generates the GLSL boilerplate necessary to translate discrete integer indices into normalized texture coordinates.

To sample the center of a texel accurately, gpu.js applies a half-pixel offset. For a texture of width \(W\), the coordinate for index \(x\) is typically calculated as:

\[\text{coord}_x = \frac{x + 0.5}{W}\]

This half-pixel offset ensures that discrete integer lookups sample the exact center of the intended texel rather than landing on a boundary between adjacent texels.

Default Texture Filtering: Nearest-Neighbor

When dealing with non-integer coordinates, the primary factor determining interpolation behavior is the texture's magnification (gl.TEXTURE_MAG_FILTER) and minification (gl.TEXTURE_MIN_FILTER) settings.

By default, gpu.js configures its internal WebGL textures with gl.NEAREST. In numerical computing and general-purpose GPU programming, data integrity is critical. Blending adjacent array values can introduce rounding errors and invalidate matrix computations. Under gl.NEAREST filtering, when a non-integer coordinate is sampled:

  1. The GPU maps the continuous floating-point coordinate to the nearest discrete texel center.
  2. No mathematical interpolation or averaging occurs between neighboring texels.
  3. The returned value is the exact, uncorrupted value stored in the closest texel.

For example, if an index operation evaluates to an effective position of 2.4, gl.NEAREST snaps to texel index 2. If it evaluates to 2.6, it snaps to texel index 3.

Bilinear Interpolation via Linear Filtering

If a texture is explicitly configured or modified to use gl.LINEAR, the GPU hardware executes hardware-accelerated bilinear interpolation when sampling non-integer coordinates.

Under bilinear filtering:

  • The GPU identifies the four texel centers surrounding the target fractional coordinate \((u, v)\).
  • It calculates horizontal and vertical weighting factors based on the fractional distance from these centers.
  • The resulting sample is a weighted average of the four surrounding values:

\[\text{Sample} = (1 - s)(1 - t)T_{0,0} + s(1 - t)T_{1,0} + (1 - s)tT_{0,1} + stT_{1,1}\]

where \(s\) and \(t\) represent the fractional distances between texel centers. While this produces smooth transitions useful in graphical rendering, it is generally avoided in gpu.js algorithms unless implementing specific image processing, continuous field simulations, or custom resamplers.

Precision and Hardware Constraints

Hardware support also dictates how non-integer coordinates are evaluated in gpu.js:

  • Floating-Point Textures: gpu.js frequently uses 32-bit floating-point textures (OES_texture_float) to maintain computational precision. On many WebGL implementations, linear interpolation (gl.LINEAR) on 32-bit float textures is not supported without the optional OES_texture_float_linear extension. Without this extension, the WebGL runtime falls back to gl.NEAREST regardless of shader logic.
  • Coordinate Clamping: When non-integer coordinates fall outside the valid \([0.0, 1.0]\) bounds, gpu.js relies on standard WebGL wrapping modes (typically gl.CLAMP_TO_EDGE), causing coordinates below \(0.0\) or above \(1.0\) to sample the edge-most texels.

Through its automated coordinate mapping and strict reliance on gl.NEAREST filtering, gpu.js prevents unintentional data blending, ensuring that non-integer texture lookups resolve deterministically to the nearest discrete data point.
