How VRR Affects GPU.js Animation Loop Timing

Variable Refresh Rate (VRR) technologies, such as NVIDIA G-Sync, AMD FreeSync, and Apple ProMotion, dynamically alter a display's refresh cycle to match the delivery rate of rendered frames. When running GPU-accelerated calculations via GPU.js within an animation loop, this variable synchronization directly alters the execution frequency of requestAnimationFrame. This article explores how VRR impacts GPU.js execution timing, the computational challenges introduced by fluctuating frame intervals, and the methods required to maintain stable, deterministic simulations.

The Baseline: Fixed Refresh Rates vs. GPU.js

Traditional animation loops in JavaScript rely on window.requestAnimationFrame() (rAF). On a standard fixed-rate display (such as 60Hz or 144Hz), rAF fires at consistent, predictable intervals—roughly 16.67ms or 6.94ms, respectively. Developers using GPU.js often rely on this predictability, sometimes designing kernels that assume a constant delta time (\(\Delta t\)) per frame for physics simulations, particle systems, or cellular automata.

When the workload of a GPU.js kernel exceeds the frame budget on a fixed display, the browser drops frames, causing the effective frame rate to halve (e.g., from 60 FPS down to 30 FPS) to maintain synchronization with the monitor's V-Sync pulses.

How VRR Changes Animation Loop Timing

VRR eliminates fixed refresh cycles by waiting to refresh the screen until the GPU presents a finished frame, up to the monitor's maximum limit. This changes how GPU.js animation loops behave in several critical ways:

  1. Dynamic rAF Intervals: Instead of snapping to fractions of 60Hz or 144Hz, the interval between consecutive rAF callbacks fluctuates dynamically based on the exact execution duration of the GPU.js kernel and its surrounding JavaScript code. If a kernel takes 18ms to execute, the monitor refreshes at ~55Hz; if the next frame takes 12ms, it refreshes at ~83Hz.
  2. Amplified Micro-Stutter from Pipeline Stalls: Reading data back from the GPU to the CPU (e.g., converting kernel results back into JavaScript arrays) blocks the pipeline. On a VRR display, these pipeline stalls immediately stretch the monitor's active frame time, resulting in visible pacing irregularities rather than being absorbed into a standardized refresh window.
  3. Low Framerate Compensation (LFC) Jitter: Most VRR monitors have a lower boundary (typically between 40Hz and 48Hz). If a demanding GPU.js operation pushes frame delivery times past this threshold, the display hardware engages LFC, duplicating frames to keep the monitor above its minimum refresh rate. If GPU.js frame times oscillate around this boundary, the constant engagement and disengagement of LFC can cause severe visual stutter and erratic timestamp pacing.

Mitigating VRR Timing Issues in GPU.js

To ensure consistent performance and visual fidelity on VRR displays, developers must adapt their animation architecture:

  • Pass Variable Delta Time to Kernels: Never hardcode time-step constants inside GPU.js kernels. Calculate the elapsed time using the DOMHighResTimeStamp argument provided natively by requestAnimationFrame, clamp it to prevent physics explosions during severe hitches, and pass it directly into the kernel as a dynamic uniform argument.
  • Implement a Fixed Timestep with an Accumulator: If a GPU.js application performs numeric integration or physics simulations that require mathematical determinism, decouple the simulation loop from the render loop. Accumulate the variable delta time provided by rAF and run the GPU.js kernel in fixed sub-steps (e.g., exactly 60Hz steps) while allowing the display to render as frequently as the VRR screen requests.
  • Avoid Synchronous Readbacks: Keep data resident on the GPU. Instead of calling .toArray() or pulling data to the CPU every loop iteration, pipe the output texture of one GPU.js kernel directly into the next, or render directly to a WebGL canvas using GPU.js graphical output features. This keeps execution times predictable and prevents the browser from stalling the VRR frame cycle.
