Memory Bandwidth Saturation in GPU.js Kernels

This article examines how memory bandwidth saturation degrades the execution speed of memory-intensive kernels in gpu.js. When kernels read or write large volumes of data relative to the number of mathematical operations performed, they encounter hardware memory bottlenecks. Understanding this dynamic—governed by the ratio of compute to memory operations—explains why adding GPU threads fails to improve performance for memory-bound tasks and highlights how developers can structure their kernels to maximize throughput.

Understanding Memory-Bound Kernels in gpu.js

GPU computing relies on massively parallel execution across hundreds or thousands of lightweight processing cores. The efficiency of this architecture depends on the arithmetic intensity of the kernel, defined as the number of floating-point operations (FLOPs) performed per byte of data transferred to and from memory.

In gpu.js, algorithms are transpiled into WebGL fragment shaders. Input arrays are converted into WebGL textures, and execution results are rendered back into framebuffers. In memory-heavy tasks—such as large matrix additions, basic image blurs, or element-wise transformations—the operational intensity is low. The GPU cores must fetch data from texture memory, perform a trivial operation (such as adding two numbers), and write the result back.

The Mechanism of Bandwidth Saturation

Memory bandwidth is the maximum rate at which data can be transferred between the GPU's dedicated VRAM (or unified system memory) and its execution units. Bandwidth saturation occurs when memory bus controllers reach 100% capacity while the arithmetic logic units (ALUs) remain underutilized.

When a gpu.js kernel requests more data per clock cycle than the memory bus can supply, the execution pipeline experiences several cascading effects:

  1. Warp and Thread Stalls: GPUs hide memory latency through fast context switching between groups of threads (warps or wavefronts). When all scheduled threads are waiting for memory reads from WebGL textures to return, the scheduler runs out of active threads to execute. As a result, compute cores sit idle.
  2. Texture Fetch Bottlenecks: Because gpu.js maps arrays to 2D textures, reads are subject to texture-sampling pipelines. While modern GPUs feature hardware texture caches (L1 and L2 caches), memory-heavy algorithms with scattered or non-contiguous memory access patterns cause frequent cache misses, directly hitting the saturated global memory bus.
  3. Loss of Parallel Scaling: Increasing the kernel output dimensions or processing larger arrays yields diminishing returns. Once the memory bus is saturated, overall throughput caps out regardless of how many streaming multiprocessors are available.

Architectural Constraints within the WebGL Layer

Because gpu.js runs on top of WebGL, it cannot access lower-level memory features available in native frameworks like CUDA or WebGPU, such as manually managed shared memory (local scratchpads) or warp-level shuffle primitives.

Every read in gpu.js resolves as a texture lookup via shader instructions (texture2D). These lookups must traverse WebGL’s abstraction layer, which enforces standardized bounds checking and precision conversion. When memory bandwidth is saturated, this overhead is magnified, as the memory subsystem cannot clear read queues fast enough to maintain smooth execution.

Impact on Pipeline Performance

The negative impact of bandwidth saturation in gpu.js often extends beyond the GPU execution time itself:

  • PCIe Bus Congestion: If output textures must be retrieved back to JavaScript as standard arrays (kernel()), large readbacks block the main thread. While this is host-to-device/device-to-host transfer rather than VRAM bandwidth, it often acts as an additional bottleneck in memory-heavy workflows.
  • Pipeline Mode Degradation: Using kernel.setOutputOrder('precision') or pipeline: true allows outputs to stay on the GPU as textures for subsequent kernels. While this prevents CPU readbacks, chaining multiple memory-saturated kernels will continuously bottleneck on texture writes and reads, compounding memory stalls across the execution chain.

Strategies to Mitigate Saturation

To bypass memory bandwidth limits in gpu.js, algorithms must be refactored to increase arithmetic intensity:

  • Kernel Fusion: Combine multiple consecutive operations into a single kernel. Instead of writing intermediate results back to memory and reading them again in a second kernel, compute them in local variables within one kernel run.
  • Vectorized Reads (RGBA Packing): Leverage four-component vector operations. Packing four numerical values into the r, g, b, and a channels of a single texel allows a single texture fetch instruction to retrieve four data points simultaneously, maximizing bus efficiency.
  • Temporal Locality: Structure algorithms so that fetched data is reused locally as many times as possible before moving on to the next segment of an array.
