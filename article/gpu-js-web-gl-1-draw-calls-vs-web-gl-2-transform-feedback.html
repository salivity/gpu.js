gpu.js: WebGL 1 Draw Calls vs WebGL 2 Transform Feedback

This article examines the internal architectural changes that occur within gpu.js when moving from WebGL 1 draw-call-based computation to WebGL 2 transform feedback. It covers shader stage migration, texture framebuffer bypasses, memory layout adaptations, precision-packing elimination, and differences in multipass chaining.

Shader Stage Relocation

In WebGL 1 mode, gpu.js utilizes the rasterization pipeline. Computations are executed within the Fragment Shader. To trigger the calculation, gpu.js draws a full-screen quad (two triangles) covering the viewport. The vertices are trivial coordinates mapped to a canvas, while the computational logic runs per-fragment.

When switching to WebGL 2 with Transform Feedback, the computational logic shifts to the Vertex Shader. gpu.js compiles the kernel code into vertex instructions rather than fragment routines. No rasterization or fragment stage is utilized. The GPU treats input datasets directly as vertex attributes or uniform buffers and performs math per vertex execution.

Memory Targets: Framebuffers vs. Buffer Objects

The destination for calculated data changes fundamentally:

  • WebGL 1 (Textures & Framebuffers): WebGL 1 lacks generic compute write targets. gpu.js must attach a 2D texture to a custom WebGLFramebuffer via gl.framebufferTexture2D(). The output of the fragment shader is captured inside this texture.
  • WebGL 2 (Transform Feedback Buffers): gpu.js binds a raw WebGLBuffer to gl.TRANSFORM_FEEDBACK_BUFFER. The output of the vertex shader streams directly into sequential memory locations without texture abstractions or color-attachment binding overhead.

Elimination of Texture Packing and Unpacking

Because WebGL 1 outputs to color textures, writing high-precision floating-point numbers requires specialized workarounds:

  • Float Packing: If floating-point texture extensions (OES_texture_float, WEBGL_color_buffer_float) are unsupported or restricted, gpu.js injects math inside the fragment shader to encode 32-bit floats into four 8-bit channels (gl_FragColor = encodeFloat(value)). The CPU must subsequently decode these bytes.
  • Direct Primitives: With WebGL 2 Transform Feedback, values are written natively as 32-bit floats or integers into the destination buffer via gl.transformFeedbackVaryings(). This removes all arithmetic overhead associated with channel encoding and decoding.

Disabling the Rasterizer

In the WebGL 1 pipeline, the GPU must process primitives, interpolate varyings, and calculate fragment coverage across the screen dimensions.

In WebGL 2 transform feedback mode, gpu.js invokes:

gl.enable(gl.RASTERIZER_DISCARD);

This instruction cuts off the graphics pipeline immediately after the vertex (or geometry/transform) stage. The GPU bypasses the clipper, the rasterizer, depth/stencil tests, and the fragment processing unit entirely. This saves silicon cycles, drops bandwidth demands, and avoids viewport dimension limitations.

Chaining and Multipass Kernels

When kernels run sequentially, where the output of kernel \(A\) serves as the input to kernel \(B\):

  • WebGL 1: gpu.js implements texture ping-ponging. The texture written by the framebuffer in pass \(A\) is unbound and rebound as a sampler uniform for pass \(B\).
  • WebGL 2: The target WebGLBuffer from pass \(A\) can be immediately bound as a vertex attribute array pointer (gl.vertexAttribPointer) for pass \(B\). There is no context overhead from switching framebuffer attachments.

Data Readback

Data retrieval to JavaScript changes in both method and synchronization:

  • WebGL 1: Data must be retrieved using gl.readPixels(). This command blocks the CPU until the entire render queue completes, creating a pipeline stall.
  • WebGL 2: gpu.js reads back memory via gl.getBufferSubData(). Coupled with WebGL 2 fence sync objects (gl.fenceSync), gpu.js can query completion asynchronously, minimizing CPU-GPU lockstep pauses.
