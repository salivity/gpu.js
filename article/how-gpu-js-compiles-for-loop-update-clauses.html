How GPU.js Compiles For-Loop Update Clauses

This article examines how the GPU.js compiler processes and translates compound expressions within JavaScript for-loop update clauses into performant OpenGL Shading Language (GLSL). It covers the internal Abstract Syntax Tree (AST) parsing, the translation of compound assignment operators, the handling of sequence expressions, and the strict type enforcement required by the WebGL shader target.

Abstract Syntax Tree Parsing

GPU.js relies on an internal parser (historically Acorn) to convert JavaScript function source code into an Abstract Syntax Tree (AST). When encountering a standard for loop, the compiler isolates the ForStatement node, which consists of three distinct parts: init, test, and update.

The update clause is represented as an expression node. Depending on the syntax used in the JavaScript source, this node is typically classified as:

  • An UpdateExpression (e.g., i++, --i)
  • An AssignmentExpression with a compound operator (e.g., i += 2, i *= 1.5)
  • A SequenceExpression containing multiple comma-separated expressions (e.g., i++, step *= 2)

Operator Translation to GLSL

Because GLSL is derived from C, its syntax for basic arithmetic and compound assignment largely matches JavaScript. The GPU.js code generation layer traverses the AST node of the update clause and maps JavaScript operators directly to their corresponding GLSL tokens.

When an AssignmentExpression contains compound assignment operators such as +=, -=, *=, or /=, GPU.js emits them directly into the generated loop header:

// JavaScript source
for (let i = 0; i < 100; i += 4) { ... }
// Generated GLSL
for (int i = 0; i < 100; i += 4) { ... }

The compiler preserves the compound structure rather than expanding it into an explicit binary reassignment (such as i = i + 4), ensuring clean and compliant GLSL loop statements.

Strict Type Enforcement and Numeric Literals

The primary challenge GPU.js faces when compiling compound update clauses is GLSL's strict typing system. Unlike JavaScript, GLSL does not allow implicit type coercion between integers and floating-point numbers.

During semantic analysis, GPU.js tracks the type signature of the loop iterator:

  1. Integer Iterators: If the loop counter is inferred as an integer (int), the right-hand operand of the compound expression must evaluate to an integer. If a programmer writes i += 1, GPU.js ensures the numeric literal translates to 1 (an integer token in GLSL). If the user writes i += 1.0, the compiler will either cast the float to an integer or throw a compilation error, depending on mode and target precision.
  2. Float Iterators: If the loop variable is defined as a float, any update expression must use float values. An update such as i += 1 will be transpiled to i += 1.0 to prevent shader compilation failure.

Sequence Expressions (Multiple Update Clauses)

In cases where a compound expression involves comma-separated updates, the AST produces a SequenceExpression. GLSL natively supports comma-separated expressions in the iteration clause of a for loop:

// JavaScript source
for (let i = 0, j = 10; i < 10; i++, j -= 2) { ... }

GPU.js processes the expressions array within the SequenceExpression node sequentially. It compiles each sub-expression independently using its respective update or assignment rule and joins them using commas. The resulting string is placed directly into the third slot of the GLSL for loop construct:

// Generated GLSL
for (int i = 0, int j = 10; i < 10; i++, j -= 2) { ... }

Through direct operator mapping, strict literal typing, and sequence preservation, GPU.js ensures that compound loop updates match the execution semantics of native JavaScript while strictly adhering to WebGL GLSL requirements.
