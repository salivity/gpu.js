Parallel Flood Fill on Game Maps in gpu.js

Parallel flood-fill algorithms can be implemented in gpu.js to perform connected component labeling (CCL) on grid-based game maps. This approach utilizes WebGL shaders to rapidly identify contiguous regions—such as distinct rooms, traversable terrain, or isolated islands—by transforming the traditional recursive flood-fill into an iterative, parallel data-propagation model. While highly efficient for large procedural maps, utilizing gpu.js for this task requires adapting graph traversal to SIMD (Single Instruction, Multiple Data) architectures, handling texture ping-ponging, and mitigating convergence bottlenecks.

Adapting Flood Fill to the GPU

Standard flood-fill algorithms rely on Breadth-First Search (BFS) or Depth-First Search (DFS) using queues or call stacks. These sequential approaches perform poorly on GPU architectures because GPUs lack dynamic per-thread memory allocation and shared execution queues.

To execute connected component labeling on a GPU via gpu.js, the problem must be restructured into an iterative neighborhood relaxation algorithm (similar to cellular automata) or a Jump Flooding Algorithm (JFA).

1. Initialization

The map data is converted into a 2D array or texture. Each passable cell is assigned a unique identifier, commonly derived from its coordinates:

\[\text{Label} = y \times \text{width} + x\]

Impassable cells (such as walls or water) are assigned a reserved null label (e.g., -1 or 0).

2. Parallel Label Propagation

A gpu.js kernel is executed over the map grid. Each thread corresponds to a single tile and compares its current label to the labels of its valid orthogonal or diagonal neighbors. If a neighbor holds a lower (or valid non-zero) label, the thread updates its own label to match the minimum found:

\[\text{Label}_{t+1}(x, y) = \min(\text{Label}_t(x, y), \text{ValidNeighbors}_t)\]

3. Iteration and Convergence

Because gpu.js runs on top of WebGL, it cannot update data in place. Iterations require ping-pong rendering, where the output of one step becomes the input texture for the next. This is handled natively in gpu.js by setting pipeline: true on the kernel, keeping the data stored on the GPU VRAM between steps to prevent costly CPU readbacks. Iterations continue until no label values change.

Optimization: Jump Flooding Algorithm (JFA)

Naive neighbor-based label propagation requires \(O(D)\) iterations to converge, where \(D\) is the maximum diameter of a connected component. On long, winding corridors, this requires hundreds of kernel dispatches.

To accelerate convergence, developers use the Jump Flooding Algorithm inside gpu.js. Instead of checking adjacent neighbors (step size \(k = 1\)), JFA samples neighbors at decreasing step sizes:

\[k = \left\lfloor \frac{N}{2} \right\rfloor, \left\lfloor \frac{N}{4} \right\rfloor, \dots, 1\]

JFA reduces the iteration complexity to \(O(\log N)\), allowing large game maps (e.g., \(2048 \times 2048\)) to resolve fully connected regions in approximately 10 to 12 iterations.

When to Use gpu.js for CCL

Using gpu.js for game map labeling provides distinct advantages depending on scale and frequency:

  • Large Map Sizes: For maps \(1024 \times 1024\) and larger, parallel GPU labeling significantly outperforms single-threaded JavaScript implementations.
  • Procedural Generation Pipelines: When generating large cellular-automata caves or Voronoi-based biomes directly on the GPU, keeping CCL passes within the GPU pipeline eliminates the need to pass data back and forth to the main thread.
  • Batch Map Validation: Evaluating multiple distinct map sectors concurrently in a single multi-layered texture.

Limitations and Trade-offs

  • CPU-GPU Transfer Overhead: If a map is small (e.g., \(128 \times 128\) or smaller), the overhead of transferring data to VRAM, compiling shaders, and reading back the result (kernel.toArray()) makes traditional CPU-based BFS or Disjoint-Set (Union-Find) algorithms significantly faster.
  • Termination Detection: Determining when the algorithm has reached convergence requires checking if any pixels changed. Reading a convergence flag back to the CPU after every iteration can stall the GPU pipeline. JFA mitigates this by allowing developers to run a fixed number of predetermined \(\log_2(N)\) steps instead of polling for convergence.
  • Floating-Point Precision: gpu.js relies on WebGL textures under the hood. When working with very large maps where the total tile count exceeds \(2^{24}\), precision limits in standard 32-bit floating-point textures can cause integer rounding errors in label IDs unless high-precision packing strategies are used.
