Running Pathfinding and Maze Algorithms on GPU.js

This article explores the technical feasibility, architectural constraints, and implementation methods for executing pathfinding and maze generation algorithms on the GPU using gpu.js. It details how parallel flood-fill naturally aligns with GPU fragment compute architectures, outlines the specific challenges and viable approaches for GPU-accelerated maze generation, and highlights performance trade-offs such as kernel overhead and memory ping-ponging.

Feasibility of Parallel Flood-Fill

Parallel flood-fill and breadth-first search (BFS) variations, such as the Lee algorithm, are exceptionally well-suited for execution via gpu.js. A traditional CPU-based flood-fill evaluates cells sequentially using a queue. In contrast, the GPU approaches flood-fill as a cellular automaton, operating across the entire 2D grid simultaneously.

In gpu.js, each grid cell corresponds to an individual execution thread mapped to an output texture coordinate. During each execution pass:

  1. Each thread reads the state of its current cell and its orthogonal neighbors (North, South, East, West) from the input texture.
  2. If an open neighbor has already been reached by the flood front, the current cell updates its state to mark itself as visited or to store the step distance from the source.
  3. If the cell is an obstacle or already visited, its state remains unchanged.

Because gpu.js functions compile into WebGL fragment shaders, memory is inherently stateless between draws. Running an iterative flood-fill requires a "ping-pong" buffering technique, where two textures alternate as the input and render target over multiple kernel invocations until the target is reached or no further cells can be updated.

Maze Generation on the GPU

Maze generation is more architecturally constrained than pathfinding when mapped to GPU compute shaders. Standard generation algorithms—such as Randomized Depth-First Search (Recursive Backtracker), Kruskal’s, or Prim’s—are strictly sequential and rely on a shared global state with atomic operations, neither of which are natively accessible in gpu.js WebGL compute pipelines.

However, maze and terrain generation can still be achieved on gpu.js by selecting parallel-friendly algorithms:

  • Cellular Automata (Cave Generation): Similar to Conway's Game of Life, rules can be applied where cells become walls or paths based on the density of neighboring walls. This operates cleanly within standard gpu.js kernel patterns.
  • Perlin/Simplex Noise Thresholding: Mazes can be generated functionally by evaluating procedural noise functions inside the kernel, creating labyrinthine structures without inter-thread dependencies.
  • Parallel Subdivided Division: Recursive division can be parallelized if the boundaries of subdivisions are determined mathematically per thread rather than dynamically traversed sequentially.

Traditional "perfect" mazes (mazes with exactly one path between any two points and no loops) remain difficult to produce efficiently on gpu.js due to the synchronization overhead required to guarantee acyclic graphs across independent execution threads.

Architectural Constraints and Performance Considerations

While gpu.js can accelerate parallel grid algorithms, several technical factors influence practical performance:

  • Kernel Dispatch Overhead: Iterative algorithms require the CPU to orchestrate multiple GPU dispatches. If a grid requires 500 iterations to bridge start and end points, 500 individual draw calls are issued. The cumulative JavaScript-to-WebGL driver overhead can negate GPU execution speedups on smaller grids.
  • Data Transfer Bottlenecks: Passing large 2D arrays from the CPU to the GPU and reading the final matrix back to the CPU via readPixels is computationally expensive. Maximum throughput is achieved only when the grid data originates on the GPU (e.g., as a texture) and remains there for downstream rendering.
  • Grid Scale: For small grids (under \(256 \times 256\)), optimized CPU pathfinding with a priority queue typically outperforms gpu.js. For massive grids (\(1024 \times 1024\) and larger), the massive parallelism of gpu.js processes thousands of neighbor evaluations concurrently, making parallel flood-fill significantly faster than a single-threaded CPU loop.
