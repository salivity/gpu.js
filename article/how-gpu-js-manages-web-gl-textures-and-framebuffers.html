How GPU.js Manages WebGL Textures and Framebuffers

GPU.js accelerates JavaScript operations by compiling functions into WebGL shaders, using textures as data containers and framebuffers as computation targets. Because WebGL lacks native automatic garbage collection for graphics memory, GPU.js implements a lifecycle management system that handles texture encoding, framebuffer binding, resource recycling, and manual deallocation to ensure efficient GPU memory utilization and prevent memory leaks.

Texture and Framebuffer Allocation

In WebGL, the GPU performs general-purpose computation (GPGPU) by treating data as pixels. GPU.js translates JavaScript arrays and matrices into WebGL textures:

  1. Input Textures: When data is passed to a GPU.js kernel, the library creates a 2D texture using gl.createTexture(). It maps the input array elements into texture channels (RGBA), typically leveraging floating-point extensions such as OES_texture_float to maintain precision.
  2. Output Framebuffers: Because WebGL cannot write directly back to memory arrays, it renders to a WebGL Framebuffer Object (FBO) using gl.createFramebuffer(). GPU.js attaches an empty output texture to the framebuffer's color attachment point via gl.framebufferTexture2D(). The fragment shader then writes computational results directly to this attached texture.

Allocation occurs on demand. When a kernel executes with a new input dimension, GPU.js allocates a texture sized to the smallest power-of-two or standard rectangular dimensions capable of holding the data.

Texture Recycling and the Pipeline Mode

Allocating and destroying WebGL contexts, textures, and framebuffers repeatedly incurs high performance overhead. GPU.js optimizes this through texture reuse and pipeline execution:

  • Kernel Output Caching: Successive executions of a kernel with the same output dimensions reuse existing texture and framebuffer instances instead of reallocating them on every cycle.
  • Pipeline Mode (pipeline: true): When pipeline mode is enabled, GPU.js suppresses the costly gl.readPixels() operation that transfers data back to CPU memory. Instead, the output texture remains in GPU memory as a Texture object, which can be fed directly as an input texture into the next kernel.
  • Ping-Pong Buffering: For iterative algorithms where a kernel's output becomes its subsequent input, GPU.js alternates between two textures (ping-ponging). One texture is bound to the FBO as the render target, while the second acts as the read-only input, preventing read-write hazards within the same WebGL draw call.

Resource Deallocation and Cleanup

The JavaScript garbage collector manages standard heap objects but cannot reliably track or release native WebGL resources held in GPU VRAM. GPU.js handles deallocation via both internal cleanup routines and explicit user APIs:

  • Manual Texture Deallocation: Textures generated in pipeline mode expose a .delete() method. Calling texture.delete() explicitly invokes gl.deleteTexture() and detaches the texture from any associated framebuffers.
  • Kernel Destruction: Calling kernel.destroy() frees all internal WebGL resources bound to that specific kernel, including its compiled shaders, programs, internal input textures, and output framebuffers via gl.deleteFramebuffer().
  • Context Teardown: Calling gpu.destroy() releases the entire WebGL context, iterating through all cached kernels, programs, framebuffers, and textures to delete them from hardware memory, completely releasing the GPU allocation.
