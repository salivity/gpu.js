Benchmark Array.prototype.map vs GPU.js

This guide demonstrates how to build an accurate micro-benchmark suite comparing the performance of native JavaScript Array.prototype.map against GPU-accelerated execution using gpu.js. You will learn how to initialize the environments, account for hardware-specific overheads such as kernel compilation and memory transfers, and measure execution times across varying array sizes to identify performance inflection points.

Understanding the Architectural Differences

Native Array.prototype.map runs on the CPU, processing elements sequentially or leveraging limited SIMD (Single Instruction, Multiple Data) optimizations through the JavaScript engine's JIT compiler. In contrast, gpu.js compiles JavaScript functions into GLSL shaders, dispatching computations across thousands of GPU threads simultaneously.

Because transferring data between CPU system memory and GPU VRAM introduces latency, and the initial kernel creation incurs a compilation penalty, micro-benchmarks must separate initialization overhead from pure compute time across various payload sizes.

Setting Up the Benchmark Suite

Install gpu.js using npm:

npm install gpu.js

The benchmark suite uses Node.js's built-in performance.now() API to ensure high-resolution timing.

const { GPU } = require('gpu.js');
const { performance } = require('perf_hooks');

const gpu = new GPU();

// Configuration
const SIZES = [1000, 10000, 100000, 1000000, 5000000];
const ITERATIONS = 10;

// Benchmark mathematical operation: f(x) = (x * 2.5 + 1.2) / 1.5
function cpuOperation(arr) {
  return arr.map(x => (x * 2.5 + 1.2) / 1.5);
}

function createGpuKernel(size) {
  return gpu.createKernel(function (arr) {
    return (arr[this.thread.x] * 2.5 + 1.2) / 1.5;
  }).setOutput([size]);
}

Implementing the Measurement Runner

To obtain valid results, the benchmark must:

  1. Warm up both the CPU JIT and the GPU pipeline before timing.
  2. Run multiple iterations to compute a stable average.
  3. Exclude kernel compilation from the raw execution loop while noting its initial cost.
async function runBenchmark() {
  console.log('Size\t\tCPU (ms)\tGPU Exec (ms)\tGPU Total (Inc. Init)');

  for (const size of SIZES) {
    // Generate synthetic input data
    const inputData = new Float32Array(size);
    for (let i = 0; i < size; i++) {
      inputData[i] = Math.random();
    }

    // 1. Warm-up runs
    cpuOperation(inputData.slice(0, 100));
    const warmupKernel = createGpuKernel(100);
    warmupKernel(inputData.slice(0, 100));
    warmupKernel.destroy();

    // 2. Measure GPU Compilation Overhead
    const compileStart = performance.now();
    const kernel = createGpuKernel(size);
    kernel(inputData); // First run triggers compile
    const compileTime = performance.now() - compileStart;

    // 3. Measure Average CPU Execution
    let cpuTotalTime = 0;
    for (let i = 0; i < ITERATIONS; i++) {
      const start = performance.now();
      cpuOperation(inputData);
      cpuTotalTime += performance.now() - start;
    }
    const cpuAvg = (cpuTotalTime / ITERATIONS).toFixed(3);

    // 4. Measure Average GPU Pure Execution
    let gpuTotalTime = 0;
    for (let i = 0; i < ITERATIONS; i++) {
      const start = performance.now();
      kernel(inputData);
      gpuTotalTime += performance.now() - start;
    }
    const gpuAvg = (gpuTotalTime / ITERATIONS).toFixed(3);
    const gpuWithInit = (parseFloat(gpuAvg) + compileTime).toFixed(3);

    console.log(`${size}\t\t${cpuAvg}\t\t${gpuAvg}\t\t${gpuWithInit}`);

    kernel.destroy();
  }

  gpu.destroy();
}

runBenchmark();

Analyzing Benchmark Outcomes

When running this suite, review the data against these primary behavior patterns:

  • Small Arrays (< 10,000 items): Array.prototype.map will consistently beat gpu.js. The overhead of packing JavaScript typed arrays into WebGL textures, executing draw calls, and unpacking the data back to CPU memory outweighs the parallel compute benefit.
  • Large Arrays (> 1,000,000 items): gpu.js will significantly outperform native .map(), achieving 5x to 50x speedups depending on the complexity of the math inside the map callback.
  • Arithmetic Intensity: Simple operations (like adding a constant) are bandwidth-bound and may favor CPU memory controllers longer. Complex multi-step equations (trigonometric functions, nested floating-point operations) show an earlier inflection point where the GPU begins to outperform the CPU.
