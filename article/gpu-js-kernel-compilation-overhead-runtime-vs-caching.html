GPU.js Kernel Compilation Overhead: Runtime vs Caching

Compiling new kernels at runtime in gpu.js incurs a substantial performance penalty compared to caching and reusing existing ones. When a kernel is defined on the fly, the library must translate JavaScript functions into GLSL shaders, validate data types, compile those shaders via WebGL or WebGPU drivers, and link the program before dispatching work to the hardware. Caching compiled kernels eliminates this pipeline setup overhead, reducing execution latency from tens or hundreds of milliseconds down to sub-millisecond memory-dispatch operations.

The Steps and Cost of Runtime Compilation

Every time a new kernel is created using gpu.createKernel(), a multi-stage compilation pipeline runs on the CPU and the GPU driver:

  1. Abstract Syntax Tree (AST) Parsing: gpu.js parses the JavaScript function using Acorn to understand loops, mathematical operators, and variable scopes.
  2. GLSL Code Generation: The AST is transpiled into GLSL (OpenGL Shading Language) shader source code compatible with the active WebGL context.
  3. Driver-Level Shader Compilation: The browser passes the GLSL string to the underlying graphics driver via gl.compileShader(). The driver compiles the GLSL into the GPU's native machine code (ISA).
  4. Program Linking and Buffer Binding: The compiled vertex and fragment shaders are linked into a WebGL program via gl.linkProgram(), and default uniform locations, attribute buffers, and output framebuffers are established.

This pipeline typically introduces an overhead of 10 to 150 milliseconds per kernel, depending on the host CPU, client GPU, and kernel complexity. In applications that run real-time graphics, physics simulations, or iterative machine learning models, dynamically compiling kernels inside an execution loop causes severe frame drops, CPU spikes, and memory thrashing from discarded WebGL program handles.

Performance Profile of Cached Kernels

When a kernel is declared once and cached as a reusable function reference, gpu.js bypasses the translation and compilation pipeline entirely on subsequent calls.

During cached execution, the lifecycle consists solely of:

  • Argument Serialization: Mapping input arrays or typed arrays to WebGL textures or uniforms.
  • Uniform Updates: Uploading altered scalar values to the GPU via gl.uniform* calls.
  • Draw Call Dispatch: Executing a single draw call (such as gl.drawArrays over a screen-aligned quad) to trigger parallel execution.
  • Data Retrieval (Optional): Reading pixels back from the GPU via gl.readPixels, or retaining the output directly on the GPU as a texture for chained computations.

Because the underlying WebGL program remains compiled in GPU memory, running a cached kernel typically takes between 0.05 and 5 milliseconds for moderate payload sizes—representing a performance gain often exceeding 100x over on-the-fly compilation.

Summary Comparison

Metric Runtime Compilation (New Kernel) Cached Kernel Execution
Primary Bottleneck CPU parsing & driver shader compilation GPU memory bandwidth & compute limits
Typical Latency 15ms – 200ms+ 0.05ms – 5ms
Garbage Collection High (frequent buffer/context recreation) Minimal (reused typed buffers and textures)
Framerate Impact Significant stutter, blocking main thread Smooth execution suitable for 60+ FPS

To maximize throughput in gpu.js, instantiate all required compute kernels during application initialization. Vary computations by passing new data as arguments or uniforms rather than generating new kernel functions during runtime loops.
