Non-Uniform Memory Access and Cache Misses in gpu.js

This article examines how non-uniform thread memory access patterns degrade performance in gpu.js by triggering high cache miss rates. When GPU threads execute divergent or non-contiguous memory requests, the hardware cannot coalesce operations, causing significant memory pipeline stalls, decreased throughput, and inefficient VRAM utilization. Understanding these bottlenecks is critical for writing performant parallel algorithms in JavaScript environments.

The Mechanism of Memory Coalescing in gpu.js

gpu.js accelerates JavaScript calculations by compiling code into WebGL or WebGPU shader pipelines, executing parallel kernels across thousands of GPU threads organized into warps (NVIDIA) or wavefronts (AMD). The GPU architecture expects adjacent threads within a warp to access adjacent memory addresses simultaneously. When this condition is met, the GPU’s memory controller performs memory coalescing, consolidating dozens of individual thread requests into a single, high-speed 32-, 64-, or 128-byte memory transaction.

When kernels written in gpu.js feature non-uniform memory access—such as accessing data using non-sequential indices, large strides, or indirect lookups (e.g., data[indices[this.thread.x]])—coalescing breaks down. Instead of a single transaction, the memory controller must issue multiple serialized transactions for a single instruction cycle.

Impact on L1 and L2 Cache Misses

Non-uniform access fundamentally destroys spatial locality, the principle that nearby memory locations are likely to be accessed concurrently. The consequences on GPU cache structures include:

  1. Severe Cache Line Underutilization: GPU caches fetch data in fixed-size blocks (cache lines), typically 32 to 128 bytes wide. If adjacent threads access widely scattered memory addresses, each thread requires a distinct cache line. The application effectively transfers 32 to 128 bytes to read a single 4-byte float, drastically reducing useful data density and polluting the cache.
  2. Rapid Cache Thrashing: Because each divergent thread loads a unique cache line, the limited L1 and L2 cache capacities fill up immediately. This rapid influx forces early evictions of previously loaded data before other threads can reuse it, dropping L1 and L2 hit rates near zero.
  3. Escalation to Global Memory (VRAM): When cache lines miss at the L1 and L2 levels, the request cascades to high-latency global device memory. Accessing global memory takes hundreds of clock cycles compared to the near-instantaneous access of register files or L1 cache, forcing the warp scheduler to stall while awaiting data arrival.

Practical Consequences on Application Performance

In gpu.js, high cache miss rates caused by irregular memory patterns manifest in distinct operational penalties:

  • Memory-Bound Pipeline Stalls: Modern GPUs disguise memory latency by swapping executing warps to those ready to compute. When non-uniform access causes widespread cache misses, all available warps simultaneously stall waiting for VRAM transactions, leaving compute units idle.
  • Memory Bus Saturation: Non-coalesced access floods the internal GPU memory crossbar with dozens of low-efficiency requests. This memory bus saturation limits total system throughput, often making the gpu.js implementation slower than an optimized, single-threaded CPU loop.
  • Overhead from Texture-Based Buffers: Because gpu.js frequently encodes arrays into 2D WebGL textures under the hood, irregular access patterns disrupt the GPU's 2D spatial texture cache (texel caching), creating non-linear stride penalties unique to graphics-oriented compute wrappers.

Mitigation Strategies

To maintain low cache miss rates in gpu.js:

  • Align Indexing with Thread Coordinates: Structure array reads directly around this.thread.x without complex offsets or unpredictable mathematical shifts.
  • Flatten Multi-Dimensional Data: Ensure nested arrays are flattened sequentially so that incrementing thread coordinates map linearly to incrementing memory offsets.
  • Minimize Indirect Lookups: Avoid pointer-chasing patterns and lookups where the target address depends on the dynamic output of another array calculation.
