GPU.js Matrix Dot Product Computational Complexity

Computing large matrix dot products in standard JavaScript is computationally expensive due to the sequential execution of nested loops on the CPU, yielding a cubic time complexity of \(O(N^3)\). By offloading these calculations to the GPU using gpu.js, the computational workload is parallelized across thousands of shader cores via WebGL. While the total number of operations (work complexity) remains constant, the execution time complexity drops significantly from \(O(N^3)\) to \(O(N)\) under ideal parallel conditions, dramatically accelerating execution speed for large-scale datasets.

The Baseline: CPU-Bound Matrix Multiplication

When multiplying two square matrices, \(A\) and \(B\), each of dimension \(N \times N\), the resulting matrix \(C\) contains \(N^2\) elements. Calculating each individual element requires the dot product of a row from \(A\) and a column from \(B\), which involves \(N\) multiplications and \(N - 1\) additions:

\[C_{ij} = \sum_{k=0}^{N-1} A_{ik} \cdot B_{kj}\]

In a single-threaded CPU environment, such as the standard JavaScript runtime, this operation requires three nested loops:

  1. Iterating through rows (\(N\))
  2. Iterating through columns (\(N\))
  3. Accumulating the sum of products (\(N\))

This leads to:

  • Work Complexity (Total Operations): \(O(N^3)\)
  • Time Complexity (Sequential Execution): \(O(N^3)\)

As \(N\) scales to values like 2,048 or 4,096, the total operation count reaches tens of billions, leading to CPU bottlenecks and blocking the JavaScript event loop.

How gpu.js Restructures the Computation

gpu.js compiles a written JavaScript kernel directly into WebGL/GLSL fragment shaders. In this model, matrix multiplication changes from a sequential process to an embarrassingly parallel one.

Instead of iterating over every row and column, gpu.js sets the output dimensions to [N, N]. The GPU assigns an individual execution thread to compute the value of each cell \((i, j)\) in parallel.

Within each thread, only the innermost loop remains: iterating \(N\) times to compute the sum of products for that specific cell.

The Complexity Reduction

The computational complexity reduction achieved by gpu.js can be evaluated across theoretical and practical frameworks:

1. Theoretical Step (Span) Complexity

  • CPU: \(O(N^3)\) sequential steps.
  • GPU (Unbounded Parallelism): Assuming an ideal architecture with at least \(N^2\) execution units, all output cells are processed concurrently. The depth of the computation graph per thread is solely the loop of length \(N\). Thus, the theoretical time complexity drops from \(O(N^3)\) to \(O(N)\).

2. Practical Time Complexity (Bounded Parallelism)

Physical GPUs have a finite number of compute units (\(P\)). When \(N^2 > P\), thread execution is scheduled into warps or wavefronts.

  • Bounded Parallel Time Complexity: \(O\left(\frac{N^3}{P} + N\right)\)

Because modern GPUs contain thousands of stream processors, \(P\) is typically large enough (ranging from 1,000 to over 16,000 cores) to provide a 10x to 100x wall-clock speedup for sufficiently large \(N\).

Work Complexity vs. Time Complexity

It is important to distinguish between total work and execution time:

  • Total Work Complexity remains \(O(N^3)\): gpu.js does not alter the fundamental algebraic algorithm (unlike Strassen’s algorithm, which reduces work to \(O(N^{2.81})\)). The system still performs \(N^3\) arithmetic multiplications.
  • Time Complexity reduces to \(O(N)\) (ideal) or \(O(N^3/P)\) (actual): The operational efficiency comes entirely from distributing the \(N^3\) operations across concurrent execution units.

Practical Overhead Considerations

While the parallel complexity reduction is substantial, real-world performance gains in gpu.js depend on specific system overheads:

  • Memory Bus Latency: Transferring input matrices from CPU RAM to GPU VRAM (encoded as textures) introduces an \(O(N^2)\) memory transfer overhead.
  • Readback Cost: Retrieving the computed texture back into a JavaScript typed array introduces additional latency.
  • Matrix Threshold: For small matrices (typically \(N < 256\)), the overhead of compiling WebGL shaders and transferring data outweighs the parallel benefits, making CPU execution faster. However, as \(N\) grows beyond this threshold, the \(O(N^3)\) CPU curve diverges rapidly from the parallel GPU execution curve.
