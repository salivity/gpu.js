GPU.js Failure: Essential Client Error Report Data

When GPU.js fails in a client browser, automated fallbacks and debugging pipelines depend heavily on rich diagnostic context. Capturing a basic error message is rarely sufficient because client-side failures stem from heterogeneous hardware configurations, missing WebGL extensions, browser-specific sandbox restrictions, or invalid kernel transpilation. This guide details the exact diagnostic information developers must extract and bundle into client-side error telemetry to effectively troubleshoot and resolve GPU.js failures in production.

1. GPU.js Kernel Metadata and Execution State

Capture the configuration and inputs of the failing kernel instance:

  • Target vs. Fallback Mode: Record whether the kernel was initialized to run in 'gpu', 'cpu', or auto-detect mode, and whether a fallback was triggered prior to total failure.
  • Kernel Dimensions: Include the defined output array dimensions (e.g., [width, height, depth]). Mismatched or out-of-bounds output configurations frequently cause memory allocation failures.
  • Kernel Compilation Flags: Document settings such as graphical, precision, immutable, and pipeline.
  • Generated GLSL Source: GPU.js transpiles JavaScript functions into GLSL shaders. Include the generated GLSL string via kernel.getDebugString() or equivalent transpiled output to identify syntax or logic conversion issues.

2. WebGL Context and Hardware Specifications

Hardware inconsistencies across end-user devices are the primary cause of GPU.js execution errors. Query the underlying rendering context for:

  • Unmasked Renderer and Vendor: Using the WEBGL_debug_renderer_info extension, capture UNMASKED_VENDOR_WEBGL and UNMASKED_RENDERER_WEBGL. This reveals the exact GPU model and driver stack rather than the generic browser wrapper string.
  • Context Version: Note whether GPU.js initialized a webgl2, webgl, or experimental context.
  • Critical Capabilities and Limits: Query and record WebGL implementation limits via gl.getParameter():
    • MAX_TEXTURE_SIZE
    • MAX_3D_TEXTURE_SIZE (if WebGL2)
    • MAX_RENDERBUFFER_SIZE
    • MAX_FRAGMENT_UNIFORM_VECTORS
    • MAX_TEXTURE_IMAGE_UNITS
  • Floating-Point Texture Support: Query whether necessary extensions are present, such as OES_texture_float, OES_texture_float_linear, or EXT_color_buffer_float. Missing float texture support prevents GPU.js from performing precise mathematical calculations.

3. Native Error Stack and WebGL Logs

Standard JavaScript exceptions often conceal the underlying graphics pipeline breakdown. Bundle low-level error data:

  • JavaScript Error Details: Extract error.name, error.message, and the complete error.stack.
  • Shader Compilation and Program Linker Logs: If accessible during compilation failures, bundle gl.getShaderInfoLog() and gl.getProgramInfoLog().
  • Context Loss Status: Check if gl.isContextLost() returns true. If the browser terminated the graphics context due to a system GPU reset, crash, or excessive execution time (TDR - Timeout Detection and Recovery), document this event.

4. Client Environment Context

Hardware capability is heavily mediated by the client environment:

  • User Agent String: Capture navigator.userAgent to diagnose browser engine quirks or blacklisted GPU driver versions.
  • System Resource Metrics: Capture navigator.deviceMemory (RAM approximation in GB) and navigator.hardwareConcurrency (available logical processor threads).
  • Display and Viewport Profiles: Include window.devicePixelRatio, screen color depth, and window dimensions, as these directly affect WebGL memory allocation.
