Parallel CSR Matrix Multiplication in gpu.js

Parallelizing sparse matrix-matrix multiplication (SpGEMM) using the Compressed Sparse Row (CSR) format in gpu.js is technically feasible, but it presents significant architectural challenges and performance trade-offs. While gpu.js allows developers to execute parallel JavaScript code on the GPU via WebGL, standard SpGEMM algorithms rely on dynamic memory allocation and irregular memory access patterns that do not map naturally to WebGL's execution model. Consequently, achieving efficient parallelization requires specific algorithmic adaptations, such as multi-pass execution or outputting to dense structures.

The Challenge of CSR SpGEMM on the GPU

The CSR format represents a sparse matrix using three one-dimensional arrays: values, col_indices, and row_ptr. Computing the product of two CSR matrices (\(C = A \times B\)) requires traversing the non-zero elements of row \(i\) in matrix \(A\) and matching them with the corresponding rows in matrix \(B\).

In native GPU environments like CUDA, this is handled through dynamic shared memory, warp-level primitives, or parallel hash tables. In gpu.js, however, kernels are compiled into WebGL fragment shaders, which impose strict limitations:

  • No Dynamic Output Sizes: WebGL shaders must output to a pre-allocated texture of fixed dimensions. Because the number of non-zero entries in the product matrix \(C\) is unknown beforehand, allocating an exact CSR output buffer in a single pass is not possible.
  • Lack of Atomic Operations: Standard gpu.js shaders do not support atomic operations, preventing multiple threads from concurrently appending non-zero values to a shared CSR array.
  • Thread Divergence: Because sparse rows have varying numbers of non-zero elements, parallel threads executing loops based on row_ptr offsets will experience severe thread divergence, reducing GPU execution efficiency.

Implementation Strategies in gpu.js

To run CSR multiplication in gpu.js, you must adapt the algorithm to work within these constraints using one of the following approaches:

1. CSR-to-Dense Output (Simplest Approach)

If the resulting matrix can fit within system memory as a dense grid, you can parallelize across the output cells \((i, j)\) or rows \(i\).

  • Kernel Design: Define a 2D kernel matching the dimensions of output matrix \(C\).
  • Execution: Each GPU thread computes a single cell \(C[i][j]\). Thread \((i, j)\) reads the non-zero elements of row \(i\) from matrix \(A\) and checks whether any of those column positions have a corresponding entry in column \(j\) of matrix \(B\).
  • Limitation: This eliminates the memory benefits of sparse matrices, rendering it impractical for extremely large, high-dimensional matrices.

2. Two-Pass Symbolic and Numeric Approach (True CSR Output)

To retain a CSR output format, the computation must be split into multiple kernel passes:

  1. Symbolic Multiplication Pass: A kernel computes only the number of non-zero elements produced per row. This output is read back to determine the row_ptr array for matrix \(C\).
  2. Buffer Allocation: The total number of non-zero elements is calculated on the CPU, and the exact buffer sizes for values and col_indices are allocated.
  3. Numeric Multiplication Pass: A second kernel evaluates the actual values and column indices, writing them into predetermined offsets calculated during the symbolic phase.

Because gpu.js lacks fine-grained inter-thread communication, intermediate sorting and compaction often require transferring small index buffers back to the CPU, introducing PCIe transfer overhead.

Performance Considerations

  • Memory Bandwidth: Storing CSR arrays inside textures requires packing 1D data into 2D floating-point textures, adding index-decoding overhead inside the shader.
  • Overhead vs. Native JS: For small-to-medium sparse matrices, CPU-based sparse algorithms (which can freely use dynamic hash maps or heaps per row) often outperform gpu.js due to the overhead of kernel compilation and texture data transfers.
  • WebGPU Alternatives: Modern WebGPU compute shaders provide atomic operations, storage buffers, and workgroup shared memory. If your environment supports WebGPU, writing compute shaders directly provides a much more suitable foundation for parallel SpGEMM than WebGL-backed gpu.js kernels.
