How to Monitor GPU VRAM Usage in gpu.js

Monitoring GPU VRAM usage during heavy workloads in gpu.js requires external tooling and manual memory tracking because the WebGL abstraction underlying the library does not expose a direct VRAM query API. This article outlines how to track memory utilization across both browser and Node.js environments, calculate memory footprints programmatically, and manage gpu.js resources to prevent out-of-memory crashes.

The WebGL Abstraction Barrier

Because gpu.js compiles JavaScript into WebGL shaders, it operates under the standard WebGL security and portability sandbox. The WebGL standard intentionally omits APIs that report real-time physical VRAM utilization to prevent device fingerprinting and hardware-level exploits. As a result, you cannot call a native gpu.js method to return currently consumed megabytes of video memory. Monitoring must be handled through environment-level tools or memory estimation.

Monitoring in Node.js Workloads

When running gpu.js on the server using headless-gl, the most accurate method to observe VRAM utilization is through host-level GPU management interfaces.

1. Real-Time CLI Profiling (NVIDIA)

If your system utilizes an NVIDIA graphics card, monitor allocation continuously in your terminal using the system management interface:

nvidia-smi --query-gpu=memory.used,memory.free,memory.total --format=csv -l 1

This command queries memory stats once per second (-l 1). For a continuous visual interface showing per-process consumption, use interactive tools such as nvtop.

2. Programmatic Polling

You can sample VRAM metrics inside your Node.js application by spawning a sub-process alongside your gpu.js pipeline:

const { execSync } = require('child_process');

function getVRAMUsage() {
  const output = execSync('nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits');
  return parseInt(output.toString().trim(), 10); // Returns VRAM used in MB
}

console.log(`Pre-execution VRAM: ${getVRAMUsage()} MB`);
const result = heavyKernel(largeDataArray);
console.log(`Peak VRAM: ${getVRAMUsage()} MB`);

Monitoring in Browser Workloads

In client-side applications, system-level CLI commands are inaccessible. Instead, you must rely on browser diagnostic panels:

  • Chrome Task Manager: Press Shift + Esc inside Google Chrome, right-click the table header, and select GPU Memory. This isolates the exact VRAM footprint assigned to the current tab, including WebGL textures generated by gpu.js.
  • DevTools Performance Monitor: Open Chrome DevTools (F12), press Ctrl + Shift + P (or Cmd + Shift + P), type Show Performance Monitor, and observe real-time spikes in the "JS heap" and graphics pipeline alongside WebGL draw calls.

Calculating Theoretical Memory Allocation

You can predict memory consumption before execution by calculating the byte footprint of your input and output matrices. Under default settings, gpu.js stores 2D floating-point matrices as 32-bit floating-point textures (4 bytes per element):

\[\text{Memory (bytes)} = \text{Rows} \times \text{Columns} \times 4\]

For example, two \(4096 \times 4096\) matrices processed to create a third output matrix require:

\[3 \times (4096 \times 4096 \times 4 \text{ bytes}) \approx 201.3 \text{ MB}\]

Multiply this baseline by a factor of 1.5 to 2 to account for intermediate framebuffers and internal driver overhead created during execution.

Releasing VRAM to Prevent Leaks

Uncollected textures and dead kernels rapidly consume VRAM during iterative operations. To maintain stable memory usage:

  1. Dispose of Output Textures: When returning textures using { output: [w, h], pipeline: true }, explicitly call .delete() on textures that are no longer needed: 
    const textureResult = pipelineKernel(inputData);
// Process data...
textureResult.delete();
  2. Destroy Unused Kernels: If creating kernels dynamically inside a loop, clean up graphics contexts when finished: 
    kernel.destroy();
  3. Reset Contexts: If running sequential batch processing where VRAM gradually climbs, manually destroy the primary GPU instance and instantiate a new one to force the underlying driver to free unreferenced framebuffers.
