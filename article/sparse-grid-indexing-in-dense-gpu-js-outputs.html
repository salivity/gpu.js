Sparse Grid Indexing in Dense GPU.js Outputs

Simulating sparse spatial grids within GPU.js presents unique challenges because WebGL and GPU.js inherently allocate and output dense, rectangular arrays. When most grid cells contain empty space, rendering or computing over an entire dense domain results in wasted memory and redundant computations. This article explores practical techniques—including spatial hashing, Morton order linearization, two-pass indirection buffers, and tiled hierarchical binning—that enable developers to emulate sparse data structures efficiently while constrained by dense GPU.js output buffers.

Spatial Hashing with Fixed Buckets

Spatial hashing maps sparse multi-dimensional coordinates \((x, y, z)\) into a linear, fixed-size dense output array. In a GPU.js kernel, each output thread represents a hash bucket index rather than an absolute coordinate.

To implement spatial hashing in GPU.js:

  1. Define a deterministic hash function inside the kernel, such as: \[\text{hash}(x, y) = ((x \times p_1) \oplus (y \times p_2)) \pmod{\text{tableSize}}\] where \(p_1\) and \(p_2\) are large prime numbers.
  2. Store key-value pairs in the output (e.g., packing the original coordinates alongside the computed values into distinct RGBA channels).
  3. Handle collisions using fixed-step linear probing within the kernel or by reserving multiple consecutive slots per bucket as a uniform capacity buffer.

Two-Pass Indirection Buffers

The most reliable approach to avoid executing kernels over empty space is an indirection architecture. Instead of running a kernel across the entire sparse bounding box, the computation is split into two stages:

  1. Active Cell Compaction: Identify non-empty cells. This can be pre-computed on the CPU for dynamic updates or processed via a reduction kernel that records only valid coordinates into a compact 1D index array.
  2. Dense Compute Kernel: Configure the primary GPU.js kernel output size to match exactly the number of active cells (\(N\)). Inside the kernel, read the target \((x, y, z)\) coordinate from the indirection array using this.thread.x. The kernel calculates results only for occupied cells and writes directly to a compact 1D dense array.

This decouples compute scale from spatial resolution, ensuring 100% thread utilization during the heavy calculation phase.

Morton Order Linearization (Z-Order Curves)

Linearizing sparse grids using Morton codes preserves spatial locality better than row-major ordering. Interleaving the binary bits of coordinate indices transforms multi-dimensional coordinates into a single 1D index:

  • Cells close to each other in 2D or 3D space remain clustered together in the linear buffer.
  • Memory bandwidth is optimized when neighboring GPU threads access adjacent cache lines.
  • A Morton decoding function implemented within GPU.js functions can quickly reconstruct \((x, y, z)\) coordinates from a 1D thread ID using bitwise emulation via integer arithmetic.

Coarse Tile Binning (Block-Sparse Grids)

Rather than tracking individual sparse cells, divide the simulation space into uniform macro-tiles (e.g., \(8 \times 8\) or \(16 \times 16\) blocks):

  • Macro Grid: Maintain a small bitmask or dense metadata texture where each entry represents an entire block. An entry of 0 denotes an entirely empty block, while 1 marks a block containing active data.
  • Block Storage: Allocate a dense 2D texture sized only to accommodate the active blocks packed contiguously.
  • Coordinate Remapping: The kernel evaluates coordinates by determining which active block a thread belongs to via a lookup table. This provides a balance between sparse storage flexibility and dense execution efficiency, matching the GPU's natural tendency to run threads in local warps or wavefronts.
