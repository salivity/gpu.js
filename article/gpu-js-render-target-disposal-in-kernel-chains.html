GPU.js Render Target Disposal in Kernel Chains

This article examines how GPU.js manages intermediate render targets when chaining kernel executions. It covers the underlying WebGL framebuffer and texture lifecycle, explains the mechanics of pipeline mode, details how memory deallocation is handled between execution stages, and highlights strategies to prevent GPU memory leaks during intensive operations.

Understanding Pipeline Mode and Render Targets

In GPU.js, operations are executed by compiling JavaScript functions into WebGL GLSL shaders. Under normal operation, a kernel finishes its execution by reading the pixel data from the GPU back to the CPU via gl.readPixels, converting the output into standard JavaScript arrays. This CPU-GPU synchronization is costly.

To avoid this bottleneck, GPU.js provides a pipelining mechanism enabled via kernel.setPipeline(true). When pipeline mode is enabled, the kernel outputs a Texture object rather than a multidimensional array. This texture represents an active WebGL render target—specifically, a WebGLTexture attached to a WebGLFramebuffer. Chaining occurs when this output Texture is passed directly as an argument into a subsequent kernel.

The Lifecycle of Intermediate Render Targets

When chaining multiple kernels (e.g., Kernel A \(\to\) Kernel B \(\to\) Kernel C), intermediate textures are generated to store the outputs of the intermediate stages. GPU.js handles these textures through distinct phases:

  1. Target Allocation: When Kernel A executes, GPU.js binds an internal WebGL framebuffer and attaches a newly created or cached WebGLTexture as the color attachment. The fragment shader writes its results directly to this texture.
  2. Transfer to Subsequent Kernels: The resulting Texture instance wraps the native WebGLTexture. When passed into Kernel B, GPU.js binds this texture to a WebGL texture unit (e.g., gl.TEXTURE0), treating the output of Kernel A as an input sampler in Kernel B's shader.
  3. Downstream Execution: Kernel B executes, writing to a new intermediate render target, leaving the output of Kernel A bound only as an input texture.

Internal Disposal vs. JavaScript Garbage Collection

WebGL resources exist in GPU VRAM and are not directly managed by the JavaScript engine’s standard Garbage Collector (GC). Although JavaScript manages the wrapper object, the underlying native GPU allocations (WebGLTexture and WebGLFramebuffer) persist until explicitly freed through the WebGL context.

During chained calls, GPU.js does not automatically dispose of intermediate render targets on its own accord between independent kernel calls. The runtime assumes intermediate textures may still be required by the user application for subsequent computation, branched pipelines, or debugging.

  • No Implicit Intermediate Deletion: In a manual chain (const b = kernelB(kernelA(data));), the texture produced by kernelA remains allocated in WebGL memory even after kernelB finishes, because the reference is returned and held.
  • Garbage Collector Lag: If an intermediate texture loses all JavaScript references, the browser's Garbage Collector will eventually trigger the finalizer, which may release the WebGL resource. However, relying on JavaScript GC for GPU memory frequently leads to out-of-memory (OOM) errors or context loss, as the GC has visibility into the small JavaScript wrapper size, not the massive VRAM footprint of the texture.

Explicit Cleanup with texture.delete()

To guarantee determinism and prevent VRAM exhaustion, GPU.js equips its Texture class with an explicit .delete() method. When handling linear pipelines or loops, intermediate render targets must be explicitly disposed of by the consumer once they are consumed:

const textureA = kernelA(inputData);
const textureB = kernelB(textureA);

// Dispose of the intermediate texture manually
textureA.delete();

const finalResult = kernelC(textureB).toArray();
textureB.delete();

Calling .delete() executes gl.deleteTexture() and detaches/deletes associated framebuffers internally, releasing the intermediate render target immediately back to the GPU driver.

Texture Recycling and Ping-Pong Buffering

In iterative operations (such as Conway's Game of Life or physics simulations), continuously creating and destroying textures causes driver overhead. GPU.js supports iterative chaining through ping-pong rendering techniques.

Rather than allocating and destroying intermediate render targets on every iteration, developers cycle between two pre-allocated textures: using Texture 1 as an input while Texture 2 serves as the render target, and swapping their roles in the next cycle. In this design, no internal disposal is required during the loop; only two render targets are maintained in memory, and both are disposed of manually once the loop completes.

Combined Kernels and Sub-Kernels

For pipelines that can be pre-determined, GPU.js provides gpu.combineKernels(). When kernels are executed as a combined chain:

  • GPU.js manages the sub-kernel execution path internally.
  • The intermediate state transitions occur directly on the hardware without round-trips to CPU memory.
  • However, intermediate WebGL textures allocated between sub-kernels still need to be handled by the engine. Where possible, GPU.js avoids redundant allocation by executing sequentially, but users must ensure that top-level returned textures from the compound operation are cleanly deleted or converted back to arrays using .toArray(), which triggers an internal cleanup cycle.
