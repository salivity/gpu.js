How GPU.js Inlines Custom Functions in GLSL

GPU.js allows developers to write standard JavaScript functions and execute them on the GPU by transpiling the code into OpenGL Shading Language (GLSL). To handle custom helper functions, GPU.js parses the JavaScript code into an Abstract Syntax Tree (AST), infers the necessary static types, converts the logic into valid GLSL function syntax, and integrates these subroutines directly into the generated fragment shader before passing it to WebGL for compilation.

1. Abstract Syntax Tree (AST) Parsing

When a user defines a kernel or registers an external custom function using gpu.addFunction(), GPU.js does not treat the function as a raw string. Instead, it extracts the function's source code via .toString() and parses it using an internal JavaScript parser (such as Acorn). This creates an AST—a structured, hierarchical representation of the function's statements, variable declarations, loops, and return statements.

2. Type Inference and Argument Validation

GLSL is a statically typed language, whereas JavaScript is dynamically typed. Before inlining or declaring any custom function in the shader, GPU.js analyzes how arguments are passed and used:

  • Argument Signatures: When functions are registered, parameter types (e.g., float, int, Array(2)) can be explicitly declared or inferred from the caller's arguments.
  • Return Type Analysis: The parser inspects ReturnStatement nodes within the AST to infer the return type, ensuring that the function signature in GLSL matches the evaluated output (e.g., turning a JS numeric return into a GLSL float).

3. Syntax Transpilation to GLSL

Once the AST is constructed and types are resolved, GPU.js walks the tree and translates JavaScript constructs into their GLSL equivalents:

  • Standard JavaScript math functions (e.g., Math.sin(), Math.floor()) are converted directly to native GLSL functions (sin(), floor()).
  • Dynamic loop constructs are rewritten into statically bound GLSL for loops.
  • Variable declarations are assigned concrete GLSL types (such as float or vec4) rather than var, let, or const.

4. Direct Inlining vs. Function Definition Injection

GPU.js handles custom functions primarily by declaring them at the top of the generated GLSL fragment shader, though true AST-level node inlining can also occur:

  • Top-Level Function Injection: In standard operations, GPU.js transpiles the custom function into a standalone GLSL function definition and places it in the shader code above the main() function. When the kernel calls the custom function, the compiled GLSL simply calls the injected GLSL function natively.
  • AST Call Replacement (Inlining): In cases where functions are marked for explicit inlining, or for small sub-expressions, the compiler replaces the CallExpression node inside the caller’s AST with the actual body or expression of the target function. This eliminates function call overhead directly within the GLSL output.

5. Final Shader Assembly

During the final build step of the kernel:

  1. All global definitions, precision specifiers, and uniform declarations are written.
  2. The transpiled custom functions (and any recursive dependencies they require) are output in topological order to ensure that any function is declared before it is called.
  3. The main kernel logic is wrapped inside GLSL's void main().
  4. The entire string is passed to the WebGL context via gl.shaderSource() and compiled into a native GPU program with gl.compileShader().
