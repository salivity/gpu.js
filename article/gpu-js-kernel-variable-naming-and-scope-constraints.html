gpu.js Kernel Variable Naming and Scope Constraints

Writing compute kernels with gpu.js requires understanding that JavaScript code is transpiled directly into WebGL shader language (GLSL). Because of this compilation process, variable naming and identifier scoping inside a kernel function do not follow standard JavaScript flexibility. Instead, they must strictly adhere to the static typing, shadowing, and namespace limitations imposed by GLSL and the gpu.js parser.

Variable Naming Constraints

Identifiers declared inside a gpu.js kernel must conform to both JavaScript syntax and WebGL/GLSL naming specifications.

  • GLSL Reserved Keywords: You cannot use identifiers that match GLSL native types and keywords. Avoid names such as float, int, vec2, vec3, vec4, mat2, mat3, mat4, sampler2D, attribute, uniform, varying, discard, and precision. Using these as variable names will trigger compiler errors during shader generation.
  • Reserved Prefixes: WebGL reserves specific prefixes for internal pipeline variables. Identifiers must not begin with gl_ (such as gl_Position or gl_FragColor) or contain consecutive underscores (__), as these patterns are reserved by OpenGL.
  • Kernel Namespace Properties: The this context is restricted to pre-defined execution properties. You cannot define custom properties on this. Identifiers such as this.thread.x, this.thread.y, this.thread.z, and this.output.x are reserved for thread coordinates and output dimensions.
  • Character Restrictions: Variable names must begin with a letter or an underscore and can only contain alphanumeric characters and underscores. Extended Unicode or special characters valid in standard JavaScript are not supported by the GLSL compiler.

Identifier Scoping Constraints

Because kernels execute in parallel across GPU threads without access to the JavaScript engine's runtime environment, scoping rules differ significantly from typical JavaScript execution.

  • No Closure Scope Access: A kernel function cannot access variables declared outside its immediate function body via standard JavaScript closures. Any external data must be explicitly passed into the kernel as an argument or registered during creation using the constants configuration object.
  • No Access to Browser or Node.js Globals: Identifiers referring to standard runtime environments—such as window, document, process, or console—do not exist on the GPU and will cause transpilation failures if referenced.
  • Static Type Binding per Scope: In JavaScript, a variable declared with let can change types dynamically. In a gpu.js kernel, the transpiler infers the static type (such as integer or float) upon the variable's initial assignment. Reassigning an identifier to a different data type within the same scope is prohibited.
  • Variable Shadowing: Shadowing variables across parent and child blocks (such as defining a variable inside a for loop with the same name as one in the outer function body) can lead to compilation failures or undefined behavior depending on the underlying GPU driver's strictness. It is recommended to maintain unique identifiers across all blocks within a single kernel.
  • Sub-function Scoping: When using helper functions added via gpu.addFunction(), variables defined inside the helper are strictly local to that function. The helper cannot access variables from the calling kernel's scope unless they are passed explicitly as arguments.
