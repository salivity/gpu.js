Nagel-Schreckenberg Traffic Simulation in gpu.js

This guide explains how to implement the Nagel-Schreckenberg traffic flow model using gpu.js to leverage parallel hardware acceleration. You will learn the core mathematical rules governing this cellular automaton, how to map the agent dynamics into GPU compute shaders, and how to execute the simulation loop in JavaScript to observe emergent phenomena like phantom traffic jams.

1. The Nagel-Schreckenberg Model Mechanics

The Nagel-Schreckenberg (NaSch) model is a discrete cellular automaton that simulates single-lane highway traffic. The road is divided into discrete cells of uniform length, where each cell is either empty or occupied by a single vehicle. Each vehicle has an integer velocity ranging from \(0\) to \(v_{\max}\).

At each discrete time step \(t \to t + 1\), all vehicles update simultaneously according to four sequential rules:

  1. Acceleration: Drivers attempt to accelerate up to the maximum speed limit: \[v \leftarrow \min(v + 1, v_{\max})\]
  2. Slowing Down (Collision Avoidance): Drivers decelerate to avoid hitting the vehicle ahead. If \(d\) is the distance in cells to the next car: \[v \leftarrow \min(v, d - 1)\]
  3. Randomization: Drivers unpredictably reduce speed with probability \(p \in [0, 1]\) (representing driver hesitation or road imperfections): \[v \leftarrow \max(v - 1, 0) \quad \text{with probability } p\]
  4. Motion: Each vehicle advances by its updated velocity: \[x \leftarrow (x + v) \pmod L\] (where \(L\) is the total road length using periodic boundary conditions)

2. Adapting NaSch for GPU Execution

Graphics processing units (GPUs) excel at executing identical logic across many data points in parallel. In gpu.js, computations run via compiled WebGL fragment shaders.

In a parallel architecture, the Lagrangian (agent-based) representation is optimal:

  • Instead of mapping a road grid where cells search backward to determine if a vehicle enters them, each thread processes a single vehicle.
  • Array 1 stores vehicle positions: positions[i].
  • Array 2 stores vehicle velocities: velocities[i].
  • Thread i evaluates vehicle i by inspecting vehicle i + 1 (the car directly ahead) to calculate distance \(d\).

Because GPU shaders do not have access to JavaScript’s native Math.random(), stochastic deceleration requires a fast pseudo-random number generator (PRNG) implemented directly inside the kernel using a hash function.

3. Implementation in gpu.js

Setting Up gpu.js

First, include gpu.js in your project via npm or a CDN:

npm install gpu.js

Initialize the GPU instance:

const { GPU } = require('gpu.js');
const gpu = new GPU();

Pseudo-Random Number Function for the Kernel

Since GPU threads execute independently, create a deterministic hash based on the vehicle index and the current simulation step:

function pseudoRandom(seed, index) {
  // Classic fractional sine hash suitable for GLSL
  const x = Math.sin(seed * 12.9898 + index * 78.233) * 43758.5453;
  return x - Math.floor(x);
}

Kernel: Updating Velocities

The velocity update kernel computes acceleration, distance braking, and randomization:

const updateVelocities = gpu.createKernel(function(positions, velocities, roadLength, numCars, vMax, pSlow, seed) {
  const i = this.thread.x;
  
  // Identify the lead car index (periodic boundary)
  const nextCarIndex = (i + 1) % numCars;
  
  // Calculate distance to lead car
  let distance = positions[nextCarIndex] - positions[i];
  if (distance <= 0) {
    distance += roadLength;
  }

  // 1. Acceleration
  let v = velocities[i];
  if (v < vMax) {
    v += 1;
  }

  // 2. Deceleration (avoid collision)
  if (v >= distance) {
    v = distance - 1;
  }

  // 3. Randomization
  const rand = pseudoRandom(seed, i);
  if (rand < pSlow && v > 0) {
    v -= 1;
  }

  return v;
}, {
  functions: [pseudoRandom]
}).setOutput([NUM_CARS]);

Kernel: Updating Positions

The position kernel advances cars based on the calculated velocities:

const updatePositions = gpu.createKernel(function(positions, velocities, roadLength) {
  const i = this.thread.x;
  return (positions[i] + velocities[i]) % roadLength;
}).setOutput([NUM_CARS]);

4. Running the Simulation Loop

Initialize the vehicle state arrays and execute the two kernels sequentially:

const ROAD_LENGTH = 1000;
const NUM_CARS = 200;
const V_MAX = 5;
const P_SLOW = 0.3;
const TIME_STEPS = 500;

// Initialize vehicles evenly spaced on the road
let positions = new Float32Array(NUM_CARS);
let velocities = new Float32Array(NUM_CARS);

const spacing = ROAD_LENGTH / NUM_CARS;
for (let i = 0; i < NUM_CARS; i++) {
  positions[i] = Math.floor(i * spacing);
  velocities[i] = Math.floor(Math.random() * (V_MAX + 1));
}

// Ensure car positions are strictly sorted
positions.sort();

// Simulation loop
for (let t = 0; t < TIME_STEPS; t++) {
  // Step A: Calculate velocities on the GPU
  velocities = updateVelocities(
    positions,
    velocities,
    ROAD_LENGTH,
    NUM_CARS,
    V_MAX,
    P_SLOW,
    t + 1 // Seed varies by step
  );

  // Step B: Calculate new positions on the GPU
  positions = updatePositions(
    positions,
    velocities,
    ROAD_LENGTH
  );
}

5. Key Considerations

  • Pipeline Modes: By default, gpu.js downloads array buffers back to the CPU after each call. To maximize performance over large iterations, set { pipeline: true } in your kernel options to keep memory directly on the GPU texture buffer between steps.
  • Order Maintenance: The NaSch model assumes the relative ordering of cars remains invariant. Because car \(i\) cannot overtake car \(i + 1\), maintaining array order allows each thread to look strictly at index (i + 1) % NUM_CARS without performing costly search operations across the road.
