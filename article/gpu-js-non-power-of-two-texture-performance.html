GPU.js Non-Power-of-Two Texture Performance

Using non-power-of-two (NPOT) textures in gpu.js can introduce subtle but significant performance bottlenecks in compute workloads. Because gpu.js translates JavaScript functions into GLSL shaders and relies on WebGL textures to store and read numeric data, memory alignment directly dictates computational efficiency. Reading from NPOT textures forces the underlying graphics hardware to manage unaligned memory lookups, leading to reduced texture cache hit rates, potential shader instruction overhead, and WebGL backend limitations.

Memory Alignment and Cache Inefficiency

Modern GPU memory controllers and texture sampling units are architected around power-of-two (POT) memory boundaries, typically fetching data in cache line sizes of 32, 64, or 128 bytes. When textures have dimensions that are powers of two (e.g., \(256 \times 256\) or \(1024 \times 1024\)), data addresses map linearly and cleanly to texture cache lines.

With NPOT textures (such as \(300 \times 700\)), the memory strides across texture rows become irregular. When a shader program generated by gpu.js executes texture lookups (texelFetch or normalized sampling), neighboring threads in a warp or wavefront often request addresses that cross cache line boundaries. This leads to higher texture cache miss rates, increased memory bus traffic, and higher latency while threads wait for memory fetches to resolve.

WebGL 1.0 vs. WebGL 2.0 Backend Constraints

The severity of the performance impact depends largely on the underlying WebGL context initialized by gpu.js:

  • WebGL 1.0 (Limited NPOT Support): WebGL 1.0 does not support full NPOT texturing by default. Textures with NPOT dimensions are restricted to CLAMP_TO_EDGE wrap modes and cannot generate mipmaps. To circumvent hardware limitations, gpu.js may pad data internally or inject additional index-mapping logic into the shader to simulate the expected array dimensions. This adds runtime computation to every pixel or kernel invocation.
  • WebGL 2.0 (Full NPOT Support): While WebGL 2.0 natively supports NPOT textures without wrapping restrictions, hardware-level memory penalties remain. Even though the API accepts arbitrary dimensions without failing, the physical texture-mapping units (TMUs) must still handle the non-aligned strides in silicon.

Coordinate Normalization and Coordinate Arithmetic

gpu.js maps multi-dimensional JavaScript arrays into flattened or rectangular 2D textures, calculating texture coordinates automatically inside the generated shader. When dealing with POT dimensions, bitwise shifts or simple bitmasking can theoretically optimize coordinate transformations at the driver level.

With NPOT dimensions, the driver and shader must use standard floating-point division and modulo arithmetic to compute normalized texture coordinates (\(u, v \in [0, 1]\)) or integer texel coordinates. These extra arithmetic operations increase register pressure and consume arithmetic logic unit (ALU) cycles that would otherwise be spent on primary computational tasks.

Mitigating NPOT Overhead in gpu.js

To eliminate the performance degradation associated with reading NPOT textures:

  1. Pad Input Arrays: Pad array lengths to the nearest power of two (e.g., padding an array of length 700 to 1024) using neutral dummy values (like zeros), and discard the padded results after kernel execution.
  2. Force WebGL 2.0: Ensure the gpu.js instance is explicitly configured to use WebGL 2.0 (new GPU({ mode: 'webgl2' })), which avoids software-level emulations and utilizes hardware-level NPOT sampling.
  3. Restructure Data Dimensions: When dealing with 2D kernels, dimension arrays into balanced POT configurations (e.g., \(512 \times 512\) rather than \(1000 \times 262\)) to maximize spatial locality within the texture cache.
