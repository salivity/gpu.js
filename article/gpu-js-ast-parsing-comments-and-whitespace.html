gpu.js AST Parsing: Comments and Whitespace

This article explores how the AST (Abstract Syntax Tree) parser in gpu.js handles comments and whitespace when transpiling JavaScript kernel functions into GLSL shader code. It covers the parsing stage using Acorn, the omission of non-functional syntactic trivia during lexical analysis, and how the transpiler generates clean, deterministic shader output.

The Parsing Mechanism in gpu.js

To run JavaScript on the GPU, gpu.js must translate written JavaScript functions into GLSL (OpenGL Shading Language) compatible with WebGL or WebGPU. To achieve this, gpu.js uses the Acorn JavaScript parser to convert the function string into an Abstract Syntax Tree (AST).

An AST is a structural, hierarchical tree representation of the source code's syntax. During this conversion, code is broken down into semantic nodes such as VariableDeclaration, BinaryExpression, and ReturnStatement.

How Whitespace is Handled

During the lexical analysis (tokenization) phase of parsing:

  1. Token Delimitation: Whitespace characters (spaces, tabs, and line breaks) are used solely to distinguish between separate identifiers, keywords, and operators.
  2. Discarding Trivia: Once the parser identifies tokens, it discards whitespace entirely. The generated AST contains no dedicated nodes for whitespace because structural hierarchy and parent-child node relationships inherently define execution flow.
  3. Synthetic Formatting: When gpu.js traverses the AST to construct GLSL code, it emits its own formatting. Any indentation or line breaks present in the final GLSL shader string are generated programmatically by the transpiler to produce valid GLSL, completely independent of the original JavaScript layout.

How Comments Are Handled

Comments—both single-line (//) and multi-line (/* */)—are treated similarly to whitespace during the compilation process:

  1. Ignored During Parsing: By default, standard AST generation treats comments as trivia. Unless an AST parser is explicitly configured to preserve comments by attaching them as node metadata, the tokenizer simply skips them. gpu.js does not configure Acorn to attach comment metadata to AST nodes.
  2. Omission in Transpilation: Because comments do not generate AST nodes, they are absent from the structural representation traversed by the GLSL code generator.
  3. Absence in Output: The transpiled GLSL string contains only executable instructions, variable definitions, and framework-specific header declarations required by the GPU. JavaScript comments are never forwarded into the resulting shader program.

Implications for Kernel Development

Because whitespace and comments are discarded at the AST stage, developers writing gpu.js kernels can format their code and write extensive inline documentation without impacting GPU memory, shader compile times, or runtime execution performance. The resulting GLSL shader remains strictly functional and minimal.
