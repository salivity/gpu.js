Why GPU.js Does Not Support Nested Objects

GPU.js accelerates JavaScript operations by compiling kernel functions into shaders executed directly on the graphics hardware. However, it cannot accept complex nested objects as kernel inputs due to the fundamental architectural gap between dynamic JavaScript environments and GPU execution models. This limitation stems from the constraints of shading languages like GLSL, the physical design of GPU memory architectures, and the performance costs associated with pointer chasing and memory serialization.

The GLSL Translation Barrier

GPU.js functions under the hood by transpiling JavaScript code into WebGL shader code, typically written in GLSL (OpenGL Shading Language). GLSL is a strictly typed, low-level language that requires all data structures to be defined with fixed sizes and explicit types before compilation. JavaScript objects, by contrast, are dynamically typed, non-contiguous, and variable in shape. WebGL cannot directly interpret arbitrary JavaScript reference types or dynamic object trees, meaning GPU.js would need to generate complex custom struct definitions and data-packing routines for every unique object structure passed to a kernel.

Contiguous Memory vs. Pointer References

Modern GPUs rely on massively parallel Single Instruction, Multiple Data (SIMD) or Single Instruction, Multiple Threads (SIMT) pipelines designed to process flat, contiguous blocks of data simultaneously.

  • Lack of Pointer Dereferencing: GPUs excel at accessing regular memory buffers, such as 1D, 2D, or 3D textures and typed arrays. JavaScript nested objects rely on pointers referencing memory scattered across the host system's heap. GPUs do not have native mechanisms to safely follow dynamic heap references or resolve arbitrary pointer chains.
  • Cache Inefficiency: Thread warps require coalesced memory access, where neighboring threads access adjacent memory addresses in parallel. Traversing nested object references causes fragmented, non-coalesced memory reads, severely degrading hardware performance.

Serialization Overhead

To make a nested object readable by a GPU, the CPU runtime would first need to recursively traverse the object graph, serialize it, and pack it into a flat, predictable memory layout (such as a typed array or a texture buffer) before transferring it over the PCI-e bus. Performing deep object serialization in JavaScript adds substantial CPU overhead. This overhead often exceeds the computation time saved by executing the task on the GPU, directly undermining the primary objective of using GPU.js for high-performance computation.

Recommended Alternatives

To process structured data in GPU.js, developers must normalize and flatten data structures before supplying them as inputs:

  1. Flattened Typed Arrays: Flatten nested objects into 1D Float32Array or Int32Array buffers, using fixed mathematical stride formulas (e.g., index = objectId * propertyCount + propertyOffset) to access specific attributes.
  2. Structure of Arrays (SoA): Instead of using an array of objects containing multiple properties, store each property in its own dedicated, parallel array. This approach mirrors the hardware's native buffer layout and aligns with GPU memory access patterns.
  3. Multi-dimensional Matrix Inputs: Group related numerical attributes into 2D or 3D numeric matrices that GPU.js can natively map to hardware texture memory.
