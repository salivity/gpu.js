WebGL 2 Multi-Render Targets in GPU.js

This article explains how GPU.js implements and manages Multi-Render Targets (MRT) under a WebGL 2 context. You will learn how the library translates JavaScript functions into GLSL ES 3.0 shaders, configures the underlying WebGL 2 framebuffers and color attachments, and leverages kernel maps to output multiple distinct datasets in a single execution pass.

Native WebGL 2 MRT Architecture

In WebGL 1, rendering to multiple textures simultaneously required the optional WEBGL_draw_buffers extension. When operating under a WebGL 2 context, Multi-Render Target capabilities are native to the core specification. WebGL 2 guarantees support for multiple simultaneous color attachments through gl.drawBuffers(), providing a hardware-accelerated pipeline where a single fragment shader execution can write to distinct output buffers.

GPU.js capitalizes on this native support to execute complex multi-output computational tasks without the performance penalty of multipass rendering.

Abstracting MRT via Kernel Maps

GPU.js exposes multi-render target functionality primarily through its createKernelMap API. Instead of writing separate kernels that each execute their own render cycle, developers provide a collection of sub-functions (sub-kernels) mapped to an object or array.

When the target context is set to WebGL 2, GPU.js treats these sub-kernels not as independent execution units, but as distinct output channels of a unified fragment shader:

const gpu = new GPU({ mode: 'webgl2' });

const megaKernel = gpu.createKernelMap({
  addResult: function(a, b) {
    return a[this.thread.x] + b[this.thread.x];
  },
  multiplyResult: function(a, b) {
    return a[this.thread.x] * b[this.thread.x];
  }
}, function(a, b) {
  addResult(a, b);
  multiplyResult(a, b);
}).setOutput([1024]);

GLSL ES 3.0 Transpilation

When GPU.js compiles a createKernelMap under WebGL 2, it generates GLSL ES 3.0-compliant shader code.

  1. Output Declaration: Unlike WebGL 1, which assigns values to gl_FragColor or gl_FragData[n], WebGL 2 requires explicit out variable declarations. GPU.js declares explicit output locations for each mapped sub-kernel: 
    #version 300 es
precision highp float;
// ... input uniforms ...
layout(location = 0) out vec4 target_addResult;
layout(location = 1) out vec4 target_multiplyResult;
  2. Sub-Kernel Inlining: The logic from the individual sub-kernel functions is inlined into the main() function of the fragment shader.
  3. Data Packing: GPU.js automatically encodes the return value of each sub-kernel (floating-point numbers, integers, or vectors) into the corresponding vec4 format expected by the output locations.

Framebuffer Configuration and Draw Buffers

To receive the outputs declared by the GLSL shader, the underlying GPU.js WebGL 2 runtime configures a dedicated WebGLFramebuffer object:

  1. Texture Generation: GPU.js creates individual WebGL texture instances corresponding to the dimensions defined by setOutput().
  2. Color Attachments: Each texture is bound to a sequential attachment point on the framebuffer:
    • Texture 0 binds to gl.COLOR_ATTACHMENT0
    • Texture 1 binds to gl.COLOR_ATTACHMENT1
  3. Activation via gl.drawBuffers: GPU.js invokes gl.drawBuffers([gl.COLOR_ATTACHMENT0, gl.COLOR_ATTACHMENT1, ...]) to instruct the graphics pipeline to route the shader's layout(location = n) outputs to the respective attached textures in parallel.

Performance Benefits

Handling multi-render targets natively through WebGL 2 provides several computational advantages in GPU.js:

  • Single-Pass Execution: Fragment geometry, uniforms, and common sub-computations are evaluated once per thread, drastically reducing memory bandwidth.
  • Synchronized State: All output textures are updated simultaneously, eliminating race conditions between interdependent datasets.
  • Lower CPU Overhead: The JavaScript driver only submits a single draw call (gl.drawArrays or gl.drawElements) rather than iterating through multiple draw calls and framebuffer re-bindings.
