CPU vs GPU Thread Virtualization in GPU.js

This article explores how thread virtualization functions within gpu.js, contrasting the execution models of native GPU hardware against multi-core CPU fallback modes. In gpu.js, written kernels represent operations executed over a multidimensional output domain. While both CPU and GPU implementations abstract this domain into individual threads of execution, the underlying virtualization mechanisms—governing thread scheduling, memory allocation, and context switching—differ fundamentally between massively parallel GPU architectures and latency-optimized multi-core CPUs.

The GPU Execution Model: Massive SIMT Virtualization

When gpu.js runs on a GPU, it compiles JavaScript kernel functions into WebGL shaders. In this environment, thread virtualization is handled entirely in hardware through a Single Instruction, Multiple Threads (SIMT) architecture.

  1. Massive Thread Concurrency: The output dimensions defined in gpu.js (e.g., kernel.setOutput([1024, 1024])) directly instantiate over a million virtual threads. The GPU hardware groups these virtual threads into blocks and warps (or wavefronts, typically 32 to 64 threads).
  2. Zero-Overhead Context Switching: Unlike CPUs, GPUs maintain the execution state (registers and program counters) of thousands of threads simultaneously in hardware register files. When one warp stalls waiting for memory or texture retrieval, the warp scheduler instantly swaps to an active warp with zero instruction cycles lost.
  3. Hardware-Level Scheduling: The virtualization of millions of output coordinates is mapped dynamically onto hundreds or thousands of physical Arithmetic Logic Units (ALUs). The programmer and runtime do not manage scheduling queues; the GPU hardware dispatches threads as functional units become idle.

The CPU Fallback Model: Coarse-Grained Virtualization

When WebGL is unavailable or when explicitly configured, gpu.js falls back to JavaScript CPU execution. The CPU model handles the output domain through traditional sequential or coarsely parallel mechanisms rather than fine-grained hardware threads.

  1. Emulated Threads via Iteration: In the standard CPU fallback, thread virtualization is an abstraction implemented using nested JavaScript loops. Each "thread" at coordinate (x, y, z) is executed sequentially on a single thread of the host environment unless Web Workers are explicitly leveraged.
  2. Heavyweight Multi-Core Context Switching: When multi-core concurrency is introduced (such as across Node.js worker threads or Web Workers), virtualization depends on the Operating System scheduler. OS threads require heavy context switches, saving and restoring full register states, clearing execution pipelines, and risking CPU cache misses.
  3. Scale and Limits: While a GPU virtualizes millions of concurrent threads effortlessly, a multi-core CPU handles dozens to a few hundred threads before OS scheduling overhead degrades performance. In gpu.js, CPU execution does not map one-to-one to individual physical cores; instead, large chunks of the output matrix are processed in batch.

Key Architectural Contrasts in gpu.js

  • Latency Hiding vs. Latency Minimization: GPU virtualization relies on running vast numbers of threads to hide memory latency—if thread A is waiting for data, thread B computes. CPUs rely on large L1/L2/L3 caches and branch predictors to minimize latency for a small number of active threads.
  • Thread Divergence: In the GPU virtualization pipeline, if adjacent threads inside a warp follow different branches (via conditional if/else statements), both branches are executed serially across the warp, masking inactive threads. On the CPU, branch predictors allow independent cores to execute diverging paths without penalizing neighboring logical threads.
  • Memory Access Virtualization: GPU threads expect coalesced memory access, where adjacent virtual threads access adjacent memory addresses in parallel. CPU threads run independently across large contiguous blocks, relying on cache line prefetching rather than simultaneous cross-thread bus transactions.
