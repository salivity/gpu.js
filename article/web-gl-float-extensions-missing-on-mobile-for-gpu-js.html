WebGL Float Extensions Missing on Mobile for gpu.js

When running general-purpose GPU computing on mobile browsers using gpu.js, operations often fail or lose precision due to missing hardware and driver support for floating-point textures. While desktop environments almost universally support full 32-bit floating-point textures and render targets, mobile chipsets frequently omit key WebGL extensions to save power and memory bandwidth. This article outlines the specific WebGL 1.0 and WebGL 2.0 extensions typically absent on mobile devices, explains why their absence disrupts gpu.js, and details the resulting architectural limitations.

The Critical Missing Extensions

To compute and store high-precision numerical data, gpu.js requires both the ability to create floating-point textures and the capability to use them as render targets (framebuffer attachments). On mobile devices, the following extensions are most commonly missing or restricted:

  • WEBGL_color_buffer_float (WebGL 1.0): This is the most frequently missing extension on mobile WebGL 1.0 implementations. While a device might support reading float textures, this extension is required to render calculation outputs directly into 32-bit float textures.
  • EXT_color_buffer_float (WebGL 2.0): WebGL 2.0 natively supports 32-bit floating-point textures for storage and sampling, but it does not mandate the ability to render to them. The EXT_color_buffer_float extension is required to attach 32-bit float formats (like R32F, RG32F, and RGBA32F) to framebuffers. Mobile GPUs often omit this extension, breaking the write cycle in gpu.js compute kernels.
  • OES_texture_float_linear (WebGL 1.0 & 2.0): This extension provides linear interpolation filtering for 32-bit floating-point textures. Many mobile drivers only support nearest-neighbor filtering (NEAREST) on float textures, preventing smooth interpolation if intermediate sampling is needed.
  • OES_texture_float (WebGL 1.0): Although more widely supported than its framebuffer counterpart, older or low-end mobile chipsets sometimes lack base support for allocating 32-bit floating-point textures altogether.

The Read vs. Write Disconnect

A frequent point of failure in mobile environments is the difference between texture sampling (reading) and render target attachment (writing). Mobile architectures frequently support OES_texture_float, allowing shaders to read 32-bit floats. However, they omit WEBGL_color_buffer_float or EXT_color_buffer_float.

Because gpu.js functions by executing fragment shaders that write calculation results into a texture via Framebuffer Objects (FBOs), the inability to write to float textures renders the pipeline non-functional. When gpu.js attempts to bind a 32-bit float texture as a color attachment without these extensions, the driver returns an INCOMPLETE_ATTACHMENT or FRAMEBUFFER_UNSUPPORTED error.

Mobile Architectural Constraints

Mobile GPUs—such as ARM Mali, Qualcomm Adreno, and Imagination PowerVR—employ Tile-Based Deferred Rendering (TBDR) architectures. Writing 32-bit float data per channel requires significant memory bandwidth and on-chip tile memory, which generates heat and drains battery life.

Consequently, mobile hardware vendors prioritize half-precision (16-bit float) extensions over full 32-bit float extensions. Mobile browsers are far more likely to support:

  • OES_texture_half_float
  • EXT_color_buffer_half_float

These half-float alternatives reduce the memory footprint by half, but they limit the dynamic range and numerical precision available for scientific or intensive numerical workloads executed by gpu.js.

Impact on gpu.js and Fallback Mechanisms

When gpu.js detects that 32-bit float render targets are unsupported due to missing extensions, it cannot perform direct single-pass floating-point calculations. To function on these devices, the library must fall back to manual byte-packing algorithms.

In this fallback mode, 32-bit floating-point values are mathematically split and encoded across the standard 8-bit channels (RGBA) of an integer texture. A subsequent shader pass must then decode these bytes back into floating-point numbers. While this allows code to run on mobile devices lacking float extensions, it introduces significant computational overhead, reducing the overall performance gains of GPU acceleration.
