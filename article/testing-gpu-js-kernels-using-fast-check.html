Testing GPU.js Kernels Using fast-check

This guide demonstrates how to design property-based tests using fast-check to thoroughly stress-test mathematical kernels written in gpu.js. By shifting away from static, example-based assertions and instead testing broad mathematical invariants and differential behaviors against CPU reference models, you can systematically uncover precision drift, race conditions, dimension mismatch crashes, and boundary anomalies across thousands of randomly generated inputs.

The Challenge of Testing GPU Kernels

Mathematical kernels executing on the GPU run in highly parallel environments with hardware-specific constraints. In gpu.js, JavaScript functions are compiled down to WebGL or WebGPU shaders. This transformation introduces unique failure modes:

  • Floating-point discrepancies: GPU shaders default to 32-bit single-precision (IEEE 754 float32), whereas JavaScript numbers are 64-bit double-precision (float64).
  • Out-of-bounds thread indexing: Off-by-one errors in dimensional indexing (this.thread.x, this.thread.y) often return 0.0 silently or cause memory faults.
  • Driver and optimization quirks: Aggressive hardware compiler optimizations can cause subtle arithmetic drift.

Property-based testing with fast-check mitigates these risks by generating wide distributions of inputs—including extreme values like zeros, infinities, subnormals, and large matrices—and shrinking failures to minimal reproducible cases.

Step 1: Establish a Differential Oracle

The most effective pattern for testing a gpu.js kernel is differential testing (or test oracle comparison). You compare the output of the compiled GPU kernel against a simple, demonstrably correct CPU reference implementation.

import { GPU } from 'gpu.js';
import fc from 'fast-check';

const gpu = new GPU({ mode: 'gpu' });

// 1. Define the GPU Kernel (e.g., Element-wise Matrix Multiplication)
const matrixMultiplyGPU = gpu.createKernel(function(a, b) {
  return a[this.thread.y][this.thread.x] * b[this.thread.y][this.thread.x];
}).setOutput([4, 4]);

// 2. Define the CPU Reference Implementation
function matrixMultiplyCPU(a, b, width, height) {
  const result = [];
  for (let y = 0; y < height; y++) {
    const row = [];
    for (let x = 0; x < width; x++) {
      row.push(Math.fround(a[y][x] * b[y][x])); // Math.fround forces 32-bit precision
    }
    result.push(row);
  }
  return result;
}

Using Math.fround() in your CPU oracle ensures your reference computations replicate the single-precision semantics native to GPU fragment shaders.

Step 2: Define Targeted Arbitraries

Generators (arbitraries) must be designed to generate valid structural shapes while stressing floating-point boundaries.

// Generates finite, 32-bit float values that avoid immediate overflow
const floatArbitrary = fc.float({
  noDefaultInfinity: true,
  noNaN: true,
  min: -1e4,
  max: 1e4
});

// Generates an N x M 2D array of floats
const matrixArbitrary = (width, height) =>
  fc.array(fc.array(floatArbitrary, { minLength: width, maxLength: width }), {
    minLength: height,
    maxLength: height
  });

To stress-test hardware robustness, define a secondary arbitrary that explicitly permits non-standard inputs:

const adversarialFloatArbitrary = fc.oneof(
  fc.constant(0),
  fc.constant(-0),
  fc.constant(Number.EPSILON),
  fc.constant(1.0),
  fc.constant(-1.0),
  fc.float()
);

Step 3: Implement Tolerance-Based Assertions

Exact equality (===) fails in GPU testing due to differences in fused multiply-add (FMA) instructions and intermediate rounding. Instead, use a relative and absolute tolerance comparison:

function matricesClose(gpuResult, cpuResult, epsilon = 1e-4) {
  for (let y = 0; y < gpuResult.length; y++) {
    for (let x = 0; x < gpuResult[y].length; x++) {
      const g = gpuResult[y][x];
      const c = cpuResult[y][x];
      
      const diff = Math.abs(g - c);
      const largest = Math.max(Math.abs(g), Math.abs(c));

      // Handle exact matches (e.g., zeros) or values within tolerance
      if (diff > epsilon && diff > largest * epsilon) {
        return false;
      }
    }
  }
  return true;
}

Step 4: Construct the Property-Based Test

Combine the arbitrary, the execution steps, and the assertion inside fc.assert and fc.property.

describe('Matrix Kernel Stress Tests', () => {
  const WIDTH = 4;
  const HEIGHT = 4;

  const kernel = gpu.createKernel(function(a, b) {
    return a[this.thread.y][this.thread.x] * b[this.thread.y][this.thread.x];
  }).setOutput([WIDTH, HEIGHT]);

  it('maintains parity with the CPU reference implementation', () => {
    fc.assert(
      fc.property(
        matrixArbitrary(WIDTH, HEIGHT),
        matrixArbitrary(WIDTH, HEIGHT),
        (matrixA, matrixB) => {
          const gpuOut = kernel(matrixA, matrixB);
          const cpuOut = matrixMultiplyCPU(matrixA, matrixB, WIDTH, HEIGHT);

          return matricesClose(gpuOut, cpuOut);
        }
      ),
      {
        numRuns: 1000,
        endOnFailure: true,
        verbose: true
      }
    );
  });
});

Step 5: Test Intrinsic Mathematical Invariants

If a CPU reference is unavailable or computationally prohibitive, test algebraic invariants inherent to the operation:

  1. Identity Laws: Multiplying a matrix by an identity-equivalent representation must return the original matrix within floating-point tolerance.
  2. Commutativity: Operations like element-wise addition or dot products must yield: \[\text{kernel}(A, B) \approx \text{kernel}(B, A)\]
  3. Homogeneity: Scaling inputs by a scalar \(k\) must scale the output by \(k\) (for linear operations): \[\text{kernel}(k \cdot A) \approx k \cdot \text{kernel}(A)\]
it('satisfies commutativity: kernel(A, B) == kernel(B, A)', () => {
  fc.assert(
    fc.property(
      matrixArbitrary(WIDTH, HEIGHT),
      matrixArbitrary(WIDTH, HEIGHT),
      (matrixA, matrixB) => {
        const outAB = kernel(matrixA, matrixB);
        const outBA = kernel(matrixB, matrixA);
        return matricesClose(outAB, outBA);
      }
    ),
    { numRuns: 500 }
  );
});

Critical Considerations

  • GPU Memory Leaks: Avoid compiling kernels inside fc.property. Creating WebGL contexts or compiling shaders repeatedly during a 10,000-run test will exhaust GPU memory. Instantiate kernels once outside the test loop and pass dynamic inputs into the runner.
  • Context Teardown: Call gpu.destroy() in an afterAll hook to prevent dangling WebGL contexts during test runner teardown.
  • Dynamic Dimensions: If testing kernels over arbitrary array sizes, use dynamic kernels via gpu.createKernel(...).setOutput([w, h]) wrapped in a factory that manages a finite pool of dimensions, rather than creating a new kernel for every random size.
