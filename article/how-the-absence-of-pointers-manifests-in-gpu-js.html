How the Absence of Pointers Manifests in gpu.js

Because gpu.js compiles a subset of JavaScript into GPU-executable shader code (such as WebGL GLSL), it operates within the strict architectural boundaries of graphics hardware. This environment inherently lacks general-purpose pointers, dynamic memory allocation, and traditional reference types. As a result, working within gpu.js requires shifting from reference-heavy, object-oriented paradigms to strictly structured, flat memory layouts where spatial coordinates and immutable return values replace pointer mechanics.

Elimination of Dynamic and Linked Data Structures

In standard JavaScript, data structures such as linked lists, binary trees, and nested object graphs rely fundamentally on references pointing to arbitrary memory addresses. Inside a gpu.js kernel, these structures cannot exist. Shaders require predictable, contiguous memory layouts.

Any graph or complex hierarchical structure must be flattened into one-dimensional, two-dimensional, or three-dimensional numerical arrays before being passed to a kernel. Relationships between nodes cannot be traversed via pointer chasing; instead, they must be represented through integer indices within contiguous matrices.

Gather-Only Memory Architecture Over Arbitrary Writes

A defining characteristic of pointers in low-level programming is the ability to write to arbitrary memory locations (scatter operations). Because gpu.js maps execution across graphics pipelines, kernels strictly follow a gather pattern.

Individual execution threads cannot dereference a pointer to mutate an arbitrary global variable or modify an array at an arbitrary index. Instead, every thread is bound to its spatial coordinate (this.thread.x, this.thread.y, this.thread.z) and can only compute the output for that single designated cell via a return statement.

Simulated Pointer Arithmetic Through Coordinate Math

Where C or assembly might navigate a buffer using pointer arithmetic, gpu.js requires explicit mathematical indexing. Reading neighbor data—such as in image processing or cellular automata—cannot be achieved by shifting an internal pointer address. Developers must manually calculate array lookups based on thread offsets:

// Reading adjacent data via index calculation rather than pointer traversal
const left = input[this.thread.y][this.thread.x - 1];
const right = input[this.thread.y][this.thread.x + 1];

OutOfBounds conditions cannot be protected by null-pointer checks; they must be guarded with explicit conditional bounds checking to prevent undefined hardware behavior or texture sampling artifacts.

Strict Pass-by-Value Semantics

Standard JavaScript passes objects and arrays by reference, meaning modifications inside a helper function often mutate the underlying object. Inside custom functions called within a gpu.js kernel, parameters behave purely under pass-by-value semantics.

Because the underlying transpiled GLSL assigns values to local registers, a function cannot accept a variable and mutate the original version held by the calling scope. All inter-function communication must rely strictly on passing values in as arguments and returning computed values back to the caller.

Inability to Share Mutable State Between Threads

The absence of shared pointers prevents multiple GPU threads from communicating or sharing state during a single pass. In CPU programming, multiple execution threads can point to a shared object protected by mutexes or atomic operations. In gpu.js, threads execute in complete isolation from one another without shared mutable pointer references. Any workflow requiring iterative state updates must execute across multiple kernel dispatches, reading the output of the previous step as an immutable input texture for the next.
