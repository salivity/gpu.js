Mock WebGL Contexts to Test gpu.js in CI

Testing gpu.js kernels in Continuous Integration (CI) environments is a common hurdle due to the lack of native hardware acceleration and physical displays on remote build servers. While lightweight custom mocks or libraries like gl-matrix cannot be used as substitute WebGL rendering contexts, you can achieve reliable automated testing using the official headless-gl package or by utilizing gpu.js’s built-in CPU fallback mode. This guide breaks down why standard JavaScript mocks fail for WebGL kernels and details the working methods for running your test suites in CI pipelines.

Why Custom Mocks and gl-matrix Cannot Mock WebGL

A custom mock object or a library like gl-matrix is insufficient for running gpu.js WebGL kernels:

  • gl-matrix is a Math Library: gl-matrix provides high-performance matrix and vector operations. It does not provide or simulate a WebGLRenderingContext.
  • Shader Compilation Requirement: gpu.js does not merely call context methods like a standard 2D canvas; it transpiles your JavaScript functions into GLSL (OpenGL Shading Language), compiles shaders, links programs, and binds framebuffers to extract calculations via texture data. A JavaScript mock would need to re-implement an entire OpenGL pipeline and GLSL compiler to evaluate the kernel, which is impractically complex.

Supplying a custom, shallow JavaScript object mimicking WebGLRenderingContext will cause gpu.js to fail during the shader initialization and verification stages.

Solution 1: Use the CPU Fallback Mode for Logic Testing

For standard unit testing in CI, the simplest and fastest solution is to test using gpu.js's native CPU fallback. In CPU mode, gpu.js compiles the kernel into pure JavaScript rather than GLSL, allowing it to run in standard Node.js environments without any WebGL context or binary dependencies.

const { GPU } = require('gpu.js');

// Force CPU mode in CI environments
const gpu = new GPU({
  mode: process.env.CI ? 'cpu' : 'gpu'
});

const kernel = gpu.createKernel(function(a, b) {
  return a[this.thread.x] + b[this.thread.x];
}).setOutput([5]);

const result = kernel([1, 2, 3, 4, 5], [5, 4, 3, 2, 1]);
console.log(result); // Runs purely in Node.js

This approach tests the mathematical correctness of your kernel logic, argument passing, and integration flow without requiring GPU hardware or headless display configurations.

Solution 2: Use headless-gl (node-gles) for Real Kernel Testing

If you must verify GLSL compilation, precision quirks, or WebGL-specific output in CI, use the headless-gl (published as gl on npm) package. headless-gl creates a true headless OpenGL context on top of software renderers like SwiftShader or OSMesa.

1. Supplying the Context to gpu.js

Initialize the headless context and pass it explicitly to the GPU constructor:

const { GPU } = require('gpu.js');
const gl = require('gl')(1, 1); // Width and height

const gpu = new GPU({
  webGl: gl
});

const kernel = gpu.createKernel(function() {
  return this.thread.x * 2;
}).setOutput([4]);

const output = kernel();
console.log(output);

2. CI Runner Dependencies

Because headless-gl relies on native binaries and OpenGL drivers, you must install system dependencies on your CI container. For example, in a GitHub Actions Ubuntu runner, add the necessary rendering libraries:

- name: Install Headless OpenGL Dependencies
  run: |
    sudo apt-get update
    sudo apt-get install -y libgl1-mesa-dev libxi-dev libxext-dev

Summary of Best Practices

  • Do not use shallow JS mocks: They cannot evaluate GLSL shader pipelines.
  • Avoid gl-matrix as a context: It handles matrix math, not graphics execution.
  • Use CPU mode for standard CI testing: It is fast, deterministic, and requires no system-level dependencies.
  • Use headless-gl for compilation testing: If shader-level execution must be tested, supply an instance of require('gl') directly to the webGl option of the GPU constructor.
