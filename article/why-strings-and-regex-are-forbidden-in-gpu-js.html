Why Strings and Regex Are Forbidden in GPU.js

GPU.js accelerates JavaScript code by compiling it into WebGL shaders that run directly on the graphics processor. However, it completely forbids the use of string operations and regular expressions inside kernel functions. This limitation stems from the fundamental architecture of GPUs, which are designed exclusively for high-throughput, parallel mathematical computations rather than the dynamic memory allocation, non-deterministic branching, and arbitrary byte-level inspection required to process text.

Translation to GLSL (Shading Language)

Under the hood, GPU.js transpiles JavaScript kernel functions into WebGL Shading Language (GLSL). GLSL is a strictly typed language built for rendering graphics and executing fast linear algebra. Its native data types are limited to numbers, vectors, matrices, and fixed-length structures:

  • float, int, uint, bool
  • Vectors (vec2, vec3, vec4)
  • Matrices (mat3, mat4)
  • Arrays of fixed size and fixed type

GLSL does not possess a native string data type, nor does it provide a standard library for string concatenation, slicing, or character encoding. Because the underlying hardware target cannot represent a string, GPU.js cannot compile JavaScript string primitives into valid shader code.

Absence of Dynamic Memory and Heaps

In CPU architectures, strings are typically managed as variable-length arrays allocated on a managed heap. Operations like substring extraction, concatenation, or string templating require dynamic memory allocation and garbage collection.

GPUs, by contrast, lack a dynamic heap inside execution threads. When a GPU launches thousands of threads concurrently, each thread operates within a strictly partitioned, fixed-size memory space (registers and local scratchpad memory). Every data structure must have a deterministically known size at compile time. Variable-length data like text cannot be dynamically allocated, resized, or freed inside an active GPU thread.

Regex Engines Require Unpredictable Control Flow

Regular expressions depend on complex parsing algorithms, such as Deterministic Finite Automata (DFA) or Non-Deterministic Finite Automata (NFA). Evaluating a regular expression involves:

  • Unpredictable loop counts
  • Deep backtracking or recursion
  • State lookups based on arbitrary characters

GPUs execute instructions using Single Instruction, Multiple Threads (SIMT) architectures. In SIMT, groups of threads (warps or wavefronts) execute the exact same instruction simultaneously. When threads within the same group take different execution paths—known as branch divergence—the hardware must serialize those paths, stalling execution and destroying performance. The irregular, heavily branching nature of regex engines is fundamentally incompatible with SIMT hardware.

Working Around the Limitation

To process text-related data using GPU.js, all string operations must be preprocessed on the CPU:

  1. Tokenization and Encoding: Convert strings into numerical representations (such as ASCII values, UTF-8 byte arrays, or integer token IDs) using standard JavaScript on the CPU.
  2. Fixed-Size Buffers: Pack these integers or floats into 1D, 2D, or 3D typed arrays of fixed dimensions.
  3. Kernel Execution: Pass the numerical arrays into the GPU.js kernel to perform parallel numeric computations (e.g., matching character IDs by integer comparison).
  4. Decoding: Read the resulting numeric outputs back on the CPU and decode them back into strings.
