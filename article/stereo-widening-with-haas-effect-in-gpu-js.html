Stereo Widening with Haas Effect in gpu.js

This article explains how to accelerate audio stereo widening by implementing the Haas effect using parallel GPU processing with gpu.js. You will learn the core acoustic principles of the Haas effect, how to calculate sample-accurate delays, and how to write and execute a dedicated GPU kernel that simultaneously processes left and right audio channels to achieve real-time or offline spatial expansion.

Understanding the Haas Effect in Digital Audio

The Haas effect, or precedence effect, occurs when two identical or nearly identical sounds arrive at human ears with a slight time difference between roughly 10 and 35 milliseconds. Instead of perceiving two distinct sounds, the auditory system fuses them into a single auditory event while perceiving an expanded stereo image directed toward the earlier sound.

In digital signal processing, you apply this effect by leaving one channel untouched (or delayed slightly) while delaying the opposing channel by \(N\) samples, calculated as:

\[\text{delaySamples} = \text{sampleRate} \times \text{delayTimeInSeconds}\]

For example, at a standard sample rate of 44,100 Hz, a 20ms delay requires delaying one channel by 882 samples.

Preparing Audio Buffers for gpu.js

gpu.js operates on multi-dimensional or flat typed arrays (Float32Array). For optimal performance on the GPU, pass discrete mono channel arrays (leftChannel and rightChannel) rather than interleaved stereo buffers.

import { GPU } from 'gpu.js';

const gpu = new GPU();
const sampleRate = 44100;
const delayMs = 20; 
const delaySamples = Math.floor(sampleRate * (delayMs / 1000));

Writing the Haas Widener GPU Kernel

The GPU kernel runs once per audio sample in parallel. Because the delay requires reading a sample from an earlier point in time (\(i - \text{delay}\)), the kernel checks boundary conditions to ensure it does not access negative indices.

const haasWidenerKernel = gpu.createKernel(function(leftChannel, rightChannel, delaySamples, mix) {
    const i = this.thread.x;
    
    // Direct audio for the left channel
    const leftDirect = leftChannel[i];
    
    // Delayed audio for the right channel
    let rightDelayed = 0.0;
    if (i >= delaySamples) {
        rightDelayed = rightChannel[i - delaySamples];
    }
    
    // Apply wet/dry mix to balance the stereo width
    const outLeft = leftDirect;
    const outRight = (rightChannel[i] * (1.0 - mix)) + (rightDelayed * mix);

    // Write back stereo channels into a 2D output format: [Left, Right]
    if (this.thread.y === 0) {
        return outLeft;
    } else {
        return outRight;
    }
})
.setOutput([audioLength, 2])
.setPipeline(true); // Retains output on GPU if chaining with other DSP kernels

Executing the Kernel and Retrieving Data

To run the processor, supply the input channels along with the delay parameters:

function processStereoWidening(leftBuffer, rightBuffer, wetDryMix = 0.8) {
    const audioLength = leftBuffer.length;

    // Reconfigure kernel output dimension dynamically if sample size changes
    haasWidenerKernel.setOutput([audioLength, 2]);

    // Execute computation on the GPU
    const stereoOutput = haasWidenerKernel(leftBuffer, rightBuffer, delaySamples, wetDryMix);

    // Extract the separated left and right arrays from the GPU memory
    const processedLeft = new Float32Array(audioLength);
    const processedRight = new Float32Array(audioLength);

    // In non-pipeline mode or after calling .toArray():
    const rawResult = stereoOutput.toArray();
    for (let i = 0; i < audioLength; i++) {
        processedLeft[i] = rawResult[0][i];
        processedRight[i] = rawResult[1][i];
    }

    return { processedLeft, processedRight };
}

Key Considerations for GPU Audio Processing

  • PCIe Transfer Overhead: Transferring audio data between CPU system memory and GPU VRAM introduces latency. This approach is most effective for large audio buffers, batch offline rendering, or when chained with other GPU-based audio DSP filters.
  • Phase Coherence: Extreme delay times or aggressive wet mixes can cause comb filtering when summed to mono. Keep delays strictly between 10ms and 30ms, and verify mono compatibility by summing (processedLeft + processedRight) * 0.5.
