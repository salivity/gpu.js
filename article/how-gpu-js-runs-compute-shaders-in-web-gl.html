How GPU.js Runs Compute Shaders in WebGL

Standard WebGL lacks native compute shader support, posing a major hurdle for high-performance computing in browser environments. GPU.js overcomes this limitation by repurposing WebGL's standard graphics pipeline for general-purpose computing (GPGPU). By transpiling JavaScript functions into GLSL fragment shaders, encoding numerical data into 2D textures, and rendering an off-screen quad, GPU.js effectively tricks the graphics hardware into executing parallel data processing tasks instead of rendering graphics.

Transpiling JavaScript to GLSL

GPU.js begins by converting user-written JavaScript into OpenGL Shading Language (GLSL). It parses the JavaScript function using an Abstract Syntax Tree (AST) analyzer to evaluate mathematical expressions, loops, and variable declarations. Once parsed, the library generates equivalent GLSL code targeted specifically at a fragment shader. This enables developers to write standard JavaScript code while executing native GPU instructions under the hood.

Mapping Data to Textures

Because WebGL 1.0 and 2.0 lack arbitrary storage buffers, data must enter and exit the GPU disguised as image assets. GPU.js converts incoming multi-dimensional numerical arrays into WebGL textures. Each data point is encoded into the color channels (Red, Green, Blue, Alpha) of a pixel:

  • Floating-Point Textures: On devices supporting the OES_texture_float or WebGL 2.0 extensions, numbers are stored directly as 32-bit floating-point values within texture channels.
  • Byte Packing: If floating-point textures are unsupported, GPU.js packs 32-bit floating-point numbers across the four 8-bit channels (RGBA) of a standard unsigned byte texture, ensuring mathematical precision across diverse hardware configurations.

The Render Pipeline as a Compute Grid

To initiate parallel execution, GPU.js sets up an off-screen viewport sized to match the dimensions of the output array. It renders a single, screen-aligned rectangle composed of two triangles covering the entire viewport.

When the GPU rasterizes these triangles, it triggers the compiled fragment shader once for every pixel. The pixel's coordinates \((x, y)\) correlate directly with the matrix coordinates \((i, j)\) of the target calculation. The fragment shader samples values from the input data textures using these coordinates, executes the mathematical logic, and outputs the calculated result as the pixel's color.

Reading Back Results and Pipeline Chaining

The output color values are directed to an off-screen Framebuffer Object (FBO) rather than the visible canvas. To return the data to JavaScript, GPU.js reads the pixel values from the FBO back into CPU memory using gl.readPixels(), automatically unpacking the byte channels back into native JavaScript arrays or typed arrays.

To prevent performance penalties caused by transferring data between the CPU and GPU, GPU.js also allows output textures to remain stored in GPU memory. The result of one calculation can be immediately passed as an input texture to a subsequent kernel, mimicking the execution pipeline of native compute shaders while remaining fully compatible with older WebGL standards.
