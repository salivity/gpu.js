GPU.js for Massive 2D Point Cloud Convex Hulls

GPU.js can effectively evaluate convex hull approximations for massive 2D point clouds by translating data-parallel mathematical operations into WebGL shaders. While traditional exact algorithms like the Graham scan or Quickhull perform poorly on graphics hardware due to dynamic branching and global state dependencies, approximation techniques based on directional projections map cleanly to the GPU.js architecture, enabling substantial speedups over single-threaded CPU implementations.

Algorithmic Fit for GPU Parallelism

Exact convex hull algorithms rely heavily on sorting, stack manipulation, and recursive partitioning. These patterns clash with the SIMD (Single Instruction, Multiple Data) execution model of GPU.js, which compiles JavaScript functions into WebGL fragment shaders. Shaders operate best when calculating deterministic outputs across independent threads without complex communication between threads.

Approximation algorithms bypass these limitations by reframing the problem around extreme points. Instead of computing the exact polygon boundary iteratively:

  1. Directional Sampling: Generate a fixed set of \(k\) uniform directional vectors spanning 360 degrees.
  2. Parallel Dot Products: For each direction vector, calculate the dot product with every point in the cloud to find the point that maximizes the projection.
  3. Boundary Reconstruction: Collect the maximum points corresponding to each angle and connect them sequentially to form an approximate bounding polygon.

Implementing the Approximation in GPU.js

In GPU.js, this is achieved using a parallel reduction or a two-pass kernel:

  • Kernel Computation: The 2D point cloud is passed as a flat or structured array texture. A kernel computes the projection of \(N\) points against \(k\) directional slices. With massive point clouds (millions of vertices), the computation distributes across thousands of shader cores simultaneously.
  • Reduction: GPU.js handles parallel min/max reductions to identify the extreme index along each axis.

Because the runtime complexity shifts from \(O(N \log N)\) or \(O(N H)\) on the CPU to \(O((N \cdot k) / P)\) on the GPU (where \(P\) represents the number of parallel GPU pipelines), processing throughput for initial filtering is vastly superior.

Performance Constraints and Trade-offs

While feasible, using GPU.js for this workflow introduces specific bottlenecks:

  • Data Transfer Latency: Moving millions of coordinate pairs from JavaScript memory (RAM) to GPU memory (VRAM) incurs overhead. If the point cloud is generated dynamically on the CPU for a single one-off calculation, data transfer times can negate the computational gains. It is most effective when data already resides on the GPU or when multiple queries run over static geometry.
  • Floating-Point Precision: WebGL 1.0/2.0 implementations may suffer from precision limitations depending on the client device. Floating-point roundoff can lead to degenerate hulls if coordinates are tightly clustered or span massive ranges. Normalizing coordinates before kernel invocation is necessary.
  • Approximation Accuracy vs. Thread Count: Increasing the angular resolution (\(k\)) improves accuracy toward the true convex hull but increases the number of kernel runs or texture reads. For massive datasets, a low-to-moderate \(k\) (e.g., 64 to 256 directions) captures over 99% of the hull area while maintaining real-time frame rates.

GPU.js is well-suited for approximating convex hulls on massive 2D point clouds when using direction-based projection methods, offering real-time performance that CPU-based alternatives struggle to match at scale.
