Dynamic Wind Flow Around Obstacles in GPU.js

Computing dynamic wind flow around physical obstacles for particle interaction is fully achievable in GPU.js by implementing a grid-based fluid dynamics solver paired with an advection pass for particles. By compiling JavaScript math functions into WebGL fragment shaders, GPU.js enables browser-based parallel execution of the Navier-Stokes equations or the Lattice Boltzmann Method. This article explains how to architect a real-time wind simulation, enforce solid boundary conditions for obstacles, and drive interactive particles using GPU kernels.

The Simulation Architecture

Simulating wind interacting with particles requires a hybrid Eulerian-Lagrangian approach. The fluid (wind) is solved on a fixed grid (Eulerian), while particles move continuously through this velocity field (Lagrangian).

  1. The Velocity Grid (Eulerian): A 2D or 3D grid where each cell stores horizontal and vertical velocity vectors, along with pressure values.
  2. The Obstacle Mask: A secondary grid or texture representing solid boundaries, where cells are flagged as either fluid or obstacle.
  3. The Particle System (Lagrangian): A set of particle coordinates that update dynamically by reading values from the velocity grid.

Implementing the Fluid Solver in GPU.js

Wind dynamics follow the incompressible Navier-Stokes equations, commonly implemented using Jos Stam’s Stable Fluids algorithm. GPU.js executes this process through sequential kernel passes:

  • Advection: Computes how the velocity field moves itself over time. A GPU.js kernel samples the previous velocity field using back-tracing and interpolation.
  • External Forces: Injects directional forces into the grid to simulate continuous wind currents or gusts.
  • Diffusion: Solves viscous resistance across neighboring grid cells using iterative methods like Jacobi iteration.
  • Pressure Projection: Ensures mass conservation (incompressibility). This step requires multiple Jacobi iterations to solve the Poisson pressure equation, followed by subtracting the pressure gradient from the velocity field to make it divergence-free.

To maintain real-time frame rates across multiple passes, GPU.js kernels must use the pipeline: true option. This keeps intermediate textures in GPU memory and avoids expensive readbacks to the CPU.

Handling Physical Obstacles

Obstacles in the wind path are represented by setting boundary conditions on the grid:

  • No-Slip Condition: Fluid velocity directly at the surface of a stationary solid is zero.
  • Free-Slip Condition: Fluid flows parallel to the surface without penetrating it.

In GPU.js, an obstacle kernel inspects the obstacle mask. For any cell marked as a solid, the kernel overrides the velocity to zero (or applies a bounce-back rule) and sets the normal pressure gradient to zero during the pressure-solve step. As the simulation runs, the pressure projection naturally forces the wind vector field to curve around these blocked cells, creating realistic deflection, drag, and downstream vortex shedding.

Driving Particle Interaction

Once the fluid solver updates the velocity field for a given frame, a dedicated particle kernel executes the physical interaction:

  1. Position Read: The kernel takes an array of particle positions [x, y].
  2. Velocity Sampling: Using bilinear interpolation, the kernel samples the velocity vector from the nearest fluid grid cells corresponding to each particle's position.
  3. Integration: The particle position updates by applying the sampled wind velocity multiplied by the time step (dt).
  4. Collision Handling: If a particle moves into an obstacle cell, its position is clamped to the obstacle boundary, or its velocity is inverted to produce a bounce.

Practical Limitations in GPU.js

While GPU.js simplifies GPGPU programming by abstracting GLSL shaders, complex simulations face specific constraints:

  • Iteration Overhead: Pressure solving requires 20 to 40 Jacobi iterations per frame. Chaining this many GPU.js kernel executions can introduce JavaScript-to-WebGL dispatch overhead compared to a single handwritten GLSL pipeline.
  • Dimension Limitations: 2D dynamic flow scales efficiently, but 3D wind flow requires large 3D textures, which can quickly exceed WebGL texture memory limits on lower-end devices.
  • Precision: GPU.js relies on floating-point textures (OES_texture_float), which may have varying levels of precision and hardware support across mobile browsers.

When configured with pipelined execution and an optimized grid resolution (such as 128x128 or 256x256), GPU.js reliably computes real-time dynamic wind flow around complex obstacle geometries to drive tens of thousands of interactive particles directly in the browser.
