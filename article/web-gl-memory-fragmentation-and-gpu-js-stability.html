WebGL Memory Fragmentation and gpu.js Stability

Long-running computational tasks in gpu.js can suffer from stability degradation caused by VRAM and driver-level memory fragmentation. While WebGL Framebuffer Objects (FBOs) are lightweight state containers rather than direct memory allocations, they bind textures and renderbuffers that consume physical video memory. Continuously allocating, resizing, or discarding these backing textures during iterative GPGPU tasks fragments the underlying graphics memory space, eventually leading to performance throttling, erratic execution times, and unrecoverable WebGL context loss.

How gpu.js Uses Framebuffers

To perform calculations on the GPU using WebGL, gpu.js utilizes a technique known as GPGPU (General-Purpose computing on Graphics Processing Units). Since WebGL does not natively support compute shaders, gpu.js converts mathematical logic into GLSL fragment shaders. The inputs are encoded into textures, and the computation results are rendered into an off-screen Framebuffer Object (FBO) backed by another texture.

When chains of computations or iterative calculations occur, these output textures frequently become the input textures for subsequent passes. The lifecycle of these textures directly dictates how memory is claimed and released on the GPU.

The Mechanism of Memory Fragmentation

Framebuffers do not fragment on their own because they are merely references. Fragmentation occurs within the underlying driver and VRAM management layers due to how backing textures are handled:

  1. Varying Matrix Dimensions: If a gpu.js application processes dynamic workloads where input array dimensions change regularly, gpu.js must instantiate new textures matching those dimensions. Constant creation and disposal of non-uniform textures produce unevenly sized memory blocks in VRAM.
  2. Driver Heap Inefficiencies: Unlike CPU memory, which often handles arbitrary fragmentation gracefully via sophisticated virtual memory tables, GPU memory management depends heavily on contiguous address spaces for high-bandwidth texture sampling. When free memory becomes scattered in small blocks, allocating a large contiguous texture fails, even if total free VRAM is technically sufficient.
  3. Garbage Collection Latency: JavaScript garbage collection cannot free GPU-side allocations immediately. Discarding a texture in JavaScript leaves the GPU counterpart allocated until the browser's internal WebGL resource manager releases it, creating artificial memory pressure.

Impact on Long-Term Stability

Over hours or days of continuous execution, memory fragmentation manifests through several clear symptoms:

  • Latency Spikes: When memory is fragmented, the graphics driver must perform memory compaction or swap data between VRAM and system RAM. This produces noticeable execution stutter.
  • Context Loss (webglcontextlost): When the driver fails to locate a contiguous memory segment for a new texture pass, it triggers an out-of-memory error. In browser environments, this typically causes the browser to forcefully reset the entire WebGL context to prevent system-wide instability.
  • Memory Leaks from Retained States: If old kernels or output textures maintain references inside closures, the associated FBO attachments cannot be collected, compounding the fragmentation issue with active memory bloat.

Mitigating Fragmentation in gpu.js

To maintain stability across sustained workloads, resource churn must be minimized:

  • Pad Array Sizes: Normalize input array sizes to static dimensions. Padding inputs to fixed power-of-two boundaries allows textures to be reused without triggering reallocations.
  • Texture Recycling: Avoid recreating kernel functions dynamically. Reuse existing kernel instances and keep pipeline outputs within pre-allocated textures where possible.
  • Explicit Resource Deallocation: Do not rely exclusively on browser garbage collection. Call destroy() on gpu.js kernel instances and explicitly release textures when workloads complete.
