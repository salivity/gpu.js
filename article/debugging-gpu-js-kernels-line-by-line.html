Debugging gpu.js Kernels Line by Line

Debugging GPU-accelerated code line by line presents unique challenges due to the massive parallelism of graphics hardware, which lacks traditional interactive step-debugging support in the browser. This article explores the primary tools and strategies available for stepping through and inspecting gpu.js kernel executions line by line, focusing on gpu.js's built-in CPU fallback mode, browser developer tools, and specialized WebGL inspection utilities.

The CPU Fallback Mode in gpu.js

Because WebGL shaders execute concurrently across thousands of GPU threads, web browsers cannot pause execution at an arbitrary line of GLSL shader code using standard JavaScript breakpoints. The most direct and reliable tool to step through a gpu.js kernel line by line is the library's native CPU execution mode.

When creating a kernel, you can explicitly force it to compile and run on the CPU rather than the GPU by setting the mode option:

const gpu = new GPU();
const kernel = gpu.createKernel(function(a, b) {
    debugger; // Triggers browser breakpoint
    let result = a[this.thread.x] + b[this.thread.x];
    return result;
}, {
    output: [512],
    mode: 'cpu'
});

kernel(arrayA, arrayB);

In CPU mode, gpu.js transpiles the kernel logic back into standard JavaScript loops. This allows developers to use conventional debugging tools to step through the execution path of each virtual thread.

Browser Developer Tools (Chrome DevTools, Firefox Developer Tools)

Once a kernel is running in CPU mode, standard browser developer tools become fully functional:

  • Breakpoints and debugger Statements: Inserting a debugger; statement inside the kernel function halts execution immediately when DevTools is open.
  • Step-by-Step Execution: You can use "Step Over" (F10), "Step Into" (F11), and "Step Out" (Shift+F10) to inspect local variables, intermediate calculations, and control flow line by line.
  • Thread Context Inspection: You can inspect this.thread.x, this.thread.y, and this.thread.z directly in the Scope panel or the Console to monitor which coordinate is currently being calculated.

IDE Debuggers (VS Code and Node.js)

If you are running gpu.js in a Node.js environment or using a modern IDE like Visual Studio Code, CPU mode enables IDE-level line-by-line debugging:

  1. Launch your script using the Node.js inspector (node --inspect index.js) or a VS Code launch configuration.
  2. Place visual breakpoints directly in the margin next to your kernel code.
  3. Step through statements, evaluate watch expressions, and inspect call stacks just like any regular asynchronous or synchronous JavaScript code.

WebGL Profilers and Inspection Utilities

While the CPU mode is required for interactive line-by-line stepping, other tools help diagnose issues when running directly on the GPU hardware:

Spector.js

Spector.js is a WebGL inspection tool created by the BabylonJS team, available as a browser extension. While it does not allow interactive line-by-line stepping through shader logic:

  • It captures individual WebGL draw calls generated by gpu.js.
  • It displays the compiled GLSL fragment and vertex shaders.
  • It allows inspection of uniforms, textures, and framebuffers sent to the GPU, making it easier to determine if input data is misaligned before a kernel runs.

RenderDoc and NVIDIA Nsight

For advanced desktop-level debugging, native graphics debuggers such as RenderDoc or NVIDIA Nsight Graphics can be hooked into Chromium-based browsers via command-line flags (e.g., --enable-gpu-benchmarking --no-sandbox). These tools capture WebGL draw calls at the driver level and allow post-execution shader debugging, showing intermediate variable states per invocation on supported graphics drivers.

Recommended Debugging Workflow

  1. Develop and Debug in CPU Mode: Set { mode: 'cpu' } and use debugger; statements to verify mathematical correctness and step through loop iterations.
  2. Switch to Auto/GPU Mode: Once the logic is confirmed, switch the mode back to gpu (or remove the option to let gpu.js default to the fastest available backend).
  3. Compare Numerical Outputs: Run both modes side by side with identical input data to detect precision discrepancies or unsupported functions between the JavaScript engine and the target GPU's floating-point implementation.
