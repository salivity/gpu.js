GPU.js Texture Memory: Float32 vs Packed 8-Bit

Understanding texture memory allocation in GPU.js is critical for optimizing WebGL kernel performance and managing GPU VRAM usage. When computing with numerical data, GPU.js can either output data to unpacked 32-bit floating-point textures or encode (pack) those values into standard 8-bit unsigned byte textures. In standard WebGL 1 configurations, maintaining unpacked Float32 textures typically incurs a 4x (400%) memory overhead compared to packed 8-bit textures, significantly impacting memory consumption and memory bandwidth.

The Underlying Texture Formats

GPU.js relies on WebGL textures as its primary mechanism for passing data to and from the GPU. The representation of individual elements in VRAM differs depending on the packing configuration:

  • Packed 8-bit Textures (gl.RGBA, gl.UNSIGNED_BYTE): GPU.js encodes a single 32-bit IEEE 754 floating-point number across the red, green, blue, and alpha channels of a single pixel. Each channel holds an 8-bit unsigned byte.
    • Memory Footprint: 4 channels × 1 byte = 4 bytes (32 bits) per scalar value.
  • Unpacked Float32 Textures (gl.RGBA, gl.FLOAT): In WebGL 1 environments, rendering directly to a floating-point target via the OES_texture_float extension generally requires an RGBA framebuffer. Because single-channel float render targets (gl.LUMINANCE or gl.ALPHA) are either unsupported or read-only on many drivers, GPU.js must allocate an RGBA texture where each channel is a full 32-bit float.
    • Memory Footprint: 4 channels × 4 bytes = 16 bytes (128 bits) per texel. Even if only one float is calculated per element, the driver allocates the entire 4-component vector.

Direct Memory Overhead Comparison

When processing an array of \(N\) float values:

Metric Packed 8-bit (UNSIGNED_BYTE) Unpacked Float32 (WebGL 1 FLOAT) WebGL 2 Unpacked (R32F)
Bytes per Element 4 bytes 16 bytes 4 bytes
VRAM for 1 Million Floats ~4 MB ~16 MB ~4 MB
Relative VRAM Overhead Baseline (1x) 4x (300% increase) 1x (parity)

In modern browsers running a WebGL 2 context, GPU.js can leverage gl.R32F (single-channel red float textures), bringing the unpacked memory footprint down to 4 bytes per scalar float. However, fallback conditions to WebGL 1—common on mobile hardware or restrictive environments—instantly trigger the 16-byte-per-element RGBA allocation.

Performance and Bandwidth Trade-offs

The 4x memory overhead of unpacked Float32 textures introduces key hardware performance implications:

  1. Memory Bandwidth Saturation: A 4x increase in texture size requires four times more data to be pushed across the memory bus during texture read, write, and copy operations. For bandwidth-bound kernels, this overhead often negates the computational advantage of working directly with raw floats.
  2. GPU Cache Eviction: Larger texels consume L1 and L2 texture caches significantly faster. Packed textures allow four times as many scalar values to fit into the same cache line, resulting in higher cache hit rates during neighboring texture lookups.
  3. ALU vs. Memory Bottlenecks: Packed textures require additional arithmetic operations (bitwise manipulation and division) within the fragment shader to encode and decode IEEE 754 components into [0.0, 1.0] byte ranges. Unpacked Float32 textures bypass these ALU cycles entirely, making unpacked textures faster only when the kernel is heavily compute-bound rather than memory-bandwidth-bound.
