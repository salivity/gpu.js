How GPU.js Performs Fast Vector Addition

This article explores how GPU.js accelerates element-wise vector addition across millions of floating-point numbers by offloading computations from the central processing unit (CPU) to the graphics processing unit (GPU). By transpiling JavaScript functions into WebGL shaders, GPU.js bypasses typical single-threaded JavaScript performance bottlenecks. Below, we break down the step-by-step process of how data serialization, shader compilation, massively parallel GPU execution, and result retrieval occur under the hood.

The Limitation of CPU Processing

In standard JavaScript environments like Node.js or the browser, an element-wise addition of two arrays with millions of elements relies on a single-threaded loop:

for (let i = 0; i < length; i++) {
  c[i] = a[i] + b[i];
}

Even with modern JIT (Just-In-Time) compilation and TypedArrays, the CPU must compute each addition sequentially or across a small set of SIMD instructions and thread pools. When handling millions of floating-point values, memory bandwidth limitations and thread saturation lead to high latency.

1. JavaScript to GLSL Transpilation

When you define a kernel in GPU.js, the library does not execute your JavaScript code directly. Instead, it parses the JavaScript Abstract Syntax Tree (AST) of the function and transpiles it into GLSL (OpenGL Shading Language), specifically targeting WebGL fragment shaders.

For vector addition, GPU.js converts a function like this:

const addVectors = gpu.createKernel(function(a, b) {
  return a[this.thread.x] + b[this.thread.x];
}).setOutput([1000000]);

into a fragment shader where this.thread.x is calculated from the normalized coordinates of the fragment being rendered.

2. Texture Encoding and Data Transfer

GPUs are designed to process pixels rather than arbitrary numeric arrays. To make vectors accessible to the GPU:

  1. Packing into Textures: GPU.js converts the input floating-point arrays into 2D WebGL textures. Each pixel in a texture contains four channels: Red, Green, Blue, and Alpha (RGBA).
  2. Precision Handling: Depending on hardware support (such as the OES_texture_float WebGL extension), numbers are stored either as direct 32-bit floating-point textures or packed across standard 8-bit RGBA channels.
  3. VRAM Upload: These textures are loaded into the GPU’s high-bandwidth Video RAM (VRAM), making them immediately accessible to the graphics pipeline.

3. Massively Parallel Fragment Execution

Once the data resides in VRAM, GPU.js renders a simple 2D quad spanning the dimension of the target output array:

  • Grid Distribution: The output array size (e.g., 10,000,000 floats) is mapped to a viewport grid of fragment threads.
  • Simultaneous Execution: Modern GPUs feature thousands of Stream Processors or CUDA cores. Rather than iterating sequentially, the GPU schedules thousands of fragment shader invocations concurrently.
  • Per-Element Computation: Each core executes the compiled fragment shader for a specific index i. It fetches the corresponding values from texture A and texture B, executes the single-cycle hardware floating-point addition (A[i] + B[i]), and writes the sum to the render target (framebuffer).

4. Reading Results Back to JavaScript

After the GPU finishes rendering the output texture:

  1. Readback: GPU.js extracts the data from the GPU framebuffer using the WebGL readPixels pipeline.
  2. Decoding: If the output was encoded across 8-bit channels, GPU.js decodes the bytes back into floating-point numbers. If float textures were supported and active, it reads the data directly into a JavaScript Float32Array.
  3. Pipelining (Optional): If the data is needed for further GPU calculations, GPU.js can keep the result as a texture in VRAM, avoiding the CPU-GPU transfer penalty entirely for subsequent operations.
