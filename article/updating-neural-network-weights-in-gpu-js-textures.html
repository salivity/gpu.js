Updating Neural Network Weights in gpu.js Textures

This article examines whether weights and biases of a deep neural network can be updated entirely within gpu.js textures without transferring data back to the CPU. It explores how gpu.js pipeline mode facilitates in-memory texture chaining, the mechanics of implementing backpropagation and optimizer updates on the GPU, the necessity of ping-pong buffering to circumvent WebGL read-write constraints, and the key architectural trade-offs involved in end-to-end GPU training within a browser or Node.js environment.

The Short Answer

Yes, weights and biases can be updated entirely inside gpu.js textures. By enabling pipeline mode (kernel.setPipeline(true)), gpu.js keeps kernel outputs in WebGL textures on the GPU rather than serializing them into JavaScript typed arrays. These output textures can be passed directly as input arguments into subsequent kernels, allowing the forward pass, gradient calculation, and weight update steps to execute continuously on the GPU.

The Mechanism: Pipeline Mode

By default, gpu.js compiles JavaScript functions into GLSL shaders, executes them, and reads the results back to the CPU via WebGL's readPixels operation. This readback creates a severe performance bottleneck during neural network training.

When pipeline mode is activated:

const kernel = gpu.createKernel(function(weights, gradients, learningRate) {
    return weights[this.thread.y][this.thread.x] - (learningRate * gradients[this.thread.y][this.thread.x]);
})
.setOutput([width, height])
.setPipeline(true);

The output of this kernel is an instance of a Texture object rather than a nested array. This texture lives inside GPU VRAM and can be supplied directly as an input to the next training iteration or activation kernel.

Handling In-Place Updates: The Ping-Pong Pattern

In WebGL, a single texture cannot act as both an active read source and a write target (framebuffer attachment) in the same render pass. Because standard optimizers (such as Stochastic Gradient Descent or Adam) update existing weights using those same weights as a baseline, you cannot perform an in-place update directly on a single texture.

To overcome this, you must implement a "ping-pong" buffering pattern:

  1. Maintain two textures for each parameter matrix: WeightsA and WeightsB.
  2. In iteration \(t\), read from WeightsA, compute the update using the gradient texture, and write the result to WeightsB.
  3. In iteration \(t+1\), read from WeightsB and write the result back to WeightsA.
  4. Alternate the pointers for each forward and backward cycle.

This eliminates CPU involvement while respecting WebGL’s memory access constraints.

Implementing an End-to-End Training Loop

An end-to-end texture-based training loop in gpu.js follows this sequence:

  1. Forward Pass: The input texture and weight textures are passed to a matrix multiplication kernel, followed by an activation kernel (such as ReLU or Sigmoid), yielding intermediate activation textures.
  2. Loss and Delta Calculation: Output activations and target textures are compared in an error kernel to produce the initial output layer deltas.
  3. Backpropagation: Layer deltas are propagated backward using transposed weight textures to generate gradient textures for each layer's weights and biases.
  4. Parameter Update: An optimizer kernel computes the new parameter values from the current weight texture, the gradient texture, and learning hyper-parameters, writing the updated state directly to the alternate texture buffer.

Throughout this entire loop, no intermediate tensors need to leave the GPU.

Technical Limitations and Considerations

While fully feasible, several WebGL constraints must be managed:

  • Floating-Point Precision: Training deep networks generally requires 32-bit floating-point precision. WebGL requires explicit support for floating-point textures (via the OES_texture_float extension), which gpu.js manages internally, but availability depends on the client hardware.
  • Texture Disposal: gpu.js does not automatically garbage-collect orphaned WebGL textures created during loop iterations. Unused intermediate textures (such as activations and deltas from prior batches) must be manually deleted using texture.delete() to prevent GPU memory leaks.
  • Debugging and Inspection: Because values stay packaged as textures, inspecting weights requires invoking .toArray() on the texture, which triggers a synchronous CPU readback and degrades frame rates if used frequently.
