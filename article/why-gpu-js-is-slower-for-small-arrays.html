Why GPU.js Is Slower for Small Arrays

While GPU.js provides substantial performance improvements by leveraging the massive parallelism of modern graphics cards, running small arrays on the GPU is often significantly slower than using a standard JavaScript loop. This performance penalty occurs because the architectural overhead of preparing, transferring, and coordinating execution on the GPU vastly outweighs the computational work required for small datasets. For small inputs, the CPU can execute the logic almost instantly, while the GPU spends the majority of its execution time on setup rather than actual calculation.

1. Data Transfer Overhead (PCIe and Memory Copying)

CPUs access data stored in system RAM and ultra-fast onboard cache (L1, L2, L3) with minimal latency measured in nanoseconds. In contrast, running code on the GPU via GPU.js requires data to be converted into WebGL-compatible structures (often textures or typed arrays) and transferred from CPU system memory to GPU VRAM. The time it takes to serialize data, transmit it across the PCIe bus, and deserialize it on the graphics card introduces latency that is far greater than the entire execution time of a native JavaScript for loop processing a few hundred or thousand elements.

2. Kernel Compilation and Initialization

Before GPU.js can execute your JavaScript function on the GPU, it must first transpile that code into a WebGL shader language (such as GLSL) and compile it on the GPU driver. While GPU.js caches compiled kernels after the initial run, the invocation, uniform binding, and context setup still require several non-trivial operations. A CPU loop, especially one optimized by V8 or SpiderMonkey's Just-In-Time (JIT) compiler, requires zero driver interaction and begins executing machine code immediately.

3. Thread Dispatch and Hardware Underutilization

GPUs achieve their speed by dividing workloads across thousands of lightweight stream cores running in parallel. When you dispatch an array of 50 or 500 items, most of the GPU's processing cores sit idle, yet the system must still pay the scheduling cost to initialize thread blocks and dispatch warps/wavefronts. The GPU cannot achieve high computational throughput unless there are enough data points to saturate its parallel pipeline.

4. CPU Cache Locality and JIT Optimizations

Modern JavaScript engines are heavily optimized for sequential memory access. When iterating over a standard array with a native loop, the CPU fetches contiguous memory into high-speed caches, predicting access patterns and executing instructions with minimal delay. For small datasets that fit comfortably inside L1 or L2 CPU cache, calculation times are practically instantaneous, making any GPU offloading counterproductive.

The Breakeven Point

GPU acceleration only becomes advantageous when the sheer volume of arithmetic operations eclipses the constant overhead of data transfer and shader coordination. As a general rule, GPU.js excels with large multidimensional matrices, complex mathematical operations per element, or datasets containing tens of thousands to millions of entries. For small arrays, native JavaScript loops running on the CPU remain the faster, more efficient choice.
