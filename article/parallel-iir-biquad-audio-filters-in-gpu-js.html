Parallel IIR Biquad Audio Filters in gpu.js

Infinite impulse response (IIR) biquad audio filters can mathematically be parallelized across time using parallel prefix scan algorithms, but executing them effectively in gpu.js presents severe practical limitations. While linear recurrence relations can be restructured into associative matrix operations to run in logarithmic time on a GPU, the WebGL-based architecture of gpu.js, dispatch overhead, and memory bandwidth constraints make it inefficient for typical audio processing compared to optimized CPU or WebAssembly alternatives.

The Inherent Sequential Problem of IIR Filters

A standard direct-form IIR biquad filter calculates output samples using the difference equation:

\[y[n] = b_0 x[n] + b_1 x[n-1] + b_2 x[n-2] - a_1 y[n-1] - a_2 y[n-2]\]

Because each output \(y[n]\) directly depends on previous outputs \(y[n-1]\) and \(y[n-2]\), the algorithm is naturally sequential. In traditional CPU processing, time-domain filtering is executed sample-by-sample in an \(O(N)\) loop, which cannot be directly mapped to GPU parallel threads where each thread calculates an individual sample independently.

The Mathematical Solution: Parallel Prefix Scans

To parallelize an IIR filter across time, the difference equation must be reformulated into a first-order state-space matrix recurrence:

\[S[n] = A \cdot S[n-1] + B \cdot X[n]\]

Where:

  • \(S[n]\) is a state vector containing the feedback history.
  • \(A\) is a constant transition matrix derived from the feedback coefficients \(a_1\) and \(a_2\).
  • \(B\) is an input coefficient vector.

Because matrix multiplication and affine transformations are associative, this linear recurrence relation can be solved in parallel across time using an associative scan algorithm (such as the Kogge-Stone or Blelloch scan). Instead of taking \(O(N)\) sequential steps, the scan computes all outputs across an array of length \(N\) in \(O(\log N)\) parallel steps using an up-sweep and down-sweep tree structure.

Practical Bottlenecks in gpu.js

Although the prefix scan works theoretically on modern GPU hardware, implementing it effectively in gpu.js introduces several major performance barriers:

  1. Lack of Shared Memory: gpu.js relies heavily on WebGL fragment shaders behind the scenes. WebGL lacks compute-shader primitives like fast thread-group shared memory (local storage) and subgroup/warp shuffles. A multi-step prefix scan requires writing back to and reading from WebGL textures across multiple passes, incurring significant memory bandwidth penalties.
  2. Kernel Dispatch Overhead: A Blelloch scan requires \(2 \times \log_2(N)\) distinct dispatch passes. In gpu.js, invoking multiple sequential kernel executions introduces JavaScript-to-WebGL driver overhead that quickly exceeds the execution time of the actual arithmetic.
  3. Audio Buffer Size vs. Latency: Real-time audio typically operates on small buffer sizes between 128 and 1024 samples to maintain low latency (under 10 ms). At these small sizes, \(O(N)\) sequential CPU computation takes mere microseconds. The latency required to transfer audio buffers from the CPU to the GPU, run multiple texture-bound shader passes, and read the float data back completely nullifies any theoretical parallel speedup.

Verdict

While you can parallelize IIR biquad filters across time in gpu.js for educational demonstration or very large offline batches (millions of samples), it cannot be done effectively for real-time audio. For low-latency filtering, single-threaded SIMD implementations in WebAssembly or native C++ are significantly faster, simpler, and more cache-efficient than parallelizing recurrence relations in gpu.js.
