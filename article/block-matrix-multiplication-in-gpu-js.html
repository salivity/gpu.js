Block Matrix Multiplication in gpu.js

This article explains how to implement block matrix multiplication in gpu.js to optimize performance by taking advantage of GPU texture caches. Standard matrix multiplication quickly becomes memory-bandwidth bound on large datasets; by partitioning matrices into smaller sub-blocks, memory access patterns can be aligned with the GPU's spatial 2D texture cache. Below, we cover the underlying cache mechanics in WebGL-based compute shaders, the algorithmic design of tiled matrix multiplication, and a complete code implementation in gpu.js.

The Memory Bottleneck in WebGL and gpu.js

Under the hood, gpu.js compiles JavaScript functions into WebGL fragment shaders. In this architecture, matrices are stored as 2D floating-point textures rather than linear memory buffers.

In a naive matrix multiplication kernel (\(C = A \times B\)), every thread computes a single output element \(C[i][j]\) by calculating the dot product of row \(i\) of matrix \(A\) and column \(j\) of matrix \(B\):

let sum = 0;
for (let k = 0; k < size; k++) {
  sum += this.constants.A[this.thread.y][k] * this.constants.B[k][this.thread.x];
}
return sum;

While row traversal along \(A\) benefits from linear memory reads, traversing column \(j\) in matrix \(B\) causes strided texture lookups across different cache lines. For large matrices, this creates frequent cache thrashing and memory latency, underutilizing the GPU's arithmetic logic units (ALUs).

Leveraging the 2D Texture Cache via Tiling

Dedicated compute environments (like CUDA or WebGPU) use programmer-managed shared memory to stage data blocks. In WebGL 1.0 and 2.0 (the backends for gpu.js), shared memory is unavailable. However, GPUs feature dedicated 2D texture caches designed for spatial locality, which cache small spatial rectangular regions (e.g., \(4 \times 4\) or \(8 \times 8\) texels) rather than purely contiguous 1D memory lines.

To exploit this hardware feature, matrix multiplication is reformulated into blocks of size \(M \times M\). Instead of streaming arbitrary rows and columns, the inner loop processes blocks sequentially. By synchronizing the reads across adjacent threads, texels fetched from matrix \(A\) and matrix \(B\) remain resident in the L1/L2 texture cache lines long enough to serve neighboring threads executing concurrently in the same warp or wavefront.

Implementation in gpu.js

To structure block execution, the loop traverses the inner dimension \(K\) in increments of a fixed tile size (e.g., 16 or 32). Inside each step, an unrolled sub-loop iterates through the coordinates within that tile.

const { GPU } = require('gpu.js');
const gpu = new GPU();

const MATRIX_SIZE = 1024;
const TILE_SIZE = 16;

const blockedMatrixMultiply = gpu.createKernel(
  function (A, B) {
    let sum = 0.0;
    const row = this.thread.y;
    const col = this.thread.x;
    const numTiles = this.constants.matrixSize / this.constants.tileSize;

    for (let t = 0; t < numTiles; t++) {
      const tileOffset = t * this.constants.tileSize;

      // Iterate through the current block/tile
      for (let k = 0; k < this.constants.tileSize; k++) {
        const currentK = tileOffset + k;
        sum += A[row][currentK] * B[currentK][col];
      }
    }

    return sum;
  },
  {
    constants: {
      matrixSize: MATRIX_SIZE,
      tileSize: TILE_SIZE,
    },
    output: [MATRIX_SIZE, MATRIX_SIZE],
    tiling: true,
    pipeline: true,
  }
);

Register Tiling: Expanding Outputs per Thread

To extract even higher throughput from the 2D texture cache, register tiling can be applied. In register tiling, each GPU thread calculates a small \(2 \times 2\) or \(4 \times 4\) sub-patch of the output matrix rather than just a single point.

By fetching a value from \(A\) and storing it in a local register, that value can be multiplied across multiple values of \(B\) loaded from the texture cache, drastically reducing total memory fetch instructions:

const tiledKernel2x2 = gpu.createKernel(
  function (A, B) {
    const row = this.thread.y * 2;
    const col = this.thread.x * 2;

    let c00 = 0.0, c01 = 0.0, c10 = 0.0, c11 = 0.0;

    for (let k = 0; k < this.constants.size; k++) {
      const a0 = A[row][k];
      const a1 = A[row + 1][k];
      const b0 = B[k][col];
      const b1 = B[k][col + 1];

      c00 += a0 * b0;
      c01 += a0 * b1;
      c10 += a1 * b0;
      c11 += a1 * b1;
    }

    // Pack or return based on output format requirements
    return c00; 
  },
  {
    constants: { size: MATRIX_SIZE },
    output: [MATRIX_SIZE / 2, MATRIX_SIZE / 2],
  }
);

Optimization Considerations

  1. Tile Dimension Alignment: Choose a TILE_SIZE that aligns with GPU warp/wavefront dimensions (typically multiples of 16 or 32). The total matrix dimension should ideally be evenly divisible by the tile size to avoid branching inside the shader loop.
  2. Loop Unrolling: Modern WebGL drivers unroll small, fixed-size inner loops automatically when loop counts are constants. Defining tileSize inside constants allows the shader compiler to optimize register allocation and issue parallel texture fetches.
  3. Pipelining: Setting pipeline: true in the kernel configuration ensures the output remains as a WebGL texture on the GPU, avoiding expensive memory transfers back to the CPU if further matrix operations follow.
