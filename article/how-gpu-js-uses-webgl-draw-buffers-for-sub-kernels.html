How GPU.js Uses WEBGL_draw_buffers for SubKernels

This article provides an overview of how the GPU.js library executes multiple subKernels concurrently in a WebGL 1 environment by leveraging the WEBGL_draw_buffers extension. It explains the mechanics of Multiple Render Targets (MRT), how GPU.js bypasses the native single-output limitation of WebGL 1, and the step-by-step shader and framebuffer compilation pipeline used to write to multiple output textures in a single compute pass.

The Single-Target Constraint in WebGL 1

Standard WebGL 1 pipelines operate under a strict limitation: a fragment shader can only write to a single render target per draw call. In standard GLSL ES 1.00, output is assigned directly to the built-in gl_FragColor variable. Under this model, computing multiple distinct arrays or matrices from a single set of operations requires multipass rendering, where the application must re-render geometry and re-execute shared calculations for every individual output buffer.

Multiple Render Targets via WEBGL_draw_buffers

The WEBGL_draw_buffers extension introduces Multiple Render Targets (MRT) to WebGL 1. This extension enables an application to attach several color buffers to a single Framebuffer Object (FBO) and write to them simultaneously during a single rasterization pass.

Instead of routing output exclusively to gl_FragColor, the extension unlocks the gl_FragData built-in array within the fragment shader:

#extension GL_EXT_draw_buffers : require
// ...
gl_FragData[0] = resultA;
gl_FragData[1] = resultB;

It also exposes the WebGL method drawBuffersWEBGL(), which defines an array of color attachments (COLOR_ATTACHMENT0_WEBGL, COLOR_ATTACHMENT1_WEBGL, etc.) that map directly to the corresponding indices in gl_FragData.

How GPU.js Implements subKernels with the Extension

GPU.js allows developers to bundle multiple computational outputs inside a single kernel execution using subKernels. When executing in a WebGL 1 context, GPU.js follows a structured process to utilize WEBGL_draw_buffers:

  1. Extension Detection and Feature Checking: Before kernel compilation, GPU.js queries the WebGL context for the WEBGL_draw_buffers extension using gl.getExtension('WEBGL_draw_buffers'). If unsupported, GPU.js cannot use MRT and must fall back to separate rendering passes or CPU execution.
  2. Framebuffer and Texture Allocation: For each declared subKernel, GPU.js allocates a backing WebGL texture sized to the kernel's output dimensions. It attaches these textures sequentially to the active FBO as ext.COLOR_ATTACHMENT0_WEBGL, ext.COLOR_ATTACHMENT1_WEBGL, and so forth.
  3. Buffer Mapping: GPU.js issues a call to ext.drawBuffersWEBGL([ext.COLOR_ATTACHMENT0_WEBGL, ext.COLOR_ATTACHMENT1_WEBGL, ...]). This informs the GPU pipeline that draw operations should route outputs to each attached texture concurrently.
  4. GLSL Code Generation: During kernel parsing, GPU.js compiles the JavaScript functions declared inside the subKernels object into a unified fragment shader:
    • It injects #extension GL_EXT_draw_buffers : require at the beginning of the shader source.
    • It analyzes the return values of the individual subKernel functions.
    • Instead of assigning results to gl_FragColor, it maps each subKernel's return value to an explicit index of gl_FragData[n].
  5. Single-Pass Dispatch: GPU.js executes a single draw call (typically rendering a screen-aligned quad). The GPU evaluates the shared logic, computes the specific results for each subKernel, and updates all bound textures simultaneously.

Advantages of the Draw Buffers Implementation

Utilizing WEBGL_draw_buffers provides substantial performance gains when executing subKernels:

  • Elimination of Redundant Computations: Mathematical operations shared between subKernels are evaluated once per fragment rather than recalculated in separate render passes.
  • Reduced State Overhead: The WebGL pipeline avoids repeated FBO binding, uniform re-uploads, and draw call overhead.
  • Unified Texture Pipelining: Output textures are populated at the same instant, making them immediately ready to be bound as input textures for subsequent kernels in a GPGPU pipeline.
