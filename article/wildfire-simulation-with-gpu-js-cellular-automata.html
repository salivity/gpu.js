Wildfire Simulation with GPU.js Cellular Automata

This article explores how cellular automata (CA) can be implemented and visualized for wildfire spread simulation using GPU.js. By compiling JavaScript functions into WebGL shaders, GPU.js leverages hardware acceleration to evaluate grid states simultaneously, making it fully capable of executing high-resolution, real-time fire propagation models directly in web browsers.

Cellular Automata for Wildfires

Cellular automata model fire behavior by dividing an environment into a uniform 2D grid of cells. Each cell contains distinct state parameters, such as vegetation density, moisture level, elevation, and burn status (unburned, burning, or burned).

During each simulation step, the state of a cell changes based on deterministic or probabilistic transition rules that evaluate its neighboring cells. These local rules can account for complex physical variables:

  • Fuel load and moisture: Determines ignition delay and burn duration.
  • Wind speed and direction: Skews the probability of ignition toward downwind neighbors.
  • Topography and slope: Accelerates fire spread uphill and slows it downhill.

Why Use GPU.js?

Traditional CPU-based implementations iterate through each cell sequentially using nested loops. For grids exceeding \(512 \times 512\) cells, CPU execution times degrade rapidly, preventing fluid interaction or real-time simulation.

GPU.js solves this bottleneck by compiling standard JavaScript code into GLSL shaders executed on the user's graphics processor. Because cellular automaton transition rules only depend on the previous state of neighboring cells, every cell update is independent and embarrassingly parallel. The GPU processes thousands of cells concurrently, maintaining interactive frame rates even at high resolutions.

Implementation Architecture

Building a wildfire simulation with GPU.js involves three primary steps:

  1. Grid Representation: Data is stored in 2D arrays representing elevation, fuel, and fire states.
  2. The Compute Kernel: A GPU.js kernel takes the current grid state as an input texture, inspects the adjacent cells (typically using a Moore neighborhood of eight cells), computes ignition probabilities based on wind and slope equations, and returns the updated state.
  3. Double Buffering (Ping-Ponging): To advance simulation steps continuously without reading and writing to the same memory space, two framebuffers alternate roles between source and destination textures.

Real-Time Visualization

GPU.js natively supports rendering output directly to an HTML5 <canvas> element using graphical kernels (graphical: true). Inside the kernel, each cell's state is mapped to an RGBA color value:

  • Unburned vegetation can be assigned varying shades of green based on fuel density.
  • Active fire cells transition from bright yellow to red according to temperature and burn progression.
  • Consumed cells render as gray or black to depict ash and scorched earth.

Because the computation and rendering happen within the same WebGL pipeline, the simulation avoids expensive memory transfers between CPU and GPU memory, ensuring consistent 60 FPS performance.

Limitations to Consider

While GPU.js is effective for browser-based simulations, developers should account for certain constraints:

  • Memory Bandwidth: Large state arrays passed between CPU and GPU each frame will degrade performance; state updates should remain on the GPU as textures whenever possible.
  • Floating-Point Precision: Mobile and low-end GPUs may lack full 32-bit floating-point precision in WebGL contexts, which can cause minor drift in fine-grained probabilistic models.
  • Global Data Access: Simulating dynamic, non-local environmental shifts—such as sudden shifts in atmospheric wind patterns influenced by the fire itself—requires multi-pass rendering architectures.
