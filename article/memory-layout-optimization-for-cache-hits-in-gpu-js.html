Memory Layout Optimization for Cache Hits in GPU.js

Memory layout optimization directly governs execution performance in GPU.js by determining how efficiently data transfers between the GPU’s high-bandwidth global memory and its on-chip cache hierarchy. Because GPU.js compiles JavaScript kernels into WebGL shaders, inputs are encoded into textures or buffers accessed simultaneously by thousands of parallel threads. Structuring memory to facilitate coalesced reads and high spatial locality drastically increases L1 and L2 cache hit rates, minimizing memory stalls and maximizing compute throughput.

The Mechanism of GPU Caching in GPU.js

GPUs process data through groups of parallel threads known as warps or wavefronts. When a warp executes a memory instruction inside a GPU.js kernel, the hardware attempts to service the data requests of all threads in that warp through a single or minimal number of memory transactions.

Under the hood, GPU.js primarily packs JavaScript array data into WebGL textures or storage buffers. Modern GPUs employ specialized L1/L2 caches and texture caches designed to exploit spatial locality—meaning adjacent threads accessing adjacent memory addresses fetch data that fits inside a single cache line (typically 32 to 128 bytes). If the layout scatters adjacent values across non-contiguous memory, each thread triggers an independent fetch, causing cache thrashing, high miss rates, and memory latency bottlenecks.

Contiguous Access and Thread Mapping

The primary driver of cache hits in GPU.js is mapping your kernel iteration variables (this.thread.x, this.thread.y, this.thread.z) to contiguous indices in your data:

  • Unit-Stride Access: When neighboring threads (differing by this.thread.x) read neighboring indices in an array, a single memory load loads an entire cache line that serves multiple threads. This generates near-100% cache line utilization and high hit rates.
  • Strided Access: If threads read data separated by large intervals (e.g., accessing column elements in a row-major array), every access pulls a new cache line into memory while utilizing only a fraction of the fetched bytes. This quickly evicts useful data from the cache, degrading performance.

Structure of Arrays (SoA) vs. Array of Structures (AoS)

JavaScript developers frequently work with Arrays of Structures (AoS), such as an array of objects containing {x, y, z} coordinates. In GPU computing, this layout severely reduces cache efficiency:

  • Array of Structures (AoS): If a kernel only needs to compute the x coordinates, an AoS layout forces the GPU cache to load y and z values into the cache lines alongside x. This pollutes the cache with unneeded data, reducing the effective cache size and causing frequent cache misses.
  • Structure of Arrays (SoA): Separating attributes into distinct, parallel typed arrays (e.g., a dedicated array for all x values, another for all y values) ensures that 100% of the data loaded into a cache line is actively consumed by the kernel. This significantly improves L1/L2 cache residency.

Texture Memory and 2D Spatial Locality

When GPU.js utilizes texture-based pipelines, hardware texture units utilize specialized 2D cache layouts (often using Morton order or Z-order curves) rather than linear memory addressing. In kernels performing 2D operations, such as image processing or matrix multiplication:

  • Accessing localized 2D patches (e.g., sampling neighboring pixels via this.thread.x ± 1 and this.thread.y ± 1) yields exceptionally high cache hit rates due to hardware-level 2D spatial caching.
  • Arbitrary lookups or large, non-linear jumps across coordinates bypass the texture cache's spatial assumptions, resulting in continuous cache misses and forced round-trips to VRAM.

Practical Guidelines for GPU.js

  1. Use 1D Flat TypedArrays: Supply data as flat Float32Array or Int32Array buffers instead of nested JavaScript arrays to eliminate pointer indirection and guarantee contiguous memory.
  2. Align the Fastest Dimension: Ensure the inner-most loop or the fastest-moving thread coordinate (this.thread.x) maps directly to the contiguous stride of your input arrays.
  3. Minimize Stride Distance: Reorganize matrix and multidimensional operations so that read operations process elements consecutively along memory lines rather than down columns.
