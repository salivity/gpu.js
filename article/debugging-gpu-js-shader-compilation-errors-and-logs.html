Debugging GPU.js Shader Compilation Errors and Logs

When a kernel fails to compile in GPU.js, debugging requires inspecting the underlying WebGL diagnostics and transpiled shader code. This article covers the specific error logs, metadata properties, and debugging surfaces exposed by GPU.js when a shader compilation or program linking phase fails, enabling developers to quickly trace syntax, type mismatch, and hardware-limit issues.

The JavaScript Error Object

When shader compilation fails, GPU.js throws a standard JavaScript runtime Error during kernel creation or upon the first invocation of the kernel. The error message typically indicates the stage of the failure—such as a failure to compile the fragment shader or an issue during the WebGL program linking stage.

Catching this error provides immediate high-level feedback:

try {
  const kernel = gpu.createKernel(function() {
    // Unsupported syntax or invalid logic
  }).setOutput([100]);
  kernel();
} catch (e) {
  console.error(e.message);
}

WebGL Shader Info Log

Under the hood, GPU.js compiles generated GLSL (OpenGL Shading Language) code inside the active WebGL context. When compilation fails, GPU.js extracts the internal compiler diagnostic via WebGL's getShaderInfoLog() method.

This log exposes:

  • GLSL Line Numbers: The line within the generated GLSL string where the error occurred (e.g., ERROR: 0:42: 'assign' : cannot convert from 'int' to 'float').
  • Error Categories: Syntactic errors, type mismatches, or calls to unsupported GLSL built-ins.
  • Shader Stage: An indication of whether the error originated in the vertex shader or the fragment shader (GPU.js primarily runs user logic in the fragment shader).

Transpiled GLSL Source Code

Because GPU.js translates JavaScript functions into GLSL, the line numbers reported in the shader info log correspond to the generated GLSL, not the original JavaScript source. GPU.js exposes the generated source string on the kernel instance, which can be inspected to align with the compiler log:

  • kernel.source: A string containing the entire generated GLSL fragment shader code sent to the WebGL compiler.
  • kernel.subKernels metadata: When using sub-kernels, source tracking maps which sub-kernel contributed to the compilation failure.

Reviewing kernel.source alongside the line numbers from the compilation error allows you to locate the exact translated operation that caused the failure.

Program Link Logs

If the vertex and fragment shaders compile successfully but fail to link into a runnable WebGL program, GPU.js surfaces the result of gl.getProgramInfoLog(). This log provides metadata regarding:

  • Varying and Uniform Limits: Indications that the kernel exceeded the maximum allowable uniform vectors or texture units supported by the GPU.
  • Varying Mismatches: Discrepancies between variables passed from the vertex stage to the fragment stage.

Context and Feature Detection Metadata

Compilation issues frequently stem from unsupported hardware capabilities (such as missing 32-bit floating-point texture support). GPU.js provides context-level properties that indicate the environment's capabilities before compilation is attempted:

  • gpu.canvas / WebGL Context: Provides direct access to the WebGL rendering context to query constants via gl.getParameter() (e.g., MAX_TEXTURE_SIZE, MAX_FRAGMENT_UNIFORM_VECTORS).
  • GPU.isWebGLSupported and GPU.isWebGL2Supported: Boolean flags indicating whether the current runtime environment supports the targeted WebGL API version.
  • Feature Fallback Warnings: When run in default environments, GPU.js logs warnings to console.warn if requested floating-point extensions or WebGL2 features are unavailable, forcing an automatic fallback to CPU mode if configured to do so.
