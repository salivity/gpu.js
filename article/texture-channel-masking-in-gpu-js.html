Texture Channel Masking in GPU.js

This article explains how the gpu.js library manages texture channel masking and vector component outputs during kernel execution. While low-level WebGL APIs natively support selective channel writing via color masking, gpu.js abstracts execution into GLSL fragment shaders that overwrite entire vector components. Understanding this mechanism is essential for developers seeking to optimize memory layout, manipulate multidimensional data, and selectively write to specific RGBA channels without triggering WebGL feedback loops.

The WebGL Abstraction Layer

In native WebGL, texture channel masking is typically achieved on the host side using gl.colorMask(red, green, blue, alpha). This call informs the graphics pipeline which specific components of a frame buffer can be written to, preserving the unmasked channels of an existing texture.

However, gpu.js operates at a higher level of abstraction. It compiles JavaScript functions directly into GLSL fragment shaders. In this execution model, each kernel invocation corresponds to a single fragment (or pixel) evaluation. Rather than exposing native colorMask toggles directly to kernel logic, gpu.js relies on the GLSL output pipeline, where every fragment must assign a complete four-component vector (vec4) to gl_FragColor.

Component Writing in Kernels

When configuring a kernel to output graphical data or multi-channel vectors, gpu.js expects the kernel to return an array corresponding to vector coordinates, such as [r, g, b, a].

Because fragment shaders cannot leave components "unassigned" at runtime, gpu.js handles vector writes through explicit assignment:

  1. Full Vector Emission: Any assignment to a target coordinate writes to all four channels simultaneously. If a kernel returns fewer than four values, gpu.js automatically pads the remaining components (typically with 0.0 or 1.0 depending on context and output format) to generate a valid vec4.
  2. Read-Modify-Write via Ping-Ponging: Because WebGL prohibits reading from and writing to the same texture within the same render pass (which causes an illegal feedback loop), a kernel cannot selectively mask a single channel in-place. To modify a single component (such as the red channel) while preserving the others (green, blue, alpha), the developer must pass the original texture as an input, sample all four components, update only the intended component, and emit the combined vec4 to a secondary output texture.

Float Packing and Internal Texture Layouts

When dealing with non-graphical numeric computations (such as 2D floating-point matrices), gpu.js utilizes texture channel packing under the hood if 32-bit floating-point textures are unsupported or disabled.

In packed mode, gpu.js splits a single 32-bit floating-point number across the red, green, blue, and alpha channels using bit-shifting arithmetic encoded directly into the generated GLSL. In this scenario, channel masking is neither permitted nor beneficial; altering an individual channel would corrupt the IEEE-754 representation of the stored float. The library reserves full control over all four channels to guarantee data integrity across encode and decode cycles.

Working Around Channel Masking Limitations

To emulate selective channel masking in gpu.js without native gl.colorMask access:

  • Pipeline Mode: Utilize kernel.setPipeline(true) to keep output textures in GPU memory. Chain kernels so that one pass reads the existing state, updates the relevant vector components, and outputs the updated state to the next buffer.
  • Sub-kernels: If multiple distinct values need to be written in a single pass, use sub-kernels. Sub-kernels allow multiple return values to be mapped to multiple render targets (MRT) when supported, rather than attempting to interleave multiple independent writes into individual channels of a single texture manually.
