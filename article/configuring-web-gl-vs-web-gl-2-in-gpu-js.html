Configuring WebGL vs WebGL2 in GPU.js

GPU.js accelerates browser-based computation by compiling standard JavaScript functions into GLSL shaders that run directly on the graphics card using WebGL. This article outlines how GPU.js manages the distinction between WebGL and WebGL2 modes, detailing automatic context selection, explicit configuration parameters, underlying architectural differences, and how to verify or override the runtime execution environment.

Automatic Detection and Fallback Hierarchy

By default, when you instantiate new GPU() without specifying a mode, the library employs a fallback priority sequence to determine the runtime environment:

  1. WebGL2 ('webgl2'): GPU.js first attempts to acquire a webgl2 rendering context. WebGL 2.0 provides modern shader language support (GLSL ES 3.00), native 32-bit floating-point textures, and broader hardware feature compatibility.
  2. WebGL 1 ('webgl'): If the client hardware, browser, or platform does not support WebGL 2.0, GPU.js falls back to requesting a standard webgl context (or experimental-webgl). In this mode, it relies on specific WebGL extensions (such as OES_texture_float) to emulate high-precision computational capabilities.
  3. CPU ('cpu'): If no WebGL hardware acceleration is available or enabled, the library falls back to pure JavaScript execution on the CPU.

Explicit Mode Configuration

You can bypass the automatic fallback logic by explicitly defining the execution mode in the constructor options. This is accomplished using the mode property:

// Force WebGL 2 mode
const gpu = new GPU({ mode: 'webgl2' });

// Force WebGL 1 mode
const gpuLegacy = new GPU({ mode: 'webgl' });

When you force a specific mode, GPU.js skips the discovery cascade. If you request webgl2 on an environment where WebGL 2.0 is unavailable, the constructor will throw an error rather than silently degrading to WebGL 1 or the CPU. This explicit configuration is particularly useful during debugging or when your application relies strictly on features exclusive to a specific context.

Other valid values for mode include 'cpu', 'headlessgl' (for Node.js environments), and 'dev' (which enables debugging features for kernel development).

Technical Differences Between WebGL and WebGL2 Modes

The operational differences between WebGL and WebGL2 contexts directly influence performance and output formatting in GPU.js:

  • Floating-Point Textures: Output data in GPU.js is represented internally as textures. WebGL2 supports IEEE 754 32-bit floating-point textures natively without requiring vendor extensions. WebGL 1 requires checking for and enabling OES_texture_float and WEBGL_color_buffer_float. If these extensions are absent in WebGL 1 mode, precision drops to 8-bit integers per channel, or execution fails.
  • Shader Generation: GPU.js compiles JavaScript kernels into GLSL. Under webgl2, it compiles to GLSL ES 3.00, enabling features like flat interpolation, bitwise operators, and non-constant loop indices. Under webgl, it compiles to GLSL ES 1.00, which has stricter syntax rules and lacks native integer operations.
  • Precision Settings: The precision kernel setting (e.g., 'single' or 'unsigned') interfaces directly with the active mode. WebGL2 reliably provides full single-precision floating-point math across most devices, whereas WebGL 1 precision varies depending on driver support for mediump vs. highp precision qualifiers in fragment shaders.

Providing Custom Canvas and Existing Contexts

GPU.js also permits supplying an existing HTMLCanvasElement or rendering context directly into the constructor:

const canvas = document.getElementById('custom-canvas');
const gl = canvas.getContext('webgl2');

const gpu = new GPU({
  canvas: canvas,
  context: gl
});

When passing an existing context, GPU.js automatically infers the mode from the prototype of the provided context (identifying WebGL2RenderingContext as 'webgl2' and WebGLRenderingContext as 'webgl'). Supplying a pre-existing context is common when integrating GPU.js kernels into larger graphical rendering pipelines.

Inspecting the Active Mode

To programmatically determine which context GPU.js is currently running after initialization, read the mode property of the instance:

const gpu = new GPU();

console.log(gpu.mode); // Outputs 'webgl2', 'webgl', or 'cpu'

Querying this property allows applications to dynamically adjust workload sizes, precision expectations, or UI indicators based on whether the device successfully initialized a WebGL2 pipeline or was relegated to WebGL 1.
