GPU.js Memory Leaks: Undisposed Textures Explained

Repeatedly creating textures without disposing of them in gpu.js leads to severe memory leaks in both GPU video RAM (VRAM) and system RAM, ultimately causing application crashes or WebGL context loss. Because gpu.js relies on WebGL underneath, allocating textures continuously consumes hardware-accelerated resources that the browser's standard garbage collector cannot efficiently reclaim on its own.

How GPU.js Allocates Textures

When you execute a kernel with graphical output or use pipeline mode (pipeline: true), gpu.js outputs data directly as a WebGL texture. Textures are not standard JavaScript arrays; they are high-performance data buffers allocated directly inside the GPU's memory. Each new texture instantiates a new WebGL texture object bound to the active rendering context.

The Garbage Collection Disconnect

JavaScript employs automatic garbage collection (GC), but garbage collectors primarily monitor the memory footprint within the JavaScript virtual machine (such as V8). A gpu.js texture object in JavaScript is merely a lightweight reference—a wrapper around a resource that lives inside GPU memory.

Because the JavaScript engine sees only a tiny wrapper object taking up negligible heap space, it does not prioritize running garbage collection. Meanwhile, the actual GPU memory (VRAM) rapidly fills up with heavy graphical buffers that remain tied to the active WebGL context.

Consequences of Continuous Allocation

If textures are created inside a continuous loop, animation frame, or recurring task without explicit cleanup, the following issues occur sequentially:

  1. VRAM and Dedicated Memory Spike: Video memory usage will climb continuously. If the GPU runs out of dedicated VRAM, the operating system attempts to swap data to shared system memory, introducing immense latency.
  2. Performance Degradation: Kernel execution times increase significantly as the GPU and driver struggle with texture thrashing and allocation bottlenecks.
  3. WebGL Context Loss: Once memory limits are reached, the browser will forcibly terminate the WebGL context with a webglcontextlost error to protect system stability. Any running kernels will fail immediately.
  4. Browser Tab Crash: In extreme cases, rapid unmonitored allocations outpace the browser's safeguards, resulting in an Out of Memory (OOM) browser crash.

Preventing Texture Memory Leaks

To maintain steady memory consumption, textures must be manually destroyed when they are no longer required.

gpu.js provides an explicit cleanup method for this purpose:

const texture = myKernel();

// Process or read data from texture...

// Explicitly free the texture from GPU memory
texture.delete();

When using pipelining across multiple kernel passes, ensure that intermediate textures from previous cycles are deleted immediately after their successor kernels finish reading them. Explicit disposal guarantees that the underlying WebGL textures are unbound and destroyed instantly, keeping VRAM utilization stable and predictable.
