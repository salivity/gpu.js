GPU Memory Fragmentation in Long-Running gpu.js Apps

Continuous, long-running applications built with gpu.js can be significantly affected by GPU memory fragmentation. Because gpu.js relies on underlying graphics APIs like WebGL to manage textures and compute pipelines, frequent allocation and deallocation of dynamic buffers can scatter available VRAM into non-contiguous blocks. Over time, this fragmentation leads to unexpected out-of-memory errors, frame drops, context losses, and degraded execution speeds even when overall VRAM usage appears low.

How gpu.js Manages GPU Memory

gpu.js compiles JavaScript functions into GLSL shaders and executes them on the GPU using WebGL (in the browser) or headless-gl (in Node.js). In this architecture, arrays and matrices are encoded as GPU textures, and computation results are written to output framebuffers.

Every time a kernel runs with new input sizes or when intermediate textures are created without reuse, the graphics driver allocates new texture space in VRAM. When textures fall out of scope in JavaScript, their corresponding GPU memory is marked for deletion.

The Mechanism of Fragmentation in gpu.js

GPU memory allocators generally require contiguous blocks of memory to store 2D or 3D textures. Fragmentation occurs in continuous systems due to three primary factors:

  1. Varying Input Dimensions: If a continuous process processes variable-sized data batches, gpu.js must allocate textures of differing sizes. Repeated allocation of mismatched blocks creates "holes" of free memory that are too small for subsequent large operations.
  2. Asynchronous Garbage Collection Desynchronization: JavaScript’s garbage collector (GC) operates independently of the GPU memory allocator. A texture may be dereferenced in JavaScript, but the underlying VRAM is not freed until the host GC runs and WebGL releases the native resource. This delay causes temporary VRAM bloat and worsens fragmentation.
  3. Driver-Level Limitations: Most consumer graphics drivers do not aggressively defragment VRAM during runtime because moving active textures incurs a significant latency penalty. Once fragmented, memory remains fragmented until allocated buffers are explicitly released or the process restarts.

Symptoms in Long-Running Applications

When memory fragmentation reaches critical levels in a continuous gpu.js pipeline, applications experience distinct failure modes:

  • WebGL Context Loss: The browser or runtime terminates the WebGL context (webglcontextlost) when a contiguous allocation fails, halting computation entirely.
  • Sudden Out-of-Memory (OOM) Errors: The driver rejects a new texture allocation despite reporting sufficient total free VRAM, because no single contiguous block matches the requested size.
  • Latency Spikes: The driver attempts internal compaction or swaps textures to system RAM, causing severe throughput degradation and jitter in real-time workloads.

Best Practices to Prevent Fragmentation

To maintain stability in continuous environments, developers must adopt strict memory management patterns:

  • Keep Input Sizes Constant: Pad dynamic inputs to fixed, standard dimensions. Consistent texture sizes allow the driver to cleanly reuse memory slots without leaving unusable gaps.
  • Reuse Output Textures: Utilize the pipeline: true mode in gpu.js to pass textures directly between kernels without reading data back to the CPU or constantly recreating texture objects.
  • Explicit Resource Cleanup: Do not rely solely on JavaScript garbage collection. Manually invoke .destroy() on kernels, textures, and contexts when they are no longer required to trigger immediate VRAM deallocation.
  • Implement Periodic Restarts: For 24/7 continuous services (such as video analysis or background processing in Node.js), schedule controlled worker restarts or WebGL context re-initializations to clear and reset the hardware memory space completely.
