Real-Time Water Ripple Simulation with GPU.js

Water ripple dissipation models on two-dimensional heightfield grids can be simulated in real time using gpu.js. By compiling JavaScript functions into WebGL shaders, gpu.js offloads the intensive per-cell calculations of a 2D wave equation to the graphics processor. This article examines how the underlying wave dissipation physics operate on a discrete grid, why the parallel architecture of gpu.js makes real-time framerates achievable, and the key technical considerations required for an efficient implementation.

The Physics of 2D Heightfield Ripple Dissipation

A 2D heightfield represents water as an array of discrete vertical displacement points on an \(X \times Y\) grid. The propagation and dissipation of surface ripples can be modeled using a discretized version of the 2D wave equation combined with a damping coefficient.

In this model, the state of any grid cell at the next time step (\(h_{x,y}^{t+1}\)) depends on its current height, its previous height, and the average height of its immediate orthogonal neighbors (North, South, East, West):

\[h_{x,y}^{t+1} = \left( \frac{h_{x-1,y}^t + h_{x+1,y}^t + h_{x,y-1}^t + h_{x,y+1}^t}{2} - h_{x,y}^{t-1} \right) \times d\]

The variable \(d\) represents the dissipation or damping factor (typically a scalar such as 0.96 to 0.99). Values below 1.0 ensure that energy is lost over time, causing ripples to naturally attenuate and flatten out rather than oscillating indefinitely.

Why GPU.js Enables Real-Time Performance

Simulating this process on a CPU requires iterating through nested loops over every cell in the grid for each animation frame. While a \(128 \times 128\) grid (16,384 cells) may run adequately on modern CPUs, scaling to higher resolutions like \(512 \times 512\) (262,144 cells) or \(1024 \times 1024\) (over 1,000,000 cells) introduces severe framerate drops due to thread execution limits and cache constraints.

Heightfield wave propagation is an embarrassingly parallel problem. Because the calculation for cell \((x, y)\) relies exclusively on data from the preceding time step, every cell can be computed simultaneously.

GPU.js leverages this characteristic by transpiring standard JavaScript kernel functions into WebGL fragment shaders. Each grid cell maps to an execution thread running concurrently on the GPU's streaming multiprocessors. This allows modern integrated and dedicated graphics cards to compute millions of cell updates well within the 16.6-millisecond budget required for a stable 60 frames per second (FPS).

Implementation Considerations

To achieve real-time execution in gpu.js, three architectural details are critical:

  1. State Buffering (Ping-Pong Technique): Calculating wave motion requires tracking at least two previous states (time \(t\) and time \(t-1\)). Because shaders cannot safely read from and write to the same memory buffer simultaneously, you must alternate between two or three textures—reading from previous states and rendering into the next.
  2. Pipeline Mode: Standard gpu.js operations transfer computed data back to the CPU as typed arrays via readPixels, which introduces a severe performance bottleneck. Enabling pipeline mode (pipeline: true) keeps the output directly on the GPU as a WebGL texture, allowing consecutive simulation steps to execute without memory transfer overhead between the GPU and CPU.
  3. Boundary Conditions: The kernel must account for grid edges. Clamping edge indices or setting fixed Dirichlet boundaries (\(h=0\)) prevents out-of-bounds memory lookups and manages wave reflection behaviors when ripples strike the perimeter of the heightfield.

Through pipeline mode and parallel shader execution, gpu.js provides more than enough throughput to execute 2D heightfield wave propagation and dissipation models in real time for interactive applications, games, and web-based physics visualizations.
