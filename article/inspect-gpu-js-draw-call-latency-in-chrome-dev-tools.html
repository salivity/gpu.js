Inspect gpu.js Draw Call Latency in Chrome DevTools

This guide details how to leverage the Chrome DevTools Performance panel to detect, measure, and minimize draw call latency in gpu.js applications. By capturing and analyzing runtime profiles, developers can inspect the handoff between JavaScript execution on the main thread and shader processing on the GPU. You will learn how to configure DevTools for GPU profiling, identify gpu.js execution phases, and isolate bottlenecks such as synchronous texture readbacks and pipeline stalls.

1. Configure the DevTools Performance Panel

To capture accurate timing metrics for WebGL-based operations executed by gpu.js, the DevTools environment must be properly configured:

  1. Open Chrome DevTools (F12 or Ctrl+Shift+I / Cmd+Option+I).
  2. Navigate to the Performance tab.
  3. Click the Capture settings (gear icon) in the top-right corner.
  4. Enable Advanced paint instrumentation (slow). While this adds minor overhead, it provides deeper visibility into rasterization and rendering events.
  5. Optional: Under CPU, select 4x slowdown or 6x slowdown if you need to simulate performance on lower-tier hardware.

2. Record the Kernel Execution

To isolate the latency of a gpu.js kernel:

  1. Click the Record button (the solid circle) in the Performance panel.
  2. Trigger the gpu.js kernel run in your application (for example, clicking a button or letting an animation loop complete a few cycles).
  3. Click Stop once the kernel execution finishes.
  4. Allow DevTools to finish processing the profile trace.

3. Locate the Main Thread JavaScript Calls

In the generated trace, locate the Main thread track to inspect how the CPU issues instructions to the GPU:

  • Identify the Call Stack: Look for your custom JavaScript function calling the gpu.js kernel. Underneath it, gpu.js will invoke internal WebGL functions.
  • Locate WebGL Dispatches: Zoom in (using the W and S keys) on the kernel execution block. Look for low-level WebGL API calls such as drawArrays, drawElements, useProgram, and bindTexture.
  • Measure Dispatch Duration: The total width of the JavaScript block containing these calls represents the CPU overhead required to set up parameters, uniforms, and dispatch the draw command.

4. Inspect the GPU Track

Scroll to the GPU track, situated beneath or alongside the Main and Compositor tracks:

  • GPU Activity Blocks: The green blocks in the GPU track indicate when the GPU hardware is actively processing commands.
  • Measuring Draw Call Latency: Check the interval between the moment the main thread issues the WebGL draw call (e.g., gl.drawArrays) and when the corresponding GPU block finishes processing. The time gap between dispatch and completion is your total latency.
  • Pipeline Stalls: If there is an extensive gap where the CPU is waiting and the GPU shows no activity, the pipeline may be waiting for resource uploads, compilation, or context switches.

5. Identify Synchronous Readback Bottlenecks

The most common cause of high latency in gpu.js is retrieving data back to the CPU:

  • Look for calls to gl.readPixels or gpu.js functions that convert textures back to arrays (e.g., returning numeric arrays instead of texture outputs).
  • gl.readPixels forces synchronous CPU-GPU synchronization, blocking the Main thread completely until the GPU finishes all queued commands and returns the pixel data.
  • If a prominent red marker appears in the Main thread over these calls, the thread is blocked waiting for the GPU.

6. Interpret Results to Optimize gpu.js Performance

  • Long CPU Duration, Short GPU Duration: The overhead of setting up the kernel and parsing input arrays outweighs the actual parallel computation. Mitigate this by passing textures directly into kernels (pipeline: true) instead of raw JavaScript arrays.
  • Long GPU Execution: The kernel computation itself is heavy. Optimize shader logic, reduce output dimensions, or decrease loop iterations inside the kernel.
  • Frequent Main Thread Stalls: Keep computations on the GPU by chaining multiple kernels together using texture outputs, deferring CPU readback until the final calculation step.
