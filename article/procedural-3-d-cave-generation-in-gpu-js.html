Procedural 3D Cave Generation in GPU.js

Procedural cave generation using 3D cellular automata can be executed seamlessly in gpu.js, provided the system is designed to leverage GPU-native pipelines and avoid CPU-GPU memory bottlenecks. By converting 3D grid state evaluations into parallel compute shaders via WebGL, gpu.js accelerates neighborhood calculations across millions of voxels. However, maintaining high frame rates requires careful management of texture-based ping-pong buffers, memory limits, and the subsequent mesh extraction step.

How 3D Cellular Automata Maps to GPU.js

Cellular automata algorithms generate cave systems by initializing a 3D grid with random binary states (rock versus air) and iteratively updating each cell based on the state of its surrounding neighbors (typically the 26 adjacent cells in a 3D Moore neighborhood).

Because the state of every voxel in iteration \(N+1\) depends strictly on the static state of the grid at iteration \(N\), the algorithm is embarrassingly parallel. GPU.js compiles written JavaScript into GLSL fragment shaders, allowing developers to define a 3D execution kernel:

const caveKernel = gpu.createKernel(function(grid) {
    let neighbors = 0;
    // Iterate through the 26 neighbors in 3D space
    for (let z = -1; z <= 1; z++) {
        for (let y = -1; y <= 1; y++) {
            for (let x = -1; x <= 1; x++) {
                if (x !== 0 || y !== 0 || z !== 0) {
                    neighbors += grid[this.thread.z + z][this.thread.y + y][this.thread.x + x];
                }
            }
        }
    }
    // Apply cave generation rules
    return neighbors >= 14 ? 1 : 0;
})
.setOutput([width, height, depth])
.setPipeline(true);

Achieving Seamless Computation

The compute phase itself runs well within the threshold required for real-time applications (typically 16ms or faster for mid-sized grids) when following specific practices:

  1. Pipeline Mode (Ping-Pong Buffering): Enabling .setPipeline(true) is vital. Instead of serializing the 3D array back to CPU memory after every iteration, gpu.js outputs a WebGL texture that stays in video memory. This texture can be fed directly back into the next iteration as an input, executing multiple smoothing passes virtually instantly.
  2. Dimension Constraints: A grid size of \(128 \times 128 \times 128\) consists of roughly 2.1 million voxels, which modern GPUs evaluate in a few milliseconds. Scaling up to \(256 \times 256 \times 256\) (16.7 million cells) approaches texture dimension and VRAM limits in browser environments, leading to frame drops if not handled in chunks.

Primary Bottlenecks

While the automata computation itself is seamless, two downstream bottlenecks often break real-time performance:

  • Data Readback Overhead: If the simulation must return data to the CPU to construct geometry or handle physics, calling .toArray() forces the GPU to synchronize with the CPU via gl.readPixels(). This stalls the main browser thread.
  • Surface Reconstruction (Meshing): A voxel field generated by cellular automata must be converted into visible geometry, commonly using Marching Cubes, Dual Contouring, or blocky meshing. If this step is performed on the CPU in pure JavaScript, it quickly becomes the primary bottleneck, offsetting the performance gained from GPU-accelerated generation.

Practical Verdict

Procedural 3D cave generation via cellular automata runs smoothly in gpu.js if the world is divided into manageable chunks (e.g., \(32^3\) or \(64^3\) volumes) and computation loops remain on the GPU using pipelined textures. To maintain end-to-end seamless performance, the generated data should either be rendered directly using volumetric raymarching inside a WebGL shader or processed into polygonal meshes asynchronously via Web Workers to avoid main-thread stutter.
