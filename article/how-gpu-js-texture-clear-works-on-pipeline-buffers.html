How gpu.js Texture.clear Works on Pipeline Buffers

In gpu.js, invoking Texture.clear() on an active pipeline buffer initiates an immediate, low-level WebGL resource release rather than waiting for JavaScript garbage collection. This article breaks down the internal sequence triggered by this method call, covering underlying OpenGL ES state alterations, framebuffer detachment side effects, and the resulting disruption to GPU-accelerated compute chains.

Direct WebGL Texture Deletion

At its core, a Texture object in gpu.js acts as a high-level JavaScript wrapper around a native WebGLTexture reference. When Texture.clear() is called, the method directly accesses the underlying rendering context (gl) and executes:

gl.deleteTexture(this.texture);
this.texture = null;

This commands the GPU driver to mark the associated video memory (VRAM) allocation for immediate reclamation. Unlike standard JavaScript objects that rely on engine-level mark-and-sweep garbage collection, WebGL texture allocations reside directly in GPU memory, making explicit deallocation essential to prevent memory leaks in continuous rendering loops.

Framebuffer Detachment and State Invalidation

When a kernel operates in pipeline mode (pipeline: true), gpu.js routes its output to an offscreen WebGLFramebuffer (FBO) rather than the screen canvas. The current Texture instance serves as the color attachment point (gl.COLOR_ATTACHMENT0) for that framebuffer.

Invoking clear() while the buffer is active forces the WebGL implementation to automatically detach the deleted texture from the bound framebuffer. Consequently, the framebuffer transitions into an incomplete state (gl.FRAMEBUFFER_INCOMPLETE_MISSING_ATTACHMENT). Any subsequent draw call that targets this framebuffer before a valid texture is reattached will fail and generate an internal INVALID_FRAMEBUFFER_OPERATION error.

Breaking the Pipeline Ping-Pong Mechanism

In multi-pass compute pipelines, gpu.js utilizes a "ping-pong" buffering pattern: one texture acts as the read-only uniform input while a secondary texture acts as the writable render target, alternating roles on each successive kernel call.

If Texture.clear() is executed on an active buffer within this cycle, the reference chain is broken. When the downstream kernel attempts to bind the deleted texture via gl.bindTexture(gl.TEXTURE_2D, texture.texture), it binds an invalid/null pointer. WebGL handles this by sampling from an empty, black fallback texture (evaluating to [0, 0, 0, 0] in floating-point operations), leading to corrupted computational output or runtime driver crashes without an explicit JavaScript exception.

CPU-Side Metadata Reset

Alongside the GPU resource release, Texture.clear() clears internal tracking flags on the JavaScript object itself. Properties representing dimensions, texture formats, and kernel references are invalidated. Attempting to pass this cleared instance into .toArray() or as an input argument to another kernel will cause gpu.js to fail at the validation layer, as the wrapper can no longer provide valid texture target IDs or dimension arrays to the shader compilation pipeline.
