GPU.js Texture vs JavaScript Object Lifecycle

In GPU.js, a Texture object represents data stored directly in the GPU's memory (VRAM) rather than the standard JavaScript heap, leading to a fundamentally different lifecycle. While standard JavaScript objects are fully managed by the runtime's automatic garbage collection, a GPU.js Texture requires active lifecycle management, explicit deallocation, and awareness of the boundary between the CPU and the GPU. Understanding these differences is critical for preventing memory leaks, eliminating unnecessary data transfer bottlenecks, and maximizing WebGL compute performance.

Memory Allocation and Placement

When a standard JavaScript object is created, the JavaScript engine allocates space on the process heap. In contrast, instantiating or outputting a Texture in GPU.js involves two distinct layers: a lightweight JavaScript reference object on the CPU heap and an underlying WebGL texture allocated directly in GPU VRAM. This distinction allows GPU.js kernels to run computations and output results directly onto the graphics hardware without the expensive overhead of serializing data back into native JavaScript arrays.

Garbage Collection vs. Manual Disposal

The most significant divergence in lifecycle management is deallocation:

  • Standard JavaScript Objects: The JavaScript engine uses mark-and-sweep garbage collection. Once an object falls out of scope and loses all references, the engine automatically frees its memory during a future garbage collection cycle.
  • GPU.js Texture Objects: The underlying GPU texture is not reliably tied to JavaScript's garbage collector. While the JavaScript wrapper might be garbage-collected, the corresponding WebGL texture can remain allocated in video memory. To fully release VRAM, developers must explicitly call the .delete() method on the Texture instance. Failing to invoke .delete() can cause severe VRAM leaks and eventually crash the WebGL context.

Execution and Kernel Chaining

Standard objects pass by reference or value across synchronous and asynchronous CPU functions, maintaining accessibility until dereferenced. A GPU.js Texture functions as an execution pipeline component designed for kernel chaining.

When a kernel is configured with { output: [...], pipeline: true }, it returns a Texture instead of a multi-dimensional array. This Texture can be passed immediately into a subsequent kernel as an input. Throughout this chained lifecycle, the data never leaves the GPU. This eliminates the latency of copying data across the PCI bus back to the CPU until the final result is required.

Materialization and End-of-Life

A standard object exists in a readable state at all points in its lifecycle. A GPU.js Texture, however, exists in an encoded hardware state optimized for parallel compute operations. To convert the texture data back into standard CPU-accessible JavaScript structures, it must be explicitly materialized using the .toArray() method. Calling .toArray() synchronously reads the pixels from the WebGL context, translates them into JavaScript arrays or typed arrays, and transitions the computational data out of the GPU pipeline into standard garbage-collected heap memory.
