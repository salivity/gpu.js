gpu.js Simultaneous Thread Limit Explained

While gpu.js allows developers to dispatch millions of parallel computations by mapping JavaScript functions to WebGL shaders, the practical limit of truly simultaneous hardware threads is governed by the host machine's physical GPU architecture and WebGL driver limits rather than the library itself. In practice, a standard consumer GPU executes between 1,000 and 30,000 threads concurrently at any given clock cycle, even though gpu.js can queue and manage virtual grid sizes containing hundreds of millions of elements.

Virtual Threads vs. Physical Execution

When you configure an output size in gpu.js (such as kernel.setOutput([width, height])), you are defining the total number of work items, or "virtual threads," required to complete the workload.

  • Virtual Dispatches: gpu.js can effortlessly process workloads of \(10^6\) to \(10^8\) items. The library serializes this array into texture space, letting the GPU scheduler distribute the data across available compute resources.
  • Physical Concurrency: The GPU's hardware scheduler breaks down this workload into batches (known as warps on NVIDIA or wavefronts on AMD). Only a limited subset of these batches can physically execute on the hardware compute units at the same instant.

The Hardware Bottleneck

The absolute ceiling for simultaneous thread execution depends on three primary hardware specifications:

  1. Compute Units and Multiprocessors: Modern GPUs are divided into Streaming Multiprocessors (SMs) or Compute Units (CUs). Each unit contains a fixed number of execution pipelines (ALUs).
  2. Occupancy and Warps: An NVIDIA SM typically manages up to 1,024 to 2,048 in-flight threads distributed across 32-thread warps. An AMD Compute Unit typically manages up to 2,560 threads in 64-thread wavefronts.
  3. Register and Memory Pressure: If a gpu.js kernel requires many local variables or complex mathematical operations, it consumes more GPU registers. High register usage lowers hardware occupancy, drastically reducing the number of active threads executing side-by-side.

On modern mid-to-high-end hardware (such as an NVIDIA RTX 3070 or 4080), total concurrent in-flight threads across all SMs typically range from 15,000 to 60,000 threads. On integrated graphics (such as Intel Iris Xe or Apple M-series base chips), concurrent hardware threads generally range between 512 and 4,096.

WebGL Abstraction Limits

Under the hood, gpu.js compiles JavaScript into GLSL fragment shaders executed via WebGL (or headless-gl in Node.js environments). This pipeline introduces structural boundaries:

  • Maximum Texture Dimensions: Output grids are limited by the browser's MAX_TEXTURE_SIZE query. On most devices, this limit is either 8,192 or 16,384 pixels per side. Consequently, a 2D dispatch cannot exceed dimensions like \(8192 \times 8192\) (roughly 67.1 million elements) in a single slice without hitting memory allocation failures.
  • Lack of Compute Shader Workgroups: Because standard gpu.js builds upon the WebGL 1.0/2.0 fragment shading pipeline rather than dedicated WebGPU compute shaders, developers cannot explicitly set low-level workgroup sizes (e.g., \(16 \times 16\)). The hardware driver dictates scheduling and fragment parallelism automatically.

The Practical Rule of Thumb

To optimize performance without encountering hardware crashes or browser context loss:

  • Ideal Batch Sizes: Keep your total array output between 100,000 and 4,000,000 elements. This range fully saturates modern hardware execution units while minimizing overhead.
  • Browser Timeout Avoidance: Executing a kernel that monopolizes hardware execution for more than a couple of seconds triggers the OS-level Display Driver Recovery (TDR) mechanism, causing the WebGL context to crash. Long-running workloads should be split across multiple smaller dispatches rather than attempted in a single massive kernel invocation.
