GPU.js Performance: Passing Large Arrays Every Frame

Passing large arrays to GPU.js kernels on every render frame introduces severe performance bottlenecks primarily driven by CPU-to-GPU memory transfer limits, WebGL texture conversion overhead, and JavaScript garbage collection. While GPU.js executes calculations across thousands of parallel threads efficiently, repeatedly transferring large datasets across the system bus on every frame negates the benefits of GPU acceleration, leading to frame drops and high latency.

The Host-to-Device Transfer Bottleneck

The primary cost of passing arrays every frame is the physical transfer of data from system memory (RAM) to graphics memory (VRAM) across the PCIe bus. While the GPU compute cores operate exceptionally fast, the PCIe bandwidth is finite. For example, passing a standard array of one million 32-bit floating-point numbers consumes roughly 4 MB of raw data. Transferring that data at 60 frames per second requires moving at least 240 MB/s of data across the bus, creating significant synchronization stalls where the GPU remains idle waiting for the CPU to finish dispatching data.

WebGL Texture Upload Overhead

Under the hood, GPU.js compiles JavaScript kernels into WebGL shaders and encodes input array data into WebGL textures. When an array argument is provided each frame, GPU.js must:

  1. Parse the JavaScript array.
  2. Flatten or normalize the array into an internal typed structure.
  3. Call WebGL texture allocation methods (such as texImage2D or texSubImage2D) to upload the data into GPU memory.

Re-binding and repopulating textures every frame forces the browser's WebGL context to synchronize with the GPU, halting asynchronous execution pipelines and resulting in high frame-time variance.

JavaScript Memory and Garbage Collection Pressure

Standard JavaScript arrays are not stored as contiguous blocks of memory; they are dynamic objects. Converting these dynamic arrays into WebGL-compatible buffers incurs significant CPU overhead. Furthermore, if new arrays or wrapper structures are allocated each frame, the JavaScript engine's garbage collector must frequently pause execution to clean up unreferenced memory. These garbage collection spikes cause noticeable stuttering and dropped frames in real-time applications.

Strategies to Minimize the Performance Cost

  • Keep Data on the GPU: When running multi-pass computations or iterative simulations, set the kernel option { output: [...], pipeline: true }. This instructs GPU.js to return a texture instead of reading results back to the CPU as a JavaScript array, allowing you to pass the output directly into the next kernel without leaving VRAM.
  • Use TypedArrays: Always use Float32Array or Int32Array instead of standard JavaScript arrays. Typed arrays occupy contiguous memory, eliminating the need for GPU.js to convert data formats before passing it to WebGL buffers.
  • Update Only Changed Data: If only a subset of the array changes per frame, avoid sending the full array repeatedly. Instead, restructure the kernel to update localized regions or generate the mutations procedurally on the GPU.
