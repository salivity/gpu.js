Parallelizing GRU Gates Across Batches in gpu.js

Gated Recurrent Unit (GRU) gate update operations can be efficiently parallelized across batches in gpu.js by mapping the batch index and hidden state dimensions directly to the GPU kernel execution grid. While the recurrent state transitions remain strictly sequential along the time dimension, all linear projections and element-wise activation functions for a given time step are independent across the batch. This guide details how to structure GRU gate computations within gpu.js kernels to achieve optimal batch-level parallelism.

The Mathematics of Batch Parallelism in GRUs

A standard GRU computes three primary vectors at each time step \(t\): the update gate (\(z_t\)), the reset gate (\(r_t\)), and the candidate hidden state (\(\tilde{h}_t\)). For a batch of size \(B\), an input feature size of \(D\), and a hidden state size of \(H\), the operations can be expressed as:

  • \(Z_t = \sigma(X_t W_z + H_{t-1} U_z + b_z)\)
  • \(R_t = \sigma(X_t W_r + H_{t-1} U_r + b_r)\)
  • \(\tilde{H}_t = \tanh(X_t W_h + (R_t \odot H_{t-1}) U_h + b_h)\)
  • \(H_t = (1 - Z_t) \odot H_{t-1} + Z_t \odot \tilde{H}_t\)

Here, \(X_t\) has the shape \([B, D]\), and \(H_{t-1}\) has the shape \([B, H]\). The weight matrices \(W\) and \(U\) are shared across all samples in the batch. Because matrix multiplications against \(W\) and \(U\) do not share dependencies between sample \(i\) and sample \(j\) within the batch, every row of the resulting \([B, H]\) matrices can be evaluated concurrently.

Implementing Batch Parallelism in gpu.js

gpu.js compiles high-level JavaScript functions into WebGL shaders, assigning computations to individual execution threads across defined dimensions. To process a batch in parallel, the kernel's output dimensions should correspond to the matrix output shape: [H, B], where this.thread.x corresponds to the hidden unit index and this.thread.y corresponds to the batch index.

const { GPU } = require('gpu.js');
const gpu = new GPU();

// Fused matrix multiplication and gate calculation for a batch
const computeGateKernel = gpu.createKernel(function(X, H_prev, W, U, bias, hiddenDim, inputDim) {
  const h = this.thread.x; // Hidden unit index
  const b = this.thread.y; // Batch index

  let sum = bias[h];

  // Input projection: X_t * W
  for (let d = 0; d < inputDim; d++) {
    sum += X[b][d] * W[d][h];
  }

  // Recurrent projection: H_{t-1} * U
  for (let j = 0; j < hiddenDim; j++) {
    sum += H_prev[b][j] * U[j][h];
  }

  // Sigmoid activation function
  return 1.0 / (1.0 + Math.exp(-sum));
}).setOutput([H, B]);

By specifying .setOutput([H, B]), the GPU spawns \(B \times H\) parallel threads. Each thread independently computes the linear combination and non-linear activation for a single unit within a specific batch sample, completely removing CPU batch iteration overhead.

Managing the Sequential Constraint

While gate calculations are parallel across the batch, GRUs cannot parallelize across the sequence length \(T\) due to the temporal dependency on \(H_{t-1}\).

To maintain maximum performance:

  1. Loop in JavaScript: Execute the temporal sequence loop sequentially in the host JavaScript environment.
  2. Use Texture Pipelining: Enable .setPipeline(true) on your gpu.js kernels. This prevents the GPU from downloading the updated hidden state matrix (\(H_t\)) back to the CPU memory at every step. The resulting WebGL texture can be passed directly as the \(H_{t-1}\) input for the next time-step kernel.
  3. Combined Linear Transforms: Concatenate the gate weights \([W_z, W_r, W_h]\) into a single matrix of dimension \([D, 3H]\) and recurrent weights into \([H, 3H]\). This reduces the number of kernel dispatches from three separate calls to a single fused kernel per time step, maximizing GPU occupancy across the batch.
