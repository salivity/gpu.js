Mitigating Float Drift in gpu.js Inner Products

Computing large inner products in gpu.js frequently leads to floating-point accumulation drift due to the inherent constraints of 32-bit IEEE 754 precision in WebGL shaders. As vector sizes scale into the tens or hundreds of thousands, sequential summation discards low-order bits, resulting in significant numerical inaccuracies and catastrophic cancellation. This article covers practical numerical techniques—including compensated summation, parallel tree reduction, and double-single arithmetic emulation—to preserve precision when performing large vector dot products on the GPU.

The Precision Bottleneck in gpu.js

By default, WebGL and WebGL2 execute fragment shaders using single-precision (32-bit) floating-point numbers (fp32), even if the host JavaScript runtime natively supports double-precision (fp64). In standard sequential addition within a single GPU kernel loop:

let sum = 0.0;
for (let i = 0; i < length; i++) {
  sum += a[i] * b[i];
}

The error bounds grow linearly with the vector length, \(O(N \cdot \epsilon_{\text{mach}})\). When adding a tiny product to an already massive running sum, the smallest significand bits fall off the register boundary and are permanently lost.

Kahan and Neumaier Compensated Summation

The most computationally direct method to mitigate drift inside a single gpu.js kernel loop is Kahan summation. It maintains a secondary variable that captures the low-order bits lost during each addition step, effectively running an error-compensation feedback loop.

In a gpu.js kernel, the implementation looks like this:

const dotProductKahan = gpu.createKernel(function(a, b, length) {
  let sum = 0.0;
  let c = 0.0; // Running compensation for lost bits

  for (let i = 0; i < length; i++) {
    let y = (a[i] * b[i]) - c;
    let t = sum + y;
    c = (t - sum) - y;
    sum = t;
  }
  return sum;
}).setOutput([1]);

If the operands vary widely in magnitude such that the newly added term can exceed the running accumulator, Neumaier summation improves upon Kahan's approach by checking which value is larger before calculating the compensation term. This reduces accumulated drift to \(O(\epsilon_{\text{mach}})\), effectively behaving as if intermediate calculations were performed at twice the precision.

Hierarchical Tree Reduction

Sequential loops on a single thread underutilize the GPU and maximize rounding depth. Dividing the inner product into a parallel tree reduction splits the computation across multiple threads and passes.

  1. Element-wise Multiplication: Compute \(C_i = A_i \times B_i\) across an output array of length \(N\).
  2. Recursive Folding: In iterative reduction passes, have each thread sum pairs of values (\(C_j = C_{2j} + C_{2j+1}\)), halving the array size on each pass until a single value remains.

By structuring summation hierarchically, the worst-case error growth drops from \(O(N \cdot \epsilon)\) to \(O(\log_2 N \cdot \epsilon)\). In addition to maximizing parallel throughput across GPU cores, pairwise additions naturally combine numbers of similar relative magnitudes, minimizing truncation errors.

Emulated Double-Precision (Double-Single Arithmetic)

When absolute precision is paramount and the underlying hardware does not support native fp64 extensions in WebGL, double-precision can be emulated using two 32-bit floats (vec2). This approach, based on Knuth's TwoSum and TwoProd algorithms, represents a high-precision number as an unevaluated sum of a high float (hi) and a low float (lo):

// TwoSum algorithm in GLSL/gpu.js style
function twoSum(a, b) {
  let s = a + b;
  let v = s - a;
  let e = (a - (s - v)) + (b - v);
  return [s, e]; // [hi, lo]
}

Using pairs of fp32 numbers provides approximately 48 to 53 bits of effective significand precision. While this increases instruction count and register pressure inside the shader, it completely eliminates accumulation drift for vectors up to millions of elements.

Sign-Separated Accumulation

When computing inner products containing both positive and negative values, catastrophic cancellation occurs if large partial sums of opposite signs are added together.

To prevent this in gpu.js:

  • Accumulate positive products into one running sum (pos_sum) and negative products into another (neg_sum).
  • Use compensated summation on each stream independently.
  • Perform a single, final subtraction (pos_sum - abs(neg_sum)) at the output stage.

This ensures that intermediate additions only involve operands of identical signs, entirely avoiding subtractive cancellation until the final step.
