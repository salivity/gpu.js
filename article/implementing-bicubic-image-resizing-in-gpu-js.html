Implementing Bicubic Image Resizing in GPU.js

Image resizing using bicubic interpolation can be implemented directly in gpu.js. Because gpu.js compiles a subset of JavaScript into WebGL fragment shaders, it allows for highly parallelized, per-pixel mathematical operations across the GPU. This makes it an ideal tool for computational photography tasks in the browser, enabling high-quality upscaling and downscaling by sampling a 4x4 grid of surrounding pixels for every output pixel.

Feasibility and Architecture

gpu.js is fully capable of executing bicubic interpolation. The algorithm is an embarrassingly parallel problem: each output pixel's color value is calculated independently based on the source image data. In gpu.js, you define an execution kernel with the dimensions of the target (resized) image. When executed, the GPU runs this kernel concurrently across thousands of threads, calculating each destination pixel in parallel.

Core Implementation Steps

Implementing the algorithm directly in a gpu.js kernel requires four primary components:

  1. Coordinate Mapping: Calculate the continuous coordinate in the source image that corresponds to the discrete pixel coordinate (this.thread.x, this.thread.y) in the target image. This requires multiplying the target coordinate by the ratio of source-to-target dimensions.
  2. Neighborhood Sampling: Identify the integer coordinate of the top-left anchor pixel and sample a 16-pixel neighborhood (a 4x4 matrix) around the continuous coordinate. Boundary checks (clamping) must be applied to handle edge pixels safely.
  3. Cubic Weighting Function: Implement a standard cubic weighting polynomial (such as the Keys cubic convolution kernel or Catmull-Rom spline). In GLSL and gpu.js, this polynomial assigns weights to the 16 sample points based on their distance from the target coordinate.
  4. 2D Interpolation: Apply the weights across the horizontal axis for each of the four rows, and then interpolate the resulting four values along the vertical axis (or evaluate the full 2D tensor product directly).

Example Kernel Structure

const gpu = new GPU();

// Cubic weighting function (Catmull-Rom with a = -0.5)
function cubicWeight(x) {
  const a = -0.5;
  const absX = Math.abs(x);
  if (absX <= 1.0) {
    return (a + 2.0) * Math.pow(absX, 3) - (a + 3.0) * Math.pow(absX, 2) + 1.0;
  } else if (absX < 2.0) {
    return a * Math.pow(absX, 3) - 5.0 * a * Math.pow(absX, 2) + 8.0 * a * absX - 4.0 * a;
  }
  return 0.0;
}

gpu.addFunction(cubicWeight);

const resizeKernel = gpu.createKernel(function(src, srcWidth, srcHeight, scaleX, scaleY) {
  const outX = this.thread.x;
  const outY = this.thread.y;

  // Map destination coordinates back to source space
  const srcX = (outX + 0.5) * scaleX - 0.5;
  const srcY = (outY + 0.5) * scaleY - 0.5;

  const x0 = Math.floor(srcX);
  const y0 = Math.floor(srcY);
  const dx = srcX - x0;
  const dy = srcY - y0;

  let sum = 0.0;
  let weightSum = 0.0;

  // 4x4 neighborhood evaluation
  for (let m = -1; m <= 2; m++) {
    for (let n = -1; n <= 2; n++) {
      const sampleX = Math.max(0, Math.min(srcWidth - 1, x0 + n));
      const sampleY = Math.max(0, Math.min(srcHeight - 1, y0 + m));

      const weight = cubicWeight(n - dx) * cubicWeight(dy - m);
      const pixelVal = src[sampleY][sampleX];

      sum += pixelVal * weight;
      weightSum += weight;
    }
  }

  return sum / weightSum;
}).setOutput([targetWidth, targetHeight]);

Technical Considerations and Optimization

  • Data Representation: For multi-channel images (RGB or RGBA), you must either run separate kernels for each color channel or structure your kernel output to return a vector of four values.
  • Texture Inputs: Passing large images as flattened nested arrays in JavaScript can introduce garbage collection and serialization overhead. Passing the source as an HTML5 Canvas or WebGL texture directly into the kernel maximizes throughput.
  • Precision Limits: WebGL shaders execute using 32-bit floating-point precision, which is more than sufficient for bicubic filtering. However, values should be clamped to the valid pixel range (typically [0, 255] or [0.0, 1.0]) at the end of the calculation to prevent ringing artifacts from overshooting.
