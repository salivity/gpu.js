GPU.js Particle Physics: Boundary Reflection and Damping

This article examines how gpu.js executes boundary reflection and damping in GPU-accelerated particle physics simulations. It breaks down how the library translates JavaScript logic into WebGL shaders, computes parallel boundary collisions across thousands of particles, applies coefficients of restitution to simulate energy loss, and handles velocity clamping to maintain physical stability.

The gpu.js Execution Model for Particle Systems

gpu.js compiles standard JavaScript functions into WebGL compute shaders (or GLSL fragment shaders), allowing thousands of particle trajectories to be integrated concurrently. In a typical particle system, particle data such as positions and velocities are stored in flat typed arrays or data textures.

Each invocation of a GPU kernel maps directly to an individual particle through this.thread.x. Because GPUs rely on data-parallel architectures, collision resolution and energy loss are computed independently per particle per simulation step, avoiding the overhead of CPU iterations.

Boundary Detection and Reflection Logic

Boundary reflection requires identifying when a particle's projected position exceeds the defined containment volume and inverting its velocity along the collision normal. Because gpu.js maps JavaScript directly into GLSL, conditional statements (if/else) are used to check boundaries on each coordinate axis.

When a particle collides with a boundary:

  1. Detection: The kernel checks if the projected position (\(x + v_x \cdot \Delta t\)) violates the boundary limits (\([x_{\min}, x_{\max}]\)).
  2. Normal Inversion: The velocity component perpendicular to the boundary is multiplied by \(-1\).
  3. Positional Correction (Clamping): The position is clamped directly to the boundary or mirrored across the boundary plane to prevent particles from penetrating the walls or getting trapped.

In GLSL-compiled code, this manifests as straightforward axis-aligned boundary checks:

const updateParticles = gpu.createKernel(function(positions, velocities, bounds, dt, restitution) {
    let px = positions[this.thread.x][0];
    let py = positions[this.thread.x][1];
    let vx = velocities[this.thread.x][0];
    let vy = velocities[this.thread.x][1];

    // Compute prospective positions
    let nextX = px + vx * dt;
    let nextY = py + vy * dt;

    // Horizontal boundary reflection
    if (nextX < bounds[0]) {
        nextX = bounds[0];
        vx = -vx * restitution;
    } else if (nextX > bounds[1]) {
        nextX = bounds[1];
        vx = -vx * restitution;
    }

    // Vertical boundary reflection
    if (nextY < bounds[2]) {
        nextY = bounds[2];
        vy = -vy * restitution;
    } else if (nextY > bounds[3]) {
        nextY = bounds[3];
        vy = -vy * restitution;
    }

    return [nextX, nextY, vx, vy];
}).setOutput([particleCount]);

Damping and Energy Dissipation

Damping in particle systems falls into two distinct categories: collision damping (restitution) and ambient damping (drag or friction).

Collision Restitution

When a particle strikes a wall, kinetic energy is absorbed. In gpu.js, this is simulated using a coefficient of restitution (\(e \in [0, 1]\)). During boundary inversion, the inverted velocity component is scaled by \(e\):

\[v_{\text{reflected}} = -v \cdot e\]

A value of \(1.0\) represents a fully elastic collision with no energy loss, while values approaching \(0.0\) simulate inelastic collisions where particles rapidly lose momentum on contact.

Ambient Drag

To model resistance through a medium such as air or fluid, ambient damping is applied continuously on every frame, independent of collisions. The kernel scales all velocity components by a decay factor:

\[v_{t+1} = v_t \cdot (1 - \gamma \cdot \Delta t)\]

Where \(\gamma\) is the drag coefficient. Because gpu.js executes this scaling in parallel, fluid resistance introduces zero computational bottleneck compared to CPU-based simulations.

Managing State via Texture Ping-Ponging

GPUs are inherently stateless between render passes. To persist positions, velocities, and damping effects across frames, gpu.js employs texture ping-ponging:

  1. Kernel A reads current positions and velocities from Texture 0.
  2. Kernel A calculates boundary reflections, applies restitution, and writes the updated states to Texture 1.
  3. On the subsequent frame, Texture 1 is passed as the input, and Texture 0 becomes the write target.

Setting pipeline: true within gpu.js ensures these intermediate textures remain on the GPU memory bus, eliminating expensive readbacks to the CPU during continuous collision loops.

Technical Considerations

  • Branch Divergence: Branching (if/else) inside GPU shaders can cause slight thread serialization if nearby threads take different paths. In large particle systems, however, the parallelism gains of the GPU still drastically outperform single-threaded CPU processing.
  • Tunneling: High-velocity particles can pass completely through thin boundaries in a single time-step (\(\Delta t\)). To counter tunneling in gpu.js, developers must either clamp positions strictly to the boundary edge, decrease the simulation time step, or implement continuous ray-casting techniques within the kernel.
