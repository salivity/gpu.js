Why gpu.js Stutters on First User Interaction

In gpu.js applications, users frequently encounter an abrupt freeze or frame drop the first time an interaction triggers a GPU calculation. This stutter is primarily caused by deferred, just-in-time (JIT) shader compilation, graphic driver pipeline creation, and synchronous memory allocation occurring entirely on the main JavaScript thread during that initial trigger.

Just-in-Time Transpilation and Compilation

gpu.js translates written JavaScript functions into GLSL (OpenGL Shading Language) at runtime. While the JavaScript-to-GLSL string parsing is relatively fast, the actual compilation into machine code does not happen when the kernel is defined. Instead, WebGL defers the compilation of vertex and fragment shaders until the kernel is invoked for the first time.

When a user clicks a button or interacts with the interface to run a kernel, WebGL invokes gl.compileShader() and gl.linkProgram(). Because these operations run synchronously on the browser's main thread, the entire user interface freezes until the shader program finishes building.

Underlying GPU Driver Compilation

Even after WebGL reports that a shader program is compiled and linked, the underlying operating system graphics driver often defers generating hardware-native binary instructions. Most graphics drivers compile the intermediate representation into target machine code only when the first draw call—or in the case of gpu.js, compute pass—is issued. This driver-level pipeline compilation introduces a significant one-time latency penalty of several tens to hundreds of milliseconds.

Synchronous Data Marshalling and Texture Allocation

Running a compute kernel requires passing input data from the CPU to the GPU. gpu.js handles this by packing JavaScript arrays into WebGL textures.

On the first interaction:

  • WebGL must allocate new texture memory on the graphics hardware via gl.texImage2D().
  • The browser must serialize large JavaScript arrays and upload them over the PCI-e bus.
  • Framebuffers must be created and bound to capture the computation's output.

Because the memory buffers do not exist prior to the first execution, this initial allocation adds heavy overhead alongside shader compilation.

Resolving First-Interaction Stutter

To eliminate the stutter, applications must perform an explicit warm-up pass before user interaction:

  1. Eager Compilation (Warming Up): Execute every defined gpu.js kernel once during the application loading state using minimal or dummy datasets (such as a 1x1 array). This forces the browser and GPU driver to compile shaders, link programs, and build the graphics pipeline before the user can interact.
  2. OffscreenCanvas and Web Workers: Where supported, move gpu.js instances into a dedicated Web Worker using OffscreenCanvas. This shifts compilation latency, texture uploads, and execution off the main UI thread, preventing visual freezes even if a shader must compile dynamically.
