Mapping FAST Feature Detection to GPU.js

The Features from Accelerated Segment Test (FAST) algorithm can be effectively mapped onto parallel thread evaluation using gpu.js. Because FAST evaluates candidate corner points independently at the pixel level, its computational structure aligns naturally with the Single Instruction, Multiple Threads (SIMT) architecture leveraged by GPU-accelerated WebGL shaders. This article examines the feasibility, architectural mapping, and technical trade-offs of implementing the FAST feature detection pipeline within gpu.js.

Architectural Alignment

FAST identifies corners by examining a Bresenham circle of 16 pixels surrounding a candidate pixel \(p\). If a continuous arc of \(N\) pixels (commonly \(N=9\) or \(N=12\)) is significantly brighter or darker than \(p\) by a threshold \(t\), the pixel is classified as a feature point.

In gpu.js, computations are executed over a defined output grid. For an image of dimensions \(W \times H\), the kernel domain is defined as [W, H]. Each thread corresponds to an individual pixel coordinate (this.thread.x, this.thread.y). Because the state of pixel \(p\) depends solely on its local neighborhood and does not require mutable cross-pixel synchronization, the evaluation step is embarrassingly parallel.

Mapping the Evaluation Pipeline

To implement FAST in gpu.js, the algorithm is translated into a parallel execution flow:

  1. Kernel Input: The image is passed as a 2D array of normalized luminance values (grayscale).
  2. Offset Lookup: The thread calculates the values of the 16 circle positions relative to (this.thread.x, this.thread.y) using hardcoded offset vectors:
    • \((0, 3), (1, 3), (2, 2), (3, 1), (3, 0), (3, -1), (2, -2), (1, -3)\)
    • \((0, -3), (-1, -3), (-2, -2), (-3, -1), (-3, 0), (-3, 1), (-2, 2), (-1, 3)\)
  3. Contiguity Verification: The kernel checks whether \(N\) contiguous pixels satisfy \(I_x > I_p + t\) or \(I_x < I_p - t\).
  4. Kernel Output: The kernel outputs a binary mask or a corner response score for each pixel.

Handling GPU Divergence vs. CPU Early Exits

On a CPU, FAST achieves its speed through early rejection: it first tests pixels 1, 9, 5, and 13. If at least three of these do not meet the threshold criteria, the candidate is discarded immediately without checking the remaining 12 pixels.

In gpu.js, early rejection via standard if/else branching can cause warp/wavefront divergence on physical GPU hardware. When adjacent threads take different execution paths, both paths must be evaluated sequentially across the thread group. In gpu.js:

  • Branching is supported, but complex conditional exits may not provide the same proportional speedup as they do on CPUs.
  • Fully unrolling the evaluation loop or using bitwise operations to check circular contiguity often yields more deterministic execution times across WebGL fragments.

Non-Maximum Suppression (NMS)

Raw FAST detection typically produces clusters of adjacent positive points around a single corner. To resolve this, non-maximum suppression is applied based on a corner response score (such as the sum of absolute differences between the candidate pixel and the contiguous arc pixels).

In gpu.js, NMS cannot be reliably calculated in the same execution step that detects the corners, as shader threads cannot communicate across memory barriers within a single pass. Instead, a two-pass pipeline is required:

  1. Pass 1 (Detection & Scoring): Outputs a texture where positive detections contain their corner response score and non-corners are zeroed.
  2. Pass 2 (Suppression): Reads the output of Pass 1 and verifies if the center pixel has the maximum score within a \(3 \times 3\) window.

Technical Limitations in GPU.js

  • Boundary Conditions: Threads processing pixels within 3 pixels of the image boundary cannot evaluate full circles. These must be explicitly masked out to prevent invalid texture reads.
  • Memory Overhead: Moving high-resolution video frames back and forth between CPU memory and GPU textures introduces PCIe bus overhead. For maximum efficiency, upstream operations (like grayscale conversion) and downstream operations should remain in GPU memory using gpu.js pipeline mode (pipeline: true).
