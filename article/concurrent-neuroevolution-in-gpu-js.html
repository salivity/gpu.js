Concurrent Neuroevolution in GPU.js

Genetic algorithms and neuroevolution populations can be evaluated concurrently in GPU.js by mapping individual fitness evaluations and neural network forward passes to massively parallel GPU kernels. By flattening population parameters into multidimensional arrays or textures, thousands of candidate solutions can process inputs and compute performance metrics simultaneously. However, achieving optimal efficiency requires working within the architectural constraints of GPU computing, particularly regarding memory bandwidth, branching logic, and network topology.

How GPU.js Evaluates Populations Concurrently

GPU.js compiles a restricted subset of JavaScript into WebGL (or WebGPU) shaders, executing operations in parallel across thousands of shader cores. In a traditional CPU implementation, evaluating a population of candidate genomes involves iterating sequentially through each individual or distributing batches across a limited number of CPU threads.

In GPU.js, concurrency is achieved by setting kernel dimensions to represent both the population and the evaluation workload. For example, a 2D kernel can allocate:

  • Dimension X: The individual genome index within the population.
  • Dimension Y: The specific test case, environment step, or neuron layer.

When the kernel executes, the GPU computes the outputs for all individuals across all parallel dimensions at the same time, turning what would be nested loops on a CPU into a single dispatch call.

Structuring Neuroevolution Data for the GPU

GPU shaders cannot natively traverse complex JavaScript object graphs or dynamic class instances. To evaluate a neural network population on the GPU, all networks must be serialized into numeric data structures:

  1. Flattened Weight Matrices: Weights and biases for the entire population must be packed into structured 1D, 2D, or 3D arrays. An entire generation's weights can be passed as a single unified array where offsets determine the start and end of each individual's parameters.
  2. Batch Inputs: Environmental inputs or training samples are packed into parallel arrays, allowing every individual in the kernel to read identical or sample-specific inputs simultaneously.
  3. Layer-by-Layer Evaluation: Because GPU.js kernels output data to arrays (or textures), deep feedforward networks are typically processed by executing one kernel per layer, passing the activation output of layer \(N\) directly as the input to layer \(N+1\).

Ideal Use Cases and Topology Constraints

Evaluating populations in GPU.js is most effective under specific conditions:

  • Fixed Topologies: Architectures where all individuals share the same structure (e.g., standard dense layers with variable weights) excel on the GPU. The uniform compute graph prevents thread divergence.
  • Compute-Heavy Environments: Tasks requiring heavy matrix multiplications or processing large static datasets (such as classification benchmarks) fully saturate GPU cores.

Conversely, algorithms utilizing variable topologies (such as NEAT, where networks grow structural nodes and connections dynamically) are difficult and inefficient to evaluate concurrently in GPU.js. Conditional branching inside shaders causes execution divergence, where parallel threads stall while waiting for branches with differing lengths to complete.

The Hybrid CPU-GPU Pipeline

The most efficient architecture for genetic algorithms using GPU.js is a hybrid pipeline:

  1. CPU (Selection, Crossover, and Mutation): Genetic manipulation involves irregular data access, pointer manipulation, and dynamic array resizing. These tasks are lightweight for population sizes under tens of thousands and run faster on the CPU.
  2. CPU-to-GPU Transfer: The mutated weights of the new generation are packed into a typed array and passed to the GPU.
  3. GPU (Inference and Fitness Scoring): GPU.js executes the forward passes and computes error rates or fitness scores concurrently across the entire generation.
  4. GPU-to-CPU Readback: The resulting fitness vector is read back to JavaScript to drive the next generation's selection phase.

Minimizing the round-trip overhead between the CPU and GPU is critical. By keeping evaluations long enough—or batching multiple evaluation steps entirely within the GPU memory pipeline—the execution gains significantly outweigh the data transfer latency.
