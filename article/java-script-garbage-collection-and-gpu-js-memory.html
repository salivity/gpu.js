JavaScript Garbage Collection and GPU.js Memory

Understanding how the JavaScript garbage collector manages GPU-allocated memory in gpu.js requires looking at the boundary between host system memory and video RAM (VRAM). Because JavaScript engines only track allocations on the central CPU heap, they remain largely unaware of resources allocated on the graphics card via WebGL. Consequently, relying on automatic garbage collection to free GPU memory in gpu.js leads to latency, non-deterministic deallocations, and frequent out-of-memory errors, making explicit memory management necessary.

The Disconnect Between the JS Heap and VRAM

JavaScript utilizes an automatic garbage collector (such as the Orinoco or Scavenger collectors in V8) that inspects reference graphs on the CPU memory heap. When an object has no reachable references, its CPU memory is flagged for reclamation.

gpu.js operates by compiling JavaScript functions into WebGL shader language (GLSL) and running them on the GPU. The data processed by these kernels—inputs and outputs—is stored as WebGL textures or buffers inside dedicated GPU VRAM.

From the perspective of the JavaScript runtime, an allocated texture or kernel output is represented merely by a lightweight JavaScript wrapper object. The underlying graphics buffer, which may occupy hundreds of megabytes of VRAM, is held entirely outside the JavaScript memory space by the browser's WebGL context and graphics driver.

The Memory Pressure Problem

The garbage collector initiates collection cycles based on CPU memory pressure. Because the JavaScript wrapper object for a WebGL texture consumes only a few dozen bytes on the JS heap, the runtime does not register significant memory usage.

Even if the GPU is on the verge of running out of VRAM due to hundreds of cached frame textures or matrix calculations, the JavaScript engine assumes memory pressure is low. As a result, the garbage collector will not trigger an aggressive pass to destroy the JS references, causing the corresponding GPU textures to linger in VRAM indefinitely until an actual out-of-memory error crashes the WebGL context.

Lifecycle of Textures and Kernels in gpu.js

When a kernel runs with the default settings in gpu.js, you can specify its output type as either a standard JavaScript array or a texture:

  • Array Output (output: 'array'): gpu.js automatically reads the pixel data back from the GPU to the CPU, populates a standard JavaScript typed array, and discards the intermediate WebGL texture. In this mode, the output data is fully native to the JS heap and can be managed reliably by the standard garbage collector.
  • Texture Output (pipeline: true or returning a texture): The output data remains in VRAM as a WebGL texture to allow for fast, piped operations between consecutive kernels without incurring the performance penalty of CPU-GPU data transfers.

When outputs remain as textures, the garbage collector will eventually destroy the JavaScript wrapper once it falls out of scope, but the underlying WebGL texture is not guaranteed to be freed immediately. While modern browser implementations use internal hooks (similar to FinalizationRegistry) to prompt context cleanups when JS wrapper objects die, this process is non-deterministic and often too slow for high-throughput GPU computing loops.

Preventing VRAM Leaks with Explicit Cleanup

To maintain stable memory usage in gpu.js, developers must bypass automatic garbage collection and manage GPU lifecycles manually:

  1. Destroy Textures Explicitly: Call the .delete() or .destroy() method on any texture object once it is no longer required as an input for subsequent kernels.
  2. Destroy Kernels: If a kernel instance is dynamic or temporary, invoke kernel.destroy() to ensure that compiled programs, framebuffers, and associated shaders are wiped from the WebGL context.
  3. Download Data to CPU: If intermediate texture pipelines are unnecessary, read the output back into CPU memory using .toArray(). Once converted, the data is standard JavaScript memory that the engine's garbage collector can profile and sweep efficiently.
