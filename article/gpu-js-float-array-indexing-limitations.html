GPU.js Float Array Indexing Limitations

Using floating-point calculations to determine array indices in GPU.js introduces critical constraints rooted in WebGL shader compilation, hardware precision drift, and data type handling. Because GPU.js transpiles JavaScript kernels into GLSL (OpenGL Shading Language), indexing an array or accessing data structures with calculated floats requires strict conversion, careful error mitigation, and an awareness of internal texture lookup limitations.

Strict GLSL Type Incompatibility

GLSL enforces strict type checking. In standard JavaScript, array indices can often be coerced or evaluated loosely, but WebGL requires an explicit integer (int) to index an array or access a buffer. If an index is derived from a floating-point calculation without an explicit integer conversion, the GPU.js compiler will either throw a compilation error during kernel creation or fail to generate valid GLSL code. Any computed floating-point variable must be explicitly converted using mathematical operations like Math.floor(), Math.ceil(), or Math.round() within the kernel.

Truncation and Off-by-One Errors

Floating-point arithmetic on the GPU adheres to hardware-dependent IEEE 754 precision standards (often limited to 32-bit or even 16-bit half-precision depending on target hardware and WebGL settings). Non-integer math routinely produces values with small precision discrepancies:

  • A computed index intended to be 3.0 may evaluate to 2.9999998.
  • Applying truncation or functions like Math.floor() will drop the value to 2 instead of 3.
  • This causes silent off-by-one indexing errors that propagate inaccurate outputs throughout the dataset.

To avoid this behavior, indices must include a small epsilon adjustment (e.g., Math.floor(calculatedFloat + 0.00001)) or use Math.round() where appropriate.

Texture Lookup and Pixel-Center Offset

GPU.js internally represents large arrays and matrices as 2D WebGL textures. When an index calculation targets a coordinate within these internal data structures:

  • Texture lookups access discrete texels arranged in a grid.
  • Floating-point coordinates sample the data grid based on nearest-neighbor sampling.
  • If a float coordinate lands on or near a texel boundary (such as x.0), floating-point drift can arbitrarily snap the read operation to the left or right texel.
  • Proper texture addressing often requires shifting to the texel center (adding 0.5 / dimension) to guarantee the correct texel is read, which standard integer indices handle automatically behind the scenes.

Out-of-Bounds Clamping and Invalidation

When an index is calculated dynamically through floating-point operations, boundary checks become less predictable:

  • Slight negative values (e.g., -0.000001) resulting from rounding errors will be cast or floored into invalid array positions.
  • Unlike standard JavaScript, which returns undefined for out-of-bounds indices, GPU kernels reading out-of-bounds memory from underlying texture buffers typically return 0, the clamped edge value, or completely unpredictable data depending on the WebGL environment and clamping configuration.

Best Practices for Mitigation

To safely index arrays via derived values in GPU.js:

  1. Rely on native thread IDs: Prefer this.thread.x, this.thread.y, or this.thread.z, which are guaranteed integers.
  2. Normalize before casting: If calculating offsets via floats, apply safe rounding functions (Math.round() rather than raw truncation).
  3. Clamp boundary values: Explicitly clamp the resulting integer between 0 and length - 1 to prevent hardware texture out-of-bounds faults.
