Troubleshoot gpu.js Initialization Failure on iOS

Running gpu.js on iOS often introduces platform-specific initialization failures due to WebKit restrictions, memory constraints, and strict WebGL context limits. This article provides a systematic troubleshooting guide to diagnose and resolve gpu.js startup failures in iOS browsers, covering WebGL support verification, CPU fallback configurations, WebKit-specific context limits, and remote debugging techniques.

1. Verify WebGL Support and Context Availability

iOS browsers (all powered by WebKit) may fail to instantiate gpu.js if the WebGL context cannot be created. Run a basic check directly in the browser console or a lightweight script before calling new GPU():

const canvas = document.createElement('canvas');
const gl = canvas.getContext('webgl2') || canvas.getContext('webgl');
if (!gl) {
    console.error('WebGL is not supported or disabled on this iOS device.');
}

If gl returns null, the browser is either blocking hardware acceleration or has exhausted its available WebGL contexts.

2. Configure Fallback Modes in gpu.js

By default, gpu.js tries to initialize using the best available hardware mode (webgl2, then webgl). If WebKit blocks these modes, initialization throws an error unless explicit fallbacks are allowed. When initializing gpu.js, explicitly configure the fallback modes:

const gpu = new GPU({
    mode: 'gpu' // Will attempt webgl2/webgl, but throws if unsupported
});

// To gracefully handle failure:
try {
    const gpu = new GPU();
} catch (e) {
    console.warn('GPU mode failed, falling back to CPU:', e);
    const gpu = new GPU({ mode: 'cpu' });
}

Testing directly with { mode: 'cpu' } helps confirm whether the failure is strictly hardware-acceleration-related or tied to library bundling issues.

3. Check for WebGL Context Leaks

iOS imposes a strict limit on the number of active WebGL contexts allowed simultaneously (often as few as 8 to 16 across an entire page session). If previous instances of gpu.js or other WebGL libraries (like Three.js or PixiJS) were created without being destroyed, new contexts will fail to initialize.

  • Destroy unused instances using gpu.destroy().
  • Ensure singletons are used instead of re-instantiating new GPU() inside render loops or component re-renders.

4. Monitor iOS WebKit Memory Limits

Mobile Safari aggressively terminates WebGL processes that exceed device memory thresholds. If a gpu.js kernel requests large textures or high-dimensional output arrays, WebKit will drop the WebGL context immediately upon initialization.

  • Reduce the output array dimensions in your kernel to a minimal size (e.g., [2, 2]) to test if large buffer allocation is causing the crash.
  • Ensure data arrays passed as arguments do not exceed the MAX_TEXTURE_SIZE supported by the iOS hardware. You can check this limit via: 
    const maxTextureSize = gl.getParameter(gl.MAX_TEXTURE_SIZE);
console.log('Max Texture Size:', maxTextureSize);

5. Inspect WebKit Feature Flags in iOS Settings

Older or beta versions of iOS may disable certain WebGL features by default.

  1. On the iOS device, open Settings > Safari > Advanced > Feature Flags (or Experimental Features depending on the iOS version).
  2. Ensure WebGL 2.0 is toggled on.
  3. Check that flags related to WebGL via Metal or GPU Process rendering are set to their default states, as custom overrides can break canvas context creation.

6. Attach Safari Web Inspector for Exact Error Logs

iOS Safari suppresses detailed WebGL error messages in the standard UI. To retrieve the exact initialization stack trace:

  1. Enable Web Inspector on the iOS device via Settings > Safari > Advanced.
  2. Connect the iOS device to a Mac running macOS via a USB cable.
  3. Open Safari on macOS, navigate to the Develop menu, select the connected iOS device, and inspect the target page.
  4. Check the Console tab for specific WebGL shader compilation errors, CONTEXT_LOST_WEBGL warnings, or memory termination notices emitted during the gpu.js initialization phase.
