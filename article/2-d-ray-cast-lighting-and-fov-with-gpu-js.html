2D Ray-Cast Lighting and FOV with GPU.js

Computing dynamic ray-cast field of view (FOV) and 2D lighting masks is entirely achievable using GPU.js by compiling JavaScript functions into WebGL fragment shaders. This approach offloads computationally expensive line-of-sight checks from the CPU to the graphics processor, enabling real-time performance even in complex environments. This article breaks down the mechanics of implementing ray-cast visibility masks with GPU.js, common architecture patterns, and critical performance trade-offs to consider.

The Ray-Casting Architecture in GPU.js

GPU.js works by translating a subset of JavaScript into GLSL (OpenGL Shading Language) and executing it across thousands of GPU threads simultaneously. In a 2D game, visibility and lighting can be modeled as an "embarrassingly parallel" problem, making it well-suited for GPU acceleration.

There are two primary approaches to computing lighting masks with GPU.js:

  1. Per-Pixel Ray Marching (Screen-Space): The GPU kernel dimensions match the resolution of the light mask (e.g., \(800 \times 600\)). Each thread represents a single pixel and casts a ray back toward the light source, stepping through a 2D obstacle grid (tilemap). If an obstacle is encountered before reaching the light, the thread outputs black (\(0.0\)); otherwise, it calculates light intensity based on the Euclidean distance from the source.
  2. Radial Ray Casting (1D Radial Buffer): The GPU kernel runs a 1D array of threads where each thread corresponds to a radial angle (\(0\) to \(360\) degrees, often subdivided into 360 to 1440 rays). Each thread marches outward from the light source until it hits an obstacle, outputting the maximum travel distance. The resulting 1D distance buffer is then used to construct a visibility polygon or render dynamic shadows.

Implementing the Per-Pixel Approach

The per-pixel method is the most direct way to generate a ready-to-use alpha mask for dynamic lighting:

  • Input Data: Pass the obstacle grid as an array of numbers or an encoded texture, alongside uniforms containing the light source coordinates, light radius, and map dimensions.
  • Kernel Execution: Inside the GPU.js kernel, calculate the directional vector from the current pixel [this.thread.x, this.thread.y] to the light source coordinates.
  • Marching Loop: Execute a fixed-iteration loop that samples intermediate points along the ray. If an obstacle cell contains a collision value, terminate the ray and mark the pixel as shadowed.
  • Falloff and Attenuation: Pixels with unblocked lines of sight calculate attenuation using inverse-square or linear falloff relative to the maximum light radius.

Managing Data Transfer Bottlenecks

While the mathematical execution on the GPU is fast, naive implementations can suffer from memory bus bottlenecks between the CPU and GPU. Two techniques mitigate this:

  • Pipelining Textures: Reading raw array data back from the GPU to the CPU (readPixels) is slow. By setting { pipeline: true } in GPU.js, the lighting mask stays on the GPU as a WebGL texture. This texture can be passed directly to a WebGL rendering context (such as PixiJS, Phaser, or raw WebGL) to blend over the game scene without round-tripping to system RAM.
  • Dynamic Grid Updates: Avoid re-uploading the entire collision map every frame. Only update the input data when the static geometry changes, passing moving dynamic obstacles as an array of coordinate uniforms rather than rebinding full-size arrays.

Practical Verdict

GPU.js is capable of rendering high-resolution 2D FOV and soft dynamic lighting masks at 60 FPS in modern browsers. While writing native GLSL shaders within an established 2D game engine offers slightly tighter integration and less overhead, GPU.js serves as an accessible, mathematically robust bridge for developers seeking hardware-accelerated visibility algorithms using familiar JavaScript syntax.
