GPU.js Thread Coordinates to Fragment Coordinates

In gpu.js, computations are executed by compiling JavaScript functions into WebGL fragment shaders that run across parallel GPU cores. Because WebGL operates natively on a two-dimensional screen space using fragment coordinates (gl_FragCoord), gpu.js mathematically maps its logical one-, two-, or three-dimensional thread coordinates (this.thread) to these continuous 2D fragment positions. This article breaks down the mathematical relationships and transformations that bridge gpu.js thread indexing with WebGL fragment coordinates.

Continuous Fragments to Discrete Pixels

WebGL calculates fragment positions using the built-in variable gl_FragCoord. Unlike array indices in JavaScript, fragment coordinates are continuous floating-point values located at the center of each pixel.

For an integer pixel index \((X, Y)\):

\[\text{gl\_FragCoord.x} = X + 0.5\] \[\text{gl\_FragCoord.y} = Y + 0.5\]

To extract discrete pixel indices from fragment coordinates, gpu.js applies a floor operation:

\[X = \lfloor \text{gl\_FragCoord.x} \rfloor\] \[Y = \lfloor \text{gl\_FragCoord.y} \rfloor\]

2D Thread Mapping

When a kernel is declared with two dimensions [width, height], the thread coordinates map directly to the 2D WebGL render target dimensions.

The mathematical relationship is:

\[\text{this.thread.x} = \lfloor \text{gl\_FragCoord.x} \rfloor\] \[\text{this.thread.y} = \lfloor \text{gl\_FragCoord.y} \rfloor\]

In the underlying GLSL code generated by gpu.js:

  • this.thread.x runs from \(0\) to \(\text{width} - 1\).
  • this.thread.y runs from \(0\) to \(\text{height} - 1\).

Because standard WebGL texture coordinates have their origin \((0,0)\) at the bottom-left corner, this.thread.y = 0 corresponds to the bottom row of the output canvas unless vertically inverted.

1D Thread Mapping

When an output is defined as a 1D array of size [length], WebGL still executes the computation over a 2D texture grid if the length exceeds the GPU's maximum single-dimension texture limit.

Flat 1D Mapping

If the array fits within a single row:

\[\text{gl\_FragCoord.x} = \text{this.thread.x} + 0.5\] \[\text{gl\_FragCoord.y} = 0.5\]

\[\text{this.thread.x} = \lfloor \text{gl\_FragCoord.x} \rfloor\]

Wrapped 1D Mapping

When mapped across a 2D texture of width \(W\):

\[\text{this.thread.x} = \lfloor \text{gl\_FragCoord.y} \rfloor \times W + \lfloor \text{gl\_FragCoord.x} \rfloor\]

\[\lfloor \text{gl\_FragCoord.x} \rfloor = \text{this.thread.x} \pmod W\] \[\lfloor \text{gl\_FragCoord.y} \rfloor = \left\lfloor \frac{\text{this.thread.x}}{W} \right\rfloor\]

3D Thread Mapping

WebGL 1.0 and 2.0 fragment shaders output to 2D textures. To support 3D kernels with dimensions [depth_x, depth_y, depth_z], gpu.js tiles the 3D volume into a 2D layout on the canvas.

Typically, gpu.js packs the \(Z\) dimension along the \(Y\) (or \(X\)) axis. Assuming vertical tiling where the 2D render target has dimensions:

\[\text{Target Width} = \text{depth\_x}\] \[\text{Target Height} = \text{depth\_y} \times \text{depth\_z}\]

The fragment coordinates relate to 3D thread coordinates through the following transformations:

From Fragment Coordinates to 3D Thread Coordinates

\[\text{this.thread.x} = \lfloor \text{gl\_FragCoord.x} \rfloor\] \[\text{this.thread.y} = \lfloor \text{gl\_FragCoord.y} \rfloor \pmod{\text{depth\_y}}\] \[\text{this.thread.z} = \left\lfloor \frac{\lfloor \text{gl\_FragCoord.y} \rfloor}{\text{depth\_y}} \right\rfloor\]

From 3D Thread Coordinates to Fragment Coordinates

\[\text{gl\_FragCoord.x} = \text{this.thread.x} + 0.5\] \[\text{gl\_FragCoord.y} = (\text{this.thread.z} \times \text{depth\_y} + \text{this.thread.y}) + 0.5\]

Normalized Coordinates (UV Space)

When sampling inputs or reading framebuffers, fragment coordinates are normalized into UV coordinates ranging from \([0.0, 1.0]\). For an output target with dimensions \((W, H)\):

\[u = \frac{\text{gl\_FragCoord.x}}{W} = \frac{\text{this.thread.x} + 0.5}{W}\] \[v = \frac{\text{gl\_FragCoord.y}}{H} = \frac{\text{this.thread.y} + 0.5}{H}\]

This half-pixel offset (\(+ 0.5\)) ensures that texture lookups sample precisely from the center of the intended texel, preventing interpolation artifacts during GPU calculations.
