GPU.js Profiler: Comparing GPU and CPU Execution

The internal performance profiler in gpu.js enables developers to measure, analyze, and directly compare execution times between hardware-accelerated GPU pipelines and software-based CPU fallbacks. By enabling profiling mode, developers obtain microsecond-level timing breakdowns that reveal whether a compute-heavy task genuinely benefits from GPU parallelization or suffers from data transfer bottlenecks relative to native JavaScript CPU execution.

To benchmark GPU performance against CPU mode, gpu.js utilizes a configuration flag when creating a kernel:

const gpu = new GPU();
const kernel = gpu.createKernel(function(a, b) {
    return a[this.thread.x] + b[this.thread.x];
}, {
    output: [1024],
    profile: true
});

When profile: true is set, executing the kernel populates the kernel.profile object with high-precision timing data.

How GPU Execution Is Measured

Measuring GPU performance involves tracking asynchronous hardware operations rather than standard synchronous JavaScript execution. In GPU mode (typically running over WebGL or WebGPU), the profiler measures several distinct phases:

  1. Compilation and Setup: The time taken to compile the JavaScript function into GLSL shaders and initialize WebGL buffers or textures.
  2. Data Transfer (CPU to GPU): The latency incurred by serializing JavaScript arrays and binding them to the graphics card as textures or storage buffers.
  3. Hardware Execution: The actual kernel compute time on the GPU cores, captured using browser extensions such as EXT_disjoint_timer_query when available, or wrapped execution checkpoints.
  4. Readback (GPU to CPU): The time required to read pixels or pull buffer data back into the main JavaScript thread via operations like readPixels.

How CPU Mode Is Measured

CPU mode can be explicitly forced by initializing the kernel with { mode: 'cpu' }. In this mode, gpu.js transpiles the kernel into standard nested JavaScript loops running on the host thread.

The internal profiler benchmarks CPU execution synchronously using the browser’s high-resolution performance.now() timer. Because CPU mode executes entirely in host memory, it incurs zero memory serialization, GPU context switching, or texture mapping overhead.

Interpreting the Profiler Comparison

Comparing the profiler metrics between GPU and CPU modes highlights whether a workload is compute-bound or memory-bound:

  • Small Datasets: The profiler often reveals that CPU mode outperforms GPU mode on small array sizes. The latency of packing arrays into textures and retrieving the results across the PCIe bus often exceeds the compute time saved by parallel execution.
  • Large Datasets: For large arrays and complex mathematical operations, GPU hardware execution time remains nearly flat due to massively parallel processing threads, while CPU execution scales linearly (\(O(n)\)) or worse.
  • Overhead Isolation: The profiler explicitly separates execution run time from compile and transfer costs, allowing developers to determine if caching textures (via { pipeline: true }) will make GPU execution faster than CPU mode across iterative algorithms like matrix multiplication or neural network training.
