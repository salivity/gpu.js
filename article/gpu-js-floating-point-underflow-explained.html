GPU.js Floating-Point Underflow Explained

This article explores how gpu.js handles floating-point underflow during the multiplication of extremely small decimal values. Because gpu.js compiles JavaScript code into WebGL shader language (GLSL) to execute directly on the graphics processor, underflow behavior is determined by the underlying GPU hardware and the WebGL specification rather than standard JavaScript runtime behavior. Understanding this hardware dependency is critical for preventing silent data corruption in scientific and machine learning computations.

Compilation to WebGL Shaders

gpu.js translates written JavaScript functions directly into GLSL fragment shaders. In the WebGL pipeline, calculations do not use arbitrary-precision arithmetic or software-level precision guards. Instead, operations are executed directly by the GPU's Arithmetic Logic Units (ALUs).

By default, gpu.js utilizes single-precision 32-bit floating-point format (highp float) within the generated shader code.

The Underflow Threshold

In a standard IEEE 754 32-bit single-precision float:

  • 1 bit is allocated for the sign.
  • 8 bits are allocated for the exponent.
  • 23 bits are allocated for the mantissa.

The smallest positive normalized number that can be represented is approximately \(1.18 \times 10^{-38}\). When two small decimals (such as \(1.0 \times 10^{-20}\) and \(1.0 \times 10^{-20}\)) are multiplied together, the true mathematical result (\(1.0 \times 10^{-40}\)) falls below this threshold.

Hardware Flush-to-Zero (FTZ)

While the full IEEE 754 specification defines "subnormal" (or denormal) numbers to allow a gradual underflow down to roughly \(1.4 \times 10^{-45}\), consumer GPUs prioritize throughput and parallelism over full standard compliance.

Most modern GPUs implement Flush-to-Zero (FTZ) at the hardware level for single-precision operations. When an operation produces a result smaller than the minimum normalized value:

  1. The hardware does not generate an exception, error, or warning.
  2. The subnormal bits are discarded.
  3. The value is immediately rounded and stored as signed zero (0.0 or -0.0).

Consequently, when multiplying very small numbers in gpu.js on the GPU, the result abruptly drops to zero rather than maintaining degraded precision through subnormals.

GPU Mode vs. CPU Fallback Discrepancy

A critical side effect of this implementation is behavioral discrepancy between execution modes. If WebGL fails to initialize or if the execution mode is explicitly set to CPU, gpu.js runs the code using JavaScript's native execution engine:

  • GPU Execution (WebGL): Employs 32-bit single-precision floats. Values below \(\approx 1.18 \times 10^{-38}\) flush directly to 0.0.
  • CPU Execution (JavaScript): Employs native 64-bit double-precision floats (Float64). Values do not underflow until dropping below \(\approx 5.0 \times 10^{-324}\), and the CPU handles subnormal numbers gradually.

Code that produces valid, non-zero results during testing in CPU fallback mode may evaluate to 0.0 when run on the GPU.

Mitigating Underflow in gpu.js

To prevent underflow issues when dealing with small decimals in gpu.js kernels:

  • Log-Space Computation: Convert multiplication chains into additions in logarithmic space (\(\log(a \times b) = \log(a) + \log(b)\)). This is the standard technique used in machine learning algorithms running on GPU hardware.
  • Pre-scaling Values: Scale datasets by a fixed factor before passing them as inputs to the GPU kernel, then re-scale the final output matrix after computation completes.
