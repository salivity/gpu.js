Profile gpu.js Thread Occupancy and Spilling

This guide explains how to extract and profile the low-level hardware metrics of shaders generated by gpu.js, specifically focusing on thread occupancy and register spilling. Because gpu.js compiles JavaScript into WebGL fragment or compute shaders, the browser abstracts hardware-level execution details. Measuring register pressure and occupancy requires intercepting the generated GLSL source and analyzing it with native GPU vendor profiling tools such as AMD Radeon GPU Analyzer, NVIDIA Nsight, or RenderDoc.

1. Extract the Generated Shader Code

To evaluate register pressure, you first need access to the raw GLSL code that gpu.js compiles.

You can retrieve the compiled shader string directly from the kernel instance:

const gpu = new GPU();
const kernel = gpu.createKernel(function() {
    return this.thread.x;
}).setOutput([512]);

// Trigger compilation by calling the kernel or accessing internal properties
kernel();

// Extract the fragment or compute shader code
const glslSource = kernel.compiledFragmentShader; 
console.log(glslSource);

Alternatively, you can intercept the GLSL source at the WebGL API level by monkey-patching WebGLRenderingContext.prototype.shaderSource before compiling your kernel.

2. Static Analysis with Offline GPU Compilers

Offline shader compilers simulate compilation across various hardware targets and output assembly metrics, including vector general-purpose register (VGPR) counts, scalar general-purpose register (SGPR) counts, and theoretical occupancy.

Using AMD Radeon GPU Analyzer (RGA)

RGA is an effective tool for static analysis of GLSL shaders:

  1. Save the extracted shader code to a file (e.g., kernel.frag).
  2. Run RGA from the command line, targeting your desired GPU architecture (such as RDNA2 or RDNA3): 
    rga -s glsl --function main -c "gfx1030" --analysis output_analysis.csv kernel.frag
  3. Examine the generated analysis file:
    • Register Usage: Look at VGPR and SGPR allocation.
    • Register Spills: Check the "Scratch Memory" or "Spills" column. A value greater than zero indicates that registers have spilled into main memory, which degrades memory bandwidth.
    • Occupancy: RGA explicitly outputs the theoretical maximum wavefront occupancy percentage based on your shader's register footprint and local memory usage.

3. Dynamic Profiling with NVIDIA Nsight and RenderDoc

For run-time profiling inside the browser environment, you can attach native performance tools to Chrome or Edge.

Setup Chrome for Native Profiling

Launch Chromium with flags that expose the underlying graphics API to external profilers:

chrome.exe --disable-gpu-sandbox --gpu-startup-dialog --disable-direct-composition

Capturing with RenderDoc or Nsight Graphics

  1. Open RenderDoc or NVIDIA Nsight Graphics.
  2. Attach the profiler to the specific GPU process spawned by Chrome (the PID is displayed in the startup dialog).
  3. Execute the gpu.js kernel in the web application.
  4. Capture the frame containing the draw call or compute dispatch triggered by gpu.js.
  5. In Nsight Graphics, open the Range Profiler:
    • Warp Occupancy: Check the Warp Scheduler metrics to see actual vs. theoretical warp occupancy.
    • Register Allocation: View the registers allocated per thread. High register usage limits the number of active warps executing concurrently on a Streaming Multiprocessor (SM).
    • Local Memory Spills: Inspect the memory metrics for "Local Memory Overhead" or "L1 Cache Spills" to identify active spilling during kernel execution.

4. Resolving Spilling and Improving Occupancy

If profiling reveals low occupancy or register spilling:

  • Reduce Variable Lifetime: Minimize the number of active variables within the same scope in your gpu.js kernel function.
  • Avoid Complex Inline Expressions: Break down massive arithmetic expressions that force the compiler to allocate temporary registers.
  • Split Kernels: If a single gpu.js kernel is doing too much work, split the operation into multiple smaller kernels (pipelined via textures), allowing each kernel to fit within lower register limits.
