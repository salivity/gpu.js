Update Particles with GPU.js Pipeline Mode

Simulating particle systems in the browser often bottlenecks when repeatedly transferring large sets of coordinate and velocity data between the CPU and GPU. By leveraging the pipeline mode in GPU.js, developers can execute iterative calculations—such as updating particle velocities and positions—entirely within GPU memory as WebGL textures. This article explains how pipeline mode works, how to configure the kernels for velocity and position integration, and how to execute the continuous update loop efficiently without transferring data back to JavaScript memory on every frame.

The Role of Pipeline Mode

By default, a GPU.js kernel executes on the graphics hardware and then converts the resulting WebGL texture back into a JavaScript array (CPU memory). In an iterative simulation running at 60 frames per second, transferring thousands or millions of floats back and forth creates severe memory bandwidth overhead.

Setting pipeline: true in the kernel options instructs GPU.js to leave the output data on the GPU as a Texture object. This texture can be passed directly as an input into the next kernel execution, allowing position and velocity calculations to feed into each other with zero CPU data-transfer overhead.

Setting Up the Simulation Kernels

A typical Newtonian particle system calculates updated velocity based on forces (e.g., gravity, drag) and then updates positions based on those new velocities.

const gpu = new GPU();

// Kernel to update velocity based on acceleration/forces
const updateVelocity = gpu.createKernel(function(positions, velocities, dt) {
    const i = this.thread.x;
    
    // Read current values (assuming 2D vectors packed as [x, y])
    let vx = velocities[i][0];
    let vy = velocities[i][1];
    
    // Apply gravity
    const gravityY = -9.81;
    vy += gravityY * dt;

    return [vx, vy];
}, {
    pipeline: true,
    output: [NUM_PARTICLES]
});

// Kernel to update position using the updated velocity
const updatePosition = gpu.createKernel(function(positions, velocities, dt) {
    const i = this.thread.x;
    
    let px = positions[i][0];
    let py = positions[i][1];
    
    const vx = velocities[i][0];
    const vy = velocities[i][1];
    
    px += vx * dt;
    py += vy * dt;

    // Optional boundary collision handling
    if (py < 0) {
        py = 0;
    }

    return [px, py];
}, {
    pipeline: true,
    output: [NUM_PARTICLES]
});

The Iterative Update Loop

Once the kernels are defined, the simulation runs inside a standard requestAnimationFrame or fixed-timestep loop. The output of one kernel becomes the input to the next, cycling continuously through GPU memory.

// Initial state on CPU
let positions = initialPositionsArray; // Array of [x, y]
let velocities = initialVelocitiesArray; // Array of [vx, vy]

const dt = 0.016; // 60 FPS delta time

function step() {
    // 1. Compute new velocities; returns a GPU texture
    velocities = updateVelocity(positions, velocities, dt);

    // 2. Compute new positions using the texture from step 1; returns a GPU texture
    positions = updatePosition(positions, velocities, dt);

    // 3. Render or continue
    requestAnimationFrame(step);
}

requestAnimationFrame(step);

On the initial frame, positions and velocities are standard JavaScript arrays. GPU.js automatically uploads them to textures. In all subsequent frames, both variables store Texture references, meaning the data never leaves the GPU.

Extracting and Rendering Data

Because the output remains as a texture, the values cannot be logged or read directly using standard JavaScript index lookups without explicit conversion:

  • Retrieving Data to the CPU: Call positions.toArray() only when necessary (e.g., debugging or syncing state over a network), as this triggers the expensive GPU-to-CPU read operation.
  • Rendering on Canvas: To achieve maximum performance, feed the texture directly into a graphical kernel or combine the simulation with a WebGL rendering pipeline so that the updated coordinates are drawn directly to the canvas without converting them to arrays.

Texture Disposal

When working with long-running iterative textures in GPU.js, texture references are recycled automatically by the pipeline runner. However, if you manually break the loop, replace initial states, or stop using intermediate textures, calling .delete() on unused textures prevents WebGL memory leaks.
