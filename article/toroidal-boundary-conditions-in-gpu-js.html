Toroidal Boundary Conditions in gpu.js

This article explains how to implement toroidal boundary conditions within gpu.js kernels using coordinate wrapping techniques. Because gpu.js maps compute threads strictly across a fixed output grid, it does not automatically wrap thread coordinates at the hardware level. Instead, simulating a continuous, wrap-around toroidal space requires developers to programmatically calculate neighbor indices using mathematical modulo operations inside the kernel function.

Thread Coordinates in gpu.js

When you define a kernel in gpu.js, you set an output dimension such as [width, height]. Inside the kernel function, each execution thread accesses its current position via the built-in properties:

  • this.thread.x
  • this.thread.y
  • this.thread.z

These coordinates strictly range from 0 to dimension - 1. The GPU execution space itself is planar, meaning threads beyond these defined boundaries are never spawned, and native execution coordinates do not automatically roll over from the maximum index back to zero.

How Toroidal Wrapping is Achieved

A toroidal boundary condition (often used in cellular automata like Conway's Game of Life or physical wave simulations) dictates that moving past the right edge wraps around to the left edge, and moving past the top edge wraps around to the bottom.

Because gpu.js transpiles JavaScript code into GLSL shaders, array accesses to input matrices are translated into custom texture lookups. While native WebGL textures can technically use the gl.REPEAT wrapping mode, gpu.js abstractly manages textures under the hood and relies on discrete array-index math. Therefore, toroidal wrapping must be explicitly coded into coordinate offset calculations.

The Modulo Wrapping Formula

To read data from neighboring cells across toroidal edges, you must calculate neighbor coordinates using modulo arithmetic. In JavaScript and GLSL, handling negative offsets (such as reading a left neighbor when this.thread.x === 0) requires accounting for negative values to ensure the index stays within [0, dimension - 1]:

\[\text{wrappedIndex} = (\text{currentIndex} + \text{offset} + \text{dimension}) \pmod{\text{dimension}}\]

Adding the full dimension size before applying the modulo operator prevents negative numerators, guaranteeing that the target index correctly wraps to the opposite end of the grid.

Implementation in a gpu.js Kernel

Below is an example demonstrating toroidal coordinate wrapping in a 2D gpu.js kernel calculating the state of neighboring cells:

const gpu = new GPU();

const updateSimulation = gpu.createKernel(function(grid, width, height) {
    const x = this.thread.x;
    const y = this.thread.y;

    // Toroidal coordinate offsets for immediate neighbors
    const left   = (x - 1 + width) % width;
    const right  = (x + 1) % width;
    const top    = (y + 1) % height;
    const bottom = (y - 1 + height) % height;

    // Reading wrapped neighbor values
    const currentVal = grid[y][x];
    const leftVal    = grid[y][left];
    const rightVal   = grid[y][right];
    const topVal     = grid[top][x];
    const bottomVal  = grid[bottom][x];

    return currentVal + leftVal + rightVal + topVal + bottomVal;
}).setOutput([512, 512]);

In this kernel:

  • If x is 0, left resolves to (0 - 1 + 512) % 512 = 511, wrapping to the far-right index.
  • If x is 511, right resolves to (511 + 1) % 512 = 0, wrapping to the far-left index.
  • The same logic applies vertically along the Y-axis.

Performance and Precision Considerations

When implementing toroidal boundaries in gpu.js:

  1. Integer Arithmetic: Always pass grid dimensions (width, height) as integer parameters or define them as constants to allow the underlying shader compiler to use integer operations (% or GLSL mod) efficiently.
  2. Branch Avoidance: Using the arithmetic modulo formula is typically faster on GPU architectures than utilizing if/else conditional checks to test if a thread is at boundary coordinates, as branching can cause warp/wavefront divergence.
