Accelerating Sauvola and Otsu Thresholding with GPU.js

This article explores how the GPU.js library can be utilized to parallelize image binarization algorithms, specifically comparing local adaptive methods like Sauvola with global and localized variants of Otsu thresholding. While local window algorithms such as Sauvola map naturally to the parallel shader architecture of GPU.js, Otsu thresholding introduces algorithmic constraints that require distinct implementation strategies depending on whether it is deployed globally or locally.

Understanding GPU.js Execution Model

GPU.js compiles standard JavaScript functions into WebGL compute shaders, running calculations concurrently across thousands of GPU threads. In computer vision tasks, the canvas or pixel array is typically mapped directly to the kernel execution dimensions, where each thread computes the output for a single pixel coordinate (this.thread.x, this.thread.y).

Because GPUs excel at Single Instruction, Multiple Data (SIMD) paradigms where operations are independent and lack race conditions, the feasibility of parallelizing an algorithm depends heavily on how local and global memory are accessed.

Parallelizing Sauvola Thresholding

Sauvola thresholding is an adaptive local binarization method designed to handle degraded text and uneven illumination. It calculates a distinct threshold \(T(x, y)\) for each pixel based on the mean (\(m\)) and standard deviation (\(s\)) within a local neighborhood window of size \(W \times W\):

\[T = m \cdot \left(1 + k \cdot \left(\frac{s}{R} - 1\right)\right)\]

Where \(k\) is a user-defined parameter (commonly 0.2 to 0.5) and \(R\) is the dynamic range of standard deviation (typically 128 for 8-bit images).

Feasibility in GPU.js: High

Sauvola thresholding is an ideal candidate for GPU.js. The computation for every pixel depends entirely on read-only access to neighboring pixels and requires no synchronization between threads.

In a GPU.js implementation:

  1. The kernel receives the 2D grayscale image array and parameters (\(W\), \(k\), \(R\)).
  2. Each thread calculates its local bounding box: \([x - W/2, x + W/2]\) and \([y - W/2, y + W/2]\).
  3. A nested loop sums pixel values and squared values within the window to compute local mean \(m\) and local variance \(s^2\).
  4. The thread computes \(T\), compares the center pixel value to \(T\), and outputs either 0 or 1.

Because there are no write conflicts, Sauvola achieves near-linear speedups on the GPU compared to single-threaded CPU implementations, especially for moderate window sizes.

Parallelizing Otsu Thresholding

Otsu's method finds a threshold that minimizes intra-class variance (or equivalently, maximizes inter-class variance). The implementation strategy in GPU.js depends on whether the method is applied globally or locally.

Global Otsu Thresholding: Difficult in GPU.js

Global Otsu thresholding requires calculating a 256-bin histogram of the entire image, iterating through all candidate thresholds to find the variance maximum, and then applying that threshold across all pixels.

GPU.js struggles with the first step of this pipeline:

  • Lack of Atomic Operations: Standard WebGL shaders do not natively support atomic operations or shared memory histograms in the same way modern CUDA or WebGPU compute shaders do. Multiple threads attempting to increment the same histogram bin simultaneously create race conditions.
  • Multi-pass Workaround: Computing a histogram in WebGL typically requires multi-pass reduction rendering or scatter-to-gather transformations, which are complex and inefficient to express within the high-level abstractions of GPU.js.

Consequently, for standard global Otsu, it is generally faster to compute the 256-bin histogram and optimal threshold on the CPU, and then use GPU.js solely for the final binarization pass across pixels.

Local (Adaptive) Otsu Thresholding: Feasible but Computationally Heavy

Local Otsu thresholding runs Otsu's search over an independent local sliding window for every pixel.

In GPU.js:

  • Each thread can independently allocate an array of 256 bins within its local shader memory to compute the local histogram for its neighborhood window.
  • The thread evaluates the inter-class variance across the local histogram, determines the local threshold, and binarizes the center pixel.

While this avoids global race conditions, maintaining a 256-element array and running a 256-step loop inside every single GPU thread consumes significant register space. In WebGL, this can exceed register allocation limits or drastically reduce thread occupancy, making it performant only for relatively small window sizes.

Implementation Considerations

When building these algorithms in GPU.js, keep the following technical constraints in mind:

  • Window Size Scaling: In Sauvola thresholding, computing the local mean and variance directly inside the GPU kernel has a time complexity of \(\mathcal{O}(W^2)\) per thread. For very large windows, an integral image (summed-area table) approach is faster, though creating integral images on GPU.js requires recursive parallel scan passes.
  • Data Transfer Overhead: Transferring image buffers from the CPU to the GPU via WebGL textures introduces latency. GPU parallelization yields net speedups primarily on high-resolution images where the computational workload outweighs texture upload and readback costs.
  • Float Precision: Standardize image data to normalized single-precision floats ([0.0, 1.0]) prior to running arithmetic operations in GPU.js to avoid precision truncation during standard deviation calculations.
