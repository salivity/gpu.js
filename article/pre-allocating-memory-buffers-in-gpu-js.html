Pre-Allocating Memory Buffers in GPU.js

While gpu.js does not provide an explicit low-level API for pre-allocating raw WebGL buffers, developers can effectively mitigate runtime allocation spikes by leveraging texture pipelining and persistent GPU textures. By avoiding frequent conversions between JavaScript arrays and GPU textures, you can prevent garbage collection pauses and texture re-instantiation overhead during performance-critical loops.

The Memory Management Challenge in gpu.js

Under the hood, gpu.js compiles JavaScript-like functions into WebGL shaders. In typical WebGL architectures, data is stored and passed using textures or vertex buffers.

When you pass a standard JavaScript array or TypedArray into a gpu.js kernel, the library automatically creates a new WebGL texture, uploads the array data, runs the computation, and then translates the result back into a JavaScript array. This workflow creates two significant bottlenecks:

  1. CPU-to-GPU memory transfer overhead: Creating and uploading textures repeatedly inside a frame loop.
  2. Garbage collection (GC) pressure: JavaScript arrays and temporary WebGL structures are repeatedly generated and discarded, causing intermittent runtime frame drops.

Because gpu.js abstracts raw WebGL contexts, you cannot directly call methods like gl.bufferData() to manage fixed memory blocks. However, you can achieve the same stability using alternative architectural patterns within the library.

Solution 1: Enable Kernel Pipelining

The most effective way to eliminate runtime allocation spikes is to enable pipelining on your kernels via setPipeline(true).

When pipelining is enabled, the kernel outputs a Texture object instead of reading the pixels back to the CPU as a JavaScript array. This output texture resides directly in GPU VRAM and can be supplied directly as an input to subsequent kernel executions.

const gpu = new GPU();

const computeKernel = gpu.createKernel(function(data) {
  return data[this.thread.x] * 2.0;
})
.setOutput([1024])
.setPipeline(true); // Keeps output on the GPU

By chaining operations through textures, you avoid the continuous cycle of allocating new host-side arrays and newly bound WebGL framebuffers.

Solution 2: Reuse GPU Textures as Inputs

Instead of supplying raw JavaScript arrays on every iteration, convert your initial data into a persistent texture once, and feed that texture into your update loops.

// Step 1: Initial upload creates the texture
let currentData = computeKernel(initialArray);

function step() {
  // Step 2: Feed the existing GPU texture back into the kernel
  // This reuses GPU-side texture memory rather than allocating anew
  const nextData = computeKernel(currentData);
  
  // Step 3: Delete the intermediate texture to avoid VRAM leaks
  currentData.delete();
  currentData = nextData;

  requestAnimationFrame(step);
}

When managing textures this way, make sure to call .delete() on intermediate textures that are no longer needed. While gpu.js will allocate new texture handles if not tightly cycled, explicitly disposing of old textures ensures VRAM usage remains constant without triggering host-side GC spikes.

Solution 3: Warm-Up and Kernel Re-use

A common source of perceived allocation lag is kernel compilation and shader linking, which occurs the first time a kernel is invoked. To keep runtime smooth:

  • Pre-compile kernels: Run your kernels once with dummy data during application initialization.
  • Maintain fixed output dimensions: Altering output dimensions at runtime forces gpu.js to reallocate the underlying render targets and reconfigure viewport parameters. Keep output shapes constant.

Summary

You cannot pre-allocate static memory buffers using a dedicated allocation API in gpu.js. Instead, prevent runtime spikes by keeping your data on the GPU with .setPipeline(true), passing persistent Texture instances instead of raw arrays, and compiling your kernels during an initial warm-up phase.
