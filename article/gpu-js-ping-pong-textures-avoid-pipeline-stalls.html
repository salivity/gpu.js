GPU.js Ping-Pong Textures: Avoid Pipeline Stalls

Iterative computing tasks like cellular automata, fluid dynamics, and particle simulations in GPU.js rely on ping-pong buffering—alternating between two textures where one serves as the input and the other as the output. When implemented improperly, this technique often triggers severe WebGL pipeline stalls, forcing the CPU and GPU to wait on one another. This guide outlines the core architectural patterns required to maintain continuous GPU execution, configure kernel outputs correctly, and eliminate unnecessary CPU-GPU synchronization bottlenecks in GPU.js.

Enable Texture Output Pipeline Mode

By default, GPU.js evaluates kernels and decodes the resulting texture back into a JavaScript typed array on the CPU. This readback completely synchronizes the CPU and GPU, stalling execution until all rendering commands finish and memory transfers across the bus.

To keep data entirely on the GPU between iterations, explicitly configure the kernel to output textures:

const computeKernel = gpu.createKernel(function(inputTexture) {
    // Computation logic
    return inputTexture[this.thread.y][this.thread.x];
})
.setOutput([width, height])
.setPipeline(true)
.setOutputToTexture(true);

Setting setPipeline(true) and setOutputToTexture(true) ensures that the kernel returns a Texture instance referencing existing VRAM allocations rather than pulling data across the PCIe bus.

Pre-Allocate Static Double Buffers

Dynamic buffer allocation inside an animation or compute loop triggers garbage collection and forces WebGL context reconfigurations. Always allocate exactly two textures outside your loop:

  1. Texture A: Initialized with starting state data.
  2. Texture B: Empty or scratch texture initialized to matching dimensions.

Avoid re-instantiating textures, mutating kernel dimensions, or invoking gpu.createKernel() inside the loop. Reusing fixed memory structures keeps the driver state stationary.

Alternate Pointers Without Rebinding Contexts

The ping-pong loop should only swap variable references in JavaScript memory, passing the active input texture into the kernel while receiving the output as the next cycle's input:

let currentInput = initialTexture;
let currentOutput = null;

function stepSimulation() {
    // currentInput stays in VRAM; currentOutput is generated directly in VRAM
    currentOutput = computeKernel(currentInput);

    // Prepare pointers for the next iteration
    currentInput = currentOutput;
}

Because computeKernel operates in pipeline mode, this swap happens purely as WebGL framebuffer and texture target binding updates, preventing pipeline flushes.

Manage Texture Deallocation and Memory Leaks

When a GPU.js kernel set to pipeline mode runs continuously, returning a new texture reference each frame without manual cleanup can exhaust WebGL texture units. While swapping references, explicitly call .delete() on textures that are at least two generations old, or manage cleanup systematically to prevent the driver from stalling on out-of-memory errors:

let readTexture = initialTexture;
let writeTexture = null;

for (let i = 0; i < iterations; i++) {
    writeTexture = computeKernel(readTexture);

    // If an intermediate texture is no longer needed, dispose of it
    if (i > 0) {
        readTexture.delete();
    }

    readTexture = writeTexture;
}

Defer Synchronization and Readbacks

A pipeline stall inevitably occurs the moment CPU interaction is requested. Never call .toArray() or inspect the texture content within the hot loop.

  • Batch Iterations: If running 1,000 simulation steps, execute all 1,000 ping-pong iterations before touching the output.
  • Canvas Output for Rendering: If visual output is needed every frame, use a secondary render kernel (.setOutputToTexture(false) linked to a WebGL canvas) rather than pulling data to the CPU to draw via a 2D canvas context.
  • Final Retrieval: Only invoke .toArray() when computations are fully concluded and processing must return to the JavaScript main thread.
