GPU.js Multi-Dimensional Thread Mapping Explained

This article explores the internal mechanics of GPU.js, detailing how the library translates high-level multi-dimensional kernel coordinates into low-level hardware workgroups and fragment shader coordinates. It covers the abstraction layer, the mathematical formulas used to fold and unfold logical dimensions across 2D framebuffers, and how work is distributed across actual GPU hardware execution units.

The Logical Thread Model

In GPU.js, developers define execution domains using logical thread dimensions—such as 1D arrays, 2D matrices, or 3D volumes—via the setOutput([x, y, z]) method. Inside the kernel function, developers access their current execution index using this.thread.x, this.thread.y, and this.thread.z.

Under the hood, physical graphics pipelines do not execute arbitrary 3D JavaScript grids directly. Instead, GPU.js compiles the JavaScript kernel into a hardware-compatible shading language—primarily WebGL GLSL (fragment shaders) or, when supported, compute shaders (WebGPU / WebGL 2.0 Compute).

Emulating Thread Grids with the WebGL Rasterizer

Because WebGL 1.0 and 2.0 lack universal access to generic compute shaders, GPU.js relies primarily on fragment shaders rendered across an off-screen framebuffer (FBO). The execution is driven by drawing a full-screen quad composed of two triangles across a 2D rendering viewport.

  1. Packing Logical Dimensions into a 2D Canvas: The hardware viewport is inherently two-dimensional. If the kernel's logical output is 1D or 3D, GPU.js computes a 2D texture width and height large enough to accommodate the total number of threads (\(X \times Y \times Z\)). It balances dimensions to avoid exceeding the hardware-specific MAX_TEXTURE_SIZE limitation.

  2. Index Recovery from gl_FragCoord: Each pixel rendered corresponds to a distinct logical thread invocation. In the compiled GLSL fragment shader, GPU.js generates boilerplate code that converts the native 2D pixel coordinate (gl_FragCoord.xy) into a flat 1D global index, and subsequently into the logical x, y, and z indices.

    The flat index calculation inside the generated GLSL is essentially:

    float flatIndex = floor(gl_FragCoord.y) * uTexSize.x + floor(gl_FragCoord.x);

    From this global index, GPU.js calculates the multi-dimensional positions:

    // For 3D setups with dimensions (outX, outY, outZ)
float threadZ = floor(flatIndex / (outX * outY));
float remainder = flatIndex - (threadZ * outX * outY);
float threadY = floor(remainder / outX);
float threadX = mod(remainder, outX);

    These calculated variables are then bound to this.thread.x, this.thread.y, and this.thread.z before executing the body of your kernel.

Dispatching to Compute Shaders (WebGPU / Compute Mode)

When configured to use WebGPU or experimental WebGL compute contexts, GPU.js bypasses the rasterization pipeline and maps thread blocks directly to hardware compute workgroups.

  1. Workgroup Sizing: GPU hardware organizes execution units into local groups of threads (e.g., Warps on NVIDIA, Wavefronts on AMD). GPU.js defines a fixed local workgroup layout (such as [8, 8, 1] or [16, 16, 1], depending on dimensionality) within the shader metadata.

  2. Workgroup Dispatch Mapping: GPU.js calculates the number of workgroups to dispatch by dividing the total requested output dimensions by the local workgroup size, rounding up: \[\text{Workgroups}_x = \lceil \text{Output}_x / \text{WorkgroupSize}_x \rceil\] \[\text{Workgroups}_y = \lceil \text{Output}_y / \text{WorkgroupSize}_y \rceil\] \[\text{Workgroups}_z = \lceil \text{Output}_z / \text{WorkgroupSize}_z \rceil\]

  3. Global ID Resolution: Inside the compute shader, the multi-dimensional thread identity is derived directly from built-in hardware variables:

    • WebGPU: @builtin(global_invocation_id) provides vec3<u32>, directly providing \(x\), \(y\), and \(z\).
    • GLSL Compute: gl_GlobalInvocationID maps directly to the thread coordinates.

    A bounds check is injected at the start of the compute shader to discard any out-of-bounds invocations caused by workgroups that extend past the requested output boundary.

Hardware-Level Execution

At the physical silicon layer:

  • In rasterization mode, the GPU's rasterizer splits the 2D quad into small blocks (often 2x2 pixel quads) and distributes them across Streaming Multiprocessors (SMs) or Compute Units (CUs). Each pixel executes the compiled fragment shader concurrently.
  • In compute mode, the hardware dispatcher assigns entire workgroups directly to available compute units. Local workgroup threads run concurrently in lockstep, sharing cache and registers until the entire grid is evaluated.

Through these translation layers, GPU.js transforms intuitive multi-dimensional spatial arrays into flat memory textures and hardware thread dispatches without requiring the programmer to manage GPU memory geometry or hardware-specific coordinate spaces.
