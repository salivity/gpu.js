How gpu.js Transpiles If-Else in Helper Functions

This article explains how the gpu.js library converts JavaScript conditional statements, such as if-else blocks, within custom helper functions into native WebGL GLSL (OpenGL Shading Language). It covers the underlying Abstract Syntax Tree (AST) parsing, the mapping of dynamic branch conditions to static shading language syntax, and how gpu.js resolves type inference and scope across conditional branches.

AST Parsing and Node Identification

When you register a helper function with gpu.js using gpu.addFunction(), the compiler does not execute the JavaScript code. Instead, it parses the function's source code into an Abstract Syntax Tree (AST) using an internal JavaScript parser (such as Acorn).

During traversal of the AST, conditional logic is identified through specific nodes:

  • IfStatement: Represents standard if, else if, and else blocks.
  • ConditionalExpression: Represents ternary operators (condition ? expr1 : expr2).

The transpiler isolates the test (the condition), the consequent (the if body), and the alternate (the optional else or else if body) for individual processing.

Transpiling Conditions to GLSL Syntax

Because GLSL syntax for basic control flow closely mirrors JavaScript, the translation of the control structure itself is direct. The AST walker converts the IfStatement into corresponding GLSL code:

if (condition) {
    // Transpiled consequent statements
} else {
    // Transpiled alternate statements
}

The critical transformation occurs within the test expression. In JavaScript, conditions rely on "truthy" or "falsy" evaluation (e.g., if (1) or if (myVar)). GLSL strictly requires a boolean expression inside if statements. The gpu.js transpiler evaluates the AST test node and converts implicit truthy evaluations into explicit boolean comparisons (such as myVar != 0.0 or myVar != 0) based on the inferred type of the variable.

Handling Static Types and Variable Declarations

JavaScript is dynamically typed, whereas GLSL is statically typed. Helper functions must declare explicit types for parameters, local variables, and return values. When transpiling if-else statements, gpu.js enforces strict rules:

  1. Pre-declaration of Branch Variables: If a variable is declared within one branch of an if-else statement and used later outside of it, gpu.js hoists the declaration above the conditional block, assigning it a single inferred GLSL type (such as float, int, or vec4).
  2. Type Uniformity: Variables assigned in both the if branch and the else branch must evaluate to the same uniform data type. If a variable is assigned a float in the if block and an integer in the else block, the compiler either casts the integer to a float or throws a compilation error during the AST validation phase.

Return Statement Resolution

Helper functions in GLSL must declare a single return type. When an if-else block contains early return statements, the gpu.js transpiler inspects the returned expressions across all possible branches:

  • Return Type Inference: The transpiler verifies that every return path outputs the exact same data type.
  • Control Flow Integrity: If an if block returns early, it translates into a native GLSL return statement. If the helper function returns values conditionally, gpu.js ensures that all code paths return a value to satisfy GLSL compiler requirements, rejecting functions where a path could implicitly return undefined.

Ternary Expressions

For inline conditionals (ConditionalExpression), gpu.js determines whether the expression can be emitted directly as a GLSL ternary operation:

(condition ? true_float_val : false_float_val)

Both outputs of the ternary operator must match in type, as GLSL does not support mixed-type ternary expressions without explicit type casting. If type coercion is required, gpu.js inserts explicit constructors (such as float(...)) around the mismatched branch.
