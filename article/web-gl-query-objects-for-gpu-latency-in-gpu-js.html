WebGL Query Objects for GPU Latency in gpu.js

Profiling kernel execution in gpu.js requires distinguishing between CPU dispatch overhead and actual GPU execution time. Because WebGL operations are fundamentally asynchronous, standard JavaScript timing mechanisms like performance.now() fail to reflect actual hardware compute times. WebGL query objects—specifically through disjoint timer query extensions—provide a direct, hardware-level mechanism to track elapsed execution time on the GPU. This article examines why these queries are essential, how they measure latency without disrupting pipeline performance, and the technical considerations required when profiling gpu.js workloads.

The Problem with CPU-Side Benchmarking

When a kernel executes in gpu.js, the library compiles the provided JavaScript function into a WebGL shader (GLSL) and draws to a texture via an off-screen frame buffer. In JavaScript, invoking a kernel merely queues rendering commands into the browser's WebGL command stream.

Using traditional CPU timestamps (console.time() or performance.now()) around a kernel invocation records only the time it takes to push those commands to the queue, not the duration the GPU spends running the shader. Forcing synchronization using gl.finish() or reading pixels via gl.readPixels() introduces severe pipeline stalls, memory transfer penalties, and CPU-GPU synchronization overhead that artificially inflate the reported latency.

The Role of WebGL Timer Query Extensions

WebGL query objects solve this problem by logging timestamps directly within the GPU's internal command stream. Supported primarily via the EXT_disjoint_timer_query (WebGL 1.0) and EXT_disjoint_timer_query_webgl2 (WebGL 2.0) extensions, these queries track GPU-side durations without blocking the CPU thread.

When enabled and integrated with the underlying WebGL context in gpu.js, timer queries operate through the following steps:

  1. Query Creation: The application creates a query object using gl.createQuery().
  2. Boundary Definition: Before the kernel's internal draw call is executed, gl.beginQuery(ext.TIME_ELAPSED_EXT, query) marks the start of the timing window. After the draw call completes, gl.endQuery(ext.TIME_ELAPSED_EXT) marks the end.
  3. Asynchronous Polling: The GPU records elapsed nanoseconds during hardware rasterization and shading. The JavaScript runtime periodically checks whether the result is ready via gl.getQueryParameter(query, gl.QUERY_RESULT_AVAILABLE) using requestAnimationFrame or a microtask loop.
  4. Data Retrieval: Once the result is available, gl.getQueryParameter(query, gl.QUERY_RESULT) yields the pure GPU execution latency.

Non-Invasive Performance Profiling

The primary advantage of WebGL query objects in gpu.js is their non-blocking nature. Because they operate asynchronously within the GPU pipeline, they do not flush the command buffer or stall thread execution. This preserves natural GPU state transitions, memory access patterns, and hardware scheduling, allowing developers to measure real-world kernel performance accurately.

Handling Disjoint Events and Browser Restrictions

When using query objects to evaluate gpu.js latency, two main constraints must be accounted for:

  • Disjoint Flag Checks: A GPU can be interrupted by the operating system, thermal throttling, or context resets during execution. The extension provides a gl.getParameter(ext.GPU_DISJOINT_EXT) flag. If this returns true, the measurement was interrupted and must be discarded.
  • Security and Precision Limits: Due to side-channel attack mitigations (such as Spectre), major browsers frequently disable disjoint timer query extensions by default or round timestamps to coarse resolutions. Developers often need to explicitly enable these extensions via browser developer flags to conduct high-precision latency profiling on gpu.js kernels.
