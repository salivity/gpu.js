How gpu.js Translates JS Logical Operators to GLSL

This article explores how gpu.js transpiles JavaScript's logical && (AND) and || (OR) operators into GLSL (OpenGL Shading Language). It breaks down how the transpiler traverses the JavaScript Abstract Syntax Tree (AST), reconciles JavaScript's value-returning short-circuit evaluations with GLSL's strict boolean type system, and ensures that GPU shaders preserve the intended execution order and performance benefits without breaking shader compilation.

Abstract Syntax Tree (AST) Parsing

When a JavaScript kernel function is passed into gpu.js, the library does not execute it directly. Instead, it uses an internal parser to convert the function into an Abstract Syntax Tree (AST).

During the AST traversal, expressions containing && or || are classified as LogicalExpression nodes. The transpiler inspects the operator, the left child node, and the right child node. Because GLSL does not interpret dynamic JavaScript syntax, gpu.js must construct an equivalent GLSL string based on the semantic context in which the logical expression appears.

Reconciling Dynamic Truthiness with Static GLSL Types

The primary challenge in translating && and || from JavaScript to GLSL lies in the fundamental difference between the two languages' type systems:

  • JavaScript: Operands can be of any type (numbers, booleans, objects). The && and || operators do not always return a boolean; they return the value of the operand that determined the result (e.g., 4 && 5 evaluates to 5).
  • GLSL: The logical operators && and || accept strictly bool types and always evaluate to a bool. Supplying a float or int directly to a logical operator in GLSL results in a compilation error.

To resolve this discrepancy, gpu.js enforces truthiness checks. When translating numerical values or expressions inside logical operations, it explicitly casts or compares values to determine their boolean state. A numeric operand x is converted to an implicit condition such as (x != 0.0) so that GLSL receives valid bool operands.

Native GLSL Short-Circuiting

The GLSL ES specification mandates short-circuit evaluation for logical operators, mirroring JavaScript's execution behavior:

  • For A && B, if A evaluates to false, B is not evaluated.
  • For A || B, if A evaluates to true, B is not evaluated.

When gpu.js encounters simple conditional checks (such as inside an if statement or while loop), it translates the AST LogicalExpression directly into GLSL's native && or || operators:

// JavaScript Source
if (x > 0.0 && y < 1.0) {
  // ...
}

Transpiles directly into:

// Generated GLSL
if ((x > 0.0) && (y < 1.0)) {
  // ...
}

Because WebGL drivers respect GLSL short-circuit rules, expensive calculations or texture lookups placed on the right-hand side are bypassed if the left-hand condition settles the evaluation.

Emulating Short-Circuit Value Returns via Ternary Operators

In JavaScript, developers frequently use short-circuit evaluation for fallback assignments:

// JavaScript Source
let result = a || b;

Because GLSL cannot assign the result of a native boolean || operation to a float, gpu.js rewrites expressions that assign or return values using GLSL's ternary conditional operator (? :):

// Generated GLSL concept
float result = (bool(a)) ? a : b;

The ternary operator in GLSL also strictly adheres to short-circuit evaluation: only the selected branch is computed. By translating value-based logical expressions into ternary operations, gpu.js maintains JavaScript's return-value semantics and short-circuit guarantees while satisfying the strict type and assignment constraints of the GPU shader compiler.
