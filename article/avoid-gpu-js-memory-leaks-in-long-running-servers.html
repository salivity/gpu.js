Avoid gpu.js Memory Leaks in Long-Running Servers

Running gpu.js in long-lived server environments like Node.js requires aggressive resource management to avoid fatal memory leaks. Because gpu.js relies on native WebGL bindings (such as headless-gl) to interface with physical hardware, standard V8 garbage collection cannot automatically track or deallocate native GPU memory. Ensuring long-term process stability requires explicitly destroying unused contexts, pooling compiled kernels, manually clearing texture data, and structuring execution cycles to isolate unmanaged native memory.

Reuse Kernels Instead of Recreating Them

Compiling a kernel via gpu.createKernel() is an expensive operation that allocates native WebGL shaders and GPU-bound program buffers. A common anti-pattern in server routes is generating a new kernel per incoming request.

Define kernels once at application startup or maintain an instantiated worker pool. Re-run calculations by passing new arguments to the existing kernel instance rather than instantiating new pipelines dynamically.

// Good: Define once at startup
const renderKernel = gpu.createKernel(function(data) {
  return data[this.thread.x] * 2;
}).setOutput([1024]);

// Inside request handler: reuse existing instance
app.post('/compute', (req, res) => {
  const result = renderKernel(req.body.data);
  res.json(Array.from(result));
});

Explicitly Destroy Dynamic Kernels

If your application architecture strictly requires creating kernels on the fly (for example, with variable output sizes), you must manually release the native GPU resources. The JavaScript garbage collector only reclaims the wrapper object, leaving the native WebGL program loaded in GPU memory.

Invoke the .destroy() method explicitly within a try...finally block to guarantee execution cleanup even when exceptions occur:

let dynamicKernel = null;
try {
  dynamicKernel = gpu.createKernel(myFunction).setOutput([dynamicSize]);
  const result = dynamicKernel(payload);
  return result;
} finally {
  if (dynamicKernel) {
    dynamicKernel.destroy(true); // pass true to clean up sub-dependencies
  }
}

Clean Up Output Textures

When operating in pipeline mode (pipeline: true), gpu.js returns an intermediate Texture instance instead of a flattened JavaScript array to keep memory on the GPU for chained calculations.

Leaving these textures floating in memory without explicit deallocation creates rapid native memory accumulation. When you are done reading from or passing an intermediate texture, delete it directly:

const texture = chainedKernel(data);
const finalResult = finalKernel(texture);

// Explicitly free the intermediate GPU texture memory
texture.delete();

Prevent WebGL Context Exhaustion

The underlying headless-gl implementation enforces an operating-system-level cap on simultaneously active WebGL contexts (often between 8 and 16 contexts per process). Creating multiple new GPU() instances will quickly exhaust this limit, leading to silent calculation failures or unrecoverable context loss errors.

Maintain a single global GPU instance across your entire Node.js runtime, or initialize a strictly regulated pool where instances are checked out and returned. When tearing down an entire GPU instance, call:

gpu.destroy();

Isolate Calculations in Worker Threads or Child Processes

V8's garbage collector triggers based on heap usage and remains unaware of off-heap V8 memory and GPU VRAM pressure. Consequently, Node.js may not initiate garbage collection cycles frequently enough to release native bindings before system memory saturates.

Offloading gpu.js tasks to worker_threads or dedicated child processes offers the highest stability for long-running servers. Terminating a worker thread or recycling an isolated child process after a set number of operations forces the underlying operating system to instantly reclaim all allocated native WebGL contexts, eliminating leak risks entirely.
