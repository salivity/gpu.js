Simulating Wave Digital Filters Using GPU.js

Simulating Wave Digital Filter (WDF) models of analog synthesizer circuits using gpu.js is technically possible, but it faces significant architectural constraints that make it inefficient for standard real-time monophonic audio. While gpu.js allows developers to execute parallel JavaScript code on the GPU via WebGL shaders, the recursive, sample-by-sample nature of WDFs directly clashes with the parallel design of graphics processors. This article examines the mechanics of WDFs, the strengths and weaknesses of gpu.js, the execution bottlenecks of GPU-based audio, and the specific scenarios where this approach is viable.

The Architectural Conflict: WDFs vs. Parallel GPUs

Wave Digital Filters model analog components—such as capacitors, inductors, operational amplifiers, and diode clippers—by translating physical circuit topologies into discrete-time wave scattering networks.

Because dynamic components store energy, calculating the state of the circuit at sample \(n\) strictly depends on the state values from sample \(n-1\). This creates an intrinsically serial, low-latency feedback loop (\(IIR\) response).

GPUs are engineered for Single Instruction, Multiple Data (SIMD) tasks, excelling at crunching millions of independent calculations simultaneously (such as pixel shading or matrix multiplication). They perform poorly on inherently sequential tasks where each computation must wait for the preceding result. Simulating a single stream of audio through a recursive filter cannot be parallelized across the time domain.

Bottlenecks of GPU.js for Audio DSP

When using gpu.js to run WDF models, several technical hurdles arise:

  • Kernel Launch Overhead: Transferring state variables to the GPU and executing a kernel incurs high latency relative to standard audio buffer sizes (e.g., 64 to 256 samples).
  • Data Transfer Latency: Standard Web Audio implementations require audio processing to happen synchronously or within strict time frames (typically under 3 milliseconds) inside an AudioWorklet. Fetching calculation results back from WebGL/GPU memory to the CPU audio thread introduces massive round-trip latency and can trigger audio dropouts.
  • No Persistent Thread State Across Samples: In gpu.js, running an iterative computation across thousands of sequential audio frames requires either ping-ponging framebuffers or running a serial loop inside a single shader invocation, which eliminates the GPU's multi-core advantages.

Where GPU.js Can Work for WDF Simulation

Despite these limitations, using gpu.js for WDF simulation becomes practical in specific throughput-oriented, non-latency-critical contexts:

  1. Massive Polyphony: If an analog synthesizer patch demands hundreds or thousands of simultaneous independent voices (e.g., additive clusters or swarm synthesis), gpu.js can process each voice in parallel on a separate GPU thread.
  2. Offline Rendering and Dataset Generation: For training neural networks or generating offline sound libraries, latency is irrelevant. Audio can be rendered in large batches where memory transfer penalties are minimized.
  3. Parameter Space Exploration: Running hundreds of circuit simulations in parallel to evaluate circuit component tolerances or parameter sweeps across multiple filter settings.

The Recommended Alternative

For real-time virtual analog synthesis within the browser, the optimal approach is using WebAssembly (WASM) compiled from C++ or Rust, executed inside a dedicated AudioWorkletNode. WASM provides bare-metal CPU execution speeds, supports SIMD vectorization for parallel voices, and runs directly within the browser's dedicated low-latency audio rendering thread without GPU-CPU bus transfer penalties.
