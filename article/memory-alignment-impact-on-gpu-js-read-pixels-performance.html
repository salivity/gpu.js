Memory Alignment Impact on GPU.js readPixels Performance

This article examines how memory alignment influences the performance of gl.readPixels when extracting kernel calculation results in GPU.js. It details the underlying WebGL memory transfer mechanisms, how row byte padding impacts readback speeds, the specific performance penalties of misaligned memory buffers, and best practices for configuring kernel dimensions to achieve optimal data throughput between the GPU and CPU.

Understanding readPixels in GPU.js

GPU.js compiles JavaScript functions into GLSL shaders, running parallel computations across GPU textures. Once execution completes, the computed output resides in GPU memory as a texture. To return this data to standard JavaScript arrays or TypedArrays, the library relies on the underlying WebGL call gl.readPixels.

Because data transfer across the PCI-e bus represents one of the most severe bottlenecks in WebGL computing, the efficiency of gl.readPixels dictates overall application throughput. Memory alignment plays a decisive role in whether this transfer occurs via a fast direct memory access path or a slow, CPU-bound parsing loop.

WebGL Pack Alignment and Byte Strides

WebGL manages data packing through the gl.pixelStorei parameter PACK_ALIGNMENT. By default, WebGL sets this alignment to 4 bytes. This rule requires that the start of every individual row of pixel data in the destination memory buffer must begin at a byte offset that is an exact multiple of 4 (or 1, 2, or 8, depending on the configuration).

When calculating the byte width of a row, the formula is:

\[\text{Row Bytes} = \text{Width} \times \text{Components per Pixel} \times \text{Bytes per Component}\]

If the total number of bytes in a row is not a multiple of the PACK_ALIGNMENT value, WebGL must insert padding bytes at the end of every row to ensure the subsequent row starts on an aligned boundary.

How Misalignment Degrades Performance

When GPU.js processes an output whose dimensions and format do not produce row byte lengths matching the pack alignment, severe performance penalties occur:

  1. Loss of Fast Direct Memory Copy (DMA): Hardware drivers are optimized to stream linear, contiguous memory blocks directly from VRAM to host RAM. When alignment requirements force the driver to insert or remove row padding, hardware-level bulk copying is disabled.
  2. Driver-Level Strided Loops: The WebGL implementation must iterate through the buffer row-by-row on the CPU, copying valid data and inserting or discarding padding bytes. This introduces substantial CPU overhead and stalls the render pipeline.
  3. GPU Pipeline Stalls: readPixels is inherently synchronous. If the CPU must perform manual memory realignment on incoming frames, the pipeline stall lasts significantly longer, blocking the event loop and reducing frames per second.
  4. Sub-Optimal Cache Line Utilization: Misaligned reads disrupt CPU cache line boundaries (typically 64 bytes). Reading unaligned rows leads to multiple cache line fetches for individual values, increasing memory latency.

Single-Channel vs. Four-Channel Alignment

In GPU.js, kernels often output single-channel scalar values (such as a single floating-point or integer value per thread) or packed RGBA vectors:

  • RGBA (4-Channel) Reads: Each pixel contains 4 components. If using 8-bit integers (1 byte per channel), each pixel is 4 bytes wide. Consequently, every row is automatically a multiple of 4 bytes regardless of the width, satisfying the default PACK_ALIGNMENT = 4 and maintaining high read performance.
  • Single-Channel Reads: When reading single-channel 8-bit data, each pixel is 1 byte. If the output texture width is an odd number or not divisible by 4, row padding is introduced. Reading a \(513 \times 513\) single-channel texture causes padding at the end of every single row, resulting in measurable latency spikes compared to a \(512 \times 512\) texture.

Optimizing Memory Alignment in GPU.js

To minimize readback latency caused by memory alignment issues:

  • Align Output Dimensions: Ensure that kernel output widths are multiples of 4 or 8. Power-of-two widths (such as 256, 512, or 1024) inherently align across all common byte representations.
  • Pack Scalars into Vectors: If computing scalar outputs, pack four distinct values into a single RGBA pixel within the shader. This yields a naturally 4-byte aligned structure per pixel and reduces the total pixel count read by a factor of four.
  • Synchronize Pack Parameters: If non-aligned output widths are unavoidable, adjusting gl.pixelStorei(gl.PACK_ALIGNMENT, 1) allows tight byte packing without row padding. However, direct 4-byte or 8-byte aligned transfers typically remain faster at the hardware driver level than 1-byte packed reads.
