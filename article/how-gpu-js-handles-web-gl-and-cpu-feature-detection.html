How GPU.js Handles WebGL and CPU Feature Detection

GPU.js accelerates JavaScript calculations by compiling custom kernels to run on the graphics processor, utilizing an automated feature-detection pipeline to switch between WebGL and CPU execution. This process works by querying the host environment's capabilities in a tiered order—attempting WebGL 2 first, falling back to WebGL 1, and ultimately degrading to pure JavaScript execution on the CPU if hardware acceleration is unavailable, unsupported, or explicitly disabled.

The Detection Hierarchy

When a new GPU instance is initialized without explicit mode constraints, the library defaults to an automated mode (mode: 'gpu'). In this mode, GPU.js evaluates execution targets in the following order:

  1. WebGL 2 (webgl2): GPU.js first creates an offscreen HTML <canvas> element (or uses headless environments in Node.js) and calls canvas.getContext('webgl2'). If successful, it checks for native support of 32-bit floating-point textures and transform feedback.
  2. WebGL 1 (webgl): If WebGL 2 is unavailable or missing essential features, the engine requests canvas.getContext('webgl') or canvas.getContext('experimental-webgl').
  3. CPU (cpu): If no WebGL contexts can be instantiated, or if hardware capability tests fail, GPU.js switches to standard JavaScript execution.

Extension and Precision Verification

Merely obtaining a WebGL context is not sufficient for general-purpose computing on GPUs (GPGPU). GPU.js requires specific features to read and write numeric data accurately. It checks for critical extensions via gl.getExtension():

  • Floating-Point Textures: GPU.js requires extensions such as OES_texture_float (WebGL 1) or EXT_color_buffer_float (WebGL 2) to store and output 32-bit floating-point arrays inside texture buffers.
  • Half-Float Support: If standard 32-bit floating-point extensions are unavailable, it tests for half-float capabilities (OES_texture_half_float) before falling back.
  • Maximum Texture Sizes: The library queries gl.getParameter(gl.MAX_TEXTURE_SIZE) to determine the maximum array dimensions the hardware can allocate as input textures.

If the active context fails to provide the extensions needed to process the kernel's declared output precision or argument types, the detection layer rejects the context and moves down the fallback chain.

Kernel Validation and Compilation Fallback

Feature detection extends past the initial context creation to the kernel compilation stage. When a kernel is declared, GPU.js parses the JavaScript function into an Abstract Syntax Tree (AST) using a custom parser.

It attempts to translate the AST into a GLSL (OpenGL Shading Language) fragment shader. If the shader fails to compile via gl.compileShader() or link via gl.linkProgram(), GPU.js catches the WebGL error logs. Rather than throwing an unhandled runtime error, the engine marks the GPU execution as failed for that kernel and transparently generates a CPU fallback.

The CPU Fallback Mechanism

When CPU mode is selected—either through feature detection failure or manual configuration—GPU.js bypasses WebGL entirely. Instead of generating GLSL shaders, the AST is transpiled into native JavaScript loops.

In this state:

  • The kernel runs inside standard nested for loops that match the dimensions declared via setOutput().
  • The thread index functions (this.thread.x, this.thread.y, this.thread.z) are mapped to the outer loop iterators.
  • Array manipulations occur directly in main system memory rather than across the GPU bus, ensuring identical calculation results at the expense of parallelized performance.
