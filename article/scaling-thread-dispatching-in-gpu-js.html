Scaling Thread Dispatching in gpu.js

This article examines how gpu.js handles massively parallel workloads, specifically analyzing how thread dispatching scales when processing millions of data elements. By compiling JavaScript functions into WebGL shaders, gpu.js delegates execution to the underlying GPU hardware scheduler. Understanding this architecture reveals how thread dispatching moves from a linear CPU execution model to a highly parallel GPU pipeline, where millions of threads are scheduled, distributed across hardware compute units, and constrained by memory bandwidth rather than instruction count.

The Dispatch Architecture

When you define an execution grid in gpu.js using kernel.setOutput([width, height]), you are not spawning individual software threads. Instead, gpu.js transpiles the JavaScript kernel into a WebGL shader program.

In standard WebGL-based gpu.js modes, execution relies on fragment shaders. To evaluate millions of parallel elements, gpu.js binds a texture of the corresponding output dimensions, sets an identical viewport size, and renders a screen-aligned quad consisting of two triangles. The GPU rasterizer breaks this quad into fragments, automatically generating one thread invocation per target output pixel. When WebGL 2.0 Compute is supported, gpu.js maps the output dimensions to compute shader workgroups instead, dispatching threads across explicit local and global coordinate spaces.

Hardware Scaling and Latency Hiding

GPUs rely on massive parallelism to achieve high throughput, making workloads with millions of elements ideal for their execution model.

  • Warps and Wavefronts: The GPU's hardware scheduler groups threads into fixed-size units—warps of 32 threads on NVIDIA hardware or wavefronts of 32 to 64 threads on AMD hardware. Millions of individual operations are partitioned into tens of thousands of these groups.
  • Occupancy and Scheduling: Streaming Multiprocessors (SMs) or Compute Units (CUs) cycle between active warps on every clock cycle. When one warp encounters a high-latency operation, such as sampling from an input texture or accessing global device memory, the scheduler instantly switches to another ready warp without context-switch penalties.
  • Saturation: At low element counts (e.g., tens of thousands), GPU compute units are underutilized, and CPU-to-GPU dispatch overhead dominates run time. Scaling to millions of elements saturates all compute units, driving the GPU to maximum execution efficiency where latency is effectively masked.

Managing Architectural Constraints at Scale

Handling millions of threads through a WebGL abstraction introduces specific limitations that gpu.js must manage to prevent driver crashes or execution failures.

Texture Dimension Limits

GPUs enforce a hardware limit on single-dimension textures, defined by gl.MAX_TEXTURE_SIZE (typically 4,096 to 16,384 pixels depending on the device). A flat 1D array of 16 million elements cannot be mapped into a single 1D texture line. gpu.js overcomes this by automatically mapping 1D and 3D output topologies into 2D textures. A 1D array of 4,194,304 elements is dispatched as a 2048×2048 grid, with thread coordinates internally decoded within the generated shader code using modular arithmetic.

Memory Overhead and Serialization

While thread dispatching on the GPU itself scales with near-linear hardware efficiency, data movement scales strictly by memory bus bandwidth. The bottleneck at multi-million element scales shifts from thread dispatch to data transmission:

  1. Input Packing: JavaScript arrays must be converted to typed arrays (Float32Array) and uploaded as textures.
  2. Execution: The shader runs across millions of fragments in parallel.
  3. Output Readback: The host must retrieve the results using gl.readPixels().

Because gl.readPixels() forces a pipeline stall—blocking the CPU until the GPU finishes executing all dispatched threads—retrieving millions of elements introduces measurable synchronization latency.

Optimizing for Multi-Million Thread Kernels

To maintain high throughput when dispatching millions of threads in gpu.js:

  • Enable Pipeline Mode: Use kernel.setPipeline(true) when chaining computations. This keeps output buffers stored directly on the GPU as textures for the next kernel to consume, entirely bypassing host-device data readbacks.
  • Align Dimensions to Warp Sizes: Ensure the innermost output dimension is a multiple of 32 or 64. Misaligned outputs create partially filled warps at grid edges, leading to thread divergence and unutilized compute cycles.
  • Minimize Control Flow Divergence: When writing kernel logic, avoid data-dependent if/else branches. If threads within the same 32-thread warp take different execution paths, the hardware serializes those branches, halving effective throughput across that warp.
