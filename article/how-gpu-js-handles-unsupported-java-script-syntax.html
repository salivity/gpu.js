How gpu.js Handles Unsupported JavaScript Syntax

gpu.js accelerates web applications by compiling JavaScript functions into WebGL or WebGPU shader language (GLSL), but it cannot translate every standard JavaScript feature. When gpu.js encounters unsupported JavaScript syntax during compilation, it identifies the invalid constructs by analyzing the Abstract Syntax Tree (AST), halts the transpilation process, throws a descriptive compile-time error, or automatically falls back to standard CPU execution depending on the configured runtime mode.

AST Parsing and Syntax Validation

The compilation pipeline begins by converting the target JavaScript function into an Abstract Syntax Tree using an internal parser (Acorn). During this phase, gpu.js traverses the AST nodes to evaluate whether the code can map directly to typed, parallelized GLSL primitives.

Graphics hardware requires strictly typed variables, deterministic memory allocations, and linear execution flows. If the AST visitor encounters a node that cannot be mapped to equivalent shader code—such as closures, dynamic property lookups, or non-numeric object types—it marks the node as illegal.

Compile-Time Errors and Rejection

When configured strictly for GPU execution (such as setting the kernel mode to gpu or webgl), encountering unsupported syntax results in an immediate compilation failure. Rather than silently failing or emitting invalid GLSL code that crashes the GPU driver, gpu.js throws a runtime JavaScript exception.

These exceptions typically detail the exact line, column, and unsupported syntax construct. Common constructs that immediately trigger compilation errors include:

  • Complex Objects and Prototypes: Custom JavaScript classes, non-primitive objects, and prototype method calls.
  • Recursion: Functions that call themselves, as most GPU shading languages forbid dynamic call stacks.
  • Dynamic Standard Library Functions: Built-in methods outside of the supported mathematical utilities, such as Array.prototype.map(), String manipulations, and JSON.parse().
  • Dynamic Memory Allocation: Instantiating arrays with variable lengths inside the kernel body.

Dynamic Typing and Loop Constraints

Shaders require explicit static typing. When gpu.js processes variables, it attempts type inference based on assignment and usage. If a variable changes its type dynamically during execution (e.g., starting as a number and later becoming an array or boolean), the AST validator rejects it.

Similarly, loops are closely scrutinized. While standard for loops with constant or uniform-bound iterations translate cleanly to GLSL, while loops with non-deterministic exit conditions or unbounded execution can fail validation to prevent infinite loops on the graphics hardware.

Automatic CPU Fallback

By default, gpu.js operates in an automatic mode that prioritizes execution continuity over strict hardware acceleration. If a kernel fails to compile due to an unsupported JavaScript construct or hardware limitation, the library catches the compilation error internally and routes execution to the CPU.

In this fallback state, gpu.js runs the original JavaScript function within the standard V8 or browser JavaScript engine using multi-threaded Web Workers or basic CPU loops. While this ensures that unsupported syntax executes without breaking application flow, it bypasses the GPU entirely, resulting in standard JavaScript execution speeds rather than hardware-accelerated performance.
