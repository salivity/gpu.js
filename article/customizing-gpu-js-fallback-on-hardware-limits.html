Customizing GPU.js Fallback on Hardware Limits

GPU.js accelerates browser computations by compiling JavaScript functions into WebGL shaders, but hardware constraints like memory limits or unsupported features can trigger execution failures. Developers can customize this fallback behavior through execution mode configurations, capability checks, and custom error-handling routines. While GPU.js provides a built-in CPU fallback, relying solely on its automatic transpiler is often suboptimal, making explicit control essential for production applications.

Understanding Default Fallback in GPU.js

By default, GPU.js evaluates whether WebGL is supported in the host environment. If hardware acceleration is unavailable, or if a kernel fails to compile due to driver issues, GPU.js automatically re-runs the logic using pure JavaScript on the CPU.

However, this automatic fallback only handles basic availability and compilation errors. If a kernel exceeds specific hardware limits during execution—such as maximum texture sizes, uniform limits, or loop unrolling boundaries—the browser may throw a WebGL context loss or runtime exception rather than gracefully degrading.

Configuring Execution Modes

Developers can manage how aggressively GPU.js switches to the CPU by passing options to the constructor or the kernel creation call:

const gpu = new GPU({
  mode: 'gpu' // Options: 'gpu', 'cpu', or undefined (auto)
});
  • Auto (Default): Tries WebGL2, falls back to WebGL1, then falls back to CPU.
  • gpu: Enforces GPU execution and throws an error if WebGL fails, preventing silent performance degradation.
  • cpu: Forces standard JavaScript execution, which is useful for testing or benchmarking against hardware runs.

By setting mode: 'gpu', developers prevent the library from silently falling back to a slow CPU path, allowing them to catch exceptions and trigger an application-specific fallback.

Implementing Custom Fallback Logic

To handle cases where data dimensions exceed the GPU's maximum texture size, developers should intercept execution using structured error handling:

function executeTask(data, width, height) {
  try {
    const gpu = new GPU({ mode: 'gpu' });
    const kernel = gpu.createKernel(function(d) {
      return d[this.thread.x] * 2;
    }).setOutput([width * height]);

    return kernel(data);
  } catch (error) {
    console.warn('GPU execution failed or limits exceeded. Triggering custom fallback.', error);
    return runCustomCpuAlgorithm(data);
  }
}

Using a custom fallback function (runCustomCpuAlgorithm) rather than GPU.js's transpiled CPU mode is often preferred. The transpiled code maintains thread indexing matching WebGL pipelines, which introduces execution overhead compared to hand-optimized JavaScript or WebAssembly routines.

Proactive Hardware Limit Checking

Instead of relying on runtime failures, developers can inspect the underlying WebGL capabilities before dispatching large kernels. By querying properties like MAX_TEXTURE_SIZE or MAX_RENDERBUFFER_SIZE via a temporary WebGL context, the application can determine whether to:

  1. Execute on the GPU in a single pass.
  2. Chunk the dataset into smaller sub-arrays (tiling) that stay within texture limits.
  3. Divert the payload directly to a Web Worker or WebAssembly module to prevent blocking the main thread.

Controlling fallback behavior in this manner ensures reliable cross-device performance, preventing silent browser lockups when complex calculations exceed hardware specifications.
