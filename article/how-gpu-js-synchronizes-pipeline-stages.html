How GPU.js Synchronizes Pipeline Stages

This article explains how the gpu.js library achieves data synchronization across multi-stage kernel pipelines without requiring explicit barrier commands. By compiling JavaScript functions into WebGL fragment shaders and passing intermediate data as textures, gpu.js relies on the WebGL state machine, implicit driver-level hazard tracking, and texture ping-ponging. This architecture eliminates CPU-GPU transfer bottlenecks and automatically preserves memory coherency across sequential execution stages.

WebGL Abstraction and Kernel Pipeline Execution

Under the hood, gpu.js operates predominantly on top of the WebGL API. Instead of utilizing general-purpose compute pipelines with shared memory grids, gpu.js maps compute tasks into standard 2D rendering passes. A compiled kernel function runs as a WebGL fragment shader, where computational output is written to an off-screen Framebuffer Object (FBO) backed by a 2D texture.

When the pipeline: true configuration is enabled, the result of a kernel is not read back to JavaScript using synchronous read operations like gl.readPixels(). Instead, gpu.js returns a texture reference that remains in GPU memory, allowing subsequent kernels to consume it directly.

Implicit Driver-Level Hazard Resolution

Traditional compute APIs (such as WebGPU, Vulkan, or OpenGL 4.3+) require developers to place explicit memory barriers (e.g., glMemoryBarrier) or execution pipeline barriers between write and read passes to prevent race conditions. WebGL 1.0 and WebGL 2.0 do not expose explicit memory barrier primitives.

gpu.js achieves synchronization without explicit barriers because of how WebGL draw calls and graphics drivers operate:

  1. Sequential Command Queue: WebGL API commands submitted by gpu.js are queued in strict sequential order within the execution context.
  2. Read-After-Write (RAW) Hazard Detection: When Kernel A completes rendering into a framebuffer texture, and Kernel B binds that same texture as an active sampler uniform (gl.bindTexture), the underlying GPU driver identifies the dependency between the previous write operation and the upcoming read operation.
  3. Implicit Flushing at Render Boundaries: The driver inserts internal hardware synchronization primitives or pipeline flushes before executing the subsequent draw call. This ensures all fragment write operations from Kernel A complete before Kernel B's texture fetch units access the data.

Texture Ping-Ponging and Coherency

Writing to and reading from the exact same texture within a single rendering pass creates undefined behavior in graphics hardware. To circumvent this, gpu.js manages texture allocation through ping-ponging:

  • Distinct texture allocations are maintained for reading and writing.
  • A kernel reads strictly from input textures bound as read-only sampler uniforms.
  • The kernel writes strictly to an FBO-attached target texture.
  • Upon completion of the step, references are swapped, transforming the previous output texture into the next input texture.

Because the memory targets for reading and writing never collide inside an active draw call, the pipeline prevents intra-pass race conditions.

Avoiding CPU-GPU Synchronization Bottlenecks

By retaining data in textures and relying on implicit hardware scheduling across draw passes, gpu.js keeps the pipeline fully asynchronous with respect to the CPU. The CPU thread queues the shader invocations sequentially and continues execution, while the GPU processes the sequence in-order via its native command stream. Synchronization only forces a pipeline stall if the application explicitly requests output back into JavaScript memory, at which point an explicit read operation triggers a GPU drain.
