Encode Floats to RGBA in WebGL1 with gpu.js

WebGL 1.0 often lacks native hardware support for rendering directly to 32-bit floating-point textures, as the necessary extensions are frequently missing or read-only on mobile and low-end devices. To bypass this constraint, gpu.js automatically falls back to standard 8-bit unsigned byte textures (gl.RGBA with gl.UNSIGNED_BYTE). It decomposes a 32-bit single-precision floating-point number into four 8-bit chunks within the fragment shader, assigning each byte to the Red, Green, Blue, and Alpha color channels. This article breaks down the mathematical and architectural process gpu.js uses to execute this encoding in environments lacking native bitwise operations.

The WebGL 1.0 Float Rendering Problem

In modern WebGL 2.0 or WebGL 1.0 with the WEBGL_color_buffer_float extension, shaders can write directly to floating-point render targets. However, baseline WebGL 1.0 only guarantees rendering output to 8-bit per channel framebuffers (RGBA8). Writing raw 32-bit numbers directly results in clamping between 0.0 and 1.0 or total data loss.

To preserve the full dynamic range and precision of computation results, gpu.js must serialize each 32-bit float into 4 bytes (32 bits total) and store them in the standard RGBA channels of the output framebuffer.

IEEE 754 Representation in GLSL ES 1.00

JavaScript and WebGL natively use IEEE 754 single-precision floating-point numbers. A 32-bit float consists of:

  • 1 bit for the sign (\(S\))
  • 8 bits for the biased exponent (\(E\), bias of 127)
  • 23 bits for the mantissa / significand (\(M\))

Modern shading languages provide bitwise operators (such as >>, &, and floatBitsToUint), but WebGL 1.0 relies on GLSL ES 1.00, which completely lacks bitwise operations and unsigned integers. As a result, gpu.js relies on pure arithmetic operations—such as powers of two, logarithms, floor functions, and modulo/fractional arithmetic—to separate the float into components.

The Step-by-Step Encoding Mechanism

When compiling a kernel function down to raw WebGL 1.0 GLSL, gpu.js appends an encoding function that runs just before writing to gl_FragColor.

1. Extracting the Sign

The shader checks if the value is negative using step(0.0, -value). If negative, the sign bit is marked as 1.0; otherwise, it is 0.0. The absolute value of the number is then used for subsequent steps.

2. Determining the Exponent

To extract the 8-bit exponent:

  • The shader takes the base-2 logarithm of the absolute value using floor(log2(absVal)).
  • It adds the IEEE 754 bias of 127 to this exponent.
  • Edge cases like 0.0, subnormal numbers, infinity, and NaN are handled with conditional checks to clamp or set appropriate predefined bit patterns.

3. Calculating the Mantissa

Once the exponent is known:

  • The value is divided by \(2^{\text{exponent} - 127}\), normalizing it into the range \([1.0, 2.0)\).
  • Subtracting \(1.0\) yields the fractional mantissa (\(0.0 \le M < 1.0\)).
  • The 23 bits of the mantissa are converted into an integer-like scalar by multiplying by \(2^{23}\) (\(8388608.0\)).

4. Splitting 32 Bits Across Four 8-bit Channels

The combined 32 bits (1 sign bit + 8 exponent bits + 23 mantissa bits) are divided across the four 8-bit color channels:

  • Red Channel (8 bits): Encodes the sign bit (1 bit) and the 7 most significant bits of the exponent.
  • Green Channel (8 bits): Encodes the least significant bit of the exponent (1 bit) and the 7 most significant bits of the mantissa.
  • Blue Channel (8 bits): Encodes the next 8 bits of the mantissa.
  • Alpha Channel (8 bits): Encodes the final 8 least significant bits of the mantissa.

Because GLSL ES 1.00 does not have bit-masking operators, gpu.js performs this division using floor(), fract(), and scalar division by \(256.0\).

Each extracted 8-bit component results in an integer value from 0 to 255. Before assigning the final output to gl_FragColor, each channel is divided by 255.0 to map the values into the normalized \([0.0, 1.0]\) range required by the WebGL rasterizer.

Readback and Reconstruction

When retrieving the computation result, gpu.js uses gl.readPixels() to pull the pixel data from the framebuffer into a JavaScript Uint8Array.

Because the RGBA channels in the framebuffer mirror the exact memory layout of an IEEE 754 float in memory:

  1. The returned Uint8Array contains the consecutive raw bytes of the 32-bit floats.
  2. JavaScript creates a new typed array view over the same underlying buffer: 
    const floatView = new Float32Array(uint8Buffer.buffer);
  3. The JavaScript engine interprets the 4-byte sequences directly as 32-bit floats without needing a software-based decoding loop on the CPU, achieving native-speed reconstruction of the GPU-calculated values.
