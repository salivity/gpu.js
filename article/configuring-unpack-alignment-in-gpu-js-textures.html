Configuring UNPACK_ALIGNMENT in GPU.js Textures

This article provides an overview of how the GPU.js library configures WebGL pixel storage modes—specifically UNPACK_ALIGNMENT—during texture initialization. It examines the internal WebGL state management GPU.js uses to serialize and transfer JavaScript arrays into GPU memory, explaining why tightly packed data structures require specific byte-alignment settings to prevent memory corruption and dimension mismatches.

The Role of UNPACK_ALIGNMENT in WebGL

When GPU.js compiles and executes kernel functions on the GPU, it relies on WebGL textures to store input matrices, arrays, and numerical values. WebGL provides the gl.pixelStorei() API to dictate how raw binary data from JavaScript TypedArrays or DOM elements is unpacked into these texture buffers.

By default, the WebGL specification sets UNPACK_ALIGNMENT to 4 bytes. This default assumes that each row of pixel data in memory begins on a byte boundary that is a multiple of 4. While this works seamlessly for standard 4-channel, 8-bit image formats like RGBA (where each pixel is 4 bytes), it introduces reading offsets and memory alignment exceptions when uploading arbitrary data shapes or custom data types.

How GPU.js Configures the Pixel Store

During texture setup within its WebGL backend routines, GPU.js overrides the default alignment using the following WebGL call:

gl.pixelStorei(gl.UNPACK_ALIGNMENT, 1);

GPU.js invokes this command on the active WebGL context prior to executing gl.texImage2D or gl.texSubImage2D. By setting the value to 1, GPU.js instructs the graphics driver to treat incoming memory as a strictly continuous byte stream, eliminating any expected byte padding at the end of data rows.

Why GPU.js Requires a 1-Byte Alignment

GPU.js processes arbitrary mathematical arrays and matrices that do not inherently adhere to 4-byte boundaries. Setting UNPACK_ALIGNMENT to 1 is critical for several structural reasons:

  1. Arbitrary Matrix Dimensions: Input matrices often have widths that, when multiplied by the component size, do not produce a total row length divisible by 4. Under a default 4-byte alignment, the driver expects padding bytes at the end of each row. Because standard JavaScript arrays and TypedArrays do not include this padding, WebGL misinterprets row offsets, reading past the end of the buffer or generating corrupted inputs.
  2. Custom Channel Packing: Depending on whether GPU.js is targeting WebGL 1 or WebGL 2, and depending on hardware support, it may pack data into single-component textures (like LUMINANCE or RED) or float-based textures via extensions like OES_texture_float. When using single-channel formats where each element represents an individual float or integer, strict 1-byte alignment ensures that individual rows are parsed accurately without assuming padding.
  3. Flat TypedArray Uploads: GPU.js normalizes nested multidimensional arrays into flat Float32Arrays or Int32Arrays before texture submission. Setting an alignment of 1 ensures that the GPU memory controller unpacks every consecutive value directly from the source buffer index without injecting row skips.

Texture Lifecycle and State Management

Within the GPU.js execution cycle, pixel store parameters are typically set globally during the creation of the backend context or reaffirmed directly before texture allocation routines:

  • Kernel Context Initialization: When a WebGLKernel or WebGL2Kernel instance prepares its execution context, base WebGL states are applied.
  • Texture Allocation (GLTexture): When binding an input argument or creating output textures, the Texture abstraction binds the target texture ID (gl.bindTexture), sets gl.pixelStorei(gl.UNPACK_ALIGNMENT, 1), and uploads the buffer.
  • Pixel Pack Symmetry: Alongside UNPACK_ALIGNMENT, GPU.js may also configure related flags (such as PACK_ALIGNMENT during gl.readPixels) to ensure that data read back from the framebuffer into JavaScript TypedArrays maintains identical byte continuity.

By enforcing an unpack alignment of 1 byte, GPU.js prevents data striding errors, guarantees compatibility with non-standard matrix dimensions, and ensures predictable data transfers between CPU and GPU memory buffers.
