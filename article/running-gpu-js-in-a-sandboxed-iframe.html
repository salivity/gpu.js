Running gpu.js in a Sandboxed iframe

Running gpu.js inside a sandboxed <iframe> requires granting specific security tokens and permissions to allow JavaScript execution, access to the WebGL or WebGPU rendering contexts, and the creation of worker threads. Because sandboxing defaults to the highest level of restriction, omitting the required attributes will prevent gpu.js from detecting hardware acceleration, compiling shaders, or outputting kernel computations. This guide outlines the exact sandbox directives and Permissions Policy flags necessary to maintain both security and performance.

Essential sandbox Attributes

The sandbox attribute on the <iframe> tag enforces a unique origin and disables all scripts by default. To run gpu.js, you must add the following tokens:

  • allow-scripts: This is strictly required. Without it, the browser blocks the execution of JavaScript, preventing gpu.js from loading, compiling, and running compute kernels.
  • allow-same-origin: While gpu.js can execute pure mathematical computations in an opaque (null) origin, allow-same-origin is typically required if your kernels read image textures from the host domain, interact with OffscreenCanvas, or instantiate Web Workers via Blob URLs. Warning: Combining allow-scripts and allow-same-origin allows the iframe to remove its own sandbox attributes if it is hosted on the exact same origin as the parent page. Host the iframe content on an isolated domain (or dedicated subdomain) to mitigate this risk.

Permissions Policy Requirements

Modern browsers restrict direct hardware access inside embedded frames via the Permissions Policy (allow attribute).

  • WebGPU Access (allow="webgpu"): If you are using a modern build of gpu.js that targets WebGPU instead of WebGL, access to the navigator.gpu interface is blocked inside cross-origin iframes unless explicitly granted using allow="webgpu".
  • Execution Timing and Scheduling: While not strictly a permission flag, ensure the iframe is not hidden via display: none or throttled by browser power-saving mechanisms, as some browsers will revoke or downgrade the WebGL context of completely hidden or out-of-viewport frames.

Example Implementation

To establish a functional environment for gpu.js computations, define the iframe with the appropriate permissions:

<iframe
  src="https://compute.yourdomain.com/gpu-runner.html"
  sandbox="allow-scripts allow-same-origin"
  allow="webgpu"
  title="gpu.js Computation Worker">
</iframe>

If your kernels only compute numeric data without reading textures or relying on same-origin workers, omit allow-same-origin:

<iframe
  src="https://compute.yourdomain.com/gpu-runner.html"
  sandbox="allow-scripts"
  allow="webgpu"
  title="gpu.js Computation Worker">
</iframe>

Context Creation and Fallbacks

Even with appropriate permissions, a sandboxed frame may occasionally fail to initialize hardware acceleration if the host browser enforces strict GPU process isolation. Inside the iframe script, configure gpu.js to gracefully handle context failure by allowing fallback execution modes:

const gpu = new GPU({
  mode: 'gpu', // Attempts WebGL/WebGPU first
  fallbackToCPU: true // Prevents total failure if the sandbox blocks the GPU context
});

Enabling CPU fallback ensures that computational tasks still complete successfully if the browser's security architecture restricts hardware-accelerated contexts under constrained memory or sandboxing rules.
