Pooling gpu.js Kernels in a Node.js Daemon

Running gpu.js in a continuous Node.js daemon requires careful resource management to prevent memory leaks, context crashes, and execution bottlenecks. This article details the essential best practices for pooling and managing gpu.js kernel instances, covering GPU context reuse, concurrency controls, dynamic sizing strategies, and worker isolation for long-running services.

Maintain a Single GPU Context

The underlying HeadlessGL (headless-gl) binding used by gpu.js in Node.js interacts directly with system graphics drivers, which strictly limit the number of active WebGL contexts (often between 8 and 16 per process). Instantiating new GPU() per task will quickly exhaust available contexts and trigger catastrophic process failures. Initialize a single, shared GPU instance at the application root and reuse it across the entire lifecycle of the daemon.

Precompile and Reuse Kernel Functions

Compiling a gpu.js kernel is an expensive operation that translates JavaScript into GLSL shaders and compiles them on the graphics driver. Never invoke gpu.createKernel() dynamically inside high-frequency request handlers. Instead, precompile all required kernels during application startup, or implement a lazy-loading registry where kernels are compiled on the first invocation and cached globally for subsequent execution.

Pool by Dimensional Signatures

gpu.js kernels require fixed output dimensions defined at creation time via .setOutput([x, y, z]). If your daemon processes datasets with variable dimensions, you cannot use a single static kernel. To manage dynamic workloads efficiently:

  • Bucket sizes: Round input matrices up to predefined bucket sizes (e.g., powers of two) and pad unused cells, allowing a small set of precompiled kernels to handle all requests.
  • Implement a keyed pool: If padding is not viable, build a pool that maps dimension signatures (e.g., kernel_1024x1024) to compiled kernel instances. Enforce a Least Recently Used (LRU) eviction policy combined with kernel.destroy() to ensure unused compiled variations do not permanently consume VRAM.

Control Concurrency with Task Queues

Graphics hardware processes tasks concurrently at the hardware warp/wavefront level, but dispatching multiple simultaneous WebGL calls from a single Node.js event loop creates driver contention and unpredictable latency. Instead of executing multiple pooled kernels concurrently, place execution requests into an in-memory queue (such as a FIFO queue or an abstraction like p-queue) configured to process one or two GPU dispatches at a time. This guarantees maximum throughput without saturating the graphics pipeline.

Clean Up Resources Explicitly

JavaScript's garbage collector only manages host RAM and is unaware of native VRAM allocations held by the GPU driver.

  • Explicitly release textures: If using .setPipeline(true) to pass textures between kernels without transferring data back to the CPU, manually call texture.delete() as soon as the intermediate data is no longer needed.
  • Explicitly destroy pooled kernels: When evicting a kernel from a pool, always call kernel.destroy(true) to release both the shader programs and associated native memory buffers.

Isolate GPU Processing in Worker Threads

Graphics drivers are prone to unrecoverable native segmentation faults when unexpected input or out-of-memory errors occur. In a critical Node.js daemon, run your gpu.js kernel pool inside a separate worker_threads instance or a dedicated child process. This architectural separation ensures that a driver crash will not take down the main daemon, allows you to restart the GPU subsystem cleanly, and prevents the synchronous driver overhead from blocking the primary Node.js event loop.
