Handling WebGL Context Loss in GPU.js

When a browser or operating system encounters memory pressure, driver crashes, or power state shifts, it can trigger a WebGL context loss that wipes all active GPU memory. In applications using gpu.js, this event clears compiled shaders, kernels, textures, and canvas states without automatically restoring them. Recovering from this failure requires an application to actively intercept the loss event, tear down stale GPU references, await context restoration, and recompile all compute kernels using retained application data.

1. Intercept the Context Loss Event

By default, the browser permanently destroys a lost WebGL context unless the application explicitly states its intention to recover. You must target the <canvas> element associated with your GPU instance and prevent the default browser behavior:

const canvas = gpu.canvas;

canvas.addEventListener('webglcontextlost', (event) => {
  event.preventDefault(); // Informs the browser that the app will handle restoration
  pauseApplication();     // Halt any active render or compute loops
}, false);

Calling event.preventDefault() tells the WebGL implementation to dispatch the webglcontextrestored event once GPU resources are available again.

2. Pause Operations and Clear Stale References

Do not attempt any compute operations while the context is lost, as calls to existing kernels will fail. Immediately halt any requestAnimationFrame loops or queued computational tasks. Clean up existing references to old gpu.js objects:

  • Flag the compute pipeline as inactive to reject incoming execution requests.
  • Dereference any cached Texture objects returned by previous kernel executions using pipeline: true, as their GPU-side memory is invalidated.
  • Call gpu.destroy() if you plan to fully recreate the main GPU instance, or clean up individual kernel instances.

3. Maintain a CPU-Side State Cache

Because all GPU-side textures and buffers are destroyed during context loss, the application must maintain a source-of-truth copy of essential input data and configurations in standard JavaScript memory (such as typed arrays or plain objects). Ensure your architecture retains:

  • Original input arrays and dimension matrices.
  • Functions used to define the gpu.js kernels.
  • Configuration options passed during kernel instantiation (such as output, pipeline, and precision).

4. Listen for Context Restoration

Attach a listener for the webglcontextrestored event on the canvas. This event indicates that the graphics driver has reallocated resources and a fresh WebGL context is ready:

canvas.addEventListener('webglcontextrestored', () => {
  reinitializeGPU();
}, false);

5. Reinitialize the GPU Instance and Kernels

Once the context is restored, the old shaders and WebGL program objects no longer exist. You must re-instantiate or rebind the execution environment:

  1. Recreate the GPU Instance: If the original instance was destroyed, create a new new GPU({ canvas }) instance utilizing the restored canvas element.
  2. Recompile Kernels: Re-declare and compile all required kernels using gpu.createKernel(...). Kernels must re-run through the gpu.js transpilation and shader compilation pipeline to exist on the new context.
  3. Re-upload Textures: If using pipelined textures, feed the CPU-cached data back through the newly compiled kernels or reconstruct the required input textures.

6. Resume Processing

After verifying that the kernels have recompiled and initial data textures are loaded back onto the GPU, unset the pause flag and restart your render or compute loop. Testing this recovery flow can be performed manually in Chromium-based browsers via the WEBGL_lose_context extension to ensure zero state degradation.
