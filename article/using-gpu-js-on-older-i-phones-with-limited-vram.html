Using gpu.js on Older iPhones with Limited VRAM

Running hardware-accelerated JavaScript using gpu.js on older Apple iPhones poses unique challenges due to unified memory constraints and strict WebGL allocation limits in iOS WebKit. Older devices, such as the iPhone 6s through iPhone X, share limited system RAM with the GPU, making them prone to silent browser crashes and dropped contexts when memory thresholds are exceeded. Understanding proper memory boundaries, kernel configuration, and lifecycle management is vital to maintaining stability.

Check WebGL Limits Before Kernel Creation

Before instantiating gpu.js, inspect the underlying WebGL capabilities of the device. Query the maximum texture size (MAX_TEXTURE_SIZE) and maximum viewport dimensions using standard WebGL context queries. Older iPhones often max out at lower limits (typically 4096px) compared to modern hardware. Ensure your kernel input dimensions and output array sizes do not exceed these hardware thresholds, as passing dimensions beyond hardware capabilities causes immediate kernel compilation failures.

Implement Dynamic Fallbacks to CPU Mode

Older iOS devices frequently terminate WebGL contexts instead of throwing catchable JavaScript exceptions when memory runs low. When initializing new GPU(), initialize with a fallback strategy:

let gpu;
try {
  gpu = new GPU({ mode: 'webgl2' });
} catch (e) {
  try {
    gpu = new GPU({ mode: 'webgl' });
  } catch (err) {
    gpu = new GPU({ mode: 'cpu' });
  }
}

Catching initialization errors early allows your application to degrade gracefully to CPU mode rather than crashing the entire mobile Safari tab.

Explicitly Destroy Kernels and Free Textures

JavaScript's garbage collector does not immediately reclaim GPU texture allocations. In gpu.js, running repeated calculations without cleanup rapidly accumulates uncollected WebGL textures in VRAM. Always store references to your kernels and explicitly call .destroy() on obsolete kernels, canvases, and texture outputs. Never define kernels inside an animation or operational loop; compile the kernel once during initialization and update only the argument values on each execution run.

Break Large Workloads into Small Chunks

iOS implements a strict watchdog timer on GPU operations. If a compute shader runs for too long on an older GPU, the operating system forcibly resets the graphics driver, resulting in a lost WebGL context. Break large matrix multiplications or intense data processing tasks into smaller 2D or 1D tiles. Process chunks sequentially using requestAnimationFrame or setTimeout to yield execution back to the browser, which keeps memory pressure low and resets the watchdog timer.

Listen for WebGL Context Loss

Memory pressure on older iPhones frequently prompts the system to revoke the WebGL context. Attach explicit event listeners to the WebGL canvas utilized by gpu.js:

const canvas = gpu.canvas;
canvas.addEventListener('webglcontextlost', (event) => {
  event.preventDefault();
  // Halt active calculations and release memory references
}, false);

canvas.addEventListener('webglcontextrestored', () => {
  // Reinitialize gpu.js kernels and re-upload state data
}, false);

Handling context loss programmatically prevents the application from throwing unhandled execution errors and allows the system to recover gracefully once VRAM pressure subsides.

Avoid Floating-Point Textures Where Possible

Older Apple GPUs have strict limitations regarding floating-point textures (such as OES_texture_float and EXT_color_buffer_float). When working with gpu.js, configure the kernel to output standard integers or disable high-precision buffers if full 32-bit floating-point precision is not strictly required. Avoiding high-precision float buffers significantly cuts the per-pixel memory footprint in half, mitigating potential out-of-memory termination events.
