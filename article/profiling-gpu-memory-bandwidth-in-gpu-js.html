Profiling GPU Memory Bandwidth in gpu.js

Profiling GPU memory bandwidth saturation during heavy matrix operations in gpu.js involves tracking the balance between data movement and arithmetic throughput. Because browser-based WebGL environments do not expose hardware performance counters directly to JavaScript, measuring memory bandwidth requires combining high-resolution client-side timings with native GPU profilers like NVIDIA Nsight or RenderDoc. This guide outlines how to calculate theoretical memory usage, measure effective bandwidth in gpu.js, and capture low-level saturation metrics through native diagnostic tools.

The Memory Bandwidth Bottleneck in Matrix Operations

In gpu.js, matrix multiplication (\(C = A \times B\)) maps computations to a WebGL fragment shader, treating matrices as textures. Naive matrix multiplication requires fetching an entire row of matrix \(A\) and a column of matrix \(B\) for every output element in \(C\).

For two \(N \times N\) 32-bit float matrices:

  • Naive Reads: \(2 \times N^3 \times 4\) bytes.
  • Writes: \(N^2 \times 4\) bytes.

When \(N = 2048\), naive operations pull approximately 68.7 GB of data across the GPU memory bus to produce only 16.7 MB of output. If the GPU's memory bus cannot feed the Execution Units (EUs) or Streaming Multiprocessors (SMs) fast enough, execution stalls, causing memory bandwidth saturation.

1. Measuring Effective Bandwidth in JavaScript

To isolate memory bandwidth bottlenecks from CPU-to-GPU data transmission, measure the execution step separately from data upload and readback.

Enable pipelining in gpu.js to retain intermediate results in VRAM as textures:

const gpu = new GPU();

// Pipeline mode prevents readback to CPU
const matMult = gpu.createKernel(function(a, b, size) {
    let sum = 0;
    for (let i = 0; i < size; i++) {
        sum += a[this.thread.y][i] * b[i][this.thread.x];
    }
    return sum;
})
.setOutput([2048, 2048])
.setPipeline(true);

const size = 2048;
const a = generateMatrix(size);
const b = generateMatrix(size);

// Warm-up execution to compile shaders and allocate textures
matMult(a, b, size);

// Timed execution
const start = performance.now();
const resultTexture = matMult(a, b, size);
// Force WebGL pipeline flush without pulling the entire array
resultTexture.toArray(); 
const end = performance.now();

const durationSeconds = (end - start) / 1000;
const totalBytesTransferred = ((2 * Math.pow(size, 3) * 4) + (Math.pow(size, 2) * 4));
const effectiveBandwidthGBs = (totalBytesTransferred / durationSeconds) / 1e9;

console.log(`Effective Bandwidth: ${effectiveBandwidthGBs.toFixed(2)} GB/s`);

If the achieved throughput plateaus well below your GPU's advertised peak bandwidth (e.g., 500 GB/s on an RTX 3070), the kernel is constrained either by texture cache misses or latency stalls from non-coalesced texture lookups.

2. Low-Level Profiling via Native Hardware Counters

Browser sandboxing hides hardware memory bus metrics. To capture metrics like VRAM throughput, DRAM read/write utilization, and cache-hit rates, you must attach an external profiler to the browser process.

Launching Chrome for Profiling

Launch Google Chrome with GPU sandboxing disabled and developer flags enabled:

chrome.exe --disable-gpu-sandbox --enable-privileged-webgl-extension --disable-direct-composition

Profiling with NVIDIA Nsight Systems / Graphics

  1. Open NVIDIA Nsight Graphics or Nsight Systems.
  2. Target the specific Chrome GPU process running your gpu.js script (found via Chrome’s Task Manager: Shift + Esc).
  3. Run a Trace during the matrix multiplication loop.
  4. Inspect the following counters:
    • VRAM Throughput % (DRAM Bandwidth): Values consistently above 80–90% indicate memory bus saturation.
    • L2 Cache Hit Rate: Low hit rates indicate that threads are constantly falling back to main VRAM rather than leveraging on-chip cache.
    • SM/Compute Throughput vs. Memory Throughput: If SM throughput is low (e.g., 20%) while Memory Throughput is high (e.g., 85%), your matrix kernel is entirely memory-bound.

Profiling with RenderDoc

  1. Launch Chrome through RenderDoc targeting the executable with the argument --gpu-startup-dialog.
  2. Attach RenderDoc to the spawned child GPU process PID.
  3. Capture the frame containing the gpu.js draw call (typically a glDrawArrays or glDrawElements call rendering a full-screen quad).
  4. Review the Resource Inspector to view texture layout, texture formats (RGBA32F vs. packed 8-bit channels), and memory bandwidth utilization per draw call.

3. Resolving Memory Bandwidth Saturation

If profiling confirms memory bandwidth saturation, implement these architectural fixes:

  • Pack Matrix Channels: gpu.js processes floating-point data. WebGL often handles RGBA floats more efficiently than single-channel textures. Packing 4 float elements per pixel reduces the required texture fetch calls by 75%.
  • Sub-Matrix Tiling: Restructure the kernel computation to process matrix blocks that fit directly into the L1/L2 texture cache, avoiding continuous high-latency roundtrips to global VRAM.
  • Eliminate Pipeline Extraction: Never call .toArray() in intermediate operations. Chain kernels using kernel.setPipeline(true) to keep memory allocations resident on the GPU.
