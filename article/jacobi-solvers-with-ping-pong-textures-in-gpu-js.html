Jacobi Solvers with Ping-Pong Textures in GPU.js

This article explains how to implement a Jacobi iterative solver for linear systems of equations using ping-pong textures in GPU.js. It covers the mathematical compatibility of the Jacobi method with GPU parallelism, details how the ping-pong technique circumvents WebGL read/write hazards, outlines the step-by-step implementation architecture, and addresses performance considerations when running numerical algorithms directly in the browser or Node.js.

The Jacobi Method and GPU Parallelism

The Jacobi iterative method solves a strictly diagonally dominant system of linear equations, represented in matrix form as \(Ax = b\). To find the vector \(x\), the algorithm begins with an initial guess \(x^{(0)}\) and computes successive approximations using the formula:

\[x_i^{(k+1)} = \frac{1}{a_{ii}} \left( b_i - \sum_{j \ne i} a_{ij} x_j^{(k)} \right)\]

Because computing \(x_i^{(k+1)}\) depends exclusively on the values from the preceding iteration \(x^{(k)}\)—unlike the Gauss-Seidel method, which uses partially updated values from the current iteration—every element in the new vector can be calculated independently and simultaneously. This independence makes the Jacobi method naturally suited for parallel execution across GPU cores.

The Need for Ping-Pong Textures

Under WebGL, which powers GPU.js, a shader cannot read from and write to the same memory buffer (texture) in a single pass. Attempting to do so causes a pipeline hazard and undefined behavior.

The ping-pong technique resolves this constraint by alternating between two memory buffers:

  1. Iteration 1: Kernel reads from Buffer A and writes to Buffer B.
  2. Iteration 2: Kernel reads from Buffer B and writes to Buffer A.
  3. The cycle repeats until the system converges or reaches the maximum iteration limit.

By swapping the input and output references at each step, data flows seamlessly through successive iterations without reading from the active write target.

Implementing the Solver in GPU.js

To implement this architecture in GPU.js, follow these core steps:

1. Enable Pipeline Mode

GPU.js provides a pipeline: true configuration mode. When enabled, kernel computations return WebGL texture objects rather than transferring raw JavaScript arrays back to CPU memory. Keeping textures on the GPU prevents costly CPU-GPU memory bus bottlenecks across iterations.

const gpu = new GPU();

const jacobiKernel = gpu.createKernel(function(A, b, xOld, n) {
    let sum = 0;
    const i = this.thread.x;

    for (let j = 0; j < n; j++) {
        if (j !== i) {
            sum += A[i][j] * xOld[j];
        }
    }

    return (b[i] - sum) / A[i][i];
}, {
    output: [n],
    pipeline: true,
    immutable: true
});

Setting immutable: true ensures that textures are preserved properly during swaps and not prematurely destroyed by GPU.js memory management.

2. The Iterative Ping-Pong Loop

Initialize the solution vector \(x\) as a texture and pass it alongside the static matrix \(A\) and vector \(b\). In each cycle, assign the output of the kernel back to the alternating variable:

let xCurrent = initialXTexture;

for (let k = 0; k < maxIterations; k++) {
    const xNext = jacobiKernel(matrixA, vectorB, xCurrent, n);
    
    // Release previous texture from memory to prevent leaks
    if (k > 0) {
        xCurrent.delete();
    }
    
    xCurrent = xNext;
}

// Read final result back to CPU
const result = xCurrent.toArray();

Performance and Implementation Considerations

  • Memory Bandwidth: For dense matrices, evaluating \(\sum a_{ij} x_j\) requires substantial texture lookups. For large systems (\(N > 2048\)), packing data into 2D float textures or 4-channel RGBA formats is necessary to fit within hardware texture dimensions.
  • Convergence Checks: Evaluating the residual \(\|Ax - b\| < \epsilon\) on every iteration on the CPU requires pulling data off the GPU, which ruins pipeline efficiency. Instead, run fixed iteration batches (e.g., 50–100 iterations) entirely on the GPU before transferring data once to check for convergence.
  • Precision: WebGL 1.0 environments may default to medium precision (mediump), which causes rapid divergence in iterative solvers. Ensure the target environment supports OES_texture_float and 32-bit floating-point operations.
