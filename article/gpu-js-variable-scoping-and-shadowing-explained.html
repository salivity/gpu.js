GPU.js Variable Scoping and Shadowing Explained

GPU.js converts standard JavaScript functions into WebGL-compatible GLSL (OpenGL Shading Language) shaders to run computations massively parallel on the GPU. When handling nested block scopes containing identical variable names—a concept known as variable shadowing—GPU.js relies on an internal Abstract Syntax Tree (AST) transpiler to prevent scope collisions, resolve ambiguity, and generate valid GLSL code. This article explains the underlying mechanism GPU.js uses to parse, track, and rename shadowed variables across nested blocks.

The JavaScript to GLSL Scoping Challenge

JavaScript (ES6+) supports block scoping via let and const, allowing a nested block (such as an if condition or a for loop) to declare a variable that shares its name with a variable in an outer block:

const kernel = gpu.createKernel(function() {
  let value = 10.0;
  if (this.thread.x > 5) {
    let value = 20.0; // Shadows the outer 'value'
  }
  return value;
});

While modern GLSL versions permit standard block scoping, target platforms (such as WebGL 1.0 or non-compliant mobile GPU drivers) often enforce strict limitations or exhibit driver-specific bugs when variables are redeclared in nested compound statements. To ensure cross-platform compatibility and maintain correct execution flow, GPU.js cannot always emit shadowed variable names verbatim.

AST Parsing and the Symbol Table

GPU.js begins execution by inspecting the stringified JavaScript kernel function and converting it into an Abstract Syntax Tree (AST) using Acorn. During the traversal of this tree, the transpiler manages a lexical environment structure:

  1. Scope Stack: A stack data structure tracks the current scope level. Entering a block statement pushes a new scope layer, while exiting pops it.
  2. Symbol Table: Each scope maintains an inventory of locally declared identifiers (variables, constants, and loop counters).
  3. Type and Context Tracking: Because GLSL is statically typed, GPU.js tracks the inferred types of these identifiers alongside their names.

Variable Renaming and Disambiguation

When the compiler encounters a VariableDeclaration in a nested block, it queries the active scope stack. If the declared identifier already exists in an ancestor scope, GPU.js treats the new declaration as a shadowed variable.

To prevent GLSL compilation errors and ensure deterministic behavior across diverse graphics drivers, GPU.js applies identifier mangling. The inner variable is rewritten to a unique internal name. This is typically accomplished by appending an incremented integer, scope depth identifier, or internal prefix (for example, transforming the nested value into _value_1 or a similar unique GLSL identifier).

All subsequent references (Identifier nodes) to value within that nested block are resolved to the newly generated identifier. Once the compiler exits the nested block, references to value fall back to resolving to the outer variable declaration.

Handling Loop Scopes

A common scenario involves re-declaring index variables across sibling or nested loops:

for (let i = 0; i < 10; i++) {
  // First loop scope
}
for (let i = 0; i < 10; i++) {
  // Sibling loop scope
}

In GLSL ES 1.0, re-declaring loop indices can trigger compiler warnings or errors depending on shader compiler implementations. GPU.js tracks loop iterators explicitly. If loop variables share identical identifiers in nested or sequential scopes, GPU.js guarantees that emitted loop variables receive unique names in the output shader string, decoupling the runtime GLSL identifiers from the original JavaScript names.

CPU Fallback Execution

GPU.js includes a CPU fallback mode for environments lacking WebGL support. In this mode, the kernel function is not compiled to GLSL; it executes as standard JavaScript inside a CPU-bound loop. In this scenario, scope resolution is not handled by GPU.js itself, but rather delegated directly to the host JavaScript runtime engine (such as V8 or SpiderMonkey), which natively respects standard ECMAScript lexical block scoping rules.
