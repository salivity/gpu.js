Computing RNN and LSTM Transitions with GPU.js

This article examines whether Recurrent Neural Networks (RNNs) and Long Short-Term Memory (LSTM) cell transitions can be computed using gpu.js. It covers the mathematical compatibility of recurrent units with WebGL-accelerated JavaScript, the architectural approach required to handle sequential time steps, the use of memory pipelining to maintain high throughput, and the practical constraints encountered when implementing recurrent models in a browser or Node.js environment.

Feasibility and Core Mechanics

GPU.js can compute RNN and LSTM cell transitions. At their core, both architectures rely heavily on linear algebra and element-wise operations, which are the exact primitives gpu.js compiles into WebGL fragment shaders.

A standard vanilla RNN cell transition requires computing:

\[h_t = \tanh(W_{hh} h_{t-1} + W_{xh} x_t + b)\]

An LSTM cell transition requires computing several gate equations and cell states:

  • Forget Gate: \(f_t = \sigma(W_f [h_{t-1}, x_t] + b_f)\)
  • Input Gate: \(i_t = \sigma(W_i [h_{t-1}, x_t] + b_i)\)
  • Candidate State: \(\tilde{C}_t = \tanh(W_c [h_{t-1}, x_t] + b_c)\)
  • Cell State: \(C_t = f_t \odot C_{t-1} + i_t \odot \tilde{C}_t\)
  • Output Gate: \(o_t = \sigma(W_o [h_{t-1}, x_t] + b_o)\)
  • Hidden State: \(h_t = o_t \odot \tanh(C_t)\)

All of these building blocks—dense matrix-vector multiplications, bias additions, element-wise products (Hadamard products), and non-linear activation functions (\(\tanh\) and sigmoid)—can be written in standard JavaScript and compiled into fast GPU kernels by gpu.js.

Handling the Temporal Dependency

The primary challenge of recurrent architectures on any GPU is the sequential dependency across time steps (\(t\)). Because step \(t\) strictly depends on the output of step \(t-1\), the temporal dimension cannot be flattened and computed in parallel.

To implement this in gpu.js:

  1. Per-Step Execution: Define kernels for the matrix transformations and element-wise gating logic.
  2. Sequential Loop in JavaScript: Execute a JavaScript for loop that iterates through the sequence length \(T\). In each iteration, call the kernel to compute the state transitions for the current time step.
  3. Spatial Parallelism: While you cannot parallelize across time, gpu.js parallelizes across the hidden state dimensions and across the batch size simultaneously during each step.

Optimizing with Texture Pipelining

A common performance bottleneck when executing iterative kernels in gpu.js is the overhead of transferring data between the CPU (JavaScript memory) and the GPU (VRAM). Reading the hidden state \(h_t\) back to the CPU after every step destroys performance.

To overcome this, use the pipeline: true setting in gpu.js. Enabling pipelining forces the kernel to output a WebGL texture instead of converting the result back to a JavaScript array. The returned texture representing \(h_t\) and \(C_t\) can be passed directly as an argument into the next kernel execution for step \(t+1\). Data is only pulled back to the CPU after the entire sequence has completed.

Practical Limitations

While fully functional, implementing RNN and LSTM transitions in gpu.js involves specific trade-offs:

  • Kernel Call Overhead: Launching GPU kernels from JavaScript introduces minor CPU overhead per call. For short sequence lengths or small hidden state sizes, this dispatch overhead may exceed the parallel processing benefit of the GPU.
  • Lack of Fused Operations: Native machine learning frameworks like PyTorch or TensorFlow utilize specialized CUDA/cuDNN fused kernels where an entire recurrent step is resolved in a single pass. In gpu.js, you must manually construct combined kernels to prevent multiple draw calls per time step.
  • Precision: WebGL environments often default to 16-bit floating point precision or handle 32-bit floats differently depending on hardware support, which can occasionally lead to numerical instability during long sequence rollouts.
