Fix gpu.js Pipeline Stalls in requestAnimationFrame

This article explains how to eliminate CPU-GPU pipeline stalls caused by synchronous .toArray() calls inside a WebGL requestAnimationFrame render loop when using gpu.js. Calling .toArray() forces the CPU to block while waiting for the GPU to flush its command queue and transfer data back to the host memory. By switching to gpu.js pipeline mode, utilizing graphical output kernels, or decoupling and throttling data readbacks, you can maintain a fluid 60+ frames-per-second render loop without freezing the main browser thread.

The Cause of the Stall

In gpu.js, running a kernel executes code across GPU threads. Under normal circumstances, GPU execution is asynchronous; JavaScript queues commands into the WebGL command buffer, and the GPU consumes them independently.

When you invoke .toArray() on a kernel result inside requestAnimationFrame, the engine executes an immediate GPU-to-CPU memory transfer (internally triggering blocking calls like gl.readPixels). This forces the CPU execution thread to halt until all scheduled GPU work finishes and the pixel data is transferred to JavaScript array structures. This synchronization eliminates CPU-GPU concurrency, introduces multi-millisecond frame spikes, and ultimately causes dropped frames.

Solution 1: Use Pipeline Mode to Keep Data on the GPU

If your calculation is intermediate and feeds into another computation or visual output, avoid pulling the data back to the CPU altogether. Enable pipeline mode so the kernel outputs a WebGL texture instead of raw array data.

const gpu = new GPU();

// Configure the kernel to output a texture
const computeKernel = gpu.createKernel(function(data) {
  return data[this.thread.x] * 2.0;
})
.setOutput([1024])
.setPipeline(true); // Retains output on the GPU

function loop() {
  // Returns a Texture object without forcing a CPU readback
  const textureResult = computeKernel(inputData);

  // Pass textureResult directly into another pipeline-ready kernel
  nextKernel(textureResult);

  requestAnimationFrame(loop);
}

requestAnimationFrame(loop);

By passing textures directly between kernels, the CPU never waits for memory copies, eliminating the synchronization stall completely.

Solution 2: Render Directly to a Graphical Canvas

If your requestAnimationFrame loop uses .toArray() solely to draw computed pixels to an HTML5 canvas, switch the kernel to graphical mode. Graphical kernels output straight to a WebGL canvas context using this.color(r, g, b, a) rather than returning numerical arrays.

const gpu = new GPU();

const renderKernel = gpu.createKernel(function() {
  // Direct pixel color assignment
  this.color(1.0, 0.0, 0.0, 1.0);
})
.setOutput([512, 512])
.setGraphical(true);

document.body.appendChild(renderKernel.canvas);

function loop() {
  renderKernel(); // Renders directly to the canvas on the GPU
  requestAnimationFrame(loop);
}

requestAnimationFrame(loop);

This bypasses all CPU-side image conversions, removing .toArray() and standard 2D canvas drawing calls (putImageData) from the loop.

Solution 3: Decouple and Throttle Essential CPU Readbacks

When host-side JavaScript must inspect GPU output (such as running physics checks or logic decisions), do not call .toArray() on every single animation frame. Decouple calculation frequency from display frequency using frame subsampling:

let frameCount = 0;
const READBACK_INTERVAL = 6; // Read data every 6th frame (~10Hz at 60fps)

function loop() {
  const resultTexture = computeKernel(inputData);

  if (frameCount % READBACK_INTERVAL === 0) {
    // Stall occurs only periodically rather than every single frame
    const cpuData = resultTexture.toArray();
    processPhysics(cpuData);
  }

  frameCount++;
  requestAnimationFrame(loop);
}

requestAnimationFrame(loop);

To optimize further, maintain a ping-pong buffer with two textures. Query the results of frame N - 1 while the GPU processes frame N. Providing a full frame of latency between the rendering command and the readback prevents the GPU pipeline from having to flush immediately, reducing the duration of the synchronous stall.
