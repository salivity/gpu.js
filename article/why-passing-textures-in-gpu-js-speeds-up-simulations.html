Why Passing Textures in GPU.js Speeds Up Simulations

Running complex simulations requires executing multiple sequential computational steps across thousands or millions of data points. When using GPU.js, chaining kernels by passing textures instead of raw JavaScript arrays yields massive performance improvements by eliminating the data-transfer bottleneck between the CPU and GPU. This article breaks down the mechanics of GPU memory pipelines, why conventional array returns degrade performance, and how texture passing keeps data localized on high-speed VRAM for maximum throughput.

The Host-to-Device Bottleneck

In standard GPU.js operations, a kernel accepts standard JavaScript arrays, uploads them to the GPU for execution, and converts the computed result back into an array on the host (CPU).

While the graphics processor can perform millions of parallel calculations in milliseconds, moving data across the PCIe bus between system RAM and GPU VRAM is exceptionally slow. In an iterative simulation—such as Conway’s Game of Life, fluid dynamics, or n-body gravity models—this round-trip data conversion occurs on every single frame or tick. The time spent serializing arrays, crossing the hardware bus, and deserializing the output completely negates the parallel processing advantages of the GPU.

How Passing Textures Works

GPU.js allows kernels to output and consume native WebGL textures directly by configuring the kernel with the pipeline: true option.

When a kernel outputs a texture:

  1. The kernel executes its parallel logic.
  2. The output values are written directly to a framebuffer bound to a GPU texture.
  3. Instead of reading back the pixel data to JavaScript, GPU.js returns a reference handle to that texture.
  4. The subsequent kernel accepts this texture handle as an input parameter, binding it directly as a sampler.

At no point does the underlying computational data leave the GPU's onboard memory.

Key Factors Driving the Speedup

1. Zero Bus Transfer Latency

By leaving the data in VRAM, you eliminate the PCIe transfer cost for intermediate simulation steps. The CPU acts merely as an orchestrator sending execution commands rather than a data carrier.

2. Avoidance of Readback Stalls

Reading pixels back from the GPU to the CPU is an inherently synchronous, blocking operation in WebGL (via gl.readPixels). This forces the GPU pipeline to flush and stall until all calculations finish and the data is copied to system memory. Textures allow kernels to run asynchronously without stalling the GPU pipeline.

3. Ultra-High VRAM Bandwidth

Modern graphics cards feature dedicated memory interfaces with hundreds of gigabytes per second of bandwidth. Feeding a texture from one compute pass into the next allows the GPU to read and write intermediate states at internal VRAM speeds, which are orders of magnitude faster than standard system memory transfers.

Best Practices for Simulation Loops

To maintain peak efficiency in an iterative loop:

  • Enable Pipelining: Set { pipeline: true } on all kernels involved in the intermediate simulation steps.
  • Keep Data on the GPU: Only convert textures back to JavaScript arrays using .toArray() when user interaction or data logging strictly requires CPU-side inspection.
  • Direct Canvas Rendering: If the goal is visual output, render the final texture directly to an HTML5 canvas using GPU.js's graphical mode, avoiding CPU readbacks entirely from initialization to display.
