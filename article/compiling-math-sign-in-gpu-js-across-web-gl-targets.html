Compiling Math.sign in gpu.js Across WebGL Targets

This article provides an overview of how the gpu.js compiler translates the JavaScript Math.sign() method into executable OpenGL Shading Language (GLSL) code. It explores the abstract syntax tree (AST) traversal, type inference, and the specific differences between the WebGL 1 (GLSL ES 1.00) and WebGL 2 (GLSL ES 3.00) compilation targets.

AST Parsing and Function Resolution

When a kernel containing Math.sign() is compiled, gpu.js parses the JavaScript source into an Abstract Syntax Tree (AST) using a JavaScript parser. During the traversal phase, the compiler's AST-to-GLSL translator identifies Math.sign(x) as a member call expression targeting a standard JavaScript built-in.

Rather than emitting a JavaScript runtime call, gpu.js maps this expression to the native GLSL equivalent, which is the built-in sign() function. The input argument is evaluated recursively to resolve nested expressions and enforce appropriate shader type casting before emitting the final GLSL string.

WebGL 1 (GLSL ES 1.00) Compilation

Under the WebGL 1 profile, shaders are bound to the GLSL ES 1.00 specification. This profile imposes strict constraints on typing, variable precision, and built-in functions:

  1. Floating-Point Enforcement: GLSL ES 1.00 provides genType sign(genType x) solely for floating-point vectors and scalars. Because integers cannot be passed to sign() natively in GLSL ES 1.00, gpu.js ensures that arguments fed into Math.sign() are implicitly or explicitly cast to floats (e.g., sign(float(x))).
  2. Precision Qualification: WebGL 1 requires explicit float precision definitions in fragment shaders. gpu.js prefixes generated kernels with standard precision directives (typically precision highp float; with fallbacks to mediump), ensuring that calculations within sign() maintain consistent floating-point fidelity across mobile and desktop GPUs.
  3. Absence of Native Bitwise/Integer Types: Because WebGL 1 kernels emulate integer operations through floating-point math, Math.sign() outputs are strictly treated as float targets, emitting values as 1.0, 0.0, or -1.0.

WebGL 2 (GLSL ES 3.00) Compilation

When targeting WebGL 2, gpu.js emits GLSL ES 3.00 code. This target allows for a more direct and performant mapping:

  1. Integer Overloads: GLSL ES 3.00 adds overloaded variants for sign(), supporting both signed integers (int sign(int x)) and standard floats (genType sign(genType x)). The compiler can leave integer types intact without injecting redundant float conversion instructions.
  2. Strict Typings and Return Handling: Because GLSL 3.00 features strict type matching, gpu.js aligns the return type of sign() directly with the target variable’s inferred type within the kernel AST, reducing overhead caused by type conversions.

Semantic Differences with JavaScript

While gpu.js maps Math.sign directly to GLSL's built-in sign(), hardware execution introduces subtle divergences from pure ECMAScript specifications:

  • Signed Zero: In JavaScript, Math.sign(-0) returns -0. In GLSL across both WebGL profiles, sign(0.0) or sign(-0.0) returns 0.0 per IEEE-754 hardware implementations, without preserving the negative sign flag.
  • NaN Handling: Math.sign(NaN) produces NaN in JavaScript. In WebGL, operations yielding NaN can produce undefined hardware-specific results or flush to zero depending on the GPU implementation.

Through target-specific syntax generation and type management, gpu.js allows developers to write standard JavaScript Math.sign() calls while generating optimal, profile-compliant GLSL instructions for both WebGL 1 and WebGL 2 pipelines.
