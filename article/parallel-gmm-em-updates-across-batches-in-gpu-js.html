Parallel GMM EM Updates Across Batches in GPU.js

Gaussian Mixture Model (GMM) Expectation-Maximization (EM) updates can be parallelized across batches in gpu.js, but performance depends on how the algorithm is split across GPU kernels. While the Expectation step (E-step) is embarrassingly parallel and ideally suited for gpu.js, the Maximization step (M-step) involves data reduction operations that encounter limitations due to the underlying WebGL architecture.

Parallelizing the Expectation Step (E-Step)

The E-step calculates the responsibility that each Gaussian component holds for each data point. This calculation requires evaluating the multivariate Gaussian probability density function for every sample and normalizing the results across components.

Because each data point's responsibility calculation is independent of all others, this step is easily parallelized across both samples and batches. In gpu.js, you can define a kernel with a 2D or 3D output dimension:

  • Dimension X: Sample index within a batch.
  • Dimension Y: Batch index.
  • Dimension Z: Gaussian component index.

By passing data as 2D textures or flattened arrays, gpu.js computes the log-likelihood and responsibility matrices simultaneously across all samples and batches in parallel.

The Challenge of the Maximization Step (M-Step)

The M-step updates the parameters—means, covariances, and mixing weights—by aggregating the responsibilities across all samples within a batch. This requires summation reductions over the batch size.

gpu.js compiles JavaScript functions into WebGL fragment shaders, which introduces two constraints:

  1. No Shared Memory or Atomics: Unlike WebGPU or CUDA, WebGL shaders cannot use thread-level shared memory or atomic add operations. A thread cannot directly accumulate values into a single memory address.
  2. Ping-Pong Reductions: To sum values entirely on the GPU, you must implement multi-pass reduction kernels (logarithmic tree reductions), iteratively rendering down to smaller textures until a single aggregated value per batch remains.

Because multi-pass reductions introduce shader pass overhead, full GPU execution of the M-step can be slow for small-to-moderate batch sizes.

Recommended Implementation Approaches

1. The Hybrid Approach (GPU E-Step, CPU M-Step)

For small to medium batch sizes, the most practical implementation executes only the E-step on the GPU:

  • GPU: Compute the responsibilities for all samples across batches in parallel.
  • Data Transfer: Read the responsibility matrix back to the CPU via kernel() execution.
  • CPU: Compute the summations for updated means, covariances, and weights on the CPU using fast typed arrays, then pass the updated parameters back into the next GPU iteration.

This circumvents the need for complex reduction shaders while accelerating the most compute-heavy portion of the algorithm.

2. Pure GPU Batched Reductions

For very large datasets where reading data back to the CPU creates a memory bus bottleneck, you can perform parallel reductions inside gpu.js:

  • Structure the reduction kernel to sum chunks of responsibilities per batch over multiple iterations.
  • Maintain the batch index as an independent axis during the reduction passes so that separate batches do not interfere with one another.
  • Update the parameter textures directly in GPU memory to keep the EM loop self-contained.

Numerical Stability and Precision

When running GMM updates in gpu.js, standard WebGL textures default to 32-bit floating-point precision (or 16-bit on older devices). Evaluating multivariate Gaussians in high dimensions frequently causes underflow or overflow when calculating probabilities directly. To ensure numerical stability across parallel batches:

  • Implement the Log-Sum-Exp trick inside the gpu.js kernel to compute normalized responsibilities in log-space.
  • Add a small regularization term (shrinkage) along the diagonal of covariance matrices to avoid singularity during matrix inversion on the GPU.
