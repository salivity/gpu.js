How gpu.js Maps 1D Threads to a 2D GPU Layout

When running a 1D kernel in gpu.js, the library must bridge the gap between abstract 1D thread arrays and the underlying hardware constraints of WebGL, which requires rendering to 2D textures. This article explains how gpu.js calculates the internal 2D texture dimensions, transforms 2D fragment coordinates into linear thread indices inside the generated shader, and handles boundaries when packing 1D data into a 2D grid.

The WebGL Texture Limitation

Under the hood, gpu.js utilizes WebGL 1 or WebGL 2 to execute computations on the GPU. WebGL does not natively support arbitrary 1D compute buffers; instead, it executes fragment shaders over a 2D canvas and writes results to 2D textures bound to a framebuffer. Consequently, any output specified as a 1D array (e.g., output: [N]) must be mapped onto a 2D surface of dimensions \((W, H)\).

Calculating Texture Dimensions

To determine the width (\(W\)) and height (\(H\)) of the internal 2D texture, gpu.js checks the GPU's MAX_TEXTURE_SIZE capability via the WebGL context. The calculation generally follows a row-major packing strategy:

  1. Width (\(W\)): Set to \(\min(N, \text{MAX\_TEXTURE\_SIZE})\). If the requested output size \(N\) fits within the maximum single-dimension limit, the width is simply \(N\).
  2. Height (\(H\)): Set to \(\lceil N / W \rceil\). If \(N\) exceeds the maximum texture width, the grid wraps into multiple rows, incrementing the height to accommodate the remaining threads.

This creates the smallest rectangular texture grid that can contain all \(N\) requested threads.

Translating 2D Fragments to 1D Thread Indices

During execution, the GPU runs the compiled fragment shader for every pixel in the \(W \times H\) grid. The shader accesses its current pixel position using the built-in GLSL variable gl_FragCoord. Because gl_FragCoord references pixel centers (offset by 0.5), gpu.js generates GLSL code that rounds or floors these coordinates to obtain integer pixel coordinates:

int x = int(floor(gl_FragCoord.x));
int y = int(floor(gl_FragCoord.y));

To map these 2D coordinates back to the single thread index expected by the user kernel, gpu.js applies standard linear indexing:

int threadIndex = y * textureWidth + x;

Within the context of your JavaScript kernel function, this calculated threadIndex is injected as this.thread.x. For 1D outputs, this.thread.y and this.thread.z are omitted or default to 0.

Handling Overflows and Boundaries

Because texture dimensions are rectangular, the total capacity \(W \times H\) may exceed the requested 1D thread count \(N\). To prevent extra pixels from calculating invalid data or corrupting memory, gpu.js injects boundary guard checks directly into the preamble of the fragment shader:

if (threadIndex >= totalOutputLength) {
    discard;
}

If a thread falls outside the range of \(N\), the discard directive halts shader execution for that fragment, ensuring no invalid writes occur.

Data Readback and Formatting

Once computation completes, the 2D texture data is read back to the CPU using WebGL's gl.readPixels(). This returns a flattened typed array extracted row-by-row. Because the internal layout was arranged in row-major order, the resulting raw memory is already sequential. gpu.js then slices the array to the exact length \(N\), discarding any padding introduced by the 2D dimension rounding, and returns the result as a standard 1D JavaScript array or typed array.
