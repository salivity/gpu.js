Float32Array Byte Alignment in GPU.js Explained

This article examines how the gpu.js library manages byte alignment and memory layout when transferring Float32Array typed buffers from CPU memory to GPU memory. It details the underlying WebGL pixel store alignments, 2D texture dimensions, WebGPU buffer stride limits, and the zero-padding mechanisms used to prevent memory corruption during parallel computations.

Native 4-Byte Boundary Matching

A JavaScript Float32Array consists of 32-bit IEEE 754 single-precision floating-point numbers, where each element naturally occupies 4 bytes. Under WebGL and OpenGL specifications, memory transfers default to an unpack alignment constraint (gl.UNPACK_ALIGNMENT) of 4 bytes. Because every element in a Float32Array already adheres to a 4-byte boundary, standard scalar transfers avoid the fractional offset misalignments common with smaller data types like Int8Array or packed 24-bit RGB structures.

Texture Packing and Row Alignment in WebGL

Because WebGL 1 and standard WebGL 2 contexts lack universal support for arbitrary compute storage buffers (SSBOs), gpu.js encodes array inputs into 2D textures. Data transfer to the GPU occurs via calls such as gl.texImage2D or gl.texSubImage2D.

When passing a Float32Array to a texture, WebGL drivers require that each row of pixel data begins at an address that is a multiple of the context's unpack alignment. gpu.js ensures safety across diverse hardware by explicitly setting:

gl.pixelStorei(gl.UNPACK_ALIGNMENT, 1);

Setting UNPACK_ALIGNMENT to 1 byte removes the requirement that row strides terminate on 4- or 8-byte multiples. This permits arbitrary texture widths without triggering driver-level buffer overruns or misalignment errors when mapping 1D arrays into 2D texture coordinate spaces.

Dimension Calculation and Zero-Padding

Arbitrary-sized input arrays rarely fit into perfect square textures. When a 1D Float32Array must be mapped to a 2D texture grid, gpu.js determines the optimal power-of-two or rectangular dimensions (width and height) to host the elements.

If the capacity of the allocated 2D texture exceeds the length of the source Float32Array, trailing elements cause an incomplete final row. gpu.js prevents memory read faults by allocating an internal target buffer sized to the full dimension requirements, copying the source data, and padding the excess positions with zeros. This guarantees that the driver reads a buffer exactly matching the expected byte size of width × height × channels × 4 bytes.

WebGPU Buffer and Pitch Alignment

In its WebGPU backend, gpu.js interacts directly with GPUBuffer and GPUTexture abstractions rather than WebGL textures. WebGPU imposes rigid hardware-level alignment constraints:

  1. Copy Buffer to Texture Constraints: The bytesPerRow attribute when copying data between buffers and textures must be a multiple of 256 bytes.
  2. Uniform and Storage Offsets: Dynamic buffer offsets must align to the device’s minStorageBufferOffsetAlignment (often 256 bytes).

To satisfy these constraints, gpu.js computes the minimum row pitch that satisfies the 256-byte boundary. If the byte width of the Float32Array row does not cleanly divide by 256, gpu.js injects stride padding into the array buffer before issuing the writeBuffer or copy commands. Shaders are then compiled with indexing arithmetic that accounts for this stride, ignoring the padding bytes during kernel execution.

Fallback Packing for Unsupported Float Textures

On platforms where floating-point textures (OES_texture_float or WebGL2 EXT_color_buffer_float) are not natively writable or readable, gpu.js falls back to encoding 32-bit floats into standard 8-bit RGBA channels. In this mode, each 4-byte float is mathematically split across four 1-byte unsigned integers using bitwise operations and reassembled within the shader code. Because this fallback produces a four-channel unsigned byte array, it naturally aligns to the default 4-byte texture read requirements, avoiding byte offset errors on restricted mobile hardware.
