Computing Velocity Obstacles Using GPU.js

Crowd simulation steering vectors based on Velocity Obstacles (VO) can be computed concurrently using gpu.js. Because each agent’s collision-avoidance calculations are largely independent during a single simulation step, the algorithm maps directly to GPU data-parallel architectures. This article examines the feasibility of computing VO-based steering in WebGL via gpu.js, explains how to structure agent data for shader execution, and outlines the architectural constraints and performance trade-offs involved.

Parallelizing Velocity Obstacles on the GPU

The Velocity Obstacle algorithm and its derivatives—such as Reciprocal Velocity Obstacles (RVO) and Optimal Reciprocal Collision Avoidance (ORCA)—determine a safe steering velocity for an agent by projecting potential collisions into velocity space. For an individual agent, calculating this vector requires testing candidate velocities against the positions, velocities, and radii of surrounding neighbors.

This workload is embarrassingly parallel across the agent population. In a typical central processing unit (CPU) implementation, updating \(N\) agents requires iterating sequentially through each entity. With gpu.js, the update loop is compiled into a WebGL compute shader where each GPU thread corresponds to a single agent index (this.thread.x). The thread evaluates the geometric collision cones generated by surrounding entities and computes an optimal, collision-free steering vector simultaneously for thousands of agents.

Implementation Structure in gpu.js

To implement VO steering in gpu.js, simulation data must be adapted to conform to the functional subset of JavaScript supported by the compiler:

  1. Data Layout: GPU kernels cannot access complex objects or references. Positions, velocities, and agent radii must be flattened into typed arrays (such as Float32Array) or 2D textures. For example, positions can be passed as an array of 2D coordinates [x0, y0, x1, y1, ...].
  2. Kernel Execution: A kernel is configured with dimensions matching the total agent count:

  3. Sampling vs. Optimization: Pure ORCA uses linear programming to find the optimal velocity, which can be branch-heavy for GPU shaders. A more GPU-friendly approach in gpu.js is sampling-based VO, where a fixed number of candidate velocity vectors are evaluated across fixed iterations, minimizing divergence across shader warps.

Neighbor Search Considerations

The primary computational bottleneck in crowd simulation is spatial partitioning:

  • All-to-All Comparison (\(O(N^2)\)): For simulations under 2,000 to 5,000 agents, brute-force checking every agent against all other agents inside the GPU kernel is often faster than managing dynamic structures on the CPU, as GPU compute pipelines handle uniform loops with high throughput.
  • Spatial Hashing: For larger crowds, sorting agents into a uniform 2D grid allows each thread to query only nearby grid cells. Because gpu.js lacks dynamic memory allocation and pointers, spatial grids must be pre-flattened into static lookup textures before dispatching the compute pass.

Performance Bottlenecks and Limitations

While computing VO steering concurrently in gpu.js yields significant speedups over single-threaded JavaScript, developers must manage specific constraints:

  • CPU-GPU Data Transfer: Transferring position and velocity arrays back and forth between the CPU and the GPU every frame incurs high overhead via WebGL readPixels. For maximum efficiency, simulations should maintain state within GPU textures across consecutive simulation steps.
  • Lack of Dynamic Branching: Recursive spatial trees (like KD-trees) are incompatible with gpu.js. Algorithms must rely on fixed-size loops and constant iteration counts.
  • Numerical Precision: WebGL implementations may default to medium precision depending on hardware support. Critical collision boundaries in dense crowds require ensuring 32-bit floating-point precision is explicitly enabled.
