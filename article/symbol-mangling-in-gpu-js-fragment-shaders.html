Symbol Mangling in GPU.js Fragment Shaders

GPU.js compiles JavaScript functions into WebGL fragment shaders to execute high-performance parallel computations on the GPU. Because WebGL requires valid, strictly typed GLSL (OpenGL Shading Language), GPU.js must prevent identifier clashes between JavaScript variable names, GLSL built-in keywords, user-defined helper functions, and internal runtime uniforms. It accomplishes this through an Abstract Syntax Tree (AST) translation pipeline that parses variable scopes, maps identifiers, and applies deterministic prefixing to ensure symbol isolation.

AST-Driven Variable Renaming

During kernel compilation, GPU.js passes the JavaScript kernel function through an AST parser. The parser identifies every variable declaration, parameter, and reference within the code. Instead of directly injecting raw variable names into the final GLSL string, the compiler builds a symbol table that tracks local scopes. When an identifier is encountered, GPU.js checks it against a dictionary of GLSL reserved words (such as vec2, texture2D, precision, or sampler2D). If a variable name collides with a GLSL keyword or a WebGL internal construct, the compiler renames the identifier using an internal naming pattern, ensuring the generated GLSL remains syntactically valid.

Parameter and Uniform Prefixing

Kernel inputs and environment state must be transferred from the CPU to the GPU as WebGL textures or uniforms. To prevent an input parameter like width or data from colliding with built-in shader properties or internal math routines, GPU.js prefixes and namespaces kernel arguments.

Arguments defined in the JavaScript kernel signature are converted into standardized uniform identifiers (typically prepended with internal namespace indicators like user_). When the kernel body references these inputs, the AST compiler automatically rewrites the read operations to target the corresponding uniform or texture lookup function, creating a strict boundary between user inputs and shader mechanics.

Sub-Function Namespacing and Isolation

GPU.js allows developers to register custom JavaScript helper functions via the addSubFunction() API. In a standard WebGL fragment shader, all functions reside in a flat, global namespace. To prevent two sub-functions with identical helper variables from interfering with each other—or colliding with the primary kernel logic—GPU.js performs signature and variable transformation:

  1. Unique Function Signatures: Sub-functions are declared with sanitized identifiers, stripping out invalid characters and qualifying function names where necessary to avoid native GLSL clashes.
  2. Local Scope Encapsulation: Variables declared inside sub-functions are isolated to their local function body. The translator tracks the call tree so that locally declared identifiers do not leak into the global shader scope.
  3. Texture Fetch Helpers: Mathematical operations and array lookups are often replaced by synthetic GLSL helper routines (such as custom float unpacking functions). These auto-generated routines use reserved internal prefixes, ensuring that user logic never accidentally overrides an essential memory-access function.

Contextual Thread Mapping

Special runtime properties—such as this.thread.x, this.thread.y, and this.output—do not exist in native GLSL. GPU.js translates accesses to the this context into internally managed GLSL expressions derived from gl_FragCoord and predefined uniform bounds. By replacing these property lookups during the AST traversal phase, GPU.js eliminates the need for dynamic property evaluation, neutralizing naming conflicts between user-defined object properties and native WebGL rendering coordinates.
