Handling Kernel Argument Changes in gpu.js

In gpu.js, executing a compiled kernel repeatedly with different inputs is a standard workflow for animations, scientific simulations, and iterative calculations. This article explains how gpu.js processes updated arguments between consecutive kernel invocations, contrasting how it handles primitives, dynamic arrays, textures, and immutable constants under the hood.

The WebGL Pipeline and Argument Binding

When a kernel is declared using gpu.createKernel(), gpu.js compiles the provided JavaScript function into a WebGL GLSL shader program. Because WebGL shader compilation is computationally expensive, gpu.js does not recompile the shader when kernel arguments change on subsequent calls. Instead, it rebinds the incoming values to the existing WebGL program using GLSL uniforms and texture memory.

Primitive Types (Numbers and Booleans)

Primitive arguments—such as floats, integers, and booleans—are treated as GLSL uniforms.

When you invoke a kernel consecutively with different primitive arguments:

  1. gpu.js inspects the current values passed into the JavaScript wrapper.
  2. It calls the appropriate WebGL binding method (such as gl.uniform1f or gl.uniform1i).
  3. The GPU uses the updated uniform values during the subsequent draw call.

Because updating uniforms requires almost zero CPU-to-GPU overhead, changing primitive arguments between consecutive calls executes at near-native speed without pipeline stalls.

Arrays and Matrix Data

Large datasets like 1D, 2D, or 3D arrays cannot be passed via standard uniforms due to WebGL uniform buffer limits. Instead, gpu.js encodes array data into 2D WebGL textures.

When passing new arrays across consecutive invocations:

  • Consistent Dimensions: If the array dimensions remain identical to previous runs, gpu.js reuses the previously allocated WebGL texture and updates the pixel data using gl.texSubImage2D.
  • Altered Dimensions: If an array's length or dimension structure changes between invocations, gpu.js must reallocate the texture memory on the GPU to match the new dimensions. While it still does not recompile the shader, texture reallocation incurs a memory allocation penalty.
  • CPU-to-GPU Transfer Cost: Uploading raw JavaScript arrays to texture memory requires iterating over the arrays and packing them into typed arrays (such as Float32Array). For high-frequency loops, this serialization can become a CPU bottleneck.

Textures and Pipeline Mode

To eliminate the CPU-to-GPU upload cost between consecutive runs, gpu.js supports pipeline mode ({ pipeline: true }).

When pipeline mode is active, the kernel outputs a WebGL texture rather than serializing the result back into a JavaScript array. If the output texture of one invocation is passed directly as an argument to the next invocation:

  1. No CPU-to-GPU data transfer takes place.
  2. gpu.js simply binds the existing texture handle to the input texture sampler.
  3. The data remains entirely in GPU VRAM across consecutive runs.

Arguments vs. Constants

It is critical to distinguish between kernel arguments and kernel constants:

  • Kernel Arguments: Dynamic values passed to the invoked kernel function. Handled dynamically via uniforms and textures without shader recompilation.
  • Constants (this.constants): Static values declared in the kernel configuration object. These are hardcoded directly into the GLSL source code at compile time. Modifying a constant value requires destroying and recompiling the kernel, whereas changing an argument does not.
