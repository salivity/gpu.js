WebGL Max Texture Size and gpu.js Array Limits

WebGL relies on the host graphics hardware to allocate memory, establishing a hardware-dependent boundary known as the maximum texture size. This article explains how to determine WebGL's maximum texture size, typical limits across modern devices, and how gpu.js relies on texture encoding to process data, which directly restricts the dimensions and total volume of arrays you can compute on the GPU.

What Is the Maximum Texture Size in WebGL?

In WebGL, textures are limited by the underlying GPU hardware and driver implementation. The maximum width and height of a 2D texture can be queried using the WebGL API through the parameter gl.MAX_TEXTURE_SIZE:

const canvas = document.createElement('canvas');
const gl = canvas.getContext('webgl') || canvas.getContext('experimental-webgl');
const maxTextureSize = gl.getParameter(gl.MAX_TEXTURE_SIZE);
console.log(maxTextureSize);

Common values for gl.MAX_TEXTURE_SIZE depend on the device:

  • Older mobile devices: 2,048 or 4,096 pixels.
  • Standard laptops and modern mobile devices: 8,192 pixels.
  • Modern desktop GPUs: 16,384 pixels or higher.

This number represents the maximum allowed length for either side of a 2D texture (width or height).

How gpu.js Encodes Data into Textures

Because WebGL 1.0 and WebGL 2.0 operate as graphics APIs rather than native compute APIs (like WebGPU or CUDA), gpu.js achieves General-Purpose computing on GPUs (GPGPU) by mapping input arrays into 2D textures. Each element or set of elements in a JavaScript array is packed into the color channels (RGBA) of texture pixels, passed to a fragment shader, and rendered onto an off-screen frame buffer.

How the Limit Restricts gpu.js Arrays

The MAX_TEXTURE_SIZE parameter restricts gpu.js computations in several key ways:

1. Dimension Constraints

When passing multidimensional arrays (matrices) to a GPU kernel, gpu.js maps array dimensions directly to texture coordinates. If an input matrix has a width or height that exceeds the GPU's MAX_TEXTURE_SIZE, WebGL cannot allocate the texture, resulting in a WebGL runtime error or a kernel compilation failure. For example, on a system with a MAX_TEXTURE_SIZE of 8,192, a matrix with dimensions \(10,000 \times 2,000\) will fail because the width exceeds the hardware limit.

2. Total Array Capacity Limits

For large 1D arrays, gpu.js handles data by folding the flat array into a 2D grid. The maximum total number of elements that can be stored in a single texture allocation is mathematically bounded by:

\[\text{Maximum Elements} = \text{MAX\_TEXTURE\_SIZE} \times \text{MAX\_TEXTURE\_SIZE}\]

On a GPU with a limit of 4,096, a single texture can hold at most \(4,096 \times 4,096 \approx 16.78 \text{ million elements}\). On a system with a limit of 16,384, the theoretical maximum per texture is approximately \(268.4 \text{ million elements}\). Attempting to pass an array larger than this threshold triggers an out-of-bounds allocation error.

3. Output Dimensions

The same texture constraints apply to the kernel output. If the specified output size of a gpu.js kernel exceeds the hardware limit in any dimension (or the 2D packing capacity), WebGL fails to create the corresponding frame buffer or render target.

Working Around the Limit

To manage data sets that approach or exceed MAX_TEXTURE_SIZE:

  • Check Device Limits: Query gpu.kernel.features.maxTextureSize before dispatching large kernels to dynamically scale workload sizes based on the user's hardware.
  • Chunk Data (Tiling): Split large arrays or matrices into smaller tiles or batches that fit comfortably within the hardware bounds, execute the kernel iteratively, and assemble the results in JavaScript memory.
  • CPU Fallback: Utilize gpu.js's built-in CPU fallback mode for processing oversized arrays when GPU allocation limits cannot be met.
