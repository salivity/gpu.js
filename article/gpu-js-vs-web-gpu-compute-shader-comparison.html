GPU.js vs WebGPU: Compute Shader Comparison

This article explores the conceptual differences between gpu.js, a JavaScript-to-shader transpilation library, and native WebGPU compute shaders. While both technologies aim to run parallel computational workloads on the client GPU, they fundamentally diverge in architectural design, memory models, hardware abstraction, and developer control.

Core Abstraction vs. Native Hardware Access

The most fundamental contrast lies in their architectural level and design intent.

gpu.js is an abstraction library designed to simplify GPGPU (General-Purpose computing on Graphics Processing Units) for web developers. It allows developers to write standard JavaScript functions, which it parses at runtime using abstract syntax tree (AST) analysis and converts into WebGL fragment shaders. It abstracts away graphics concepts entirely, presenting the illusion of a multi-threaded JavaScript execution engine.

In contrast, WebGPU is a native browser API developed by the W3C to expose modern GPU capabilities (Vulkan, Metal, and Direct3D 12) directly to the web. Rather than hiding the GPU's nature, WebGPU provides first-class, explicit primitives for compute pipelines. It does not transpile JavaScript; instead, developers write native compute shaders in WebGPU Shading Language (WGSL) and orchestrate execution via command buffers, pipelines, and bind groups.

Pipeline Exploitation vs. Dedicated Compute Architecture

Because gpu.js is historically built on top of WebGL 1 and WebGL 2, it does not have access to native compute pipelines. WebGL is inherently a rasterization engine designed for drawing triangles to a screen. To perform calculations:

  • gpu.js encodes input arrays into 2D textures.
  • It renders a full-screen quad to trigger the fragment shader for every pixel.
  • It interprets each pixel as an array element, running the compiled JS logic inside the fragment stage.
  • It reads the results back into JavaScript by reading pixel data from the framebuffer.

WebGPU compute shaders bypass the rasterization pipeline completely. A compute pass in WebGPU does not use vertices, fragments, framebuffers, or render targets. Instead, it dispatches an arbitrary, multidimensional grid of threads (workgroups) that run directly on the GPU’s compute units. This eliminates the CPU and GPU overhead inherent in faking compute workloads through raster graphics.

Memory Models and Data Sharing

The contrast in memory architecture represents the largest functional gap between the two approaches.

In gpu.js, memory is restricted to what WebGL textures allow. Data structures must be flattened to fit into texture channels (RGBA). Furthermore, threads (fragment invocations) are completely isolated: a single fragment cannot read what an adjacent fragment is computing, nor can it share scratchpad memory. This severely restricts algorithms to "embarrassingly parallel" problems where outputs are entirely independent.

WebGPU introduces a modern memory model:

  • Storage Buffers: Structured, linear memory buffers supporting arbitrary data structures, structs, and arrays without texture packing hacks.
  • Shared Workgroup Memory: WebGPU exposes on-chip high-speed cache (var<workgroup>), enabling threads within the same workgroup to share intermediate states, cooperate on tasks, and perform efficient reductions.
  • Atomic Operations: WebGPU provides native atomic instructions for thread-safe read-modify-write operations on shared data, enabling locks, counters, and histograms that are impossible in gpu.js.

Execution Control and Synchronization

In gpu.js, execution is essentially a black box. The developer calls the kernel, and the library manages draw calls, texture binding, and synchronous or asynchronous readbacks. There is no fine-grained mechanism to coordinate how or when threads execute relative to one another.

WebGPU provides deterministic control over thread topology:

  • Computations are organized explicitly into workgroups and local workgroup sizes defined directly in WGSL (e.g., @workgroup_size(x, y, z)).
  • Developers explicitly manage synchronization points using barriers (such as workgroupBarrier()), which freeze execution until all threads in a workgroup catch up, preventing race conditions during parallel processing.

Ergonomics vs. Performance and Predictability

gpu.js prioritizes developer convenience over raw efficiency. It lowers the barrier to entry by removing the need to learn shader languages or GPU state machines. However, this convenience introduces substantial overhead: JavaScript AST parsing, texture serialization/deserialization, and reliance on WebGL pipeline workarounds that limit peak hardware utilization.

WebGPU prioritizes predictability, hardware parity, and maximum throughput at the expense of higher code complexity. Setting up a WebGPU compute task requires managing device adapters, pipeline layouts, bind group layouts, and asynchronous buffer mapping. In return, it unlocks the true computational ceiling of modern GPU hardware, providing a viable foundation for browser-based machine learning (such as WebLLM and ONNX Runtime Web), physics simulations, and massive data processing pipelines.
