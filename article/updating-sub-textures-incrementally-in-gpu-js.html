Updating Sub-Textures Incrementally in GPU.js

This article explains whether you can update sub-textures incrementally in GPU.js without re-uploading the entire data array. While GPU.js does not expose a native, high-level API for partial CPU-to-GPU data transfers (such as a direct wrapper for gl.texSubImage2D), incremental updates can be achieved either by mutating textures directly on the GPU using pipelined kernels or by dropping down to the underlying WebGL context.

The Native GPU.js Limitation

GPU.js abstracts WebGL texture creation and memory management to simplify parallel computing in JavaScript. When you pass a standard JavaScript array or typed array into a GPU.js kernel, the library automatically serializes the data, creates an internal WebGL texture, and uses gl.texImage2D to upload the entire buffer to the GPU.

Because the library handles input binding automatically, there is no high-level method (such as kernel.updateSubTexture(x, y, width, height, data)) to selectively write only a modified portion of a JavaScript array into an existing texture. Re-invoking a kernel with an updated JavaScript array forces a full re-upload of that array, introducing memory overhead and CPU-to-GPU bandwidth bottlenecks.

Method 1: Incremental Updates via GPU Memory (Pipelining)

If your goal is to update a portion of an existing texture without transferring the entire dataset from the CPU, you should keep the data on the GPU using kernel pipelining.

When you enable pipeline: true, a kernel returns a Texture object instead of reading pixels back to a CPU array. You can pass this output texture back into a subsequent kernel along with only the patch data and coordinates.

const gpu = new GPU();

// Kernel configured with pipeline enabled
const patchKernel = gpu.createKernel(function(baseTexture, patchTexture, offsetX, offsetY, patchWidth, patchHeight) {
  const x = this.thread.x;
  const y = this.thread.y;

  // Check if current thread falls inside the target sub-region
  if (x >= offsetX && x < offsetX + patchWidth &&
      y >= offsetY && y < offsetY + patchHeight) {
    return patchTexture[y - offsetY][x - offsetX];
  }

  // Preserve existing texture data
  return baseTexture[y][x];
})
.setOutput([1024, 1024])
.setPipeline(true);

In this architecture:

  1. The base data stays in GPU memory as a texture.
  2. Only the small patch array is uploaded from JavaScript.
  3. The GPU updates the sub-region internally, avoiding a full re-upload of the base data.

Method 2: Accessing the Underlying WebGL Context

For scenarios where high-frequency streaming of partial CPU data to the GPU is required, you can interact with the raw WebGL context managed by GPU.js via gpu.context.

  1. Extract Context and Texture: Use gpu.context to access WebGL functions and target the texture property of a GPU.js Texture instance.
  2. Execute Partial Upload: Call gl.texSubImage2D directly on the texture target.
const gl = gpu.context;

function updateSubRegion(targetTexture, xOffset, yOffset, width, height, pixelData) {
  gl.bindTexture(gl.TEXTURE_2D, targetTexture.texture);
  gl.texSubImage2D(
    gl.TEXTURE_2D,
    0,
    xOffset,
    yOffset,
    width,
    height,
    gl.RGBA,
    gl.UNSIGNED_BYTE,
    pixelData
  );
  gl.bindTexture(gl.TEXTURE_2D, null);
}

This bypasses GPU.js input handling completely, updating only the designated rectangular area directly in VRAM without creating duplicate allocations.

Conclusion

GPU.js does not provide an out-of-the-box mechanism for incremental CPU-to-GPU sub-texture uploads. If the updates are calculated dynamically, compute and merge them directly on the GPU using pipelined kernels. If you must send sub-arrays from the CPU to an active GPU.js texture, bypass the high-level API and invoke texSubImage2D via gpu.context.
