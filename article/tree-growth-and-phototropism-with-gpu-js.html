Tree Growth and Phototropism with GPU.js

Simulating tree branch growth and phototropism across thousands of individual nodes is entirely feasible in GPU.js, provided the hierarchical structure of a tree is adapted to a data-parallel architecture. While tree growth naturally relies on recursive, branching data structures that conflict with traditional GPU pipelines, flattening tree representations into parallel arrays allows GPU.js to execute both phototropic vector calculations and node updates across tens of thousands of elements concurrently.

The Architectural Challenge: Dynamic Hierarchies on the GPU

Tree growth algorithms, such as the space colonization algorithm or discrete bud-development models, depend on parent-child relationships and dynamic node allocation. Traditional JavaScript implementations use pointer-based object graphs where branches continuously subdivide and push new nodes to dynamic lists.

GPU.js compiles standard JavaScript functions into WebGL shaders, which cannot allocate dynamic memory or traverse unbounded pointer chains efficiently. To parallelize thousands of nodes:

  1. Pre-allocated Buffers: Memory must be reserved upfront as fixed-size 1D or 2D textures representing the maximum node capacity (e.g., 65,536 nodes).
  2. Flattened Node Structs: Properties must be split into parallel data arrays (or multi-channel textures):
    • positions: \([X, Y, Z]\)
    • directions: \([dX, dY, dZ]\)
    • attributes: \([ParentIndex, Age, ActiveStatus, BranchThickness]\)

Parallelizing Phototropism

Phototropism—the directional growth of plant organs in response to light—requires two computations per node: evaluating ambient light occlusion and calculating the directional growth vector.

1. Light Field Sampling

A purely local node computation does not account for self-shadowing (canopy occlusion). To parallelize this step, a voxelized light grid or an altitude/density map must be maintained. Each active node computes its local light availability by sampling the light direction against the density field. In GPU.js, this is structured as a kernel where each thread corresponds to a single node index, reading its own position, checking occlusion values, and returning an exposure scalar.

2. Vector Steering

Once light exposure is determined, calculating the phototropic response vector is completely decoupled and embarrassingly parallel:

\[\vec{V}_{\text{new}} = \text{normalize}\left((1 - w)\vec{V}_{\text{current}} + w\vec{V}_{\text{light}}\right)\]

Where \(w\) is the phototropic sensitivity weighted by light intensity and node age. GPU.js executes this vector transformation across all active nodes in a single draw pass.

Overcoming Node Spawning Bottlenecks

While calculating phototropism and extending existing nodes is straightforward in GPU.js, spawning new nodes poses a concurrency challenge. Shaders cannot directly invoke an append() operation without race conditions, as WebGL lacks atomic counter support in standard compute pipelines.

There are two primary patterns to manage branch creation in GPU.js:

  • Hybrid GPU-CPU Loop: Node positions, light sampling, and elongation vectors are computed on the GPU. The resulting array is read back to the CPU to evaluate branching logic, trigger new bud creation in the CPU-side registry, and write the updated state back to GPU buffers. While introduces read-back overhead, it easily handles complex structural rules.
  • Pure GPU Fixed-Stride Allocation: Each existing node reserves a fixed number of child slots in the buffer (e.g., binary branching allows index \(2i+1\) and \(2i+2\)). The GPU kernel activates these slots when specific biochemical or light thresholds are met, avoiding dynamic allocation entirely at the cost of memory density.

Performance Considerations in GPU.js

Simulating 10,000 to 100,000 branch segments in real-time requires minimizing texture-to-CPU readbacks. When GPU.js is configured to output directly to WebGL textures, chained kernels can compute:

  1. Light sampling kernel \(\rightarrow\)
  2. Tropism vector update kernel \(\rightarrow\)
  3. Position displacement kernel

By keeping the entire state cycle inside GPU memory, the simulation scales efficiently, allowing thousands of vegetative nodes to respond to dynamic light sources at interactive framerates.
