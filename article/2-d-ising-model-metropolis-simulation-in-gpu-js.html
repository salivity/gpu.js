2D Ising Model Metropolis Simulation in GPU.js

Simulating the 2D Ising model of ferromagnetism using Metropolis Monte Carlo steps is fully achievable in gpu.js, though it requires specific algorithmic adaptations to run correctly on parallel hardware. Because the standard Metropolis algorithm evaluates updates sequentially, direct parallelization causes race conditions and breaks thermodynamic equilibrium. By combining gpu.js kernels with a checkerboard (red-black) update scheme and pseudorandom number generation, developers can harness browser-based GPU acceleration to simulate large spin lattices at high frame rates.

The Parallelization Challenge

The standard Metropolis algorithm chooses a single spin, calculates the energy difference \(\Delta E\) that would result from flipping it, and accepts the flip with probability \(P = \min(1, e^{-\Delta E / k_B T})\). In a ferromagnet with nearest-neighbor interactions, the state of a spin depends directly on its four immediate neighbors (up, down, left, right).

If every thread on the GPU attempts to evaluate and flip its spin simultaneously, neighboring spins may flip at the same time based on outdated energy calculations. This violates detailed balance, invalidates the Boltzmann distribution, and yields unphysical artifacts such as checkerboard oscillations.

The Solution: Checkerboard Decomposition

To resolve race conditions, the 2D square lattice must be split into two independent sublattices, identical to the red and black squares on a chessboard:

  1. Sublattice A (Even parity): Sites where (x + y) % 2 == 0
  2. Sublattice B (Odd parity): Sites where (x + y) % 2 == 1

Because nearest-neighbor interactions only couple Sublattice A sites to Sublattice B sites, no two sites within the same sublattice interact with each other. Consequently, all sites in Sublattice A can be updated simultaneously in parallel without race conditions, followed by an update of all sites in Sublattice B.

Implementing in gpu.js

In gpu.js, a complete Monte Carlo step (sweeping the entire lattice) is executed using two sequential kernel passes:

  1. Pass 1 (Update Sublattice A): A gpu.js kernel runs across the entire grid. Inside the kernel, a condition checks if (this.thread.x + this.thread.y) % 2 == 0. If true, the thread calculates the local interaction energy from its four neighbors, computes \(\Delta E\), evaluates the Metropolis acceptance criterion, and writes the new spin (+1 or -1). If false, it returns the current spin unchanged.
  2. Pass 2 (Update Sublattice B): The kernel runs again, this time only evaluating sites where (this.thread.x + this.thread.y) % 2 == 1, using the newly updated values of Sublattice A.

To maintain optimal performance and avoid the expensive overhead of transferring arrays between CPU and GPU memory every step, the simulation should use gpu.js texture outputs (pipeline: true), allowing the lattice state to remain in GPU memory between updates.

Pseudorandom Number Generation on the GPU

The Metropolis algorithm requires uniform random numbers to evaluate the condition \(r < e^{-\Delta E / k_B T}\). Because standard JavaScript functions like Math.random() cannot be executed inside a GPU kernel, you must implement a deterministic hash-based pseudorandom number generator (PRNG) directly inside the kernel function. Fast PRNG algorithms like PCG, Xorshift, or integer hash functions (such as the Wang Hash) can take this.thread.x, this.thread.y, and an iteration step counter passed as a uniform to generate high-quality pseudorandom numbers per site per step.

Conclusion

Simulating the 2D Ising model via Metropolis Monte Carlo in gpu.js is both possible and efficient when using checkerboard decomposition and GPU-native PRNGs. This approach preserves the rigorous physics of the Metropolis criterion while leveraging WebGL to simulate lattice sizes far larger than what single-threaded CPU JavaScript can handle in real time.
