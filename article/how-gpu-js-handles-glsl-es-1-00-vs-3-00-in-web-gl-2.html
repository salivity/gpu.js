How GPU.js Handles GLSL ES 1.00 vs 3.00 in WebGL2

GPU.js bridges the architectural gap between WebGL1 (GLSL ES 1.00) and WebGL2 (GLSL ES 3.00) by analyzing JavaScript functions, generating an Abstract Syntax Tree (AST), and compiling them dynamically into the appropriate shading language version. When running on WebGL2, GPU.js automatically takes advantage of GLSL ES 3.00's modern features—such as enhanced type handling, updated storage qualifiers, and native integer arithmetic—while maintaining backward compatibility with GLSL ES 1.00 environments through an abstracted compiler pipeline.

Kernel Class Separation

GPU.js separates context handling into dedicated kernel classes: WebGLKernel for WebGL1 and WebGL2Kernel for WebGL2. When initialized, the library queries the host environment for WebGL2 support. If available, WebGL2Kernel is chosen, automatically directing the internal code generator to prepend the #version 300 es directive to the generated vertex and fragment shaders. If WebGL2 is not supported, it instantiates WebGLKernel, omitting the version directive to default to GLSL ES 1.00.

Input and Output Variable Declarations

One of the primary syntactic differences between GLSL ES 1.00 and 3.00 involves input, output, and varying parameters. GPU.js handles these mapping differences directly in the string generation phase:

  • Inputs: GLSL ES 1.00 uses the attribute keyword for vertex inputs and varying to pass data from vertex to fragment stages. In WebGL2Kernel, the compiler replaces these with the standardized in qualifier.
  • Outputs: GLSL ES 1.00 fragment shaders rely on the built-in gl_FragColor or extensions like WEBGL_draw_buffers for output. GLSL ES 3.00 deprecates gl_FragColor, requiring explicit output declarations. GPU.js dynamically declares custom output variables (e.g., out vec4 outColor;) and routes returned kernel values through this custom output variable in GLSL ES 3.00, while writing to gl_FragColor in GLSL ES 1.00.

Texture Sampling Functions

Texture access syntax changed significantly between GLSL ES 1.00 and 3.00.

  • In GLSL ES 1.00, texture fetching uses explicit, type-dependent functions such as texture2D() and textureCube().
  • In GLSL ES 3.00, these functions are unified into the overloaded texture() function, alongside the introduction of texelFetch() for non-normalized, direct integer coordinates.

GPU.js inspects the active backend during compilation. When compiling for WebGL2, the AST translator emits texture() calls instead of texture2D(), ensuring compatibility with the strict typing rules of GLSL ES 3.00.

Native Integer Arithmetic and Bitwise Operations

GLSL ES 1.00 lacks native integer operations, true integer types in many operations, and bitwise operators. To execute bitwise code on WebGL1, GPU.js must emulate operations mathematically using floating-point approximations.

Under WebGL2Kernel, GPU.js leverages GLSL ES 3.00’s native signed (int) and unsigned (uint) integers. The AST compiler maps JavaScript bitwise operators (&, |, ^, <<, >>) directly to native GLSL bitwise operators, resulting in faster execution and exact binary precision without requiring emulation layers.

Floating-Point Textures and Precision

WebGL1 often requires extensions (such as OES_texture_float) to read and write high-precision floating-point textures, requiring conditional precision qualifiers (precision highp float;). In WebGL2, 32-bit and 16-bit floating-point textures are integrated natively into the core specification. GPU.js adjusts its internal framebuffer and texture allocation settings based on the kernel type, ensuring that internal lookup arrays and output buffers utilize IEEE 754-compliant floating-point formats natively when compiling under GLSL ES 3.00.
