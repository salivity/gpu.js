Solving Crank-Nicolson Iteratively in GPU.js

The Crank-Nicolson implicit method for differential equations can be successfully solved in GPU.js by using iterative linear solvers. Because the implicit nature of Crank-Nicolson produces a coupled system of algebraic equations at each time step, standard direct solvers like the tridiagonal matrix algorithm (Thomas algorithm) fail to parallelize efficiently across GPU threads. However, by substituting a parallel iterative solver such as the Jacobi method or Red-Black Gauss-Seidel, developers can leverage GPU.js to accelerate solutions to partial differential equations (PDEs) directly in the browser.

The Challenge with Implicit Solvers on GPUs

The Crank-Nicolson method is widely used for solving parabolic PDEs—such as the heat equation—because it is numerically stable and second-order accurate in both time and space. Applying the method discretizes the domain into a linear system of equations:

\[A u^{n+1} = B u^n\]

Where \(u^n\) is the current state and \(u^{n+1}\) is the unknown state at the next time step.

On a CPU, a tridiagonal system of this type is typically solved using the Thomas algorithm in \(\mathcal{O}(N)\) sequential operations. On a GPU, this algorithm is inefficient because each step depends strictly on the value calculated in the preceding step, preventing parallel thread execution across the grid.

Using Iterative Solvers in GPU.js

To utilize the parallel architecture of GPU.js, the global matrix inversion must be converted into local, independent operations. Iterative relaxation methods—most notably the Jacobi iteration—allow every grid point to update simultaneously based solely on values from the previous iteration.

In a standard 1D heat equation discretized via Crank-Nicolson, the update equation for a point \(i\) can be rearranged into the iterative Jacobi form:

\[u_i^{(k+1)} = \frac{b_i - c_1 u_{i-1}^{(k)} - c_2 u_{i+1}^{(k)}}{c_0}\]

Here, \(k\) denotes the iteration index, and \(b\) represents the known explicit terms derived from time step \(n\). Because the computation of \(u_i^{(k+1)}\) depends only on values from iteration \(k\), each thread in a GPU.js kernel can compute one spatial point concurrently.

Implementation Architecture in GPU.js

Implementing an iterative Crank-Nicolson solver in GPU.js involves a nested execution loop:

  1. Explicit Step Kernel: A GPU kernel computes the known right-hand vector (\(B u^n\)) from the current state.
  2. Iterative Solver Kernels: A secondary GPU kernel executes the relaxation step (e.g., Jacobi update).
  3. Ping-Pong Textures: GPU.js handles memory via WebGL textures. Because an array cannot be read from and written to in the same pass, two buffers are alternated ("ping-ponged"): one acts as the read texture (\(u^{(k)}\)), and the other acts as the render target (\(u^{(k+1)}\)).
  4. Convergence Check: The CPU controls the inner loop, alternating the textures for a fixed number of iterations or until the difference between iterations drops below a specified tolerance.
  5. Time Advance: Once the inner iteration converges, the resulting texture becomes \(u^n\) for the next global time step.

Limitations and Considerations

  • Convergence Rates: Jacobi iteration converges slowly for fine spatial grids. While highly parallel, the number of iterations required per time step can offset parallelization gains if the grid is excessively large or the time step is wide.
  • Precision: GPU.js relies on WebGL, which traditionally uses 32-bit floating-point precision (or 16-bit on older hardware). Double-precision (64-bit) floats are generally unsupported, which can introduce numerical drift over long simulation runtimes.
  • CPU-GPU Overhead: Checking for convergence dynamically requires reading data back to the CPU via kernel(), which causes a pipeline stall. To maintain high throughput, it is usually more efficient to run a fixed number of iterations entirely on the GPU without reading back data until final visualization.
