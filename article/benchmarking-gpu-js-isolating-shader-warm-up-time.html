Benchmarking GPU.js: Isolating Shader Warm-Up Time

Benchmark harnesses can successfully isolate shader warm-up time from steady-state iteration time in gpu.js by decoupling the initial compilation and initialization phase from subsequent execution runs. In gpu.js, the first invocation of a kernel incurs significant overhead from JavaScript-to-GLSL transpilation, driver-level shader compilation, and buffer allocations. By running an unmeasured "burn-in" execution followed by synchronized steady-state iterations, benchmarking suites can capture accurate performance metrics for both phases independently.

The Anatomy of GPU.js Warm-Up Overhead

When a kernel is declared using gpu.createKernel(), gpu.js does not immediately compile it into executable machine code on the GPU. Instead, compilation occurs lazily upon the kernel's first invocation. This initial execution includes several one-time operations:

  1. AST Parsing and GLSL Transpilation: gpu.js parses the JavaScript function into an abstract syntax tree and converts it into WebGL-compatible GLSL shader code.
  2. WebGL Program Linking: The browser submits the GLSL source to the graphics driver, where it is compiled and linked into a WebGL program.
  3. Texture and Framebuffer Allocation: Initial GPU textures and framebuffers are created to pass arguments and read return values.

Because these tasks run on the CPU and the driver pipeline, the initial execution time can be orders of magnitude slower than subsequent runs.

How Harnesses Isolate Warm-Up from Steady-State

To isolate these stages, a benchmarking harness must execute a multi-phase test consisting of a warm-up pass, a synchronization barrier, and measured steady-state loops.

1. The Warm-Up Phase

The harness runs the kernel once using representative input data dimensions without recording metrics to the primary benchmark dataset. This single pass forces gpu.js to generate the GLSL code, compile the shader on the GPU driver, and configure memory layouts. The duration of this single pass can be timed separately if the goal is to measure initialization and cold-start latency.

2. Resolving WebGL Asynchrony

GPU operations in the browser are non-blocking and queued asynchronously. A common pitfall in naive benchmarks is measuring only the time it takes to dispatch commands to the command buffer rather than actual execution time.

To measure genuine execution time, the harness must force the WebGL pipeline to flush and complete:

  • Output Readback: Calling the output method (such as retrieving the array via kernel output or .toArray()) forces the CPU to wait until the GPU completes computation and reads the pixels back into system memory.
  • Sync Objects: For advanced setups using WebGL 2, gl.fenceSync and gl.clientWaitSync can be used to wait for completion without the full overhead of copying large arrays back to the CPU.

3. Steady-State Measurement

Once the pipeline is warm, the harness measures steady-state execution across multiple iterations using high-precision timers (performance.now()):

const kernel = gpu.createKernel(function(a, b) {
  return a[this.thread.x] + b[this.thread.x];
}).setOutput([1048576]);

// Phase 1: Isolated Warm-Up (triggers GLSL generation & driver compile)
const warmUpStart = performance.now();
kernel(inputA, inputB);
const warmUpDuration = performance.now() - warmUpStart;

// Phase 2: Steady-State Execution
const iterations = 50;
const runtimes = [];

for (let i = 0; i < iterations; i++) {
  const start = performance.now();
  
  const result = kernel(inputA, inputB);
  
  // Force pipeline synchronization
  result.toArray(); 
  
  const end = performance.now();
  runtimes.push(end - start);
}

Key Considerations for Reliable Isolation

  • Input Dimension Consistency: If input array dimensions change between the warm-up and the steady-state run, gpu.js may recompile the kernel or reallocate texture memory, invalidating the warm-up isolation.
  • Garbage Collection: Allocating new typed arrays inside the steady-state loop can trigger V8 or browser garbage collection pauses. Pre-allocate all inputs and reuse output buffers where possible to ensure that steady-state measurements reflect only compute and GPU dispatch latency.
