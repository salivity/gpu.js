Real-Time Vocoder Filterbanks Using GPU.js

Real-time vocoder filterbanks with arbitrary band counts can technically be parallelized using gpu.js, but practical real-time audio constraints present significant performance hurdles. While the mathematical structure of a channel vocoder—splitting signals into multiple frequency bands and tracking their envelopes—maps naturally to GPU hardware, the latency introduced by WebGL data transfers and CPU-GPU synchronization limits its viability for low-latency live audio. This article examines how vocoder filterbanks operate on a GPU, the mechanics of implementing them via gpu.js, and the architectural trade-offs between GPU acceleration and modern CPU processing.

Architecture of a Vocoder Filterbank

A classic channel vocoder processes two audio streams: an analysis signal (the modulator, typically speech) and a synthesis signal (the carrier, such as a synthesizer). Both streams are passed through matched filterbanks composed of \(N\) bandpass filters. For each band, an envelope follower calculates the instantaneous amplitude of the modulator. This amplitude is then multiplied by the corresponding filtered carrier signal, and the outputs of all bands are summed to produce the final vocoded sound.

When scaling to arbitrary or high band counts (e.g., 32, 64, or 128 bands), the computational load on the CPU increases linearly. Because each frequency band processes the audio stream independently, the workload is embarrassingly parallel across the band dimension.

Implementing Filterbanks with GPU.js

gpu.js compiles standard JavaScript functions into WebGL shader code, running computations across a 2D or 3D grid of GPU threads. To parallelize an arbitrary-band vocoder:

  1. Dimensional Mapping: The GPU kernel can be structured with a 2D output grid where the X-axis represents the time-domain audio samples in the current buffer (e.g., 128 to 1024 samples) and the Y-axis represents the filter bands (\(0\) to \(N-1\)).
  2. Filter Execution:
    • FIR (Finite Impulse Response) Filters: Convolutions are stateless across buffers and inherently parallel in time. Each GPU thread computes the dot product of the input buffer with the precomputed filter coefficients for its assigned band.
    • IIR (Infinite Impulse Response) Filters: Biquad filters depend recursively on previous output samples (\(y[n] = b_0 x[n] + b_1 x[n-1] + \dots - a_1 y[n-1]\)). This recursion prevents full parallelization across the time dimension within a single band, forcing threads to either loop sequentially across samples or parallelize strictly across bands while retaining filter state.
  3. Envelope Detection and Modulation: After filtering, full-wave rectification (Math.abs(sample)) and smoothing (a low-pass filter) are applied, followed by multiplying the smoothed modulator amplitude with the carrier sample.

Real-Time Performance Bottlenecks

While the parallel compute capacity of gpu.js easily handles hundreds of bands, integrating this into a real-time audio pipeline exposes critical bottlenecks:

  • Buffer Transfer Overhead: The Web Audio API operates in real time using an AudioWorkletNode, typically processing 128 samples per quantum (around 2.9 milliseconds at 44.1 kHz). Passing audio buffers from the CPU to WebGL textures, executing the shader, and reading data back into JavaScript via framebuffer reads introduces synchronization delays that often exceed the 2.9 ms deadline, causing audio dropouts and crackle.
  • AudioWorklet Thread Constraints: WebGL contexts are generally tethered to the main thread or an OffscreenCanvas. AudioWorklet runs on a dedicated high-priority audio rendering thread. Passing audio data between the audio thread, the main thread, and the GPU adds additional latency that destroys low-latency real-time guarantees.
  • Compute-to-Transfer Ratio: With small buffer sizes (128–512 samples), the computational density of even 64 filter bands is not high enough to outweigh the overhead of GPU pipeline setup and memory transfer.

Practical Verdict

Using gpu.js for a real-time vocoder filterbank is feasible only under high-latency conditions (such as buffer sizes of 2048 samples or higher, or in non-real-time batch processing) and with high band counts (128+ bands) using FIR-based filters.

For standard low-latency applications (sub-10ms), running the filterbank on the CPU using WebAssembly (Wasm) compiled with SIMD (Single Instruction, Multiple Data) instructions within an AudioWorklet delivers far superior performance, deterministic timing, and zero data-transfer overhead.
