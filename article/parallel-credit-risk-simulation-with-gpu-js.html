Parallel Credit Risk Simulation with GPU.js

This article explains how to leverage GPU.js to execute high-throughput Monte Carlo default probability simulations across large loan pools. By compiling standard JavaScript calculations into WebGL compute shaders, GPU.js distributes thousands of simulation paths across thousands of loan assets simultaneously. Readers will learn the underlying simulation logic, how to structure multi-dimensional loan data for GPU processing, and how to execute parallel portfolio loss calculations in Node.js or browser environments.

The Computational Bottleneck in Credit Risk

Credit risk assessment for loan portfolios typically relies on Monte Carlo simulations. In a standard model, each loan \(i\) has an Exposure at Default (\(EAD_i\)), Loss Given Default (\(LGD_i\)), and an unconditional Probability of Default (\(PD_i\)). Defaults are often driven by a structural factor model (such as the Vasicek model):

\[Y_i = \sqrt{\rho} X + \sqrt{1 - \rho} Z_i\]

Where:

  • \(X\) is the systemic market factor common to all borrowers.
  • \(Z_i\) is the idiosyncratic risk factor unique to borrower \(i\).
  • \(\rho\) is the asset correlation.

Borrower \(i\) defaults if \(Y_i\) falls below a threshold \(\Phi^{-1}(PD_i)\). Evaluating \(N\) loans across \(M\) simulated economic scenarios requires \(N \times M\) evaluations. When evaluating 50,000 loans across 100,000 scenarios, a single-threaded CPU must compute 5 billion independent mathematical evaluations, leading to severe latency.

Why GPU.js for Financial Simulations?

GPU.js is an open-source JavaScript library that transpiles a subset of JavaScript into GLSL (OpenGL Shading Language). It executes computations on the graphics card via WebGL without requiring low-level C++ or CUDA programming.

Because each simulation iteration for a given loan can be evaluated independently, the task is embarrassingly parallel. GPU.js maps these calculations directly to shader threads, processing thousands of iterations in a single clock cycle.

Designing the GPU Kernel

GPUs excel at uniform operations over flat data arrays. WebGL shaders cannot easily handle complex object hierarchies, so loan attributes must be unpacked into flat Float32 arrays or matrices.

1. Pseudo-Random Number Generation on the GPU

Shaders lack built-in random number generators like Math.random(). You must supply a pseudo-random function inside the kernel using thread coordinates and a dynamic seed. A common implementation uses a high-frequency sine function:

function pseudoRandom(x, y, seed) {
  return (Math.sin(x * 12.9898 + y * 78.233 + seed) * 43758.5453) % 1;
}

2. Setting Up the Simulation Kernel

Install the library using npm install gpu.js (for Node.js) or load it via CDN.

The following script defines a GPU kernel to simulate default losses across a portfolio:

const { GPU } = require('gpu.js');
const gpu = new GPU();

// Configuration
const numLoans = 1000;
const numSimulations = 10000;
const correlation = 0.2; // Rho

// Register helper functions
gpu.addFunction(function pseudoRandom(x, y, seed) {
  const dt = x * 12.9898 + y * 78.233 + seed;
  const sn = dt % 3.14159;
  return Math.abs((Math.sin(sn) * 43758.5453123) % 1);
});

// Simple approximation of the standard normal inverse cumulative distribution
gpu.addFunction(function normInv(p) {
  const a = 2.515517;
  const b = 0.802853;
  const c = 0.010328;
  const d = 1.432788;
  const e = 0.189269;
  const f = 0.001308;
  
  const t = p < 0.5 ? Math.sqrt(-2.0 * Math.log(p)) : Math.sqrt(-2.0 * Math.log(1.0 - p));
  const num = a + t * (b + t * c);
  const den = 1.0 + t * (d + t * (e + t * f));
  const r = t - (num / den);
  
  return p < 0.5 ? -r : r;
});

// Define the kernel: Output dimensions are [numLoans, numSimulations]
const simulatePortfolio = gpu.createKernel(function(thresholds, eads, lgds, systemicShocks, seed, rho) {
  const loanIndex = this.thread.x;
  const simIndex = this.thread.y;

  const systemic = systemicShocks[simIndex];
  
  // Generate idiosyncratic shock
  const rawRand = pseudoRandom(loanIndex, simIndex, seed);
  // Bound random number away from 0 and 1 for stability
  const clampedRand = Math.max(0.00001, Math.min(0.99999, rawRand));
  const idiosyncratic = normInv(clampedRand);

  // Vasicek factor model
  const sqrtRho = Math.sqrt(rho);
  const sqrtOneMinusRho = Math.sqrt(1.0 - rho);
  const compositeFactor = (sqrtRho * systemic) + (sqrtOneMinusRho * idiosyncratic);

  // If compositeFactor falls below threshold, the loan defaults
  if (compositeFactor < thresholds[loanIndex]) {
    return eads[loanIndex] * lgds[loanIndex];
  } else {
    return 0.0;
  }
})
.setOutput([numLoans, numSimulations])
.setPrecision('single');

3. Executing the Simulation

Run the simulation by passing standard arrays to the compiled kernel:

// Sample data generation
const thresholds = new Float32Array(numLoans).fill(-1.645); // Equivalent to ~5% default probability
const eads = new Float32Array(numLoans).fill(10000);        // $10,000 per loan
const lgds = new Float32Array(numLoans).fill(0.40);         // 40% loss given default

// Systemic shocks per simulation scenario (precomputed on CPU)
const systemicShocks = new Float32Array(numSimulations);
for (let i = 0; i < numSimulations; i++) {
  // Box-Muller transform for standard normal sample
  const u1 = Math.random();
  const u2 = Math.random();
  systemicShocks[i] = Math.sqrt(-2.0 * Math.log(u1)) * Math.cos(2.0 * Math.PI * u2);
}

const seed = Math.random() * 1000.0;

// Execute on GPU
console.time('GPU Simulation');
const losses = simulatePortfolio(thresholds, eads, lgds, systemicShocks, seed, correlation);
console.timeEnd('GPU Simulation');

// Calculate portfolio-level metrics
let totalLossPathZero = 0;
for (let i = 0; i < numLoans; i++) {
  totalLossPathZero += losses[0][i];
}
console.log(`Simulation Path 0 Total Loss: $${totalLossPathZero.toFixed(2)}`);

Best Practices and Optimization

  1. Avoid Frequent Host-to-Device Memory Transfers: The data transfer over the PCIe bus between the CPU (host) and GPU (device) creates latency. Group loans into static pools so loan attributes remain resident on the GPU across multi-period runs.
  2. Handle Precision Limitations: WebGL shaders predominantly use 32-bit floating-point (float). Ensure that your threshold transformations and inverse cumulative calculations do not result in precision underflows, especially at extreme tails (\(PD < 0.001\)).
  3. Pipeline Aggregations: The sample code outputs a 2D matrix of shape [numLoans, numSimulations]. For extremely large simulations, outputting this full matrix can exhaust system RAM. Instead, create a secondary GPU reduction kernel to sum losses across all loans for each scenario, returning a 1D array of size [numSimulations] containing total portfolio losses.
