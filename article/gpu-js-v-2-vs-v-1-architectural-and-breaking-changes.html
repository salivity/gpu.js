GPU.js V2 vs V1: Architectural and Breaking Changes

This article provides a comparative breakdown of the architectural shifts between legacy gpu.js version 1 and the modern version 2 release. Version 2 introduced a complete rewrite of the compilation pipeline, modernizing how JavaScript syntax is parsed into GLSL shaders, standardizing WebGL2 as the primary rendering context, and overhauling memory management between the CPU and GPU. Below are the definitive breaking changes and architectural divergence points separating the two releases.

AST-Based Shader Transpilation

The most profound architectural rewrite in version 2 is the deprecation of the rudimentary parsing engine in favor of a robust, AST (Abstract Syntax Tree)-based JavaScript-to-GLSL transpiler.

  • Legacy Version 1: Relied on string manipulation, regular expressions, and limited parsing logic to convert JavaScript functions into WebGL shaders. This severely limited the use of modern JavaScript syntax, variable scopes, and advanced mathematical operators inside kernels.
  • Version 2: Integrates a formal AST traversal engine. This allows gpu.js to parse ES6+ features natively—such as const, let, arrow functions, template literals, and complex inline conditional logic—reliably compiling them into valid WebGL1 or WebGL2 GLSL code without unexpected translation errors.

Class Instantiation and Module Import Syntax

Version 2 altered how the library exposes its core classes to accommodate modern packaging and tree-shaking patterns.

  • Legacy Version 1: Imported the GPU constructor directly as the default export: 
    const GPU = require('gpu.js');
const gpu = new GPU();
  • Version 2: Switched to named exports, requiring destructuring to access the main class and supporting utility types: 
    const { GPU } = require('gpu.js');
const gpu = new GPU();
    This breaking change prevents runtime instantiation errors when updating dependency trees in Node.js or modern bundler configurations.

WebGL2-First Architecture and Native Float Textures

Version 2 fundamentally redesigns the graphic context priority list, targeting modern hardware capabilities while keeping fallbacks intact.

  • Legacy Version 1: Defaulted primarily to WebGL 1 contexts. Rendering floating-point data required hacky floating-point texture extensions (like OES_texture_float), which varied wildly across different mobile and desktop browsers and caused high failure rates.
  • Version 2: Prioritizes WebGL 2 contexts out of the box, cascading downwards only if necessary: WebGL2 -> WebGL1 -> CPU. Because WebGL 2 natively supports 32-bit floating-point textures, version 2 eliminates the texture-packing workarounds required in version 1, yielding substantial throughput improvements and higher numerical precision.

Pipeline Mode and Memory Persistence

In version 1, chaining kernels required constant round-trips from the GPU to the CPU, serializing data into standard JavaScript arrays before passing them back into a new kernel texture.

  • Legacy Version 1: Kernels immediately read out pixels via gl.readPixels, turning compute results into standard CPU arrays unless complex manual configurations were applied.
  • Version 2: Introduces a formalized "Pipeline Mode" via .setPipeline(true). When enabled, the output of a kernel is kept on the GPU as a raw Texture instance. This texture can be passed directly as an input to subsequent kernels without incurring CPU transfer latency. Calling .toArray() on the texture is explicitly deferred until the final output is needed.

Introduction of Sub-Kernels

Version 2 introduced architectural support for sub-kernels, a feature completely absent in version 1.

  • Legacy Version 1: Could only execute single-output functions per kernel run. Computing multiple related arrays required running multiple kernels over identical data iterations.
  • Version 2: Allows developers to declare sub-functions inside the main kernel using this.subKernel(). The GPU computes these outputs in a single execution pass, returning an object containing multiple typed result arrays or textures.

CPU Fallback Execution Fidelity

The CPU execution fallback in version 1 frequently produced different numerical outcomes compared to its WebGL equivalent due to standard JavaScript floating-point precision quirks. Version 2 completely overhauled the CPU runner to strictly emulate GLSL math operations, precision limits, and integer truncation, ensuring that algorithms run identically in headless environments or on machines lacking hardware acceleration.
