Parallelize BLAST Seeding Lookups with GPU.js

BLAST (Basic Local Alignment Search Tool) relies on a computationally intensive seeding step, where short, fixed-length sequences (\(k\)-mers) from a query are matched against a reference database. By leveraging GPU.js, developers can compile JavaScript functions into WebGL or WebGPU shaders to execute thousands of sequence lookups simultaneously on the graphics hardware. This article explains how to encode sequence data, construct an efficient lookup strategy, and implement a parallel \(k\)-mer matching kernel using GPU.js.

The Seeding Bottleneck

The initial phase of BLAST identifies matching "words" of length \(k\) (typically \(k=11\) for DNA or \(k=3\) for protein sequences). In a standard CPU implementation, the algorithm iterates through each offset of the query sequence and queries a hash table or scans the database linearly. When scaling to genomic databases with millions of base pairs, this linear scan or repeated memory access becomes a major latency bottleneck.

Because each \(k\)-mer comparison is independent of the others, this phase maps directly to the SIMD (Single Instruction, Multiple Data) execution model of modern GPUs.

1. Encoding Sequences for GPU Processing

GPUs are designed to process numerical matrices rather than character strings. Before feeding sequences to GPU.js, convert biological characters (such as \(A, C, G, T\)) into a numeric representation.

function encodeSequence(seq) {
  const map = { 'A': 0, 'C': 1, 'G': 2, 'T': 3 };
  return seq.toUpperCase().split('').map(char => map[char] ?? 4);
}

By encoding each nucleotide as an integer, the data can be passed to GPU.js as flat 1D arrays or textures.

2. Implementing the Seeding Kernel

GPU.js allows you to write the search algorithm in pure JavaScript, which it compiles into shader code.

In this parallelized approach, each GPU thread is assigned a specific position in the reference database. The thread checks whether the \(k\)-mer starting at its assigned index matches the target \(k\)-mer from the query sequence.

const { GPU } = require('gpu.js');
const gpu = new GPU();

// k-mer length
const K = 11;

// Define kernel: 1 thread per reference database position
const blastSeedKernel = gpu.createKernel(function(reference, queryKmer, k) {
  let match = 1;
  for (let i = 0; i < k; i++) {
    if (reference[this.thread.x + i] !== queryKmer[i]) {
      match = 0;
      break;
    }
  }
  return match;
})
.setOutput([referenceLength - K + 1])
.setPipeline(true); // Retains output on GPU memory if chaining operations

Extending to Multi-Query Lookups

To check multiple query \(k\)-mers simultaneously, configure a 2D output grid where the X-dimension represents the reference database index and the Y-dimension represents the index of the query \(k\)-mer:

const blastMultiSeedKernel = gpu.createKernel(function(reference, queryKmers, k) {
  let match = 1;
  for (let i = 0; i < k; i++) {
    // queryKmers is a 2D array: [queryIndex][positionInKmer]
    if (reference[this.thread.x + i] !== queryKmers[this.thread.y][i]) {
      match = 0;
      break;
    }
  }
  // Return 1 if match is found at reference[this.thread.x] for query[this.thread.y]
  return match;
})
.setOutput([referenceLength - K + 1, totalQueryKmers]);

3. Gathering and Filtering Matches

Once the kernel finishes execution, the output matrix contains binary indicators (\(1\) for a match, \(0\) for a mismatch).

const results = blastMultiSeedKernel(encodedRef, encodedQueryKmers, K);

const seedHits = [];
for (let qIdx = 0; qIdx < totalQueryKmers; qIdx++) {
  for (let rIdx = 0; rIdx < referenceLength - K + 1; rIdx++) {
    if (results[qIdx][rIdx] === 1) {
      seedHits.push({ queryIndex: qIdx, referenceIndex: rIdx });
    }
  }
}

These identified index pairs represent exact seed matches, which can be forwarded directly to the BLAST seed extension stage (such as Smith-Waterman or banded dynamic programming) on the CPU.

Performance Considerations

  • Memory Transfer Overhead: Moving large genomic arrays between CPU host memory and GPU device memory creates bus latency. Minimize transfers by batching thousands of query \(k\)-mers into a single GPU call rather than querying one \(k\)-mer at a time.
  • Array Length Limits: GPUs have maximum texture size limits depending on hardware and backend (WebGL vs. WebGPU). For databases exceeding \(16,384\) elements per dimension, split the reference sequence into chunks and execute the kernel sequentially over each block.
  • Avoid Complex Branching: GPUs handle divergence poorly. Keep the inner matching loop straightforward so that threads within the same warp/workgroup execute synchronized operations efficiently.
