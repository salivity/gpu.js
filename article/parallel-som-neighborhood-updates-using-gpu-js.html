Parallel SOM Neighborhood Updates Using GPU.js

Self-Organizing Maps (SOMs) rely heavily on computationally expensive neighborhood updates across a grid of nodes during training. By leveraging gpu.js, a JavaScript library that compiles functions into WebGL shader code, developers can execute these neighborhood update rules in parallel directly on the graphics hardware. This article explores how SOM neighborhood calculations can be mapped to GPU parallel kernels, the mechanics of parallelizing the update step, and the performance considerations involved.

The Mechanism of SOM Neighborhood Updates

In a traditional Self-Organizing Map, an input vector is presented to the network, and the Best Matching Unit (BMU)—the node with the weight vector closest to the input—is identified. Following this, the weights of the BMU and its topological neighbors are updated using the following rule:

\[W_v(t + 1) = W_v(t) + \theta(u, v, t) \cdot \alpha(t) \cdot (D(t) - W_v(t))\]

Where:

  • \(W_v(t)\) is the weight vector of node \(v\).
  • \(\alpha(t)\) is the learning rate.
  • \(D(t)\) is the input vector.
  • \(\theta(u, v, t)\) is the neighborhood function (typically a Gaussian decay based on the distance between node \(v\) and the BMU \(u\)).

In standard single-threaded JavaScript, this requires looping sequentially over thousands of nodes and their dimensions. Because the update of each node depends only on its distance to the BMU and its current state—not on the updated state of adjacent nodes in the same step—the operation is inherently parallel.

Implementing the Update Rule in GPU.js

gpu.js allows developers to write standard JavaScript syntax that automatically compiles into GLSL shaders running on the GPU. The SOM grid maps directly to a 2D execution kernel.

  1. Kernel Setup: Define a 2D kernel matching the dimensions of the SOM grid (e.g., width \(\times\) height).
  2. Input Arguments: Pass the current weight tensors, the coordinates of the BMU, the current input vector, the current learning rate \(\alpha\), and the neighborhood radius \(\sigma\).
  3. Execution per Thread: Within the kernel, each thread corresponds to a specific node coordinate (this.thread.x, this.thread.y).
    • The thread computes its Euclidean distance to the BMU coordinate.
    • It evaluates the neighborhood influence \(\theta\): \(\exp(-\text{dist}^2 / (2 \cdot \sigma^2))\).
    • It applies the weight update equation for the node's dimensions and outputs the new weight value.

Because the GPU can execute hundreds or thousands of threads simultaneously, the time required to update large grids (e.g., \(100 \times 100\) nodes or larger) drops significantly compared to CPU-bound execution.

Architectural Considerations and Best Practices

While parallelizing neighborhood updates in gpu.js offers significant speedups, optimizing the pipeline requires addressing a few architectural trade-offs:

  • BMU Search Bottleneck: Finding the BMU requires calculating distances for all nodes and then finding the minimum value (a reduction operation). While parallel reductions can be executed on the GPU, they often introduce synchronization complexity. For moderate grid sizes, finding the BMU on the CPU or using a hybrid approach may be necessary to maintain throughput.
  • CPU-GPU Data Transfer: Moving weights back and forth between the CPU and GPU memory every iteration causes overhead. To achieve optimal performance, keep the weights stored in GPU texture memory using the pipeline: true mode in gpu.js across training iterations, reading the data back to the CPU only when training concludes or during periodic logging.
  • Grid Scaling: The performance benefit of using gpu.js becomes noticeable on medium to large grids (generally \(50 \times 50\) nodes and above). For very small maps, the overhead of kernel compilation and dispatch can exceed the execution time of a standard JavaScript loop.
