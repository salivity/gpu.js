GPU.js Memory Addressing for Flattened 2D Arrays

GPU.js executes JavaScript code on the graphics card by transpiling functions into WebGL fragment shaders, where array data is physically stored as WebGL textures rather than linear CPU memory blocks. When a flattened 2D array is accessed using a single linear index, GPU.js cannot directly read a contiguous memory address using standard pointer arithmetic. Instead, it computes memory locations by mathematically mapping the 1D index into a 2D coordinate system, calculating normalized texture coordinates \((u, v)\), and querying the underlying texture memory using GLSL texture lookup functions.

WebGL Texture-Based Storage

Fragment shaders in standard WebGL pipelines do not provide arbitrary raw memory access. To pass large numerical datasets to the GPU, GPU.js encodes input arrays into 2D floating-point textures. Even when an array is conceptually flat or represents a flattened matrix, it is arranged into a 2D grid bounded by the GPU hardware limit (gl.MAX_TEXTURE_SIZE).

Because the data is organized across rows and columns of texels, GPU.js maintains internal metadata for each array, including the physical texture width (\(W_{tex}\)) and height (\(H_{tex}\)), which are used to translate array offsets into pixel coordinates.

Mapping the 1D Index to 2D Matrix Coordinates

When code accesses an element via a single flat index \(i\), the transpiled GLSL kernel must convert this scalar integer into discrete horizontal (\(X\)) and vertical (\(Y\)) integer coordinates within the allocated texture. GPU.js achieves this using basic modular arithmetic:

\[X = i \pmod{W_{tex}}\] \[Y = \lfloor i / W_{tex} \rfloor\]

In the generated GLSL shader, this logic is implemented using floating-point operations, as WebGL 1.0 does not universally support native integer bit-shifting or integer modulo:

float x = mod(i, textureWidth);
float y = floor(i / textureWidth);

Normalizing Coordinates for Sampling

WebGL texture sampling via texture2D requires normalized coordinates ranging from \(0.0\) to \(1.0\), rather than absolute pixel coordinates. Furthermore, to avoid sampling artifacts and bilinear filtering errors between adjacent texels, the sample point must hit the center of the target pixel.

GPU.js adds a half-texel offset (\(0.5\)) to both coordinates before dividing by the total dimensions of the texture:

\[u = \frac{X + 0.5}{W_{tex}}\] \[v = \frac{Y + 0.5}{H_{tex}}\]

The resulting vector vec2(u, v) represents the exact memory address of the texel holding the requested array value.

Value Retrieval and Unpacking

Once the normalized coordinates are established, GPU.js extracts the data using the native texture sampling instruction:

vec4 texel = texture2D(uTextureSampler, vec2(u, v));

Depending on device capabilities and kernel configuration, GPU.js reads the data in one of two ways:

  1. Direct Float Textures: If the OES_texture_float or equivalent WebGL 2.0 floating-point extension is enabled, the actual scalar value is stored directly in one of the color channels (typically the red channel, texel.r).
  2. RGBA Bit-Packing: If floating-point textures are unsupported, GPU.js encodes each 32-bit floating-point number across all four 8-bit channels (r, g, b, a). In this case, an internal GLSL decoding function immediately unpacks the four 8-bit values back into a single 32-bit IEEE 754 floating-point number.

Through this combination of modulo-based coordinate transformation, half-pixel normalization, and texture retrieval, GPU.js translates a single flattened index into a precise GPU memory lookup.
