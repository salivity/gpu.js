gpu.js GPU Mode vs CPU Mode Performance Guide

In gpu.js, the performance difference between GPU and CPU modes varies dramatically based on dataset size and computational complexity, ranging from the CPU outperforming the GPU on trivial tasks to the GPU delivering a 10x to 100x speedup on large-scale parallel computations. This guide breaks down the architectural differences between both modes, highlights data transfer overheads, and outlines benchmark expectations to help developers choose the right execution target for their workloads.

Architectural Differences

The GPU mode in gpu.js transpiles a subset of JavaScript functions into GLSL (OpenGL Shading Language), executing calculations in parallel across thousands of shader cores via WebGL. In contrast, CPU mode falls back to executing standard, single-threaded JavaScript loops (or JavaScript array operations) inside the browser's engine or Node.js runtime.

Because of this fundamental difference, GPU mode excels at SIMD (Single Instruction, Multiple Data) tasks where the same mathematical operation is applied independently across vast arrays of data, while CPU mode processes items sequentially.

The Small-Data Penalty: When CPU Outperforms GPU

Developers often observe that for small workloads—such as arrays with fewer than 10,000 elements—CPU mode is noticeably faster than GPU mode. This occurs due to fixed overhead costs required by the GPU pipeline:

  1. Kernel Compilation: Compiling JavaScript into GLSL shaders and creating WebGL programs incurs a one-time execution cost.
  2. Memory Transfer: Input arrays must be packed into WebGL textures and uploaded from system RAM to GPU VRAM.
  3. Pipeline Readback: After computation, results must be read back from the GPU to the CPU using operations like gl.readPixels, which can stall the execution pipeline.

For lightweight tasks, these transfer and synchronization bottlenecks take longer than simply running the code in a standard JavaScript loop on the CPU.

Large-Scale Scaling: Where GPU Excels

Once the computational workload surpasses the overhead threshold, GPU mode scales far better than CPU mode. On operations like matrix multiplication, image processing, cellular automata, and neural network forward-passes, the performance disparity widens significantly:

  • Small Datasets (< 10,000 operations): CPU is typically 2x to 5x faster than GPU due to texture upload and compilation overhead.
  • Medium Datasets (10,000 to 250,000 operations): GPU and CPU achieve parity. This represents the breakeven zone where parallel execution speeds begin to offset data transfer costs.
  • Large Datasets (250,000 to 1,000,000+ operations): GPU mode becomes 10x to 50x faster than CPU mode.
  • Massive Datasets (1,000,000+ operations with high math intensity): GPU mode can outperform CPU mode by 100x or more, especially if calculations involve expensive trigonometric or floating-point operations per element.

Mitigating the Discrepancy

To maximize GPU efficiency and avoid performance regressions compared to CPU mode:

  • Keep Data on the GPU: When chaining multiple kernels, set { pipeline: true } so that intermediate outputs remain as textures in GPU memory rather than transferring back and forth to the CPU.
  • Warm Up Kernels: Run a throwaway iteration during initialization to compile the GLSL shader ahead of time, eliminating the initial compilation spike during runtime calculations.
  • Increase Arithmetic Intensity: Ensure each thread does sufficient computational work; running a kernel that simply copies or adds one value per thread rarely justifies the GPU overhead.
