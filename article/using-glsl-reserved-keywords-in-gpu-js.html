Using GLSL Reserved Keywords in GPU.js

When developing kernels with gpu.js, using OpenGL Shading Language (GLSL) reserved keywords as JavaScript variable names leads to syntax errors, shader compilation failures, and automatic performance degradation. Because gpu.js transpiles JavaScript functions directly into WebGL GLSL shader code, using protected identifiers breaks the underlying code generation pipeline. This overview explains the transpilation behavior, error mechanics, and performance consequences when reserved words enter a gpu.js kernel.

The Transpilation Process and Keyword Collisions

gpu.js works by parsing a JavaScript function's Abstract Syntax Tree (AST) and translating its logic into GLSL shader source code. During this translation, gpu.js preserves most JavaScript variable identifiers and maps them directly into equivalent GLSL variable declarations.

JavaScript and GLSL have vastly different sets of reserved keywords. While variable names such as float, int, input, output, texture, varying, or sample are entirely valid in standard JavaScript, they are strictly reserved in GLSL. When gpu.js converts these identifiers into shader strings without prefixing or sanitizing them, the resulting GLSL string contains syntactically invalid shader declarations.

WebGL Shader Compilation Errors

Once gpu.js constructs the GLSL shader string, it passes the source code to the browser's WebGL context via gl.compileShader(). The graphics driver's GLSL compiler analyzes the code. When it encounters a reserved word in an illegal position (such as declaring let float = 1.0;, which translates to float float = 1.0;), the compilation fails immediately.

The WebGL context flags a compilation failure and outputs an error to the browser console. Typical errors generated include:

  • ERROR: 0:X: 'keyword' : syntax error
  • ERROR: 0:X: 'keyword' : reserved word

Fallback Behavior to the CPU

By default, gpu.js uses a fallback mechanism designed to prevent application crashes when a GPU is unavailable or when shader compilation fails. When the WebGL shader fails to compile due to a GLSL reserved keyword, gpu.js intercepts the error and switches the kernel’s execution mode from the GPU to the CPU.

When this fallback occurs:

  1. Silent Performance Degradation: The operation continues using pure JavaScript on a single thread. The program may not crash, but parallel processing capabilities are lost, resulting in severe performance drops for compute-heavy workloads.
  2. Explicit Failures in Strict Mode: If the kernel is configured strictly with { mode: 'gpu' }, gpu.js suppresses the CPU fallback and throws an unhandled JavaScript exception, halting execution entirely.

Preventing and Debugging Keyword Conflicts

To prevent collisions between JavaScript identifiers and GLSL keywords:

  • Inspect Generated Code: Use kernel.toString() to view the compiled GLSL shader source code and identify syntax issues flagged by WebGL.
  • Avoid Overlapping Names: Refrain from using type names (vec2, vec3, vec4, float, int, sampler2D), layout qualifiers (attribute, uniform, varying), and standard GLSL built-in functions (texture2D, smoothstep, clamp) as variable identifiers.
  • Adopt Naming Conventions: Prefix local variables (e.g., itemCount instead of count, or dataInput instead of input) within kernel functions to ensure safe transpilation into valid GLSL.
