How GPU.js Cleans Up WebGL Shader Programs

This article provides an overview of how GPU.js manages the lifecycle of WebGL resources when a kernel is decommissioned. Because JavaScript's automatic garbage collection does not immediately free low-level GPU allocations, GPU.js utilizes explicit de-allocation routines through WebGL context APIs. By understanding the interaction between kernel destruction methods, shader detachment, and resource deletion, developers can ensure that memory leaks are minimized in high-performance web applications.

Explicit Decommissioning via kernel.destroy()

WebGL handles memory in native GPU space rather than the JavaScript V8 engine heap. When a GPU.js kernel is no longer needed, the runtime cannot simply rely on variables falling out of scope. Developers must explicitly trigger the cleanup cycle by invoking the kernel’s destroy() method, or by calling gpu.destroy(), which cascades destruction calls down to every kernel attached to that GPU instance.

When destroy() is called on a WebGL-based kernel (such as WebGLKernel or WebGL2Kernel), the library halts execution pipelines and initiates a coordinated teardown of the WebGL state machine.

Detaching and Deleting Shaders

GPU.js compiles custom vertex and fragment shaders written in GLSL to execute kernel code. During the decommissioning sequence, the cleanup process targets these compiled shaders directly:

  1. Shader Detachment: The kernel queries the active WebGL rendering context (gl) and detaches the vertex and fragment shaders from the compiled program using gl.detachShader(program, vertexShader) and gl.detachShader(program, fragmentShader). Detaching breaks the link between the program container and the individual shader objects.
  2. Shader Deletion: Once detached, GPU.js calls gl.deleteShader(shader) on both the vertex and fragment shader instances. This marks the native GPU memory allocated for the compiled GLSL binary for immediate deallocation.

Deleting the WebGL Program

After the individual shader units are detached and marked for deletion, GPU.js targets the linked program object:

  1. Unbinding the Active Program: If the decommissioned kernel is currently bound to the WebGL context, the state is cleared by executing gl.useProgram(null). This ensures that the GPU does not hold an active reference to the program during teardown.
  2. Program Deletion: GPU.js executes gl.deleteProgram(program). If the program is not in use elsewhere, the WebGL implementation immediately invalidates the program reference and frees its associated GPU instructions and uniform storage.

Auxiliary Resource Reclamation

A GPU.js kernel depends on several supporting WebGL constructs in addition to the shader program itself. The decommissioning routine cleans up these related objects:

  • Textures: Textures holding input arrays or output data are freed using gl.deleteTexture(texture).
  • Framebuffers: The off-screen framebuffers used to read compute results are deallocated via gl.deleteFramebuffer(framebuffer).
  • Vertex Buffers: The coordinate buffers that project screen-aligned quads for fragment-based calculation are released using gl.deleteBuffer(buffer).

JavaScript Reference Nullification

After invoking the respective WebGL deletion methods, GPU.js clears its internal JavaScript references. Internal properties pointing to this.program, this.outputTexture, and the underlying context are set to null. This step allows the browser's garbage collector to reclaim the lightweight JavaScript wrapper objects without retaining dangling pointers to decommissioned WebGL hardware handles.
