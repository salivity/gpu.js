GPU.js Precision on Mobile: Highp vs Mediump

This article examines how the GPU.js library negotiates floating-point precision on mobile chipsets, focusing on the mechanics of WebGL shader generation, hardware support for highp versus mediump qualifiers, and the precision fallbacks used when native 32-bit floating-point textures are unsupported.

WebGL Compilation and Precision Qualifiers

GPU.js accelerates JavaScript by transpiling standard functions into WebGL-compatible GLSL (OpenGL Shading Language) fragment shaders. When writing shaders for WebGL, declaring floating-point precision is mandatory for fragment stages. Desktop graphics cards execute almost all operations at 32-bit floating-point precision (highp) regardless of shader declarations, but mobile system-on-chips (SoCs)—such as Qualcomm Adreno, ARM Mali, and Apple Silicon—contain dedicated hardware paths for both 16-bit half-precision (mediump) and 32-bit single-precision (highp).

To maintain parity with standard JavaScript numbers (which are double-precision 64-bit floats), GPU.js explicitly declares precision highp float; at the top of generated fragment shaders by default. This forces the mobile GPU to utilize full 32-bit IEEE 754 precision registers if they are supported by the hardware and the WebGL context.

Mobile Hardware Capabilities and Context Negotiation

Mobile GPUs manage precision based on the active WebGL version and supported extensions:

  1. WebGL 2.0: The specification mandates support for highp floats inside fragment shaders. When running on modern mobile chipsets with WebGL 2.0, GPU.js can execute 32-bit calculations natively, provided the underlying driver properly adheres to the standard.
  2. WebGL 1.0: The highp qualifier in fragment shaders is entirely optional under the WebGL 1.0 specification. GPU.js queries the shader compiler via gl.getShaderPrecisionFormat(gl.FRAGMENT_SHADER, gl.HIGH_FLOAT). If the target mobile chipset returns a precision range of zero, it indicates no native highp support in the fragment stage. Under these circumstances, GPU.js is forced to downgrade the declaration to precision mediump float;.

Float Texture Support and Emulated Encoding

Performing high-precision math inside a shader is only half of the computation pipeline; the output must also be stored into a texture. Mobile chipsets frequently restrict rendering to 32-bit floating-point textures (gl.FLOAT) due to thermal, bandwidth, and hardware limitations.

When a mobile GPU lacks native 32-bit float texture rendering (such as lacking the OES_texture_float or EXT_color_buffer_float extensions), GPU.js circumvents this limitation through an encoding mechanism:

  • Pack and Unpack Functions: Instead of outputting a single 32-bit float directly to a 32-bit channel, GPU.js generates GLSL code that mathematically decomposes the 32-bit float into four 8-bit components.
  • RGBA Storage: These four bytes are written into a standard, widely supported 8-bit RGBA texture (gl.UNSIGNED_BYTE).
  • Decoding: When reading values back to CPU memory or chaining them into another GPU.js kernel, the library automatically reassembles the four 8-bit channels back into a single 32-bit floating-point number.

This encoding step allows GPU.js to preserve high precision on constrained mobile architectures, albeit at the cost of additional arithmetic instructions per pixel.

Impact of Fallback to Medium-Precision

When mobile environments restrict operations to mediump without float-packing workarounds, numerical stability changes substantially:

  • Bit Width: mediump guarantees only a minimum format roughly equivalent to IEEE 754 half-precision (16-bit), offering 1 sign bit, 5 exponent bits, and 10 mantissa bits.
  • Dynamic Range: The maximum representable value drops from approximately \(3.4 \times 10^{38}\) (highp) to around \(65,504\) (mediump). Any calculation exceeding this bound instantly results in an overflow to infinity.
  • Granularity: Machine learning kernels, physics engines, and iterative matrix operations executed on GPU.js suffer from severe rounding errors under mediump, as small step sizes (e.g., learning rates below \(0.0001\)) cannot be accurately resolved.

Developers targeting mobile browsers must either verify WebGL 2 availability to secure native highp execution or design computations that accommodate the restricted dynamic range of 16-bit mediump fallbacks.
