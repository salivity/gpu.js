gpu.js Security Considerations for Untrusted Code

Running untrusted user-supplied algorithms via gpu.js introduces serious security vulnerabilities that span both the host JavaScript environment and low-level graphics hardware. Because gpu.js translates JavaScript functions into WebGL compute shaders (GLSL) or executes them directly on the CPU as a fallback, untrusted inputs can trigger Denial of Service (DoS) attacks, GPU memory leaks, driver-level exploits, and remote code execution if isolation mechanisms are insufficient.

JavaScript Parsing and Transpilation Risks

Before any code reaches the GPU, gpu.js parses the provided JavaScript function into an Abstract Syntax Tree (AST) to generate equivalent GLSL code. If user input is passed as a string and evaluated using eval() or the Function constructor to create the kernel, malicious users can escape the computation context entirely. This can result in arbitrary JavaScript execution within the host application, leading to Cross-Site Scripting (XSS) on the client side or remote code execution on the server side (in Node.js environments). Even if a function object is provided, malicious code can exploit prototype pollution or unexpected AST structures to disrupt the runtime.

Denial of Service and GPU Freezing

Graphics processing units are designed for massive parallelism rather than preemptive multitasking. Untrusted algorithms can easily initiate infinite loops, deeply nested iterations, or massive thread allocations. On consumer operating systems, an unresponsive GPU will trigger a Timeout Detection and Recovery (TDR) event, resetting the graphics driver, killing the WebGL context, and freezing the host operating system or browser tab. In a shared or server-side environment, a single malicious algorithm can exhaust GPU compute queues and memory, rendering the system unavailable to legitimate workloads.

Side-Channel Attacks and Cross-Context Data Leakage

GPUs share physical memory and execution resources across multiple processes and browser tabs. Running arbitrary WebGL shaders allows attackers to measure precise execution timings, which can be leveraged in side-channel attacks (such as cache-timing or power-monitoring attacks) to infer sensitive data handled by other applications or the browser itself. Additionally, certain driver bugs and WebGL implementations have historically failed to zero out allocated texture memory, potentially allowing an untrusted kernel to inspect remnants of memory discarded by other processes.

Driver Exploits and Hardware Crashing

Graphics drivers are massive, complex software suites operating with kernel-level privileges. Compiling untrusted, highly complex, or purposefully malformed GLSL shaders exposes the host to underlying driver vulnerabilities. Attackers can craft workloads designed to trigger buffer overflows, unhandled null pointers, or memory corruption bugs in the graphics vendor's driver, leading to operating system crashes (Blue Screen of Death / kernel panics) or, in the worst cases, kernel-level privilege escalation.

CPU Fallback Vulnerabilities

If a client device or server lacks WebGL support, gpu.js automatically falls back to CPU execution. In CPU mode, gpu.js runs standard JavaScript loops. If untrusted code is executed here without a strict sandbox, all standard sandboxing limits are bypassed: the algorithm runs with the full privileges of the host process, with unrestricted access to memory, global objects, and system APIs available within that runtime scope.

Essential Hardening and Mitigation Strategies

To safely handle user-defined logic intended for gpu.js, implement the following architectural controls:

  • Enforce Strict Sandboxing: Never execute untrusted kernels on the main thread. Run client-side kernels inside restricted Web Workers within sandboxed, cross-origin iframe elements with strict Content Security Policies (CSP). For Node.js, run tasks inside ephemeral, unprivileged containers or virtual machines.
  • Static Code Validation: Reject arbitrary code strings. If users must define custom logic, require a restricted domain-specific language (DSL) or use an AST validator to whitelist allowed operations (e.g., purely mathematical expressions) while stripping control structures, function calls, and global object references.
  • Enforce Resource Boundaries: Strictly cap the maximum kernel dimensions, output array sizes, and loop bounds before generating the kernel.
  • Disable Unsafe Fallbacks: Explicitly configure gpu.js to disable automatic CPU fallback if running untrusted code in an environment where pure JavaScript execution carries severe security implications.
