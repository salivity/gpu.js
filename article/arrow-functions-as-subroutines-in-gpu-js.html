Arrow Functions as Subroutines in GPU.js

Arrow functions with implicit returns cannot be reliably used as subroutines registered with GPU.js. When transpiling JavaScript into WebGL or WebGPU shader code (GLSL), the GPU.js compiler expects explicit block statements and return declarations to infer data types and construct valid shader syntax. This article explains why concise arrow functions fail during AST parsing and how to properly register helper functions using gpu.addFunction().

Why Implicit Returns Fail in GPU.js

GPU.js works by parsing JavaScript functions into an Abstract Syntax Tree (AST) and translating that tree into strongly typed GLSL code. When you write an arrow function with an implicit return, such as:

const add = (a, b) => a + b;
gpu.addFunction(add);

The underlying AST creates an ArrowFunctionExpression where the body is an Expression rather than a BlockStatement containing a ReturnStatement.

The GPU.js code generation pipeline specifically looks for:

  1. An explicit function body (BlockStatement).
  2. Explicit ReturnStatement nodes to deduce the output type of the function and emit the corresponding GLSL return keyword.

When presented with an implicit return expression, GPU.js often fails to infer the return type, resulting in shader compilation errors, unexpected void returns, or syntax errors during the kernel build phase.

The Correct Syntax for Subroutines

To ensure GPU.js can parse and translate your subroutines into shader code, you must define functions using standard block syntax and explicit return statements.

1. Arrow Functions with Explicit Bodies

If you prefer arrow function syntax, wrap the body in curly braces and include an explicit return:

const add = (a, b) => {
  return a + b;
};

gpu.addFunction(add);

2. Standard Function Declarations

Traditional function declarations are the most stable and recommended pattern for gpu.addFunction():

function add(a, b) {
  return a + b;
}

gpu.addFunction(add);

Explicit Argument and Return Typing

In complex kernels, GPU.js might struggle to infer types from JavaScript alone. When registering subroutines, you can provide an options object defining argument and return types to prevent transpilation ambiguities:

gpu.addFunction(
  function add(a, b) {
    return a + b;
  },
  { argumentTypes: { a: 'Float', b: 'Float' }, returnType: 'Float' }
);

While concise arrow syntax is standard in modern JavaScript, GPU.js requires explicit structures to successfully generate native GPU shader instructions. Always use explicit blocks and return statements when declaring subroutines.
