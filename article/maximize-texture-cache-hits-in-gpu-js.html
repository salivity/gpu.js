Maximize Texture Cache Hits in gpu.js

Maximizing texture cache hits in gpu.js requires aligning kernel access patterns with the underlying 2D spatial layout used by WebGL texture samplers. Because the GPU executes adjacent threads simultaneously in warps or wavefronts, structuring your read coordinates to access contiguous or overlapping memory regions prevents high-latency global memory fetches. This guide covers how to design data layouts, map thread indices, and structure neighborhood sampling to achieve optimal cache locality in gpu.js.

Understand the 2D Texture Cache Architecture

Under the hood, gpu.js translates JavaScript arrays into WebGL textures, and kernel memory reads correspond to texture fetches (texelFetch or sampling). Modern GPU texture caches (L1 and L2) are optimized for 2D spatial locality rather than simple linear 1D locality. When a thread reads a texel at coordinate (x, y), the hardware loads a small 2D block (such as an 8x8 or 4x4 texel footprint) into the cache.

To prevent cache thrashing, threads executing together must access data within this same 2D footprint.

Align Thread Dispatch with Memory Coordinates

The execution grid in gpu.js determines how threads are bundled. In a 2D kernel:

  • this.thread.x represents the horizontal coordinate.
  • this.thread.y represents the vertical coordinate.

Adjacent threads in a warp almost always vary along this.thread.x. Therefore, ensure that this.thread.x maps directly to the fastest-moving axis of your input data.

// Optimal: Adjacent threads read adjacent memory addresses
const kernel = gpu.createKernel(function(matrix) {
    return matrix[this.thread.y][this.thread.x];
}).setOutput([width, height]);

Transposing this access pattern (e.g., reading matrix[this.thread.x][this.thread.y]) causes consecutive threads to read across large memory strides, resulting in a cache miss on nearly every fetch.

Leverage Overlapping Stencil Access

When implementing algorithms like image convolutions, blurs, or finite difference solvers, adjacent threads read overlapping neighborhoods. The 2D texture cache excels at this pattern if the neighborhood is kept tight and symmetric.

// High cache reuse: Neighboring threads share overlapping reads
const convolutionKernel = gpu.createKernel(function(image, kernelWeights) {
    let sum = 0;
    for (let ky = -1; ky <= 1; ky++) {
        for (let kx = -1; kx <= 1; kx++) {
            const x = this.thread.x + kx;
            const y = this.thread.y + ky;
            sum += image[y][x] * kernelWeights[ky + 1][kx + 1];
        }
    }
    return sum;
}).setOutput([width, height]);

In this pattern, thread (x, y) and thread (x + 1, y) share six out of nine texture lookups. Because these threads execute concurrently, the data loaded by thread x is served directly from the L1 texture cache to thread x + 1.

Favor 2D Arrays Over Flattened 1D Arrays

Flattening 2D data into a 1D array (index = x + y * width) often impairs texture cache efficiency in gpu.js.

When you pass a 1D array, gpu.js must still pack that data into a 2D internal texture to bypass WebGL dimension limits, then compute arithmetic to simulate 1D addressing. This internal mapping can break spatial coherence. Supplying native 2D arrays directly maps array dimensions to texture coordinates, preserving 2D cache locality and removing address translation overhead.

Eliminate Divergent Indexing

Cache efficiency collapses when adjacent threads compute irregular or data-dependent read offsets. Avoid patterns where the read address is determined by the data itself (indirect lookups) or scattered across conditional branches:

// Poor cache locality: Divergent offsets cause scattered memory reads
const badLookup = gpu.createKernel(function(data, offsets) {
    const offset = offsets[this.thread.y][this.thread.x];
    return data[this.thread.y][this.thread.x + offset];
}).setOutput([width, height]);

Keep index offsets deterministic and identical across neighboring threads whenever possible. If boundary conditions must be handled, clamp the coordinates mathematically rather than diverging through deep branch statements.

Structure Matrix Multiplications for Block Locality

Standard matrix multiplication performs a dot product between a row of matrix A and a column of matrix B. While reading a row of A provides good spatial locality, reading down a column of B crosses memory strides.

To maximize cache hits:

  1. Ensure the output dimensions match the iteration space such that this.thread.x indexes columns and this.thread.y indexes rows.
  2. If computing deep dot products, consider transposing Matrix B on the CPU before passing it to the kernel. This allows both read loops to traverse data along the horizontal axis, keeping subsequent lookups within the same cache lines.
