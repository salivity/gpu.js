Webcam to GPU.js Screen Latency Explained

Round-trip latency when capturing a webcam feed, processing it through GPU.js, and rendering the result to a display typically ranges between 30 and 100 milliseconds under optimal conditions, but can exceed 150 milliseconds if the pipeline is poorly configured. This article breaks down the latency introduced at every stage of the pipeline—camera capture, browser ingestion, WebGL texture upload, GPU kernel execution, and display presentation—to provide an accurate breakdown of where delays occur and how to minimize them.

1. Webcam Hardware and Capture (16 ms – 33 ms)

The pipeline begins at the camera sensor. Most consumer webcams operate at 30 or 60 frames per second (FPS).

  • At 60 FPS, the sensor frame interval is approximately 16.6 ms.
  • At 30 FPS, the frame interval is approximately 33.3 ms.

Sensor exposure time, rolling shutter readout, and onboard ISP (Image Signal Processor) compression (such as MJPEG or YUY2 conversion) add an initial 10 to 30 ms before the operating system even receives the frame over USB.

2. Browser Ingestion and Frame Delivery (5 ms – 15 ms)

Once the operating system receives the camera buffer, the browser accesses it via the MediaStreams API (navigator.mediaDevices.getUserMedia).

The browser must decode the video stream and pass the frame to a <video> element. Using standard polling or setInterval introduces synchronization jitter. Modern browsers mitigate this through the HTMLVideoElement.requestVideoFrameCallback() API, which notifies the application precisely when a new frame is ready for processing, reducing queue latency to roughly 5 to 10 ms.

3. CPU-to-GPU Texture Upload (1 ms – 5 ms)

GPU.js operates by compiling JavaScript functions into WebGL fragment shaders. To process the video frame, the image data from the <video> element must be transferred to the GPU as a WebGL texture using gl.texImage2D or gl.texSubImage2D.

For standard resolutions (720p or 1080p), copying pixel data across the PCIe bus takes approximately 1 to 5 ms depending on hardware architecture:

  • Integrated GPUs share system memory, lowering transfer overhead.
  • Discrete GPUs require explicit memory transfer over the PCIe bus, slightly increasing transfer time.

4. GPU.js Kernel Execution (0.5 ms – 8 ms)

Once the video frame resides on the GPU as a texture, GPU.js executes the compiled shader.

Because image operations (such as color grading, edge detection, or matrix transformations) are massively parallel, execution time is extremely fast:

  • Simple pixel-wise transforms: 0.5 ms to 2 ms.
  • Multi-pass convolutions or heavy math: 3 ms to 8 ms.

The output mode of GPU.js heavily dictates this step's impact:

  • Direct Canvas Render (graphical: true): The output remains on the GPU and draws straight to an HTML5 <canvas>. This has negligible overhead (<1 ms).
  • Array Readback (default mode): If the kernel outputs an array back to JavaScript, the browser must execute gl.readPixels(). This forces a CPU-GPU pipeline stall that can add 15 to 40 ms of latency, defeating the purpose of real-time GPU processing.

5. Display Compositing and VSync (8 ms – 16.6 ms)

After the canvas receives the processed frame, the browser compositor submits the frame to the OS window manager. The monitor displays the frame on its next refresh cycle (VSync):

  • On a standard 60 Hz display, the VSync interval is 16.6 ms.
  • On a 144 Hz display, the VSync interval is 6.9 ms.

Depending on when the GPU finishes relative to the refresh boundary, this step adds between 1 and 16.6 ms.

Minimizing Latency in Practice

To achieve sub-50 ms round-trip latency with GPU.js:

  1. Set the output to graphical: Always configure GPU.js with { graphical: true } and draw directly to the canvas to avoid synchronous CPU readback.
  2. Synchronize via requestVideoFrameCallback: Drive your render loop with video.requestVideoFrameCallback() instead of generic requestAnimationFrame() loops to eliminate frame queuing delays.
  3. Lock camera settings: Request a high frame rate (frameRate: { ideal: 60 }) and lower auto-exposure times in getUserMedia constraints to prevent camera sensor lag.
